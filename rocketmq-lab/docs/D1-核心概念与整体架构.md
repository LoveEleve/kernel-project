## 一、RocketMQ 解决什么问题

系统间异步通信的四个基本诉求：**解耦**（上下游互不知晓）、**削峰**（突发流量先堆积后消化）、**异步**（非核心链路不阻塞主流程）、**可靠**（消息不丢）。

## 二、5.x 组件全景

RocketMQ 5.x 有**六类**进程角色（4.x 只有前四类）：

```
                        ┌────────────────────────────────┐
                        │      NameServer 集群（无状态）    │
                        └──────▲───────────▲─────────────┘
              注册路由(30s周期)│           │查询路由(30s刷新)
        ┌──────────────────────┘           └──────────────────┐
        │                                                     │
┌───────┴───────┐   gRPC/Remoting   ┌───────────────┐   ┌────┴─────────┐
│ Broker Master │ ◀──────────────── │    Producer   │   │   Consumer   │
│  brokerId=0   │                   └───────────────┘   └──────▲───────┘
└───────┬───────┘                                                │
  复制  │              ┌───────────────┐    gRPC(8081)           │
       ▼              │  Proxy (5.x)  │ ────────────────────────┘
┌──────────────┐      │  无状态接入层   │      （v5 客户端走 Proxy）
│ Broker Slave │      └───────────────┘
│  brokerId>0  │      ┌───────────────┐
└──────────────┘      │Controller(5.x)│ ← Raft 选主，自动主从切换
                      └───────────────┘     （默认关闭）
```

| 组件 | 职责 | 展开 |
|---|---|---|
| **NameServer** | 路由注册中心，无状态、AP、各节点互不通信 | D2 |
| **Broker** | 消息存储节点，Master（brokerId=0）读写，Slave（brokerId>0）冗余 | D4 |
| **Producer** | 消息生产者 | D3 |
| **Consumer** | 消息消费者 | D5 |
| **Proxy**（5.x 新增） | 无状态 gRPC 接入层（默认端口 8081），v5 客户端经 Proxy 访问 Broker，屏蔽 Remoting 协议细节、做多协议网关 | D9 |
| **Controller**（5.x 新增） | 内嵌 Raft 的主从协调器，实现 Master 故障自动切换（`enableControllerMode` 默认 false；未开启时 Slave 不可自动升主） | D4/D9 |

本 lab 实测环境：NameServer `21.130.247.89:9876`，Broker `broker-a`（单 Master，`21.130.247.89:10911`），已实测直连可达。lab 使用 4.x 风格 Remoting 客户端（rocketmq-spring 2.3.0 默认），不经 Proxy。

## 三、核心概念（按依赖顺序定义）

### 3.1 Message（消息）

消息是 RocketMQ 的原子数据单元：

| 部分 | 内容 | 说明 |
|---|---|---|
| topic | 所属主题 | 最长 127 字符（`TOPIC_MAX_LENGTH`） |
| flag | 系统标志位 | 框架内部使用：压缩 / 多 Tag / 事务类型（`MessageSysFlag.java:33-37`，不含刷盘——刷盘是 WAIT 属性） |
| properties | 扩展属性 Map | 用户可见的 KEYS / TAGS / WAIT 等 |
| body | 消息体字节数组 | 默认上限 **4MB**（`DefaultMQProducer.maxMessageSize = 4 * 1024 * 1024`） |

`properties` 里三个最常见的键（`MessageConst.java:22-24`）：

- `KEYS`：业务索引键，用于按 Key 查消息（A10 验证）
- `TAGS`：消息标签，用于消费端过滤（A07 验证）
- `WAIT`：是否等刷盘完成再返回发送结果

#### msgId 双体系（面试高频，务必分清）

一条消息有**两个 ID**，来源和用途完全不同：

| ID | 谁生成 | 内容 | 用途 |
|---|---|---|---|
| `UNIQ_KEY` | **Producer 客户端**发送前生成 | 16 字节 hex：FIX_STRING（客户端 IP+PID+类加载器 hash，进程启动时预计算）+ 距启动时刻的时间差 + 进程内自增计数器 | 业务侧追踪、发送方查消息 |
| `offsetMsgId` | **Broker** 落盘时生成 | Broker 地址 + CommitLog 物理偏移量，hex 编码 | 精确物理定位一条消息 |

消费者收到的 `msgId` 是 offsetMsgId；生产者的 `UNIQ_KEY` 也随消息存储，两侧都能查——但**不要混用**：拿 UNIQ_KEY 当物理位点解析会直接失败。

### 3.2 Topic（主题）

Topic 是**逻辑概念**：一类消息的集合。Topic 本身不存消息，它只是把消息路由到若干 MessageQueue 的名字。Producer 按 Topic 发，Consumer 按 Topic 订阅。

**生产级要点**：`autoCreateTopicEnable`（BrokerConfig 默认 `true`）在生产环境**必须关闭**。开启时 Producer 发到不存在的 Topic，Broker 会按 `TBW102` 模板自动建 Topic——看似方便，实则让 Topic 元数据失控（队列数不可控、权限不可控、路由抖动），这是 RocketMQ 生产事故的经典源头之一。

### 3.3 MessageQueue（消息队列）

Topic 的物理分片。一个 Topic 在每个 Broker 上有 N 个 MessageQueue，每个 Queue 由三元组唯一标识：`(topic, brokerName, queueId)`。对应 Kafka 的 partition——**RocketMQ 的 Queue ≈ Kafka 的 Partition**，理解可以平移。

**为什么需要 Queue 而不是 Topic 直接存**：Queue 是**并发与负载均衡的最小单位**——

- 队列数 = 消费并发上限：10 个消费者分 4 个队列，6 个闲置
- 队列数 = 顺序边界：顺序消息只保证单队列内有序（D7 展开）

**关键默认数字**（两个层级，别混淆）：

| 参数 | 默认值 | 源码位置 |
|---|---|---|
| TopicConfig 读写队列数 | **16** | `TopicConfig.defaultReadQueueNums/defaultWriteQueueNums`（5.x 已从 4.x 的 8 上调到 16） |
| Broker 自动创建 topic 的队列数 | **8** | `BrokerConfig.defaultTopicQueueNums` |

读/写队列分离的意义：写 16 读 8 可实现**队列缩容**（先缩读队列，等堆积消费完再缩写队列），正常情况两者相等。

### 3.4 存储三件套（Broker 怎么存消息）

Broker 端一条消息会落到**三种文件**（D4 展开，这里只建概念）：

| 文件 | 内容 | 为什么需要 |
|---|---|---|
| **CommitLog** | 消息全量本体，所有 Topic 混部、顺序追加写（mmap + PageCache：写先进内存页缓存，刷盘策略决定何时落盘） | 顺序写磁盘 = 高吞吐的唯一途径 |
| **ConsumeQueue** | 每条 Queue 的定长索引（20 字节/条：CommitLog 偏移+大小+tagsCode） | 按队列消费的快速定位，不用扫全量 |
| **IndexFile** | Key → 消息 的哈希索引 | 按 Key 反查（A10） |

**设计精髓**：写一次 CommitLog，**异步分发**（ReputMessageService）生成 ConsumeQueue 和 IndexFile——写入路径只有一段顺序 IO。

### 3.5 两个可靠性开关（生产必配）

消息的"丢不丢"由两个独立开关决定，2×2 组合出可靠性×性能矩阵：

| 开关 | 可选值（默认加粗） | 语义 |
|---|---|---|
| 刷盘 `flushDiskType` | SYNC_FLUSH / **ASYNC_FLUSH** | 同步刷盘：落盘成功才返回；异步：写 PageCache 即返回，宕机丢最后一批 |
| 复制 `brokerRole` | **ASYNC_MASTER** / SYNC_MASTER | 同步复制：Slave 确认才返回；异步：Master 写完即返回，Master 宕机可能丢未同步数据 |

默认组合（异步刷盘+异步复制）= 性能最高、极端场景可丢消息；金融级用 SYNC_FLUSH + SYNC_MASTER。注意两者都在 `MessageStoreConfig`（:216,218），不在 BrokerConfig。

### 3.6 Tag 与 Key

- **Tag**：二级分类。一个 Topic 内的消息打不同 Tag（如 `create` / `pay`），Consumer 订阅时可按 Tag 过滤。**为什么过滤要分两侧**：ConsumeQueue 里存的不是 Tag 原文而是 `tagsCode`（Tag 字符串的 hashCode）——Broker 端只能按 hash 粗筛，hash 相同的不同 Tag 会被误拉；Consumer 端再逐条按 Tag 原文精确比对兜底（**pull 和 pop 两条路径都有**：`PullAPIWrapper.java:113-122` / `DefaultMQPushConsumerImpl.java:625-634`）
- **Key**：业务主键（如订单号），存入 IndexFile，可按 Key 反查消息

**设计意图**：Topic + Tag 两层模型避免了"每类消息建一个 Topic"的元数据爆炸——一个 `ORDER_TOPIC` 承载订单域全部消息，下游按 Tag 各取所需。

### 3.7 Offset（消费位点）

每个 MessageQueue 是一条只能追加的逻辑队列，Offset 是消息在队列中的序号（从 0 递增）。ConsumerGroup 对每条 Queue 记录"消费到哪个 Offset"，重启/再均衡后从这里继续。

- **集群模式**：offset 存 Broker（`RemoteBrokerOffsetStore`），全组共享进度
- **广播模式**：offset 存消费者本地文件（`LocalFileOffsetStore`），各自独立

**堆积**就是 `队列最大 offset − 消费 offset`——这是监控告警的核心指标。

#### ConsumeFromWhere：新组从哪里开始消费

一个新 ConsumerGroup 第一次启动时没有 offset 记录，`ConsumeFromWhere` 决定起点（6 值全列）：

| 值 | 语义 | 场景 |
|---|---|---|
| `CONSUME_FROM_LAST_OFFSET`（默认） | 从队列尾部开始，历史消息不消费 | 大多数在线业务 |
| `CONSUME_FROM_FIRST_OFFSET` | 从头消费全部存量 | 数据迁移/补数 |
| `CONSUME_FROM_TIMESTAMP` | 从指定时间点开始 | 精确回溯 |
| `CONSUME_FROM_MAX_OFFSET` / `CONSUME_FROM_MIN_OFFSET` | 显式从最大/最小位点 | 极少用 |
| `CONSUME_FROM_LAST_OFFSET_AND_FROM_MIN_WHEN_BOOT_FIRST` | 首次启动从最小位点，之后从尾部 | 兼容老语义 |

**坑**：这个配置**只对新组生效一次**；组已有 offset 记录后改它不生效。

### 3.8 ProducerGroup / ConsumerGroup

- **ProducerGroup**：发送者分组，主要作用是**事务消息回查**时定位同组任一生产者实例（D6 展开），普通发送无实质影响
- **ConsumerGroup**：消费者分组，是**订阅与负载均衡的单位**：
  - 同组多实例：队列级分摊（Rebalance，见 3.11）
  - 不同组：各自独立消费同一份消息（发布订阅语义）
  - **一个 Group 可订阅多个 Topic**：订阅关系是 `group × topic` 的 SubscriptionData 集合（每个 Topic 一份，含 Tag/SQL92 表达式）
  - **约束**：同组所有实例必须订阅关系一致（同 Topic 集合、同 Tag 表达式），否则 Rebalance 后部分消息无人消费——这是"消息丢失"类工单的高频根因

### 3.9 Broker 与 brokerName / brokerId

Broker 是存储进程。同一组主从共享一个 **brokerName**，用 **brokerId** 区分：

- `brokerId = 0` → Master，可读写
- `brokerId > 0` → Slave，默认**只同步数据、不可读**

**纠正常见误解**：Slave 默认不对外提供读服务（`slaveReadEnable = false`，BrokerConfig:139，需显式开启）；即使开启，消费端也只在 Master 压力大时被建议切到 Slave 拉取。Slave 的核心价值是**数据冗余**，不是读分流。5.x 若开启 Controller 模式，Slave 可在 Master 故障时自动升主（见 §二）。

### 3.10 clientId：同机多实例的经典坑

客户端实例标识 `clientId = clientIP@instanceName[@unitName]`（`ClientConfig.buildMQClientId()`）。同一个 JVM 进程内，相同 clientId 的 Producer/Consumer 共享一个 `MQClientInstance`。**同机部署多个应用实例时若 instanceName 冲突，会导致 Consumer 注册错乱、消息串组**——生产上多实例同机必须显式设置不同 `instanceName`。

### 3.11 Push / Pull / Pop 三种消费模型

| 模型 | 本质 | API |
|---|---|---|
| **Push**（最常用） | 客户端**长轮询 Pull 的封装**——名字叫 Push，实际是 Consumer 持续向 Broker 挂起拉取请求，有消息立即返回，无消息挂起约 15s | `DefaultMQPushConsumer` |
| **Pull** | 应用自己控制拉取时机与 offset | `DefaultLitePullConsumer`（轻量版，老 DefaultMQPullConsumer 已不推荐） |
| **Pop**（5.x 新增） | 无状态消费：向 Broker "弹"消息，Broker 记录不可见时间（invisibleTime），重平衡代价远小于队列级 Rebalance | PopMessageProcessor（D5/D9） |

**"Push 是假推"是面试必答点**：Broker 从不主动推送连接之外的消费者，所有消息都是 Consumer 拉走的。

### 3.12 Rebalance（负载均衡）

同组消费者与队列的再分配过程。**触发时机**：

- 消费者实例上线/下线（心跳注册变化）
- Topic 队列数变化
- 定时兜底：每 **20s** 一次（`RebalanceService.waitInterval = 20000`）

Rebalance 期间队列会**换 owner**——正在消费的队列可能被收回，这是重复消费的主要来源之一（另一个来源是 offset 批量提交）。分配算法有 6 种实现（平均/轮询/一致性哈希/机房就近/配置/Sticky），D5 展开。

### 3.13 MessageModel（消费模式）

| 模式 | 语义 | offset 存储 |
|---|---|---|
| `CLUSTERING`（默认） | 同组内队列分摊 | Broker 端 |
| `BROADCASTING` | 组内每个实例都收到全部消息 | 本地文件 |

**关键纠偏**：集群模式不是"只被消费一次"，而是 **at-least-once**——一条消息只投递给组内一个实例，但因 offset 批量提交、Rebalance 换 owner、超时重投等机制，**可能重复投递**。RocketMQ 不保证 exactly-once，**消费逻辑必须幂等**（A09 的重试机制会复现重复投递）。

### 3.14 MessageExt：消费侧看到的消息

Producer 构造的是 `Message`，Consumer 收到的是 `MessageExt`——Broker 在投递前附加的元数据（`MessageExt.java:32-46`）：

| 增量字段 | 含义 | 典型用途 |
|---|---|---|
| queueId / queueOffset | 所在队列及队列内序号 | 定位顺序问题 |
| bornTimestamp / storeTimestamp | 生产时间 / Broker 落盘时间 | 算端到端延迟 |
| **reconsumeTimes** | 已被重试消费的次数 | 判断"第几次重试"、自定义降级（如第 3 次失败转人工） |

### 3.15 Producer 侧两个机制

- **三种发送方式**：`syncSend`（等 Broker 回执，最可靠）、`asyncSend`（回调通知，高吞吐）、`sendOneway`（只管发不管结果，日志类场景）——可靠性递减、吞吐递增（D3 展开）
- **队列选择**：默认**轮询**（ThreadLocal 递增取模）；可选**故障延迟规避**（`sendLatencyFaultEnable` 默认 false，开启后按 Broker 历史延迟动态避开慢节点，`MQFaultStrategy`）——B01 会手写自定义选择器

### 3.16 消息类型地图（D6/D7 的导览）

RocketMQ 的"高级特性"不是新存储机制，而是**消息属性 + 内置 Topic 的组合**：

| 类型 | 实现思路一句话 | 展开 |
|---|---|---|
| 普通消息 | 直接写目标 Topic | A01-A02 |
| 批量消息 | 同 Topic 多条打包一次发送（≤4MB） | A02 |
| 顺序消息 | 同业务键哈希到同一队列 + 队列级消费锁 | D7/A03 |
| 延时消息 | 先写 `SCHEDULE_TOPIC_XXXX`，到点转投目标 Topic；5.x 另有时间轮任意延时 | D7/A04 |
| 事务消息 | 先写半消息（`RMQ_SYS_TRANS_HALF_TOPIC`，对 Consumer 不可见），本地事务后二阶段提交/回滚，Broker 定时回查 | D6/A06 |
| 广播消息 | 组内每实例全量，offset 存本地 | D7/A05 |

### 3.16 周边概念一句话

- **消费监听器两族**：`MessageListenerConcurrently`（并发消费，无序、失败进重试队列）vs `MessageListenerOrderly`（顺序消费，队列级加锁、失败本地无限重试）——D5/D7 展开
- **Namespace**（5.x）：多租户隔离，Topic/Group 加命名空间前缀（`withNamespace`），本 lab 不用
- **ACL**：accessKey/secretKey 鉴权（`acl` 模块），Broker 端 `aclEnable` 默认关，本 lab 不开
- **消息轨迹**：Producer/Consumer 端 `enableMsgTrace` 开启后，发送/消费事件上报 `RMQ_SYS_TRACE_TOPIC`（需配置 `enableMsgTrace`；A10 验证 Key 查询）
- **SQL92 过滤**：按消息 properties 做表达式过滤（`a > 5 AND tag='x'`），需 Broker 开 `enablePropertyFilter`（默认关）
- **类过滤模式（已废弃）**：`classFilterMode`（SubscriptionData，默认 false）——4.x 早期允许上传过滤类到 FilterServer 执行，因安全问题废弃，仅作历史概念知晓
- **Hook 扩展点**：`SendMessageHook` / `ConsumeMessageHook` 在发送/消费前后插桩（监控、染色、审计），B02 会自定义实现

## 四、系统 Topic 速查（`TopicValidator` 验证）

| 系统 Topic | 用途 | 展开 |
|---|---|---|
| `TBW102` | 自动创建 topic 的路由探测模板（生产应关闭自动创建，见 3.2） | D2/D3 |
| `SCHEDULE_TOPIC_XXXX` | 延时消息暂存（18 级固定延时） | D7 |
| `rmq_sys_wheel_timer` | 5.x 时间轮任意精度延时 | D7 |
| `RMQ_SYS_TRANS_HALF_TOPIC` | 事务半消息暂存 | D6 |
| `RMQ_SYS_TRANS_OP_HALF_TOPIC` | 已提交/回滚半消息的标记 | D6 |
| `RMQ_SYS_TRACE_TOPIC` | 消息轨迹 | A10 |
| `%RETRY%{group}` | 消费失败重试队列（前缀常量 `%RETRY%`） | D5/A09 |
| `%DLQ%{group}` | 死信队列（前缀常量 `%DLQ%`），每组固定 1 个队列 | A09 |

**重试与死信语义**（数字已验证）：消费失败的消息被发回 `%RETRY%{group}`，按**递增延时间隔**重投——机制是 `delayLevel = 3 + reconsumeTimes`（`DefaultMQPushConsumerImpl.java:776`），对照 18 级延时表首次重试 10s、之后 30s/1m/2m…逐步退避；超过 `retryMaxTimes`（默认 **16** 次，`SubscriptionGroupConfig.java:38`）后进入 `%DLQ%{group}` 死信队列，**不再自动投递**，需人工干预。

## 五、消费语义速查表

| 场景 | 结果 |
|---|---|
| 组内 2 实例，4 队列 | 每实例分 2 队列 |
| 组内 6 实例，4 队列 | 2 实例闲置（队列是分配上限） |
| 2 个不同 ConsumerGroup 订同一 Topic | 两份全量消息，互不干扰 |
| 广播模式 3 实例 | 3 份全量消息，offset 各存各的 |
| 集群模式一条消息 | 投递给组内一个实例，**可能重复**（at-least-once） |
| 批量拉取 | 每次拉取最多 `pullBatchSize=32` 条，消费回调默认每次 `consumeMessageBatchMaxSize=1` 条 |

## 六、本篇要点（面试视角）

1. **Topic 是逻辑的，Queue 是物理的**——Queue 数 = 消费并发上限 = 顺序边界；Queue ≈ Kafka Partition
2. **存储三件套**：CommitLog 全量顺序写 + ConsumeQueue 队列索引 + IndexFile Key 索引；写一次、异步分发
3. **两个可靠性开关别配错位置**：flushDiskType / brokerRole 都在 `MessageStoreConfig`，默认双双异步
4. **两个 msgId 分清**：UNIQ_KEY（客户端生成）vs offsetMsgId（Broker 物理位点）
5. **Push 是假推**——长轮询拉取封装；5.x 另有 Pop 无状态消费
6. **at-least-once，必须幂等**；Rebalance 每 20s 定时 + 实例/队列/订阅变化触发，换 owner 是重复消费主因
7. **offset 归属由消费模式决定**：集群存 Broker、广播存本地；`ConsumeFromWhere` 只对新组生效一次
8. **Slave 默认不可读**（`slaveReadEnable=false`），主从价值是冗余；5.x Controller 模式才有自动切主
9. **生产必关 `autoCreateTopicEnable`**
10. **高级特性全是内置 Topic**：延时/事务/重试/死信/轨迹，复用同一套存储与路由——这是 RocketMQ 设计最精妙的地方（D5~D7 逐一揭开）
