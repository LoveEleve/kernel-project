# D9 — 自动配置 + 5.x Proxy

> **定位**：D8 讲了 rocketmq-spring 集成，本篇讲两个"外部"话题——rocketmq-spring 自动配置怎么读取 yml + 5.x Proxy 模式与旧 remoting 客户端的关系（含 v5 客户端 starter）。
> **深度**：架构原理级——配置绑定链路 + Proxy 路由模型 + 双 starter 差异对比。
> **源码依据**：rocketmq-spring-all-2.3.0 + rocketmq-all-5.1.4（Proxy 部分；均与运行时对齐）。

---

## 一、自动配置绑定

### 1.1 属性绑定链路

`rocketmq-spring-boot-starter 2.3.0` 使用 `@ConfigurationProperties(prefix = "rocketmq")` 绑定（`RocketMQProperties`）：

```yaml
rocketmq:
  name-server: 21.130.247.89:9876
  producer:
    group: rocketmq-lab-producer
    send-message-timeout: 5000
    retry-times-when-send-failed: 2
  consumer:
    group: rocketmq-lab-consumer
    topic: test-topic        # 未注解时用的默认值
```

流程：yml → `RocketMQProperties` → `RocketMQAutoConfiguration` 创建 `DefaultMQProducer` / `DefaultLitePullConsumer` Bean → `RocketMQTemplate` 绑定 producer → **注入 `rocketmq.name-server` 必需**(条件 :53、断言 :95；不配则跳过 auto-config)

### 1.2 生产者+消费者 Bean 创建

`RocketMQAutoConfiguration` (:58-178) 自动注册：

- **生产者**：group 从 `rocketmq.producer.group` 取且**必填**（`Assert.hasText`，:96）；`AccessChannel` 可配 LOCAL/CLOUD（:98-99）。
- **消费者**：`DefaultLitePullConsumer` 等同，但大部分应用不显式用 `defaultLitePullConsumer`；**实际消费由注解驱动**——`@RocketMQMessageListener` 扫描生成新的 `DefaultMQPushConsumer` 容器。

**注意**：yml 里配的 `consumer.group` 说的是 `DefaultLitePullConsumer` 的组，不是注解消费的组——注解消费各组独立指定，不和 consumer 组重叠（D8 §三 已指认证必要性）。

## 二、5.x Proxy 架构

### 2.1 代理启动：双协议 + 可内嵌 Broker

Proxy 启动（`ProxyStartup.java:57-193`）同时拉起**两条协议栈**：

```
ProxyStartup.initialize()
  ├─ GrpcServer(port=8081)  ← gRPC 面向 v5 客户端
  ├─ RemotingProtocolServer  ← 兼容旧 4.x Remoting 客户端
  └─ (LOCAL 模式) BrokerController.start()  ← 内嵌一个完整 Broker 进程
```

- **LOCAL 模式**：Proxy 和 Broker 部署在同一进程——gRPC 请求直接走进程内部调用 Broker，不经过网络。适用于单实例开发/测试。
- **CLUSTER 模式（默认）**：Proxy 单独部署——gRPC→Proxy→**TopicRouteService → MQClientAPIExt → 网络调用远程 Broker**。生产用 CLUSTER。
- 两种模式共享相同的 `MessagingProcessor`（ProducerProcessor/ConsumerProcessor 等）——业务代码不感知 Proxy 与 Broker 物理位置。

### 2.2 路由层：TopicRouteService 替换 NameServer 直连

传统客户端自己调用 NameServer 获取路由。通过 Proxy 后，路由逻辑上移到 Proxy 侧：

| | 旧 remoting 客户端 | Proxy 客户端 |
|---|---|---|
| 路由查询 | 客户端 → NameServer | 客户端 → Proxy → TopicRouteService |
| 队列选择 | 客户端 MQClientInstance 轮询 | Proxy 侧 queueSelector（ConsumerProcessor） |
| Broker 连接 | 客户端 → Broker 多长连接 | **客户端只需要连 Proxy**（一个 gRPC channel） |

Proxy 的 `serviceManager.getTopicRouteService().getCurrentMessageQueueView(topic)` 会**拉取实时的队列视图**，选择队列后 Proxy 内部通过 `MQClientAPIExt` 把请求转发给 Broker。客户端不知道 Broker 地址在哪——这也是 Proxy 能做弹性扩缩容不引发 Rebalance 风暴的根本原因。

### 2.3 Proxy 配置速览（ProxyConfig）

比较：

| | 旧 remoting 客户端 (D8 starter) | v5 gRPC 客户端 (v5 starter) |
|---|---|---|
| 接入方式 | 客户端直接 NameServer+Broke | 只连 Proxy 的 gRPC 端点 |
| 连接数 | 每客户端 N 个 Broker 长连接 | 客户端→Proxy 一个 gRPC channel |
| 协议 | Netty+Remoting 私有协议 | gRPC (HTTP/2、TLS) |
| 负载均衡 | 客户端 MQClientInstance 轮询 | Proxy 侧代管 |
| 弹性伸缩 | Rebalance 风暴（实例数变化） | Proxy 无状态 + Pop 模式淘汰传统 Rebalance |
| Spring 集成 | rocketmq-spring-boot-starter (rocketmq-spring-boot) | rocketmq-v5-client-spring-boot-starter |

**本 lab 环境** 部署**旧 remoting 客户端**（rocketmq-spring 2.3.0 默认 connector），不经过 Proxy；D8 的 template 由 Spring 上下文直接给 DefaultMQProducer（非 RocketMQClientTemplate）。

### 2.4 v5 starter 的差异

`rocketmq-v5-client-spring-boot-starter` (同 repo 的独立模块) 与 D8 的 starter **不兼容**，核心变化：

- 注解改为按**endpoints**而非 `name-server` 配置（访问 Proxy 端点，非 NameServer）
- Template 改为 `RocketMQClientTemplate`(:128-129)，构造函数接受 `ClientServiceRegistry`
- listener 不绑定 `topic/consumerGroup` 直接——改用 `push-consumer` 配置块，在 yml 中定义端点/tag
- **协议升级到 gRPC**，不再维护 remoting 私有协议连接——旧 remoting 客户端最终会被淘汰

**迁移建议**：rocketmq-spring 2.3.0 的 remoting 客户端和 v5 gRPC 客户端**不能混用**。当前学习阶段通过 D8 starter 学习原生 remoting 模式——Producer/Consumer/Queue/Rebalance 等基础概念。迁移到 Proxy 模式应先理解 D1~D9 全部概念后再规划——v5 gRPC 客户端需要的 endpoints ACL 接入不是相同的配置替换，是一整套架构变。

## 四、本篇要点

1. spring.rocketmq.* 属性通过 `RocketMQProperties` 绑定，创建 Producer、Consumer 的 config Bean
2. rocketmq-spring 2.3.0 默认走 remoting 客户端——**v5 starter 是完全独立的 gRPC 客户端**
3. Proxy 的 gRPC 端口 8081 + LOCAL/CLUSTER 两种部署模式——消除客户端与 Broker 的直接连接
4. v5 注解从 `topic/consumerGroup` 变为 `endpoints/tag` 驱动，**迁移不是配置替换是架构重构**
5. 本 lab 全系列用 remoting 客户端，实验环境不做 Proxy——D1~D9 全部知识在 remoting 版本中落地
