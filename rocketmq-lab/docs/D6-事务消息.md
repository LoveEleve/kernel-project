# D6 — 事务消息

> **定位**：RocketMQ 的分布式事务解决方案——用半消息 + 回查代替本地消息表，实现"本地事务提交 ⇔ 消息可见"的最终一致。
> **深度**：架构原理级——时序 / 状态机 / 边界推演 / 恢复 / 与 Seata 对比。所有数字经 grep 验证。
> **源码依据**：rocketmq-all-5.1.4（`code/spring/rocketmq-5.1.4`）+ rocketmq-spring 2.3.0（`code/spring/extra/rocketmq-spring-2.3.0`，与运行时对齐）。

---

## 一、核心问题与方案对比

分布式事务的"发消息"难题：

| 方案 | 顺序 | 问题 |
|---|---|---|
| 先提交本地事务，后发消息 | DB 提交 → 发 MQ | MQ 发送失败时 DB 已提交→下游丢事件 |
| 先发消息，后提交本地事务 | 发 MQ → DB 提交 | DB 回滚时 MQ 已投递→脏数据** |
| **RocketMQ 事务消息** | 预发"不可见"半消息 → 本地事务 → Broker 根据结果决定可见性 | 本地事务未决时 Broker 回查兜底 |

## 二、完整时序（含内部细节）

```
① Producer: sendMessageInTransaction(msg, arg)
   客户端: 标记 PROPERTY_TRANSACTION_PREPARED=true + sysFlag TRANSACTION_PREPARED_TYPE (DefaultMQProducerImpl:1397)
   请求: SEND_MESSAGE 带事务头 → Broker
   
② Broker: SendMessageProcessor 收到消息
   HookUtils.checkIfTransactionMessage() → 调用 prepareMessage()
   ↓
③ Broker prepareMessage 内部（TransactionalMessageBridge）:
   - 写锁: 清空 queueId→写入 0 号保存位(TransactionalMessageUtil 生成 queueId=0)
   - 改写 topic → RMQ_SYS_TRANS_HALF_TOPIC(内部 Topic)
   - 原 topic/queueId 编码进消息属性(REAL_TOPIC/REAL_QID)
   ↓
   CommitLog append → dispatch 到 HALF topic ConsumeQueue
   (半消息对 Consumer 不可见——HALF topic 无订阅者)
   ↓
④ Producer 收到半消息写入成功→执行本地事务:
   TransactionListener.executeLocalTransaction(msg, arg)
   返回 LOCAL_TRANSACTION_STATE(commit/rollback/unknown)
   ↓
⑤ 二阶段上报(EndTransaction):
   Producer → EndTransactionProcessor
   
   COMMIT:
     getHalfMessageByOffset(commitLogOffset) → 取出半消息 → putMessageInRealTopic
     还原: topic=REAL_TOPIC / queueId=REAL_QID → 当作普通消息写入（走正常 dispatch）
     再写 RMQ_SYS_TRANS_OP_HALF_TOPIC → 批量 writeOpMessage (TransactionalOpBatchService)
   ROLLBACK:
     仅写 OP topic 把半消息标记为"已处理"
     (不再还原到真实 topic)
   UNKNOWN:
     什么都不做——回查兜底
    
⑥ Broker 主动回查:
   TransactionalMessageCheckService 定时(每 30s 扫一次)
   → fetchHalfMessages:
     扫 HALF topic 的消息(每次拉 1 条, PULL_MSG_RETRY_NUMBER=1)
     → needSkip(消息存活期超过文件保留时间→丢弃)
     → needDiscard(回查次数≥MAX_RETRY_COUNT → 丢弃)
     → isOpMsgExist(查 OP topic 上已有标记→跳过)
     → sendCheckMessage → 向同一 ProducerGroup 中任一在线实例 checkLocalTransaction(msg)
   ↓
   Producer 返回 commit→COMMIT; rollback→ROLLBACK; 超时/unknown→不标记→下轮回查
```

**关键约束**: 半消息的 commitLogOffset 在`EndTransaction` 头里传递给 Broker——Producer 在发送半消息的 SendResult 中拿到 `offsetMsgId`（编码了 CommitLog 偏移）。这就是 D1 说的 `offsetMsgId` 在事务中的真正用途——**唯一寻址半消息**。

## 三、失败推演表

| 场景 | 结果 |
|---|---|
| 半消息写入失败 | 本地事务不执行→无残留 |
| 本地事务失败 | Producer 主动 ROLLBACK→半消息进 OP→Consumer 永不可见 |
| 执行本地事务后 Producer 宕机（未 COMMIT/ROLLBACK） | 30s 后 Broker 回查组内其他实例→若查到已提交则还原消息；**不丢** |
| 组内所有实例宕机不响应回查 | 回查失败→下周期(30s)重试→最多 15 次(~7.5 分)。超限→needDiscard=true,丢弃+写 CHECK_MAX_TIME_TOPIC |
| Broker 宕机（未还原半消息） | 半消息存在 HALF topic 的 CommitLog→重启后回查继续——**不丢**（D4 §七 恢复保证） |
| Consumer 收到的还原消息处理失败 | 走%RETRY%/DLQ(D5 §四)——与事务机制无关 |

**结论**: 事务消息保证"本地事务和消息可见之间的最终一致"，不保证下游消费成功——幂等性另靠 D5/D9。

## 四、回查内部机制

### 4.1 先过滤再回查

`TransactionalMessageServiceImpl` 的回查任务启动按 30s 间隔执行，对 HALF topic 每批抓取执行以下过滤（源码顺序）:

1. **needDiscard / needSkip**（同一过滤块）: 回查次数 ≥15 → 丢弃 + 写 CHECK_MAX_TIME_TOPIC 记录；消息超过保留期（born + fileReservedTime）→ 跳过——CommitLog 可能已被删除
2. **checkImmunityTime**: 免疫空窗（默认 = `transactionTimeOut` = 6s，可由 `PROPERTY_CHECK_IMMUNITY_TIME_IN_SECONDS` 自定义）——未到则本轮不查，避免回查抢在 Producer 即将提交前触发
3. **OP 判定**: 拉取对应 OP 条目（`opMsg`）——已决（OP 条目在窗口内）则不回查；未决/无 OP → `isNeedCheck=true`
4. 通过 → `resolveHalfMsg` → 向 ProducerGroup 回查

### 4.2 OP 标记批量合流

一条半消息完成 commit/rollback 后不是单独写 OP 条目——它由 `TransactionalOpBatchService` 收集并**批次合并**写入 OP topic。**这是效率关键**：高吞吐场景下半秒可能产生上千条事务决策，每条单独写会压垮 Broker。OpBatchService 在周期性或达到最大值时把积压的多条 `commitLogOffset` 拼接成一个 OP topic 消息一次刷入。

### 4.3 checkImmunityTime 生成规则

`checkImmunityTime` 可以来自消息属性 `PROPERTY_CHECK_IMMUNITY_TIME_IN_SECONDS`，也可默认用 `transactionTimeOut`(6s)。含义：半消息到达 Broker 后有一个不检查的"免疫期"，用于给 Producer 本地事务+二阶段上报加安全缓冲。

### 4.4 重启恢复

Broker 重启后，回查以 HALF topic 的 ConsumeQueue 为基础恢复，和普通消费位点一致——**不需要额外索引**。唯一的变化：未标记的半消息会在 30s 后重新触发回查。

## 五、与 Outbox / Seata AT 方案对比

| 方案 | 消息存储点 | 回查/补偿 | 侵入性 | 适用 |
|---|---|---|---|---|
| **RocketMQ 事务消息** | Broker 的 HALF topic | Broker 向 Producer 发 checkLocalTransaction | 低（只要能 DB 查本地事务） | 单表事务+发消息 |
| **Outbox 模式** | 业务 DB 的 outbox 表 | 看门狗进程轮询 outbox | 中（需业务 DDL + 独立客户端） | 支持跨消息系统（不只是 RocketMQ） |
| **Seata AT 模式** | TC undo_log + TC service | TC 协调 TCC/AT 全局事务 | 低→中（依赖 Seata Server + 特殊 DDL） | 多 DB 跨表全局事务 |

RocketMQ 事务消息是"Broker 内嵌 outbox"模式——半消息=topic→RMQ_SYS_TRANS_HALF_TOPIC，回查=Broker 替代看门狗。和 Outbox 的不同在于：Outbox 的防重跑是靠业务 DB 表的唯一约束 × 幂等消费；事务消息是靠 OP batch 条目标记防重复回查。

## 六、API 对照（A06 验证）

```java
// 原生
TransactionListener listener = new TransactionListener() {
    LocalTransactionState executeLocalTransaction(Message msg, Object arg) { ... }
    LocalTransactionState checkLocalTransaction(MessageExt msg) { ... }
};
TransactionMQProducer producer = ...;
producer.setTransactionListener(listener);
producer.sendMessageInTransaction(msg, arg);

// Spring (rocketmq-spring 2.3.0)
@RocketMQTransactionListener
class OrderTxListener implements RocketMQLocalTransactionListener {
    RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        // 执行本地事务
        return COMMIT / ROLLBACK / UNKNOWN;
    }
    RocketMQLocalTransactionState checkLocalTransaction(Message msg) {
        // 回查——本地 DB 查事务结果
        return COMMIT / ROLLBACK / UNKNOWN; // UNKNOWN 继续等回查
    }
}
// rocketMQTemplate.sendMessageInTransaction(topic, message, arg);
```

## 七、本篇要点

1. **半消息=RMQ_SYS_TRANS_HALF_TOPIC 的不可见保存**——topic/queueId 编码进属性,Consumer 无感知
2. **二阶段=还原 real topic + OP batch 标记**——CommitLog offset 是唯一寻址键
3. **回查按 30s 周期扫描 HALF topic→最多 15 次→超限丢弃**
4. **OP batch 是性能命脉**——每秒可能上千条事务改为批量合并写入 OP topic
5. **与 Seata 的边界**: RocketMQ 事务消息解决单 DB+MQ 场景；Seata AT/TCC 解决多 DB 跨表——两者可组合
6. **Broker 宕机不丢半消息**——CommitLog 恢复 + 重启后回查重跑(D4 §七)
