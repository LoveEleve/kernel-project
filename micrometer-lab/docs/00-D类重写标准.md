## 二、每篇 8 个强制模块

1. **源码证据**：贴关键代码片段并标注 `文件:行号`
2. **设计意图**：每段代码后解释"**为什么**这样设计"（不是"做了什么"）
3. **完整 API 清单**：所有 public/protected 方法的职责概述表
4. **跨框架对比**（≥ 2 框架）：对比同类机制的**具体实现差异**（不是"概念对比"）
5. **生产场景量化**：含具体数字的内存/GC/锁竞争分析
6. **陷阱/边界案例**：≥ 2 个具体陷阱描述（不是"可能"或"需要注意"——是"会发生什么+为什么"）
7. **面试考点**：≥ 6 题（≥ 2 道标记为"**陷阱题**"——Q{N}（陷阱））
8. **自查清单**：写完后的自我验证步骤

## 三、自查 Checklist（每篇写完必做）

- [ ] **行号验证**：`grep -n "public\|protected\|abstract" <每个引用源文件>` 确认所有行号引用正确
- [ ] **代码块验证**：每个代码块 grep 对应源码确认内容一致——不是简化伪码
- [ ] **覆盖率检查**：`grep "public\|protected\|private.*Meter\|abstract" <源文件>` 统计总方法数，文档覆盖 ≥ 30%
- [ ] **跨框架对比**：≥ 2 个框架，有具体接口名/方法名/行为差异（不只是"概念上类似"）
- [ ] **面试题**：≥ 6 个（检查：是否 ≥ 2 个有"陷阱题"标签？是否有正确答案和解析？）
- [ ] **生产量化**：含 ≥ 1 个"具体数字 × 具体数字 = 具体结论"的量化分析
- [ ] **零 TODO**：`grep "TODO\|待查\|可能\|似乎\|???" <当前文档>` 返回空
- [ ] **事实核实**：所有"某某不存在/不支持/被废弃"的断言 grep 确认过

## 六、写作方法论总结

1. **先 grep 再写**：开始写之前，先 `grep "public\|protected"` 所有核心文件，了解完整方法列表——不靠记忆猜测
2. **源码证据链**：每个断言必须能追溯到具体源码片段和行号——不是"大概"
3. **不限制行数**：目标是讲透，不是填满预设行数——750 行目标是下限不是上限
4. **跨框架对比思维**：每讲一个机制，问"同类工具怎么做？Dropwizard 呢？OpenTelemetry 呢？"
5. **写完即自查**：不是"等 review 再发现"——写完立即运行 checklist
6. **0 虚构**：不知道的标注"源码中不存在"而不是猜测——D1 的 publish() 和 D4 的 synchronized 都是猜的
