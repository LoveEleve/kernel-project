# 三维配置模型与共享配置

## 一、为什么需要三维模型

如果所有配置都在一个平面里（只有一个 namespace、一个 group），100 个微服务 + 3 个环境（dev/staging/prod）= 300 个配置项挤在一起。认错环境、改错配置是家常便饭。

Nacos 的三维模型就是为了解决这个问题：

```
Namespace（环境隔离层）
  ├── Group（功能分组层）
  │   └── Data ID（配置实例层）
  └── ...
```

## 二、三维各自的职责

| 维度 | 作用 | 示例 | 隔离强度 |
|---|---|---|---|
| **Data ID** | 配置文件名 | `nacos-lab.yaml` / `shared-datasource.yaml` | 本质是文件名——同 Group 下唯一 |
| **Group** | 功能分组 | `DEFAULT_GROUP` / `DATASOURCE_GROUP` / `MQ_GROUP` | 逻辑隔离——不同 Group 下的同名 Data ID 是不同配置 |
| **Namespace** | 环境隔离 | `sca-lab-dev` / `sca-lab-prod` | 物理隔离——不同 Namespace 下的配置完全不可见 |

**为什么要三层而不是两层？**
两层（Namespace + Data ID）的问题是：一个环境内，DB 配置、MQ 配置、业务配置全混在 Default_Group 里。运维改 DB 配置时可能误触业务配置。Group 就是为了给同一环境内按功能分组用的。

## 三、共享配置的价值

10 个微服务连同一个 MySQL——每个服务都写一遍 JDBC URL 是浪费。共享配置让一份配置被多个服务引用。

```yaml
spring:
  config:
    import:
      - optional:nacos:nacos-lab.yaml                      # 自有配置
      - optional:nacos:shared-datasource.yaml?group=DATASOURCE_GROUP  # 共享
      - optional:nacos:shared-redis.yaml?group=REDIS_GROUP           # 共享
```

优先级由 **`spring.config.import` 声明顺序**决定：**后声明覆盖先声明**（Spring Boot 官方语义："later property sources override earlier ones"；imported 配置也覆盖 `application.yml` 本体的同名 key）。旧 bootstrap 时代的"主配置 > extension-configs > shared-configs"语义已不适用——想让哪个配置赢，就把它放在 import 列表的**后面**（详见 02 篇）。

## 四、验证

```
curl http://localhost:28001/config/all-sources | python3 -m json.tool
# own_config: nacos-lab.yaml
# shared_datasource: shared-datasource.yaml（DATASOURCE_GROUP）
# shared_redis: shared-redis.yaml（REDIS_GROUP）
```

## 五、生产注意

- 不要在共享配置里放敏感信息——所有引用它的应用都能读到
- Group 命名规范：`DATASOURCE_GROUP`/`MQ_GROUP`/`CACHE_GROUP`，不全放 DEFAULT
- Namespace 不是多租户方案——真正的多租户隔离需要独立 Nacos 集群
