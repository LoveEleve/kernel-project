# 心跳与自保护模式

## 一、Nacos 2.x 健康检查机制

Nacos 2.x 采用**双层健康检查**:连接驱动(主) + 定时补偿(兜底)。

### 第一层: 连接驱动(毫秒级)

临时实例(ephemeral=true)通过 gRPC 长连接维持。**连接断开 = 客户端不可用**:
- gRPC keep-alive 自动检测连接存活
- 连接断开 -> ConnectionManager.unregister -> ClientReleaseEvent -> 清理索引 + ServiceChangedEvent -> Push 通知订阅者
- 零额外网络开销(不像 1.x 需要每 5s 发心跳 HTTP)

### 第二层: 定时补偿(兜底)

用于 1.x 兼容客户端(IpPortBasedClient)或 keep-alive 异常时的兜底:

```
ClientBeatCheckTaskV2 定时任务:
  -> 拦截器链: Distro负责检查 -> 服务级开关 -> 实例级开关
  -> UnhealthyInstanceChecker: lastHeartBeat > 15s -> 标记 healthy=false
  -> ExpiredInstanceChecker: lastHeartBeat > 30s -> 删除实例(globalConfig.isExpireInstance=true)
```

**时间线**:
```
T0:     客户端停止心跳(或连接断开未被连接层检测到)
T15s:   标记不健康(healthy=false) + 发 ServiceChangedEvent -> Push(订阅者看到不健康)
T30s:   删除实例 + 发 ClientDeregisterServiceEvent -> Push(订阅者看到实例被删)
```

### 1.x vs 2.x 对比

| 维度 | 1.x | 2.x |
|------|-----|-----|
| 心跳方式 | HTTP POST /beat 每 5s | gRPC keep-alive(连接层,零开销) |
| 故障检测 | 定时扫描 lastBeat | 连接断开回调(毫秒) + 定时补偿(15s/30s) |
| 删除延迟 | 最长 30s | 连接断开即刻删 + 30s 补偿兜底 |

## 二、自保护(保护阈值)

### 触发条件(源码 ServiceUtil.selectInstancesWithHealthyProtection)

```
healthyCount / totalInstanceCount <= protectThreshold
```

默认 `protectThreshold = 0.0`:只在**零健康实例**时触发保护。设为 0.5:健康实例低于一半就触发。

### 触发后的真实机制

**不是"把所有实例标为健康"**,而是:

1. `setReachProtectionThreshold(true)` -- 标记触发了保护
2. 把不健康实例**强制 setHealthy(true)** -- 源码注释: "set all to healthy state to protect"
3. 返回全部实例(含原本不健康的)

效果: `selectInstances(healthy=true)` 在保护触发时**不会返回空列表**。宁可给可能不可用的地址,也不让调用方无地址可调,防止调用链雪崩。

### 常见误解

| 误解 | 真相 |
|------|------|
| "默认阈值 0.85" | ❌ 那是 Eureka 的默认值。**Nacos 默认 0.0**(Constants.DEFAULT_PROTECT_THRESHOLD) |
| "0.0 = 关闭保护" | ❌ 0.0 仍然保护: `0/total <= 0.0` 在零健康实例时为 true,仍触发 |
| "触发后 `allIPs=true`" | ❌ 保护靠 `reachProtectionThreshold`,不是 `allIPs` |
| "触发后直接返回不健康实例" | 接近但不够精确:实际是把不健康实例**强制标记 healthy=true** 再返回 |

### 目的

防止网络抖动导致的雪崩误杀。如果大量实例因为网络问题同时"不健康",Nacos 宁可返回全部实例(包括可能不可用的),也比返回空列表导致调用方全部 fail 更好。

### 后果

- 保护触发后,所有实例都返回(包括不健康的,但被标记为 healthy)
- 调用方可能拿到不可用的地址 -> 需要自己处理(重试、熔断)
- 保护阈值是**最终防线**,不是日常容错手段

## 三、生产实践

### 阈值选择

| 场景 | 推荐值 | 理由 |
|------|:---:|------|
| 默认(小集群 < 10 实例) | 0.0 | 只在全挂了才保护,日常由应用层容错 |
| 大集群(> 50 实例) | 0.3~0.5 | 防止大规模网络抖动导致全部摘除 |
| 严格场景(金融/交易) | 0.0 | 不容忍不可用实例,由 Sentinel 熔断兜底 |

### 为什么不在所有场景都设高阈值?

保护阈值是**双刃剑**:阈值高(如 0.8) -> 网络抖动时不会误摘实例,但会**掩盖真正的故障**。集群里真的挂了 80% 实例时,Nacos 告诉你"全部正常"。

**正确做法**: Nacos 只做服务发现,应用层(Sentinel/Resilience4j)做熔断+重试+超时。

### keep-alive 配置

```yaml
# 客户端 gRPC keep-alive 配置
nacos:
  remote:
    client:
      grpc:
        keepalive:
          time: 60s        # 最长空闲时间
          timeout: 20s     # 检测超时
```

- `time` 太大: 连接断开后很久才发现 -> 路由黑洞
- `time` 太小: 频繁重连 -> 浪费资源
- 推荐: `time=60s, timeout=20s` + ClientBeatCheckTaskV2 兜底

## 四、验证

```
# 1. 查看当前实例的健康状态
curl http://localhost:28001/discovery/status | python3 -m json.tool

# 2. 查看自保护是否触发
# Nacos 控制台 -> 服务详情 -> 查看 reachProtectionThreshold 标志

# 3. 模拟实例不健康(临时实例)
curl -X POST http://localhost:28001/discovery/set-unhealthy

# 4. 等待 15s -> 检查是否被标记不健康
# 等待 30s -> 检查是否被摘除

# 5. 恢复健康
curl -X POST http://localhost:28001/discovery/set-healthy
```

## 五、故障排查

| 现象 | 可能原因 | 排查 |
|------|---------|------|
| 大量实例标记不健康 | keep-alive 配置不当 | 检查 `keepalive.time` 和 `keepalive.timeout` |
| | 网络抖动 | `ping` Nacos Server,检查丢包率 |
| | Nacos Server CPU 满载 | `top` 查看 Nacos 进程,`ConnectionManager` 连接数 |
| 实例被误摘除 | 保护阈值未触发或阈值过低 | 检查 `protectionThreshold` 配置 |
| | `expireInstance=false`(关闭自动删除) | 检查 `GlobalConfig.isExpireInstance` |
| 实例永远不会被摘除 | 保护阈值过高(如 0.8) | 降低阈值或临时关闭保护 |
| 1.x 兼容客户端心跳异常 | HTTP 心跳被防火墙拦截 | 检查 `/nacos/v1/ns/instance/beat` 可达性 |
