# 实例生命周期：临时 vs 持久化

## 一、两种实例类型的设计起源

微服务(Pod、容器、弹性伸缩)的生命是短暂的。如果每个实例都要人工注册/注销,运维会被淹死。

但数据库、消息队列是固定的。如果让 Nacos 像对待微服务一样自动摘除它们--30s 没心跳就删掉--你会发现数据库"突然"在 Nacos 里消失了。

**两类完全不同的问题**: "我相信你会自己报告死活"(临时实例) vs "你不报我也不能删你"(持久化实例)。

## 二、完整行为对比

| | 临时实例 (ephemeral=true) | 持久化实例 (ephemeral=false) |
|---|---|---|
| **心跳** | gRPC keep-alive(连接层自动,零额外开销) | 无心跳(2.x) / 服务端主动检查(1.x) |
| **客户端请求** | InstanceRequest(gRPC) | PersistentInstanceRequest(gRPC, 无 redo) |
| **一致性** | AP(Distro 异步同步) | CP(Raft 日志复制) |
| **连接断开** | 即刻清理(毫秒级) + 15s/30s 补偿兜底 | 仅标记不健康,数据保留 |
| **服务端存储** | 纯内存(Distro 同步到其他节点内存) | JRaft log + snapshot(zip) |
| **Nacos 重启后** | 丢失,需客户端重新注册 | 保留,从 snapshot 恢复 |
| **需手动管理** | 否(自动摘除) | 是(需手动 deregister) |
| **典型场景** | 微服务、K8s Pod | 数据库、DNS、消息队列 |

> **常见误解**: 2.x 临时实例不需要"每 5s 发心跳"。gRPC keep-alive 在传输层自动检测连接存活,不需要应用层心跳。5s/15s/30s 是 1.x 的参数,2.x 中仅作为定时补偿兜底(ClientBeatCheckTaskV2)。

## 三、注册到底发生了什么(源码级)

### 临时实例注册全链路

```
[客户端 SDK 层]
namingService.registerInstance("nacos-lab", "DEFAULT_GROUP", instance)
  -> NacosNamingService: 参数校验 + checkAndStripGroupNamePrefix
  -> NamingClientProxyDelegate.getExecuteClientProxy(instance)
     // 路由决策: ephemeral=true -> GrpcClientProxy (99% 场景)
  -> redoService.cacheInstanceForRedo(serviceName, groupName, instance)
     // write-ahead: 先缓存 redo(registered=false),再发请求
  -> doRegisterService: InstanceRequest(REGISTER_INSTANCE) -> gRPC :9848

[服务端 gRPC 层]
GrpcSdkServer(9848) -> GrpcRequestAcceptor -> RequestHandlerRegistry
  -> filter chain: @Secured(鉴权) -> @TpsControl(限流) -> @ExtractorManager(参数校验)
  -> InstanceRequestHandler.handle (ephemeral=true 硬编码)
    -> clientOperationServiceProxy.chooseClientOperationService(instance)
       // 路由: ephemeral=true -> EphemeralClientOperationServiceImpl
    -> EphemeralClientOperationServiceImpl.registerInstance
       -> ServiceManager.getSingleton(service)      // 获取 Service 单例
       -> client.addServiceInstance(singleton, info) // 存入 Client 内存
         // 内部发 ClientChangedEvent -> DistroClientDataProcessor -> sync to allMembersWithoutSelf
       -> client.recalculateRevision()
       -> publishEvent(ClientRegisterServiceEvent)   // 触发索引更新 + Push
         // -> ClientServiceIndexesManager.addPublisherIndexes
         // -> ServiceChangedEvent(service, incrementRevision=true)
         // -> NamingSubscriberServiceV2Impl -> PushDelayTask(500ms)
         // -> RpcPushService.push -> gRPC bi-di stream -> 客户端

[集群同步]
ClientChangedEvent -> DistroClientDataProcessor.syncToAllServer
  -> isResponsibleClient 检查(只有负责节点才 sync)
  -> DistroProtocol.sync(distroKey, CHANGE)
    -> allMembersWithoutSelf -> DistroDelayTask(1s)
    -> gRPC -> 目标节点 onReceive -> upgradeClient(diff 合并)
```

### 持久化实例注册全链路

```
[客户端 SDK 层]
namingService.registerInstance("db-service", "DEFAULT_GROUP", instance)
  // instance.ephemeral=false
  -> NamingGrpcClientProxy.registerService
     // 按 instance.isEphemeral() 分流:
     //   ephemeral=true  -> registerServiceForEphemeral (InstanceRequest + redo)
     //   ephemeral=false -> doRegisterServiceForPersistent (PersistentInstanceRequest, 无 redo!)
  -> PersistentInstanceRequest(REGISTER_INSTANCE) -> gRPC :9848

[服务端]
PersistentInstanceRequestHandler.handle  // 独立的 Handler,不是 InstanceRequestHandler!
  -> Service.newService(namespace, group, name, false)  // ephemeral=false
  // 注意: 不经过 ClientOperationServiceProxy, 直接调 PersistentClientOperationServiceImpl
  -> PersistentClientOperationServiceImpl.registerInstance
     -> protocol.write(WriteRequest(ADD))  // JRaft 共识
       -> Leader -> Raft log -> 复制到多数派 -> commit
     -> onApply(WriteRequest)
       -> clientManager.clientConnected(clientId)  // 创建持久 Client(IpPortBasedClient)
       -> client.addServiceInstance(singleton, info)
       -> publishEvent(ClientRegisterServiceEvent)  // 触发索引更新 + Push
```

> **关键区别**: 客户端按 `instance.isEphemeral()` 分流发不同请求(InstanceRequest vs PersistentInstanceRequest);服务端有独立的 Handler 分别处理。**不经过 ClientOperationServiceProxy** -- Proxy 只用于 InstanceRequest 路径。临时实例直接写内存(微秒级),持久实例先走 Raft 共识(毫秒级)。两者最终都通过 `addServiceInstance` + `ClientRegisterServiceEvent` 触发索引和推送。

> **持久实例无 redo**: `doRegisterServiceForPersistent` 不经过 `redoService.cacheInstanceForRedo`,直接发 gRPC 请求。如果注册失败,不会自动重试。

## 四、临时实例完整时间线

### 正常运行

```
T+0:    客户端启动 -> gRPC 连接建立(:9848) -> registerInstance()
        -> redo 缓存(registered=false) -> gRPC 发送 -> 服务端确认 -> registered=true
T+0:    gRPC 连接保持(keep-alive 自动维持,不需要应用层心跳)
[正常运行: 连接不断 = 实例在线]
```

### 故障检测(2.x)

```
T+N:    客户端进程 crash / 网络断开
T+N+ms: gRPC server 检测到连接断开 -> ConnectionManager.unregister
        -> 发布 ClientReleaseEvent + ClientDisconnectEvent
        -> ClientServiceIndexesManager.handleClientDisconnect
           -> 清理 publisherIndexes + subscriberIndexes
           -> ServiceChangedEvent -> Push(订阅者立即收到实例下线)
        -> DistroClientDataProcessor.sync(DELETE) -> 集群同步删除
[总延迟: 毫秒到秒级(取决于 keep-alive 配置)]
```

### 定时补偿兜底(keep-alive 异常时)

```
T+N+15s: ClientBeatCheckTaskV2 -> UnhealthyInstanceChecker
         -> lastHeartBeat > 15s -> healthy=false
         -> ServiceChangedEvent -> Push(订阅者看到不健康)
T+N+30s: ExpiredInstanceChecker
         -> lastHeartBeat > 30s -> 删除实例
         -> ClientDeregisterServiceEvent -> Push(订阅者看到删除)
```

> 2.x 的定时补偿主要针对 1.x 兼容客户端(IpPortBasedClient)。2.x 原生客户端(ConnectionBasedClient)在连接断开时由 ConnectionManager 即刻清理,不需要等 15s/30s。

## 五、排查: 注册成功但其他客户端看不到

按源码链路逐步排查:

```
① 客户端是否真的注册成功?
   日志搜索: "register finished" / "nacos registry"
   检查: redo 队列是否有堆积(registered=false 的未确认项)
   注意: 持久实例无 redo,跳过此步

② 服务端是否收到?
   日志搜索: "Client change for service" (AbstractClient.addServiceInstance)
   检查: Nacos 控制台 -> 服务详情 -> 实例是否存在

③ ClientRegisterServiceEvent 是否发出?
   日志搜索: "current ips" (ClientServiceIndexesManager 索引更新日志)
   检查: publisherIndexes[service] 是否包含 clientId

④ ServiceChangedEvent 是否触发 Push?
   日志搜索: "push" + service 名
   检查: PushDelayTask 队列深度(delayTaskEngine.tasks.size)
   检查: pushTaskDelay 是否过大(默认 500ms)

⑤ gRPC push 是否成功?
   日志搜索: "PUSH-SUCC" 或 "PUSH-FAIL"
   检查: 订阅者的连接是否还活着(ConnectionManager)
   检查: subscriberIndexes[service] 是否包含目标 clientId

⑥ 集群其他节点是否同步?
   日志搜索: "DISTRO" + "Receive distro data" (DistroClientDataProcessor.processData)
   检查: DistroProtocol.isInitialized (新节点是否完成 load)
   检查: DistroMapper.responsible(clientId) (负责节点是否正确)
```

## 六、操作验证

```
# 临时实例(默认)
curl http://localhost:28001/discovery/status | python3 -m json.tool
# ephemeral: true

# 切换到持久化实例
# application.yml: spring.cloud.nacos.discovery.ephemeral: false
# 重启 -> Nacos 控制台 -> 实例存在 but 无心跳(2.x 连接断开仅标记不健康)

# 验证差异
# kill 临时实例 -> 连接断开 -> 毫秒级摘除(2.x) / 30s(1.x)
# kill 持久化实例 -> 实例一直存在(需手动 deregister)
```

## 七、生产决策

| 场景 | 选择 | 原因 |
|---|---|---|
| K8s Deployment(Pod IP 变化) | 临时 | Pod 生命周期短,IP 经常变 |
| K8s StatefulSet(固定 hostname) | 持久化 | hostname 不变,手动管理 |
| 数据库 MySQL/PostgreSQL | 持久化 | 地址固定,不能被自动摘除 |
| Redis/Elasticsearch | 持久化 | 基础设施,同数据库 |
| 第三方 API(支付/短信) | 持久化 | 外部服务,无心跳能力 |
| Spring Boot 微服务 | 临时(默认) | 弹性伸缩,生命周期不固定 |

**绝对不能做的**:
- 临时/持久化混用同一个 Service -- 第一个注册的决定 ephemeral,后续不同类型被拒绝(EphemeralClientOperationServiceImpl 校验)
- 把密码/密钥放在 metadata -- Nacos API 明文返回所有 metadata
