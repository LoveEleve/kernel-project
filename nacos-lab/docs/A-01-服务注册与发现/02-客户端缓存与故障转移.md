# 客户端缓存与故障转移

## 一、问题

Nacos Server 挂了之后,客户端凭什么还能发现服务?

答案:**三层缓存** -- 内存缓存(正常运行时) + 磁盘缓存(重启恢复) + failover 文件(运维应急)。

## 二、三层缓存架构(源码级)

```
getAllInstances(serviceName, subscribe=true)
  -> ServiceInfoHolder.getServiceInfo(serviceName, groupName, clusters)
     ① 检查 failover 模式是否开启(isFailoverSwitch)
        -> 开启: 从 failover 文件读取(运维手动创建,最高优先级)
        -> 未开启: 继续下一步
     ② 从内存缓存 serviceInfoMap.get(key) 读取
        -> 命中: 直接返回(正常路径,零网络开销)
        -> 未命中 || 未订阅: 调 clientProxy.subscribe() 向服务端拉取
  -> 如果服务端不可达: subscribe 抛异常
     -> getAllInstances 返回空列表(不是从磁盘恢复!)
```

> **关键**: Nacos Server 挂了时,`getAllInstances` 返回的是**内存缓存**(`serviceInfoMap`),不是磁盘缓存。磁盘缓存只在**客户端重启**时用(`DiskCache.read` 加载到 `serviceInfoMap`)。

### 第一层: 内存缓存(ServiceInfoHolder.serviceInfoMap)

```java
// ServiceInfoHolder.java
private final ConcurrentMap<String, ServiceInfo> serviceInfoMap;

// 缓存更新: 收到服务端 Push 时
public ServiceInfo processServiceInfo(ServiceInfo serviceInfo) {
    ServiceInfo oldService = serviceInfoMap.get(serviceInfo.getKey());
    serviceInfoMap.put(serviceInfo.getKey(), serviceInfo);  // 更新内存
    boolean changed = isChangedServiceInfo(oldService, serviceInfo);
    if (changed) {
        NotifyCenter.publishEvent(new InstancesChangeEvent(...));  // 通知用户 Listener
        DiskCache.write(serviceInfo, cacheDir);  // 同时写入磁盘(每次变更都写)
    }
    return serviceInfo;
}
```

**缓存更新时机**: 服务端 Push `NotifySubscriberRequest` -> `NamingPushRequestHandler.requestReply` -> `serviceInfoHolder.processServiceInfo` -> 更新 `serviceInfoMap` + 写磁盘。

**缓存读取时机**: `getAllInstances(subscribe=true)` -> `serviceInfoHolder.getServiceInfo` -> 直接从 `serviceInfoMap.get(key)` 返回。**零网络开销**。

**启动加载**: 如果配置 `namingLoadCacheAtStart=true`,启动时从磁盘 `DiskCache.read(cacheDir)` 加载到 `serviceInfoMap`。否则内存缓存为空,首次查询走服务端。

### 第二层: 磁盘缓存(DiskCache)

```
路径: {user.home}/nacos/naming/{namespace}/
文件名: {group}@@{serviceName}@@{clusters}
格式: JSON(ServiceInfo 序列化)
```

**写入时机**: `processServiceInfo` 检测到 hosts 变化时调 `DiskCache.write`(每次变更都写,不是定时)。

**读取时机**: 客户端启动时(如果 `namingLoadCacheAtStart=true`)-> `DiskCache.read` -> 加载到 `serviceInfoMap`。

**FailoverReactor.DiskFileWriter**: 每 24 小时将内存缓存全量备份到 failover 目录一次(兜底,防止变更时写文件失败)。

### 第三层: Failover 文件(运维应急)

```
路径: {user.home}/nacos/naming/{namespace}/failover/
开关文件: {failoverDir}/failover-mode  (内容 "1" = 开启, "0" = 关闭)
数据文件: {failoverDir}/{group}@@{serviceName}@@{clusters}
```

**工作机制**:
1. `FailoverReactor` 每 5s 检查 `failover-mode` 文件
2. 如果内容为 "1" -> `isFailoverSwitch()` 返回 true
3. `getServiceInfo` 优先从 failover 目录读取,**跳过内存缓存**
4. 运维在 failover 目录创建 `failover-mode`(内容 "1")+ 数据文件 -> 即时生效

**failover 不是"Server 挂了自动触发"**: 它是**运维手动触发**的应急手段。Server 挂了时,客户端靠的是内存缓存(第一层),不是 failover。

## 三、Server 挂了之后的真实行为

```
[Server 正常运行时]
  Push -> processServiceInfo -> serviceInfoMap 更新 + DiskCache.write
  getAllInstances -> serviceInfoMap.get(key) -> 命中(零网络)

[Server 挂了]
  getAllInstances(subscribe=true):
    -> serviceInfoHolder.getServiceInfo -> serviceInfoMap.get(key)
    -> 命中: 返回内存缓存(数据可能过期,但有实例列表)
    -> 未命中: clientProxy.subscribe() -> gRPC 失败 -> 抛 NacosException
       -> getAllInstances catch 异常 -> 返回空列表

  selectInstances(healthy=true):
    -> 从内存缓存过滤 -> 返回(但 healthy 状态可能不准,因为 Push 断了)

[客户端重启 + Server 挂了]
  启动:
    -> namingLoadCacheAtStart=true: DiskCache.read -> serviceInfoMap 加载磁盘缓存
    -> namingLoadCacheAtStart=false: serviceInfoMap 为空
  getAllInstances:
    -> 内存缓存命中: 返回磁盘恢复的数据(可能过期但可用)
    -> 内存缓存未命中: subscribe 失败 -> 空列表
```

## 四、与 Config 四级降级的区别

| | Naming 客户端缓存 | Config 四级降级(D-04) |
|---|---|---|
| 层级数 | 3 层(内存/磁盘/failover) | 4 层(failover/server/snapshot/null) |
| Server 挂了时 | 用**内存缓存**(还在运行) | 降级到 **snapshot**(本地快照) |
| 重启 + Server 挂了 | 用**磁盘缓存**(如果配置 loadCacheAtStart) | 降级到 **snapshot**(自动) |
| 运维应急 | 手动创建 failover 文件 | 手动创建 failover 文件 |
| 最终兜底 | 空列表 | null |

**关键区别**: Naming 的内存缓存在 Server 挂了时**仍然可用**(因为缓存在进程内存里),而 Config 的 L2 server 路径在 Server 挂了时**直接失败**(因为每次 getConfig 都要网络请求)。所以 Naming 的故障转移比 Config 更自然。

## 六、生产注意

- **内存缓存优先**: 正常运行时 `getAllInstances` 从内存返回,零网络。Push 机制保证内存缓存及时更新
- **磁盘缓存是重启恢复用的**: 不是"Server 挂了从磁盘读"。Server 挂了时内存缓存还在,不需要读磁盘
- **`namingLoadCacheAtStart=true`**: 生产建议开启,这样客户端重启 + Server 挂了时还能从磁盘恢复
- **failover 是手动应急**: 不是自动触发。运维发现配置/服务列表有问题时,手动创建 failover 文件强制覆盖
- **缓存含明文**: 磁盘缓存文件是 JSON 明文,不要在 metadata 里放敏感信息
- **pushEmptyProtection**: 配置 `namingPushEmptyProtection=true` -> 服务端推送空列表时**忽略**(防止 Push 异常导致缓存被清空)
