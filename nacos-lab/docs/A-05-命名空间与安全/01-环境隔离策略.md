# 环境隔离策略

## 一、Namespace 的正确用法

Nacos 用 **Namespace** 实现环境级别的物理隔离。不同 Namespace 下的服务实例和配置**互相不可见**。

| 场景 | 用 Namespace? | 理由 |
|---|---|---|
| dev / staging / prod 隔离 | **是** | 不同环境用不同 namespace,防止测试流量打到生产 |
| 多团队共享同一个 Nacos | **是** | 每个团队一个 namespace,互不干扰 |
| 服务分级(S1/S2/S3) | **否** | 用 Group 做功能分组,Namespace 太重 |
| 多租户(客户 A/B 数据隔离) | **否** | Namespace 没有资源隔离,需独立 Nacos 集群 |

### Namespace 的隔离强度

```
Namespace(物理隔离)
  ├── 服务实例: 不同 namespace 下的实例完全不互通
  ├── 配置: 不同 namespace 下的配置完全独立
  ├── 权限: Auth 白名单可以按 namespace 配置
  └── 不对: CPU/内存/网络没有隔离(同一个 Nacos 进程内)
```

## 二、Nacos 鉴权体系

### 两层鉴权

Nacos 的鉴权**不在 API 接口层**(NamingService/ConfigService 没有任何安全注解),而在**服务端 Handler 层**:

```
客户端 gRPC 请求
  -> GrpcRequestAcceptor
  -> RequestHandler.handleRequest
    -> filter chain:
      ① AuthFilter(@Secured 注解) -> token/ak/sk 鉴权
      ② TpsControlFilter(@TpsControl 注解) -> QPS 限流
      ③ ParamCheckFilter(@ExtractorManager) -> 参数校验
    -> handler.handle() -> 实际业务逻辑
```

### 认证方式

| 方式 | 适用场景 | 配置 |
|------|---------|------|
| Token(默认) | 内部微服务 | `nacos.core.auth.enabled=true` |
| AK/SK | 第三方调用 SDK | AuthPlugin SPI 自定义 |
| LDAP/OAuth2 | 企业统一认证 | AuthPlugin SPI 自定义(B5) |

### Spring Cloud 客户端配置

```yaml
spring:
  cloud:
    nacos:
      discovery:
        username: nacos
        password: nacos
        namespace: sca-lab-dev     # 指定 namespace
      config:
        username: nacos
        password: nacos
        namespace: sca-lab-dev
```

**注意**:`username/password` 是 Nacos Server 的认证凭据,**不是**企业 LDAP 账号。企业认证需要通过 B5(自定义 AuthPlugin)实现。

### 权限模型

```
角色管理(控制台 -> 权限控制 -> 角色管理):
  读角色: 只能查看服务列表和配置(getConfig/getAllInstances)
  写角色: 可以注册/注销服务、修改配置(registerInstance/publishConfig)
  管理员: 可以管理 namespace/用户/角色

每个 namespace 独立配置白名单:
  namespace sca-lab-dev:
    user-A: 读写
    user-B: 只读
  namespace sca-lab-prod:
    user-A: 只读       # 同一个用户,不同 namespace 可以不同权限
```

### 恶意请求防御

Nacos Server 有两层防线:
1. **@TpsControl 限流**: InstanceRequestHandler 标注 `@TpsControl(pointName="RemoteNamingInstanceRegisterDeregister")` -> 限制注册/注销 QPS
2. **ConnectionManager 限流**: 每 IP/每 AppName 最大连接数,通过 ControlManagerCenter 动态调整

## 三、命名空间设计规范

### 命名规范

```
{NACOS-INSTANCE}-{ENV}

示例:
  sca-lab-dev       # sca-lab 实例的开发环境
  sca-lab-staging   # sca-lab 实例的预发环境  
  sca-lab-prod      # sca-lab 实例的生产环境
  my-xhs-dev        # my-xhs 实例的开发环境
```

**为什么用有意义的名字而不是 UUID**:
- 控制台里几十个 UUID: `a1b2c3d4-e5f6-...` 无法区分
- 排查问题时: 日志里 `namespace=prod-bj` 比 `namespace=a1b2c3d4` 有用

### 多团队方案

```
单 Nacos 集群:
  namespace: team-A-dev, team-A-prod, team-B-dev, team-B-prod

多 Nacos 集群(大团队或严格隔离):
  Nacos-A(team-A 专用): namespace: dev, staging, prod
  Nacos-B(team-B 专用): namespace: dev, staging, prod
```

**Namespace 管理的不是权限模型**: 即使给每个团队分配了 namespace,有 `globalAdmin` 权限的人仍然可以管理所有 namespace。真正的多团队权限隔离需要 Auth 白名单配合。

### 为什么不用于多租户

| 维度 | Namespace 隔离 | 独立集群隔离 |
|------|:---:|:---:|
| 配置隔离 | ✅ | ✅ |
| 服务发现隔离 | ✅ | ✅ |
| 权限隔离 | ⚠️ 需 Auth 白名单 | ✅ 天然隔离 |
| 资源隔离(CPU/内存) | ❌ 共享进程 | ✅ 独立进程 |
| 版本升级 | ❌ 共享版本,一升全升 | ✅ 各集群独立升级 |
| 维护难度 | 低 | 高 |

真正的多租户(SaaS)需要独立 Nacos 集群 + K8s namespace 隔离。

## 四、生产建议

- **环境分离**: dev/staging/prod 必须分 namespace,**绝对不能混用**。生产事故的第一大原因
- **namespace 命名**: `{实例名}-{环境}`,不用 UUID
- **每个 namespace 配独立的 admin**: 出问题时各团队改自己的,不互相影响
- **不要用 namespace 做灰度**: 灰度用 metadata 标记(instance.metadata["version"]="canary"),配合 B3 的 LoadBalancer 做流量路由
- **定期审计**: 检查是否有废弃的 namespace(idle > 30 天),及时清理
- **Auth 不是可选的**: 生产环境必须 `nacos.core.auth.enabled=true`,否则任何人拿到 Nacos 地址就能操作
