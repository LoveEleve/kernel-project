# 刷新链路详解

## 一、完整调用链(2.x gRPC)

```
[Nacos Server 配置变更]
ConfigPublishRequestHandler -> insertOrUpdate(DB) -> ConfigDataChangeEvent
  -> AsyncNotifyService(唯一消费者)
    -> 处理自己: dumpService.dumpFormal -> ConfigCacheService 更新缓存
      -> 发布 LocalDataChangeEvent
        -> RpcConfigChangeNotifier -> ConfigChangeNotifyRequest(gRPC 推送)

[客户端 SDK 层]
ConfigChangeNotifyRequest 到达(通过 bi-di stream)
  -> ClientWorker.registerServerRequestHandler 收到
    -> cacheData.getReceiveNotifyChanged().set(true)
    -> cacheData.setConsistentWithServer(false)  // 标记需要重新检查
    -> notifyListenConfig()  // 唤醒 executeConfigListen

executeConfigListen():
  ① 收集 isConsistentWithServer=false 的 CacheData
  ② 发送 ConfigBatchListenRequest(setListen=true) via gRPC
  ③ 服务端比对每个 dataId 的 MD5 -> 返回 ConfigChangeBatchListenResponse.changedConfigs
  ④ 对变更的 dataId: refreshContentAndCheck
     -> getServerConfig(ConfigQueryRequest) 拉取完整内容
     -> cacheData.setContent(newContent)  // 更新内容+MD5
     // 注意: setContent 不自动标记 isConsistentWithServer=true!
     // 需要下一轮检查(服务端确认 MD5 一致)才标记 true(双确认模式)
     -> checkListenerMd5() -> 触发 Listener.receiveConfigInfo(newContent)

[Spring Cloud 适配层]
Listener.receiveConfigInfo(content)
  -> NacosContextRefresher 收到通知
    -> 发布 RefreshEvent
    -> ContextRefresher.refreshEnvironment()  // 更新 Environment PropertySource
    -> RefreshScope.refreshAll()  // 销毁所有 @RefreshScope Bean

[下次请求]
  -> @RefreshScope Bean 重新创建 -> @Value/@ConfigurationProperties 注入新值
```

## 二、5s 兜底机制

除了服务端推送(主通道),客户端还有 5s 周期检查(兜底):

```
ConfigRpcTransportClient.startInternal():
  while (!shutdown):
    listenExecutebell.poll(5L, SECONDS)  // 最多等 5s,或被 notifyListenConfig 唤醒
    executeConfigListen()
```

**推送丢失时**: 服务端推送的 `ConfigChangeNotifyRequest` 因网络抖动丢失 -> `receiveNotifyChanged` 不会被 set(true) -> `isConsistentWithServer` 不会被 set(false) -> 5s 兜底检查时 `isConsistentWithServer=true` 且 `needAllSync=false` -> **被跳过**(executeConfigListen line 789-791 continue)。直到 **3 分钟后**(`ALL_SYNC_INTERNAL = 3 * 60 * 1000L`)`needAllSync=true` -> 不跳过 -> 发 `ConfigBatchListenRequest` -> 服务端比对 MD5 不一致 -> 拉取新内容。

> **推送丢失的最坏延迟是 3 分钟,不是 5s!** 5s 兜底只对 `isConsistentWithServer=false` 的配置生效(即推送成功到达但内容待确认的)。推送完全丢失时,要等 3 分钟全量同步才补偿。

## 三、关键角色

| 类 | 层 | 作用 | 源码出处 |
|---|---|---|---|
| `ConfigRpcTransportClient` | Nacos SDK | gRPC 传输,`executeConfigListen` 循环 | `ClientWorker` 内部类 |
| `CacheData` | Nacos SDK | 本地缓存 + 标志位状态机(`isConsistentWithServer`/`receiveNotifyChanged`) | `impl/CacheData.java` |
| `ConfigChangeListenContext` | 服务端 | groupKey <-> connectionId 双重索引,追踪谁监听了什么 | `remote/ConfigChangeListenContext.java` |
| `RpcConfigChangeNotifier` | 服务端 | 订阅 LocalDataChangeEvent,推送 ConfigChangeNotifyRequest | `remote/RpcConfigChangeNotifier.java` |
| `NacosContextRefresher` | SCA 适配层 | 接收 SDK Listener 通知,转成 Spring RefreshEvent | Spring Cloud Alibaba |
| `ContextRefresher` | SC Commons | 刷新 Environment + RefreshScope | Spring Cloud Commons |
| `RefreshScope` | SC Commons | 自定义 Scope,Bean 销毁重建 | Spring Cloud Commons |

## 四、延迟分析

| 环节 | 延迟 | 说明 |
|------|------|------|
| Server 写 DB -> 发布 ConfigDataChangeEvent | 毫秒级 | 同步 |
| ConfigDataChangeEvent -> LocalDataChangeEvent | 毫秒级 | AsyncNotifyService 处理自己 |
| LocalDataChangeEvent -> gRPC 推送 ConfigChangeNotifyRequest | 毫秒级 | RpcConfigChangeNotifier |
| 客户端收到推送 -> executeConfigListen | 立即 | notifyListenConfig 唤醒 |
| executeConfigListen -> ConfigBatchListenRequest -> 服务端比对 MD5 | 毫秒级 | gRPC 请求/响应 |
| MD5 不一致 -> ConfigQueryRequest 拉取内容 | 毫秒级 | gRPC 请求/响应 |
| setContent -> checkListenerMd5 -> Listener 回调 | 微秒级 | 本地 |
| NacosContextRefresher -> RefreshEvent -> @RefreshScope 重建 | 毫秒到秒级 | Spring 容器操作 |

**总延迟**: 通常 **1-3 秒**(主要耗时在 @RefreshScope Bean 重建)。如果推送丢失,最坏等 **3 分钟**(ALL_SYNC_INTERNAL 全量同步)才补偿。

## 五、1.x vs 2.x 刷新机制对比

| | 1.x (HTTP 长轮询) | 2.x (gRPC 推送 + 兜底) |
|---|---|---|
| 变更感知 | HTTP 长轮询(Server hold 30s) | gRPC 服务端推送(毫秒级) |
| 兜底 | 长轮询本身就是兜轮询 | 5s 周期 executeConfigListen |
| 协议 | POST /v1/cs/configs/listener | ConfigChangeNotifyRequest + ConfigBatchListenRequest |
| 典型延迟 | 0-30s(取决于配置变更时机) | 1-3s(推送) / 最坏 3min(推送丢失+全量同步) |
| 服务端兼容 | LongPollingService(仍保留,仅 1.x 客户端) | RpcConfigChangeNotifier(2.x 原生) |

> **常见误解**: "2.x Config 还在用 HTTP 长轮询" -- 错误。`ConfigRpcTransportClient` 从 2.0.0 第一天就存在,Config 从 2.x 一开始就用 gRPC。`LongPollingService` 仅保留兼容 1.x 客户端。

## 七、生产注意

- **@RefreshScope 代价**: 每次刷新销毁重建所有 @RefreshScope Bean。如果有很多,刷新会卡顿。推荐用 `@ConfigurationProperties`(ConfigurationPropertiesRebinder 重新绑定属性,不销毁 Bean)
- **setContent 双确认**: 配置变更后 `isConsistentWithServer` 不立即变 true,需下一轮 `executeConfigListen` 确认。这意味着变更后 5s 内可能再次检查(不影响正确性,只是多一次 MD5 比对)
- **推送丢失不丢数据(但慢)**: 推送丢失 -> isConsistentWithServer 仍为 true -> 5s 兜底跳过 -> 最坏 3 分钟后(ALL_SYNC_INTERNAL)全量同步 -> MD5 不一致 -> 拉取新内容。最终一致,但推送丢失场景的延迟是分钟级
- **NacosContextRefresher 异步**: `receiveConfigInfo` 在 SDK 的回调线程执行。如果 RefreshEvent 处理慢,会阻塞该线程 -> 影响其他配置的监听回调。生产中确保 @RefreshScope Bean 重建不耗时
