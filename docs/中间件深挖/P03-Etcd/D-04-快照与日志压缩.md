## 一、它干了什么：一个例子的三个场景

```
场景① 常规触发：集群 apply 到 10 万条（SnapshotCount 默认）→ 后台生成快照文件 → 回收旧 WAL 段
场景② 新节点加入：follower 的 Next 已被 compact（落后太多）→ leader 发整个快照
     → follower restore（整体替换状态机）→ 继续增量复制
场景③ 崩溃恢复：重启 → 加载最新快照（term-index 命名）→ 从 WAL 的 snapshot 记录点回放剩余日志 → 追上
```

**一句话**：快照 = **"把状态机在某个 index 的完整状态拍成文件"**——日志（WAL）只保"自快照以来的增量"；两者配合解决"日志无限增长 + 追赶太慢 + 恢复太久"。

## 二、原理（心智模型）

### 2.1 为什么需要快照（三重动机）

| 问题 | 不加快照的后果 | 快照的答案 |
|---|---|---|
| 日志无限增长 | WAL/raft log 无限膨胀 | 快照后**压缩**旧日志（WAL 段回收 + raft storage Compact） |
| 新节点/落后节点追赶 | 从 index=1 全量回放历史 | leader 直接发快照（StateSnapshot）→ 整体替换 |
| 崩溃恢复慢 | 回放百万条日志 | 从快照恢复 + 只回放增量 |

### 2.2 快照包含什么

```
raft 快照（raftpb.Snapshot）= Metadata{Index, Term, ConfState} + Data（应用状态序列化）
etcd 的 Data = v2store 快照（含 consistent_index 等元数据）——**快照点与 backend 的一致性由 commit 保证**
文件命名：snap/db 目录下 term-index 命名（如 0000000000000002-0000000000000035.snap）
```

### 2.3 触发与压缩的配合

```
触发：appliedi - snapi > SnapshotCount（默认 100000）→ triggerSnapshot
生成：snapshot()（异步，clone 状态 → CreateSnapshot → SaveSnap 落盘 → 记 WAL snapshot 记录）
压缩：快照成功后 → raft storage Compact(快照 index) + WAL ReleaseLockTo（回收更早段）
恢复：LoadNewestAvailable（取快照 + WAL 里匹配的 snapshot 记录）→ readWAL 从快照 index 回放
```

### 2.4 follower 追赶（快照的"传输"路径）

```
Progress.State == StateSnapshot（Next 已被 compact）→ leader 发 MsgSnap
follower：raft restore（raft.go:1528，校验快照 → 整体替换 raft 状态）
       → raftNode.run 收 Ready.Snapshot → raftStorage.ApplySnapshot（:287）→ 应用层 applySnapshot（D-02:1303）
```

## 三、使用（观测与调参）

```
--snapshot-count：apply 多少条触发一次（默认 100000）
   太大：WAL 保留多、恢复回放久；太小：快照频繁、IO 抖动
快照文件：<data-dir>/member/snap/（term-index 命名；大小 ≈ backend 大小）
工具：etcdutl snapshot status/restore（离线查看/恢复）；etcdctl endpoint status 看 snapshotIndex
WAL 段：64MB/段（SegmentSizeBytes），快照后 ReleaseLockTo 回收旧段
监控：etcd_server_snapshot_apply_in_progress_total、disk IO 峰值（快照生成期）
```

## 四、源码核心（调用链 + 行号）

### 4.1 触发与生成

```
triggerSnapshot（server/etcdserver/server.go:1490）：
  条件：ep.appliedi - ep.snapi <= s.Cfg.SnapshotCount → return（未到量不拍）
snapshot（server.go:2540）：
  v2store.Clone → kv commit（确保 backend consistent_index ≥ 快照点）→
  raftStorage.CreateSnapshot（raft/storage.go:194，生成 Metadata）→
  SaveSnap（server/etcdserver/api/snap/snapshotter.go:68 → save:75，写 term-index 文件）
DefaultSnapshotCount = 100000（server.go:76）
```

### 4.2 WAL 侧的配合

```
SaveSnapshot（server/wal/wal.go:953）：在 WAL 里写一条 snapshot 记录（记录快照 index）
  ——恢复时用它对齐"从哪个 index 回放"；w.enti 推进
SegmentSizeBytes = 64MB（wal.go:55）；cut（:705）切段
ReleaseLockTo（:824）：快照后放掉旧段锁 → 段文件回收（日志压缩落地点）
```

### 4.3 恢复链（启动）

```
启动：LoadNewestAvailable（snapshotter.go:113）
  → snapNames（:217，按逻辑时间排序）/ Read（:162，读快照文件）
  → 与 WAL 的 snapshot 记录匹配
readWAL（server/etcdserver/storage.go:87）：从快照 index 开始回放 WAL → 得到 HardState + Entries
RestartNode（etcdserver/raft.go:568，restartNode:535）：以快照+日志重建 raft 状态机
```

### 4.4 follower 快照追赶

```
raft restore（raft/raft.go:1528）：校验快照（term/index 约束）→ 整体替换日志
raftNode.run：rd.Snapshot 非空 → r.storage.SaveSnap + raftStorage.ApplySnapshot（:287）
应用层：applyAll → applySnapshot（server.go:1303）——用快照整体替换 MVCC backend
```

## 五、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **快照 + 增量日志组合** | 只留快照（无日志） | 两次快照之间的写会丢；日志是"快照之后的增量"——组合才闭环 |
| **异步生成快照** | apply 时同步写快照 | 快照是重 IO——异步化不阻塞主路径（代价：生成期磁盘峰值） |
| **快照延迟在 apply 后** | 随时拍 | "快照点=已 apply 的状态"——与 backend 一致性由 commit 保证 |
| **WAL 里也记快照记录** | 只看快照文件 | 恢复时知道"快照对应 WAL 哪个位置"——对齐回放起点 |
| **段级 WAL 回收（64MB）** | 逐条删日志 | 段文件整体释放——简单且批量（ReleaseLockTo 原子语义） |
| **follower 落后太多发全量快照** | 永远增量 | 增量回放成本 >> 快照传输时——快照是"追赶加速器" |

## 六、生产陷阱

| # | 陷阱 | 根因与修复 |
|---|---|---|
| 1 | **snapshot-count 过大** | 恢复回放久（WAL 巨大）——按"恢复时间目标"调小 |
| 2 | **snapshot-count 过小** | 频繁快照 IO 抖动——调大或接受 |
| 3 | **快照期磁盘峰值** | 快照文件 + WAL 同时存在——预留空间；监控快照进行中指标 |
| 4 | **新节点追赶慢** | 快照大小 ≈ 数据量——加节点选低峰期；快照传输占带宽 |
| 5 | **误删 snap 目录** | 恢复只能回放全量 WAL（可能失败）——备份 snap+wal 一体 |
| 6 | **compact 后老 follower 掉队** | Next 已 compact → 触发快照传输——观察 StateSnapshot 状态 |

## 七、面试 Q&A（含面试官意图）

**Q1："etcd 为什么要快照？"**（意图：三重动机）
日志增长控制 + 落后节点追赶 + 恢复加速——快照是"状态机在 index 的完整定格"。

**Q2："快照和 WAL 怎么配合？"**（意图：恢复链）
WAL 里记 snapshot 记录 → 恢复：加载最新快照 + 从该 index 回放 WAL 增量 → 重建完整状态。

**Q3："snapshot-count 怎么定？"**（意图：调参）
权衡恢复时间与快照频率：大=恢复慢/IO 少；小=恢复快/IO 频繁——按恢复目标与磁盘能力定。

**Q4："follower 落后太多怎么办？"**（意图：复制机制）
leader 的 Progress 进入 StateSnapshot → 直接发快照（增量已不可行）→ follower restore 后继续增量。

**Q5："压缩压的是什么？"**（意图：概念边界）
两层：① WAL 段回收（ReleaseLockTo）+ raft log Compact；② D-03 的 MVCC compact（历史版本）——**日志压缩 ≠ 数据压缩**。
