## 一、它干了什么：三个用户体验场景

```
① 纠错：用户搜"小红书种草笔记"打成"小红书种草笔计" → term suggester 返回"笔记"（编辑距离 1）
② 补全：搜索框输入"小红" → completion suggester 瞬间返回"小红书/小红书种草/…"（前缀 FST 查找）
③ 同义词：搜"帖子"也能找到 title 含"笔记"的结果（同义词展开：帖子⇄笔记）
```

**一句话**：搜索体验 = **"容错（编辑距离）+ 预判（前缀 FST）+ 懂你（同义词图）"**——三个机制，三套索引结构。

## 二、原理

### 2.1 纠错：编辑距离（Levenshtein）

```
term suggester：拿输入词 → 在索引词典里找"编辑距离小"的候选 → 按（距离, 词频）打分排序
  maxEdits（≤2，Lucene 上限）：允许的编辑次数；accuracy（默认 0.5）：候选最低得分
  距离度量：LuceneLevenshteinDistance（插入/删除/替换各算 1）
phrase suggester：整句纠错（n-gram 语言模型：候选词序列的联合概率最高者胜）
```

### 2.2 补全：FST 专用字段

```
completion 字段类型：索引时把"输入→输出"的映射建成 FST（与词典同族结构，专为前缀查找优化）
查询：FSTCompletion.lookup(prefix) —— 沿 FST 走 prefix 路径，枚举补全（O(prefix 长 + 结果数)）
fuzzy 选项：prefix 固定 + 后面允许编辑（transpositions/min_length/prefix_length）
contexts：类别/地理过滤（补全限定在某类目/附近）
```

### 2.3 同义词：图展开（SynonymGraph）

```
SynonymGraphFilter（TokenFilter）：词流过同义词表时展开
  expand=true：双向（"笔记本"→笔记本/笔记/电脑；查任一都命中）
  includeOrig：是否保留原词
  位置（索引期 vs 查询期）：索引期展开（查得快，索引大）vs 查询期展开（灵活，可热更新）
中文注意：同义词必须在分词之后做（先 IK 切词，再对词做同义词映射）
```

## 三、使用（生产口径）

```json
// term suggester：text/错字建议
{ "suggest": { "t": { "text": "笔计", "term": { "field": "title" } } } }
// completion：prefix + fuzzy + contexts
{ "suggest": { "c": { "prefix": "小红", "completion": { "field": "title_suggest",
  "fuzzy": { "fuzziness": 1 }, "size": 5 } } } }
// 同义词：analysis filter 配 synonym_graph（synonyms_path 指向文件）
```

| 实践 | 要点 |
|---|---|
| term 参数 | `suggest_mode`（missing/popular/always）、`size`、`sort`（score/frequency）、`shard_size` |
| completion 字段 | 专用 `completion` 类型（不能复用 text）；contexts 做类目/地理限定 |
| 同义词文件 | `synonyms_path`（分析器配置）；更新需 reindex（索引期展开）或 reload（查询期） |

## 五、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **纠错用编辑距离而非语义模型** | 向量相似 | 编辑距离可解释、可调参（maxEdits/accuracy）、无模型依赖；语义纠错是另一条线（kNN） |
| **补全用独立 FST 字段** | 复用倒排前缀扫描 | FST 前缀查找 O(prefix) 且内存小；倒排前缀要扫 posting（慢一个量级） |
| **同义词做成 TokenFilter** | 查询改写层 | 在分析链里统一处理（索引/查询两端可选展开点）；图结构保位置信息（短语查询仍可用） |
| **suggest 与 search 分离** | suggest 走 match | suggest 要"快+容错+可控"，search 要"准"——不同目标不同链路 |

## 六、生产陷阱

| # | 陷阱 | 根因与修复 |
|---|---|---|
| 1 | **同义词不生效** | 配置在错误端（索引期配了查询期没配，反之）——两端展开策略统一 |
| 2 | **中文同义词错乱** | 同义词在分词前做——必须"先分词（IK）后映射" |
| 3 | **completion 查不到** | 用了 text 字段而非 completion 类型——suggest 需专用字段 |
| 4 | **纠错候选太多** | maxEdits 大 + accuracy 低——收紧参数；shard_size 控制分片候选数 |
| 5 | **suggest 与业务召回打架** | suggest 只做"提示"，最终搜走正常 DSL——两条链路 |
| 6 | **同义词文件更新不生效** | 索引期展开要 reindex——改查询期展开或走 reload 流程 |

## 七、面试 Q&A（含面试官意图）

**Q1："拼写纠错怎么实现？"**（意图：编辑距离）
Levenshtein 距离找近似词（maxEdits 上限 2）+ accuracy 过滤 + 词频排序；phrase 用 n-gram 语言模型纠整句。

**Q2："搜索框补全怎么做到毫秒级？"**（意图：FST）
completion 专用字段建 FST → 前缀路径枚举（O(prefix 长)）；fuzzy 允许后缀编辑；contexts 做限定。

**Q3："同义词在哪展开？"**（意图：分析链）
SynonymGraphFilter（TokenFilter）；索引期展开（快、索引大）vs 查询期展开（灵活）——中文先分词后映射。

**Q4："suggest 和 search 什么关系？"**（意图：架构）
分离的链路：suggest 快+容错（提示用），search 准（召回用）——最终点击走正常 DSL。
