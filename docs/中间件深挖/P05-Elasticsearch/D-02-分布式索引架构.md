## 一、它干了什么：一条文档的分布式一生

```json
PUT /note_index/_doc/123  { "title": "小红书种草" }
```

```
① 路由：shard = hash(_id=123) % num_primary（无自定义 routing 时用 _id；同 id 永远同分片）
② 主分片：translog 追加（每请求 fsync）+ indexing buffer（内存）→ 返回 ack
③ 副本：主分片把操作复制到 replica（seqNo 保障顺序）→ 副本各自写 translog+buffer
④ 1s 后 refresh：buffer → 新 segment（可搜索）；主副各自独立 refresh
⑤ 后台 merge：小 segment 按 TieredMergePolicy 合并成大 segment → 删旧段
```

**一句话**：写入是"**主分片确认 + translog 持久 + buffer 攒批**"；可见性是"**refresh 定时开新段**"；长期健康靠"**merge 不断整理碎片**"。

## 二、原理

### 2.1 分片路由（routing）

```
shard_num = hash(routing) % num_primary_shards
  默认 routing = _id（Murmur3 哈希）——同文档永远同分片（更新/删除能定位）
  自定义 _routing：把"一起查的数据"放同分片（join/父子场景），代价是倾斜风险
分片数建索引时定死（扩容只能 reindex/split）——10-50GB/片经验值
```

### 2.2 内存与可见性（indexing buffer → segment）

```
IndexingMemoryController：全节点共享 indexing buffer（默认堆 10%）——各分片按需分配
  写满 → 自动 refresh（最早的 buffer 先落段）
refresh（默认 1s）：内存文档 → Lucene IndexWriter → 新 segment → 新 reader（可搜索）
  不 fsync（只进 PageCache）——可搜索 ≠ 已持久化（D-01 的 translog 才是持久性）
```

### 2.3 Lucene 生命周期三件套

| 操作 | 做了什么 | 持久性 |
|---|---|---|
| **refresh**（1s） | buffer → 新 segment（IndexWriter 切 reader） | 未落盘（OS 崩溃会丢未 flush 数据；但 translog 可恢复） |
| **flush** | segment fsync + 清 translog（`commit` 点） | 已持久化（重启从 commit 恢复） |
| **merge** | 小 segment 合并（删已删除文档、整理碎片） | 后台 IO（自动限流） |

### 2.4 Translog（ES 的 WAL）

```
每次写 → translog 追加（每请求 fsync，durability=request 默认）→ buffer 内存
flush 时：segment 落盘 + translog 清空（旧 translog 删除）
崩溃恢复：从最后 commit 点 + 重放 translog（ES 重启/分片恢复机制）
```

### 2.5 段合并（TieredMergePolicy，Lucene 默认）

```
思想：把 segment 按大小分层（tier），每层保持约 10 个
  floor：小于 2MB 的都算 2MB（小段优先合）
  一次最多合 10 个；合并后单段不超过 5GB
  删除占比 >10-20% 的段优先被"清理式合并"（expunge 删除）
ES 包装：ElasticsearchConcurrentMergeScheduler（超了 max_thread_count 自动限流 merges）
```

## 三、使用（生产调参）

| 场景 | 配置 | 建议 |
|---|---|---|
| 批量写入 | `refresh_interval: 30s` 或 `-1`（完事改回） | 减少 refresh 开销；bulk 更快 |
| 可靠性 | `translog.durability: request`（默认） | 别改 async（丢数据窗口） |
| 只读索引 | `forcemerge max_num_segments=1` | 合并成一段（查询快）；**写索引禁止 force_merge** |
| 合并限流 | `index.merge.scheduler.max_thread_count` | 默认按 CPU 核；IO 瓶颈调小 |
| 分片规划 | 建索引时定（10-50GB/片） | 只增不改；倾斜用 routing 重分布 |

## 五、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **refresh（1s）≠ fsync** | 每次写都 fsync | 把"可见性"和"持久性"解耦：前者高频便宜（PageCache），后者靠 translog 保底 |
| **索引 buffer 全节点共享** | 每分片固定 buffer | 按写入压力动态分配（热点分片多拿）——内存利用率优先 |
| **分片路由 hash 取模** | 范围路由 | 更新/删除能 O(1) 定位分片；代价是分片数不可变 |
| **TieredMerge 同层合并** | 无脑全合 | 控制单次合并成本 + 段大小分布均匀（读放大可控） |
| **merge 自动限流** | 合并抢满 IO | 前台读写优先——合并是后台活，不能饿死查询 |
| **translog 每请求 fsync（默认）** | 批量 fsync | 默认安全（不丢）；批量场景改 async + 接受窗口——显式取舍 |

## 六、生产陷阱

| # | 陷阱 | 根因与修复 |
|---|---|---|
| 1 | **写完搜不到** | NRT（1s refresh）——正常语义；bulk 时调大 refresh_interval |
| 2 | **refresh 当持久化** | refresh 只进 PageCache——崩溃恢复靠 translog（D-01 已讲） |
| 3 | **bulk 慢** | refresh 太频繁——批量时 -1/30s，完事改回 |
| 4 | **只读索引段碎** | 大量小 segment——forcemerge 到 1 段（只对只读索引） |
| 5 | **merge 打满 IO** | 合并线程多——max_thread_count 调小；看 onGoingMerges |
| 6 | **分片倾斜** | 自定义 routing 倾斜——routing 值打散/重选键 |
| 7 | **分片数拍脑袋** | 建后不可改——按 10-50GB/片 + 增长预估 |

## 七、面试 Q&A（含面试官意图）

**Q1："文档怎么路由到分片？"**（意图：路由机制）
`hash(_id 或自定义 routing) % 主分片数`（Murmur3）——同文档永远同分片；分片数建后不可改。

**Q2："refresh/flush/merge 区别？"**（意图：生命周期）
refresh=buffer→segment（可搜索，未落盘）；flush=segment 落盘+清 translog（持久化）；merge=整理小 segment（后台 IO）。

**Q3："ES 怎么保证不丢数据？"**（意图：持久性）
translog 每请求 fsync（默认 request）；重启从 commit 点重放——refresh 只是可见性。

**Q4："merge 策略？"**（意图：存储治理）
TieredMergePolicy：同层约 10 段、单次 ≤10、最大 5GB、floor 2MB；ES 加自动限流。

**Q5："写入慢怎么调？"**（意图：调优）
bulk 时 refresh_interval 放大 + translog 保持 request + 看 merge/IO；分片数与副本先规划好。
