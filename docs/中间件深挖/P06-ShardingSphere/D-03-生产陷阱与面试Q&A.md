## 一、6 个生产陷阱

| # | 陷阱 | 场景 | 根因与修复 | 回链 |
|---|---|---|---|---|
| 1 | **笛卡尔积爆炸** | 多表 JOIN 未绑定，分片数相乘 | 绑定表组（同分片键+同算法）；慢查询先看路由单元数 | D-01 §2.2 |
| 2 | **无分片键全路由** | WHERE 无分片键 → 16 分片全扫 | 加分片键条件 / 映射表反查；hint 只做特殊场景 | D-01 §2.2 |
| 3 | **Snowflake 低位取模倾斜** | 时间型 ID 低位不平坦 → 数据挤在少数分片（实测 75% 落 2/16） | hashCode 混合高位后取模 + 存量迁移（K12：682 行） | K12 |
| 4 | **worker-id 冲突发重号** | 同机多实例同 worker-id | 三级推导（环境变量/-D/IP+端口，K12：354 vs 454） | K12 |
| 5 | **跨分片深分页** | LIMIT 放大×分片数 + 归并截断 | 禁跳页/游标；大聚合走离线 | D-01 §2.3/2.4 |
| 6 | **扩容无方案** | 固定分片数，分片满了 | 双写迁移 + 影子表比对（简历写"暂无 rehash"，不装） | K12 |

## 二、4 个面试题（意图 + 主线 + 追问链）

### Q1 "分片键怎么选？"（意图：业务驱动设计）

**主线**：按**最热查询模式**选——交易 90% 是"我的订单"→ user_id；下单/支付/取消全在单用户上下文（单用户事务不跨库）。
**追问链**：选订单号会怎样？→ 用户列表查询全路由。选商家呢？→ 用户查询全路由。非分片键查询？→ 映射表（order_no → user_id）+ 补录 Job。
**危险信号**：分片键拍脑袋；跨分片查询没方案。

### Q2 "跨分片分页/聚合怎么做？"（意图：改写与归并成本）

**主线**：LIMIT 改写放大（各分片 `LIMIT 0, offset+n`）→ 并行执行 → 归并（ORDER BY 流式 / GROUP BY 内存）→ 截断。
**追问链**：offset 很大呢？→ 代价线性涨——产品禁跳页/游标。大聚合？→ 离线数仓，不在 OLTP 做。
**危险信号**：不知道 LIMIT 要放大；以为归并免费。

### Q3 "绑定表是什么？解决什么？"（意图：JOIN 优化）

**主线**：分片规则同构（同键+同算法）的表声明绑定 → 相同分片键的 JOIN 行落在同一物理分片 → 单分片执行。
**追问链**：不绑定会怎样？→ N×M 笛卡尔积（每库拉全表内存 join）。绑定配错了？→ 错结果（比慢更严重）——显式声明即契约。
**危险信号**：不知道绑定表；把"能 JOIN"当"JOIN 得快"。

### Q4 "扩容/倾斜/时钟回拨三连？"（意图：生产边界诚实度）

**主线**：
- 倾斜：Snowflake 低位偏差 → hashCode 取模 + 迁移（131 单 75%→16/16 全用，682 行）
- 扩容：固定 4×4 无 rehash → 双写迁移 + 影子表比对（方案级回答）
- 回拨：Snowflake 时钟回拨（内置策略）+ worker-id 冲突更现实（IP+端口三级推导）
**追问链**：迁移期间服务停了吗？→ 按 id 游标分批 + 双读校验（不停服演练）——真实演练细节。
**危险信号**：宣称"无缝扩容"；Snowflake 只会背时钟回拨。
