## 一、它干了什么：两道选择题

```
Q1（分区）：100 亿行订单，按什么切到 16 个分片？
  A. Hash(user_id) % 16 —— 点查 O(1) 定位；范围查全扫（K12 就是这么选的）
  B. 范围（user_id 区间）—— 范围查只打相邻分片；热点区间倾斜（D-04 Bigtable tablet）
Q2（复制）：主库挂了，备库能顶吗？顶上来丢数据吗？
  A. 同步复制（ semi-sync/Raft ）——不丢，但主挂时写停顿
  B. 异步复制（MySQL GTID/K17）——不停顿，但可能丢（RPO>0，演练 32s 故事）
```

**一句话**：分区回答"数据在哪"，复制回答"挂了怎么办+丢不丢"——两个维度的组合决定系统性格。

## 二、原理

### 2.1 分区策略

| 策略 | 机制 | 点查 | 范围查 | 扩容 | 代表 |
|---|---|---|---|---|---|
| **Hash** | hash(key)%N（+虚拟节点） | O(1) | 全扫 | 加节点只迁邻居（Dynamo）/ 固定不可变（K12） | Dynamo(D-05)、K12、Redis Cluster |
| **范围** | key 区间→分片 | 查元数据定位 | 相邻分片 | 分裂（tablet split） | Bigtable(D-04)、HBase |
| **目录** | 查表定位 | 查表 | 按表 | 灵活 | GFS master（小规模元数据） |

```
一致性哈希 + 虚拟节点（D-05）：环上多点 → 故障负载均匀打散 + 按能力分配 + 加减节点只影响邻居
```

### 2.2 复制拓扑

| 拓扑 | 写路径 | 读路径 | 故障 | 代表 |
|---|---|---|---|---|
| **主从**（单主） | 写主→异步/半同步到从 | 读写分离（从可能旧） | 主挂→提升（RTO，K17 32s） | MySQL GTID、GFS（租约主）、Kafka ISR（leader 语义） |
| **多主** | 任节点可写 | 本地读 | 冲突要解（向量时钟/LWW） | Dynamo（N 个对等点） |
| **无主**（对等 quorum） | W 个确认即成功（sloppy） | R 个合并（读修复） | 无单点（Dynamo 设计目标） | Dynamo、Cassandra |

### 2.3 一致性模型谱系（从强到弱）

```
线性一致（Linearizability）：所有操作看起来在某个瞬间原子发生 —— Raft/2PC/ZAB（P03）
顺序一致：同客户端保序 —— 会话粘滞
因果一致：有因果的保序，无关可并发 —— 向量时钟判定（D-05）
读写一致：读到自己写过的（read-your-writes）—— 会话路由/版本号兜底
单调读：越读越新（不回退）—— 时间戳/版本号单调
最终一致：无新写后最终收敛 —— Dynamo/Gossip/DNS（需冲突解决策略）
```

### 2.4 N/R/W 调参（D-05 落地）

```
R+W > N → quorum-like（读写交集必有最新）；常见 (3,2,2)
W=1：永不拒写（可用极致）；R=1,W=N：读引擎（产品目录类）
```

## 三、怎么做 / 选型决策

```
强一致 + 事务（订单/支付）→ 主从半同步/Raft + 本地事务（K12/K17 口径）
高可用 + 可丢可合并（购物车/会话）→ Dynamo 式 NWR + 向量时钟/合并（D-05）
读多 + 范围查（ analytics ）→ 范围分区 + 列存/Bigtable 式（D-04）
元数据小 + 强一致（锁/选主）→ Raft/ZAB 单组（P03）
```

## 四、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么 |
|---|---|---|
| **分区与复制正交** | 绑定设计 | 可独立演进（换分区算法不动复制协议，反之亦然） |
| **最终一致 + 应用合并** | 写时仲裁一切 | 可用性铁律场景下，合并成本 < 拒写损失（D-05） |
| **读修复 + 反熵双保险** | 只靠一种同步 | 热数据走读修复（机会主义），冷漂移走 Merkle（D-05） |
| **RPO 诚实标注** | 默认不丢 | 异步复制的 RPO>0 必须说出来（K17 演练：RPO=0 是幸运） |

## 五、面试 Q&A（含面试官意图）

**Q1："一致性哈希解决什么？"**（意图：扩容迁移）
加减节点只影响邻居（vs 取模全迁）；虚拟节点解决不均匀+异构（D-05）。

**Q2："N/R/W 怎么配？"**（意图：quorum 调参）
R+W>N 即 quorum-like；(3,2,2) 常见；W=1 永不拒写；场景定参数（D-05 表）。

**Q3："主从和多主怎么选？"**（意图：拓扑取舍）
要强一致/事务 → 主从半同步；要永远可写 → 多主/无主 + 冲突解决。

**Q4："最终一致下怎么不丢更新？"**（意图：冲突处理）
向量时钟检测分支 + 应用合并（购物车范例）；删除复活是已知代价（tombstone/对账兜底）。
