## 一、它干了什么：购物车的一次加购之旅（论文 Figure 3 故事线）

```
客户端写新对象 → Sx 处理，时钟 [(Sx,1)] → D1
同客户端再写（仍 Sx）→ [(Sx,2)] → D2（覆盖 D1，后代关系可判定）
换节点 Sy 写 → [(Sx,2),(Sy,1)] → D3
另一客户端读到 D2 后经 Sz 写 → [(Sx,2),(Sz,1)] → D4（与 D3 无因果 → 冲突并存）
读到 D3+D4 → 返回两个版本给应用合并 → 写回 D5 [(Sx,3),(Sy,1),(Sz,1)]（分支收敛）
```

**一句话**：Dynamo = **"永远可写的 KV"**——把冲突解决推迟到读、推给应用（购物车合并），用向量时钟区分"祖先后代（覆盖）vs 并发分支（并存）"。

## 二、原理（论文机制）

### 2.1 设计前提：SLA 在 99.9 分位 + 对称去中心

```
SLA 例：500rps 下 99.9% 请求 300ms 内返回（均值/中位数不够——长尾用户才是体验）
  页面渲染扇出 150+ 服务 → 每个依赖都必须有更紧的 SLA（长尾叠加）
四原则：增量扩展（一次加一台）/ 对称（无特殊节点）/ 去中心（无中央控制）/ 异构（按能力分配负载）
接口：get(key)→对象+context；put(key,context,object)；key 经 MD5 得 128 位标识
```

### 2.2 分区：一致性哈希环 + 虚拟节点（§4.2）

```
key 哈希落环 → 顺时针第一个节点为 coordinator → 再复制到后 N-1 个（preference list，只含不同物理机）
虚拟节点（token）：每物理机占环上多点——① 故障时负载均匀打散 ② 新节点从各方均匀接管 ③ 按能力分配 token 数
```

### 2.3 复制执行：N/R/W + 协调器（§4.5）

```
读/写走"前 N 个健康节点"（跳过宕机者）；R+W>N 即 quorum-like（常见 (3,2,2)）
put：coordinator 生成新向量时钟 → 本地写 → 发 N 个最高可达节点 → W-1 个回即成功
get：要 N 个最高可达节点的全版本 → 等 R 个回 → 返回因果无关的多个版本
写协调器优化：选"上次读回最快的节点"（大概率有数据 → read-your-writes + 99.9 分位更稳）
读修复（read repair）：读到旧版本顺手推新版（机会主义同步，减轻反熵压力）
```

### 2.4 版本：向量时钟（§4.4，论文最出名的一节）

```
每版本带 [(node,counter)...]：全 ≤ 对方 → 祖先（覆盖，可 GC）；否则 → 并发冲突（并存，交应用合并）
写必须带读到的 context（声明"我在哪个版本上改"）；合并写的新时钟收敛分支
截断：(node,counter,时间戳)，超 10 对删最老（后代判定可能不准——生产未爆雷）
```

### 2.5 故障处理双件套：hinted handoff + Merkle 反熵（§4.6-4.7）

```
hinted handoff（sloppy quorum）：A 宕机 → 写本该给 A 的副本时带 hint 暂存 D → A 恢复后 D 定期扫描交付
  → 临时故障不丢不拒（W=1 时只要全系统有 1 台活着就接受写）
Merkle 反熵：每 key-range（虚拟节点）一棵哈希树 → 比根 → 逐层下钻找差异键 → 只传差异
  （根同则全同，一次比较省全量扫描）
```

### 2.6 成员与发现：gossip + 种子（§4.8）

```
加减节点走显式管理命令（持久化成员变更历史）；gossip 每秒随机 peer 对账（成员变更+token 映射）
种子节点（静态配置/配置服务）防逻辑分区；故障检测是"本地观念"（A 连不上 B 即判 B 挂，重试恢复）
```

## 三、怎么做 / 有什么坑（调参实战 §6）

| 旋钮 | 选项与后果 |
|---|---|
| **(N,R,W)** | 常见 (3,2,2)；W=1 永不拒写（可用性极致， durability 窗口大）；R=1,W=N 当高性能读引擎（产品目录类） |
| **调和策略** | 业务合并（购物车）/ 时间戳 LWW（session，直接覆盖）——按业务选 |
| **写缓冲优化** | 内存 buffer + 定期刷（99.9 分位降 5 倍）↔ 崩溃丢缓冲；折中：N 副本中 1 个做 durable 写 |
| **分区策略演进** | 策略1（随机 token，成员信息随节点涨）→ 策略3（Q 等分 + Q/S token，最优：成员信息小 3 个量级 + 文件级搬迁/归档） |
| **分歧版本率** | 生产 99.94% 请求只见单版本；多版本多来自机器人并发写（不是故障） |
| **客户端驱动协调** | 客户端缓存成员表直连 coordinator（省 LB 一跳，99.9 分位降 30ms+）；成员 10s 轮询更新 |
| **后台准入控制** | 反熵/交接任务按前台 P99 反馈动态分片——前台慢则后台让路 |
| **规模上限** | 全员 gossip 全路由表 → 只适合几百节点（上万节点要分层/O(1)DHT） |

## 四、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **冲突解决推迟到读、推给应用** | 写时仲裁（多数派/Raft） | "永远可写"是铁律（购物车不能拒单）——读时合并的代价小于拒写的损失 |
| **向量时钟而非 LWW** | 最后写入胜出 | LWW 静默丢更新；向量时钟"检测冲突但不替你决定"，更新永不丢失（删了的会复活是已知代价） |
| **sloppy quorum + hinted handoff** | 严格 quorum（必须 top N 活着） | 临时故障是常态——"先接下来、标注意图、恢复再交"保可用性与耐久 |
| **读修复 + Merkle 双保险** | 只靠一种同步 | 读修复处理"热数据不同步"，Merkle 处理"冷数据漂移"——冷热分治 |
| **对称去中心（无 master）** | 主备/协调者 | 免单点运维（对比 GFS master）；代价是 gossip 成员信息随规模涨 |
| **N/R/W 可调而非固定** | 全局统一一致性 | 不同业务 SLA 不同（购物车 vs 产品目录）——把 trade-off 做成旋钮 |

## 五、面试 Q&A（含面试官意图）

**Q1："Dynamo 怎么做到永远可写？"**（意图：可用性设计）
sloppy quorum（前 N 健康节点即可）+ hinted handoff（暂存转交）+ W=1 极端（1 台活着就接受）——代价是冲突推迟到读。

**Q2："向量时钟解决什么？"**（意图：因果判定）
区分"祖先后代（覆盖）vs 并发分支（并存）"；写带读到的 context 声明基版本；分支由应用合并收敛。

**Q3："N/R/W 怎么配？(3,2,2) 什么意思？"**（意图：quorum 调参）
N=3 副本；R=2 读要 2 个回；W=2 写要 2 个确认；R+W>N 即 quorum-like；W=1 可用极致、R=1/W=N 读引擎。

**Q4："临时故障和永久故障分别怎么修？"**（意图：双机制）
临时：hinted handoff（带意图暂存+恢复交付）；永久：Merkle 反熵（比根下钻，只传差异键）+ gossip 成员变更。

**Q5："和 Bigtable/GFS 的根本区别？"**（意图：范式对比）
去中心化对称（无 master/Chubby）vs 主备；最终一致+应用合并 vs 单行强一致/快照读；目标是"永远可写 KV"而非"结构化查询"。
