# P02-RocketMQ D-04 — 5.x 新特性：DLedger / Controller / Proxy

> **定位**：RocketMQ 深挖系列第 4 篇（按 P02 规划产出物）。4.x → 5.x 的**部署形态**变化：从"手动运维主从"到"自动选主 + 无状态接入"。
> **源码版本**：rocketmq-all-5.1.4（`code/spring/rocketmq-5.1.4`）
> **质量标准**：源码阅读清单 / 完整调用链 / 设计哲学（反面假设）/ 生产陷阱 / 面试 Q&A（意图）/ 章节依赖

## 一、它干了什么：一个例子

传统 4.x 部署的痛点：Master 挂了，**Slave 不会自动升主**——要人工改配置重启（故障恢复以小时计）。5.x 给了三种演进：

| 形态 | 机制 | 效果 |
|---|---|---|
| **DLedger**（`enableDLegerCommitLog=true`） | CommitLog 换成 **Raft 日志**（DLedger 自研 Raft） | 多数派落盘 + **自动选主**（Leader 挂了 1s 级切） |
| **Controller**（`enableControllerMode=true`） | 独立 **Controller 集群**（Raft 选主）协调 Broker 主从 | 自动主从切换 + **epoch fencing** 防脑裂 |
| **Proxy**（5.x 新增进程） | 无状态 gRPC 接入层（+remoting 兼容） | 客户端只连 Proxy——多语言、弹性扩缩、免 Rebalance 风暴 |

**一句话**：DLedger 解决"**存储层的高可用**"（Raft 复制）；Controller 解决"**主从关系的协调**"（谁当主）；Proxy 解决"**接入层的弹性**"（无状态网关）。

## 三、机制链（三块 + 其他）

### 3.1 DLedger：Raft 化的 CommitLog

```
写消息 → DLedgerCommitLog.asyncPutMessage(:418)
  → 追加到 DLedger（Raft 日志）
  → 复制到多数派节点 → 多数派 ack 后提交（Leader 本地 + 多数派持久化）
  → Leader 宕机：DLedgerLeaderElector 选举（term + 多数派投票）→ 新 Leader
  → DLedgerRoleChangeHandler.handle(:57)：新主切 Master（可写）、旧主切 Slave（同步）
```

**与主从复制的区别**：传统主从是"一主多从异步/同步复制，主挂人工切"；DLedger 是"**Raft 多数派**——数据不丢（多数派落盘）+ 自动选主"。

### 3.2 Controller：独立的主从协调者

```
Controller 集群（3 节点，Raft 选主）
  ← Broker 向 Controller 注册（CONTROLLER_REGISTER_BROKER=1003）+ 周期心跳
  ← Controller 维护 Broker 存活/角色，决定谁是 Master（brokerId=0）
  → 通知 Broker：ReplicasManager.changeToMaster(:237) / changeToSlave(:232)
  → 附带 epoch（新主 epoch+1）——旧主看到更高 epoch 自动退位（fencing）
```

**ControllerManager.start(:233)**：heartbeatManager（Broker 心跳）+ controller.startup（Raft）+ remotingClient（与 Broker 通信）。

### 3.3 Proxy：无状态接入层

```
ProxyStartup(:57)
 ├─ GrpcServer(:83, 端口 8081)          ← v5 客户端（gRPC/HTTP2）
 ├─ RemotingProtocolServer(:91)         ← 兼容旧 remoting 客户端
 └─ LOCAL 模式：内嵌 BrokerController(:187)（Proxy+Broker 同进程）
    CLUSTER 模式（默认，ProxyMode:20-22）：Proxy 独立部署
      → 客户端请求 → Proxy → TopicRouteService 查路由 → MQClientAPIExt 转发到 Broker
```

**客户端变化**：v5 客户端只连 Proxy（一个 gRPC channel），不知道 Broker 地址——路由上移 + Pop 消费模式（免 Rebalance 风暴）。

## 四、使用（生产口径）

### 4.1 配置速查

| 场景 | 配置 | 默认 | 说明 |
|---|---|---|---|
| DLedger 集群 | `enableDLegerCommitLog=true` + `dLegerSelfId`/`dLedgerGroup`（建议 3 节点） | false | 存储层 Raft 自动切主 |
| Controller 模式 | `enableControllerMode=true` + `controllerAddr`（Controller 集群地址） | false | 独立协调选主 + epoch fencing |
| Proxy | `proxyMode`（LOCAL/CLUSTER）+ `grpcServerPort`（8081） | CLUSTER / 8081 | 无状态接入层 |

### 4.2 选型决策

```
需要自动主从切换（免人工运维）？
  ├─ 只要存储高可用、部署简单 → DLedger（换 CommitLog，3 节点）
  └─ 要统一主从协调/多组 Broker 管理 → Controller 模式（可与 DLedger 叠加）
需要多语言客户端 / 弹性扩缩 / 免 Rebalance 风暴？
  └─ Proxy（CLUSTER 独立部署；v5 客户端走 gRPC）
```

### 4.3 迁移与注意

- 存量 4.x remoting 客户端：Proxy 双协议兼容（无需立即升级客户端）
- 开启前先做切主演练 + 监控/告警就绪（Controller/DLedger 故障域不同）
- 版本基线差异：以部署版本源码为准（本系列 5.1.4；5.3+ 有增强）

## 五、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **DLedger 自研 Raft 而不是用 ZK/etcd** | 依赖外部协调服务 | 中间件内嵌共识——少一个外部依赖（运维简单）；与 CommitLog 深度集成 |
| **Controller 独立于 DLedger** | DLedger 一步到位 | 两者定位不同：DLedger 换**存储层**（数据复制）；Controller 管**元数据/角色**（可叠加使用）；Controller 还能协调非 DLedger 的 HA 复制 |
| **Proxy 无状态** | 客户端直连 Broker（4.x 模式） | 多语言接入（gRPC 标准协议）+ 弹性扩缩（无 Rebalance 风暴）+ 路由/鉴权上移 |
| **双协议并存（gRPC+remoting）** | 强制升级客户端 | 兼容存量 4.x 客户端——渐进迁移 |

## 六、生产陷阱

| # | 陷阱 | 根因 | 修复 |
|---|---|---|---|
| 1 | **以为 5.x 默认自动切主** | `enableControllerMode=false` / `enableDLegerCommitLog=false` 均默认关 | 要自动切主必须显式开启其中之一 |
| 2 | **DLedger 与 Controller 混淆** | 两者都能"自动切主" | DLedger=存储层 Raft（换 CommitLog）；Controller=独立协调（管角色）——概念与配置都不同 |
| 3 | **Proxy 与 remoting 客户端混用配置** | v5 starter 与 2.x starter 不兼容 | 二选一（回链 lab D9：endpoints vs name-server） |
| 4 | **版本差异（5.1.4 vs 5.3+）** | 5.x 迭代快（Pop/Proxy 能力持续增强） | 以部署版本源码为准（本系列基线 5.1.4） |
| 5 | **Controller 集群自身高可用** | Controller 也是 Raft 集群（3 节点） | 单 Controller 是新的单点——按 3 节点部署 |

## 七、面试 Q&A（含面试官意图）

**Q1："5.x 相比 4.x 有什么变化？"**（意图：是否跟得上演进）
三块：DLedger（存储层 Raft 自动切主）、Controller（独立协调+epoch fencing）、Proxy（无状态 gRPC 接入）；另加任意延时（时间轮）与 Pop 消费。

**Q2："DLedger 和主从复制什么区别？"**（意图：Raft vs 主从）
DLedger：多数派落盘（不丢）+ 自动选主；主从：单主复制，主挂需人工/Controller 协调。DLedger 是"把 CommitLog 换成 Raft 日志"。

**Q3："Controller 模式和 DLedger 能一起用吗？"**（意图：架构理解）
能——定位不同（存储复制 vs 角色协调）；Controller 也能管理非 DLedger 的 HA 复制。**危险信号**：认为二者互斥。

**Q4："Proxy 解决什么问题？"**（意图：部署形态理解）
客户端只连 Proxy（gRPC 标准协议，多语言友好）；路由/弹性上移（无状态 Proxy + Pop 免 Rebalance）；兼容 remoting（双协议并存）。

**Q5："你们为什么还在用 4.x 模式？"**（意图：选型判断）
xhs 口径：**用 5.1.4 客户端但按 4.x 经典模型用**（无 Proxy/Controller，SYNC_FLUSH + 手动主从）——升级收益（自动切主）vs 改造成本的取舍。
