# RocketMQ 深挖 D01 — 消费端启动流程

> **定位**：RocketMQ 深挖系列第 1 篇。经典问题："`consumer.start()` 这一行背后发生了什么？"
> **源码版本**：rocketmq-all-5.1.4（`code/spring/rocketmq-5.1.4`）
> **核心文件**：`DefaultMQPushConsumerImpl.start()`（L~150-235）/ `MQClientInstance.start()`（L~250-300）/ `RebalanceService.run()` / `PullMessageService.run()`

---

## 一、它干了什么：一个例子

```java
DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("g1");
consumer.setNamesrvAddr("...");
consumer.subscribe("TopicA", "*");
consumer.registerMessageListener(listener);
consumer.start();   // ← 这一行
// 之后（约几十毫秒内）消息开始流入 listener
```

`start()` 内部依次做 12 件事：校验配置 → 订阅复制 → 找/建 client 实例 → 建 offset 存储并加载 → 启动消费线程池 → 注册到 client → 启动 client（拉取/负载均衡/心跳线程）→ **收尾四连（拉路由 + 注册客户端 + 立即心跳 + 立即 rebalance）** → 状态置 RUNNING。

**一句话**：`start()` = **资源装配（offset/线程池）→ 客户端引擎启动 → 主动触发第一轮"路由+注册+心跳+负载均衡"**——消息因此能在启动后立刻开始拉取，而不是等 20s 定时。

## 二、源码全链路（`DefaultMQPushConsumerImpl.start()`）

### 阶段 1：状态机与校验（L150-160）

```java
public synchronized void start() throws MQClientException {
    switch (this.serviceState) {
        case CREATE_JUST:
            this.serviceState = ServiceState.START_FAILED;   // ① 先置"启动中"——重复 start 会走到 default 抛异常
            this.checkConfig();                              // ② 校验：group 合法、监听器已注册、订阅非空
            this.copySubscription();                         // ③ 订阅关系复制（真正写入 subscriptionInner）
            if (MessageModel.CLUSTERING) {
                this.defaultMQPushConsumer.changeInstanceNameToPID();  // ④ 集群模式：instanceName=PID（同机多实例隔离）
            }
```

**状态机**：CREATE_JUST → START_FAILED（启动中）→ RUNNING（成功）——中途任何失败保持 START_FAILED；重复调用直接抛 `MQClientException`（"service state not OK"）。

### 阶段 2：client 实例与 offset（L162-195）

```java
    this.mQClientFactory = MQClientManager.getInstance()
        .getOrCreateMQClientInstance(this.defaultMQPushConsumer, this.rpcHook);   // ⑤ 按 clientId 复用/新建 MQClientInstance

    this.rebalanceImpl.setConsumerGroup(...); setMessageModel(...); setAllocateMessageQueueStrategy(...);
    this.rebalanceImpl.setmQClientFactory(this.mQClientFactory);                  // ⑥ 装配 Rebalance 实现

    if (this.pullAPIWrapper == null) { this.pullAPIWrapper = new PullAPIWrapper(...); }  // ⑦ 拉取 API 包装（tag 过滤等）

    switch (messageModel) {                                                       // ⑧ 创建 offsetStore
        case BROADCASTING: this.offsetStore = new LocalFileOffsetStore(...);      //    广播：本地文件
        case CLUSTERING:   this.offsetStore = new RemoteBrokerOffsetStore(...);   //    集群：远端（Broker）
    }
    this.offsetStore.load();                                                      //    ← 集群模式这是空实现！（见 §四）
```

### 阶段 3：消费线程池与注册（L196-220）

```java
    if (listener instanceof MessageListenerOrderly) {        // ⑨ 按监听器类型创建消费服务
        this.consumeMessageService = new ConsumeMessageOrderlyService(...);
    } else if (listener instanceof MessageListenerConcurrently) {
        this.consumeMessageService = new ConsumeMessageConcurrentlyService(...);
    }
    this.consumeMessageService.start();                      //    消费线程池先启动（等拉取任务投递）

    boolean registerOK = mQClientFactory.registerConsumer(group, this);   // ⑩ 注册到 client（consumerTable.putIfAbsent）
    if (!registerOK) {                                       //    重复组：回滚状态 + 关线程池 + 抛异常
        this.serviceState = ServiceState.CREATE_JUST;
        this.consumeMessageService.shutdown(...);
        throw new MQClientException("...has been created before...");
    }
    mQClientFactory.start();                                 // ⑪ 启动客户端引擎（见下）
```

### 阶段 4：客户端引擎启动（`MQClientInstance.start()`）

```java
    if (null == clientConfig.getNamesrvAddr()) { mQClientAPIImpl.fetchNameServerAddr(); }  // 无静态 NS → HTTP 拉取
    this.mQClientAPIImpl.start();          // Netty 客户端（Remoting）
    this.startScheduledTask();             // 定时任务：心跳 30s / 持久化 offset 5s / 路由刷新 30s / cleanOffline / 检查 clientInBroker
    this.pullMessageService.start();       // 拉取服务（阻塞队列 take 循环）
    this.rebalanceService.start();         // 负载均衡服务（20s 周期）
    this.defaultMQProducer.getDefaultMQProducerImpl().start(false);   // 内部 producer（发送回退消息/心跳用）
```

### 阶段 5：收尾四连 + 状态置 RUNNING（L989-995）

```java
    this.updateTopicSubscribeInfoWhenSubscriptionChanged();  // ⑫ 拉订阅 Topic 的路由（填 topicSubscribeInfoTable）
    this.mQClientFactory.checkClientInBroker();              //    向 Broker 确认客户端是否已注册（未注册会触发注册）
    this.mQClientFactory.sendHeartbeatToAllBrokerWithLock(); //    立即心跳（不等 30s 定时）
    this.mQClientFactory.rebalanceImmediately();             //    wakeup RebalanceService → 首次 rebalance 立即执行
    // serviceState = RUNNING
```

**为什么"收尾四连"关键**：`RebalanceService.run()` 是 `waitForRunning(20s) → doRebalance()` 循环——如果不主动 `wakeup()`，**首次消费要等 20s**。收尾四连把"路由、注册、心跳、负载均衡"全部提前到启动瞬间。

### 启动完成后的第一条链路

```
rebalanceImmediately() → RebalanceService.wakeup()
  → doRebalance()（RebalanceImpl）
      → 从 topicSubscribeInfoTable 拿队列全集 + 同组 clientId 列表
      → 分配算法（默认平均）算出"我该消费的队列"
      → 每个新队列：建 ProcessQueue + 投 PullRequest 到 messageRequestQueue
  → PullMessageService.run()：messageRequestQueue.take() → pullMessage()
      → 向 Broker 发拉取请求（长轮询 15s）→ 拉到消息 → 投消费线程池 → listener
```

## 三、时序图（文字版）

```
consumer.start()
 ├─ checkConfig / copySubscription / changeInstanceNameToPID
 ├─ getOrCreateMQClientInstance（clientId 复用）
 ├─ offsetStore 创建 + load()（集群=空）
 ├─ consumeMessageService.start()（消费线程池）
 ├─ registerConsumer（重复组检查）
 ├─ mQClientFactory.start()
 │    ├─ mQClientAPIImpl.start()（Netty）
 │    ├─ startScheduledTask()（心跳/offset 持久化/路由刷新）
 │    ├─ pullMessageService.start()（take 循环就绪）
 │    └─ rebalanceService.start()（20s 周期就绪）
 └─ 收尾四连：拉路由 → checkClientInBroker → 立即心跳 → rebalanceImmediately()
      └─ 首次 Rebalance → PullRequest 入队 → PullMessageService 拉取 → 消费
```

## 四、关键设计点（面试深挖）

**① 集群模式 `offsetStore.load()` 是空实现**（`RemoteBrokerOffsetStore.load() {}`）——offset 不在启动时拉，而是**消费/提交时按需从 Broker 读**（`fetchConsumeOffsetFromBroker`）。广播模式的 `LocalFileOffsetStore.load()` 才真的读本地文件。**"集群 offset 存 Broker"是消费时交互的，不是启动加载的**。

**② clientId 复用**：`MQClientManager.getOrCreateMQClientInstance` 按 `clientId = IP@instanceName[@unitName]` 查表——同 JVM 同 clientId 的 producer/consumer **共享一个 MQClientInstance**（共享 Netty 连接、线程池、路由表）。这就是"同机多实例必须改 instanceName"的根因（D1 §3.10）；集群模式自动 `changeInstanceNameToPID()` 规避。

**③ 消费线程池先于 client 启动**：先 `consumeMessageService.start()` 再 `mQClientFactory.start()`——保证拉取到消息时消费线程池已就绪（拉取服务后启动但可能立刻拿到 PullRequest）。

**④ 重复组保护 + 回滚**：`registerConsumer` 用 `consumerTable.putIfAbsent`——同 clientId 内同组第二次注册返回 false → 回滚 serviceState 到 CREATE_JUST + 关闭消费线程池 + 抛异常（**同 JVM 不要建两个同组 consumer**）。

**⑤ 首次 rebalance 的"立即"是显式 wakeup**：`rebalanceImmediately()` → `rebalanceService.wakeup()`（ServiceThread 的 CountDownLatch 机制）——否则等 20s 周期。

## 五、使用（生产口径）

### 5.1 消费者配置速查（启动相关）

| 配置 | 默认 | 说明 |
|---|---|---|
| `consumeFromWhere` | CONSUME_FROM_LAST_OFFSET | 只对新组生效一次 |
| `consumeTimestamp` | 半小时前 | CONSUME_FROM_TIMESTAMP 时生效 |
| `consumeThreadMin/Max` | 20/20 | 消费线程池 |
| `pullBatchSize` | 32 | 单次拉取条数 |
| `maxReconsumeTimes` | -1（沿用 Broker 16 次） | 重试上限 |
| `instanceName` | DEFAULT | 同机多实例必须区分（clientId） |
| `messageModel` | CLUSTERING | 集群/广播 |

### 5.2 启动排查清单（"启动后不消费"）

```
1. 订阅关系：同组所有实例订阅一致？（D1 §3.8 约束）
2. 路由：topic 路由拿到了吗？（NameServer 可达；autoCreate 关闭时 topic 必须先创建）
3. offset：CONSUME_FROM_LAST_OFFSET 跳过历史？位点是否卡在末尾？
4. clientId 冲突：同机多实例 instanceName 撞了？（日志看 registerConsumer 告警）
5. 重复组：同 JVM 同组第二个 consumer 启动直接抛异常（本文 §四）
6. Broker 端：checkClientInBroker 是否注册成功？重试队列是否堆积？
```

### 5.3 优雅停机

```java
Runtime.getRuntime().addShutdownHook(new Thread(consumer::shutdown));
// shutdown 内部顺序：persistConsumerOffset → 停拉取/负载均衡/消费线程池 → unregisterConsumer
```
- 停机前 offset 落盘（减少重复消费窗口）；K8s 场景配合 `preStop` 先摘流量再停

## 六、生产陷阱

| # | 陷阱 | 根因 | 修复 |
|---|---|---|---|
| 1 | 同机部署两个实例，消息串组/消费错乱 | clientId 冲突（instanceName 默认 DEFAULT） | 集群模式自动 PID；广播/自定义场景显式设 instanceName |
| 2 | "启动后 20s 才开始消费" | 自行封装绕过了收尾四连（如手动 new 内部对象） | 用标准 `consumer.start()`；理解 wakeup 机制 |
| 3 | 同 JVM 两个同组 consumer 启动报错 | registerConsumer putIfAbsent 失败回滚 | 合并为一个 consumer 或换组名 |
| 4 | 重复启动/关闭后重启异常 | 状态机 START_FAILED/SHUTDOWN_ALREADY | 用 `shutdown()` 后重建实例（不支持同实例重启） |
| 5 | 停机丢 offset | shutdown 顺序：先 `persistConsumerOffset()` 再停服务 | 走标准 `consumer.shutdown()` |

## 七、面试 Q&A（含面试官意图）

**Q1："consumer.start() 做了什么？"**（意图：是否读过启动链）
按五阶段回答：校验/订阅 → client 实例 + offset 存储 → 消费线程池 + 注册 → client 引擎（Netty/定时任务/拉取/负载均衡）→ 收尾四连（路由/注册确认/心跳/立即 rebalance）。**加分点**：收尾四连解释"为什么启动后立刻能消费"。

**Q2："为什么集群模式 offsetStore.load() 是空实现？"**（意图：区分集群/广播 offset 语义）
集群 offset 存 Broker、消费时按需拉取（RemoteBrokerOffsetStore 的 offsetTable 在消费过程中填充）；广播 offset 存本地文件，load() 真读文件。**危险信号**：以为启动时把所有 offset 拉下来。

**Q3："首次 Rebalance 是等 20s 还是立即？"**（意图：是否理解 ServiceThread wakeup）
立即——`rebalanceImmediately()` 显式 wakeup；20s 只是兜底周期。

**Q4："同一个 JVM 启动两个相同 group 的 consumer 会怎样？"**（意图：clientId/consumerTable 机制）
`registerConsumer` putIfAbsent 失败 → 回滚 + 抛异常（"has been created before"）——同 clientId 内同组唯一。

**Q5："启动链里哪些是异步的？"**（意图：线程模型理解）
拉取（PullMessageService 单线程 take）、负载均衡（RebalanceService 20s）、心跳/offset 持久化（scheduledExecutorService）、消费（consumeMessageService 线程池）——start() 本身同步返回，后续全异步。
