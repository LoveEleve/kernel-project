> **定位**：RocketMQ 深挖系列第 3 篇（按 P02 规划产出物）。**本地事务 ⇔ 消息可见** 的最终一致方案。

> **质量标准**：源码阅读清单 / 完整调用链 / 设计哲学（反面假设）/ 生产陷阱 / 面试 Q&A（意图）/ 章节依赖

## 一、它干了什么：一个例子

**正常路径**（下单）：
```
① producer.sendMessageInTransaction(msg)      ← 发送"半消息"
     Broker：改写 topic=RMQ_SYS_TRANS_HALF_TOPIC、queueId=0，real topic/qid 存属性 → 落盘
     消费者：看不到（HALF topic 无订阅者）
② 生产端执行本地事务 executeLocalTransaction() → 返回 COMMIT
③ producer.endTransaction(COMMIT)
     Broker EndTransactionProcessor：取出半消息 → 还原真实 topic → 重新落盘 → 消费者可见
     同时写 OP topic 标记"已决"
```

**异常路径**（生产端宕机未上报）：
```
Broker TransactionalMessageCheckService 每 30s 扫 HALF topic
  → 过滤（超期/回查超限/OP 已标记/免疫期）→ sendCheckMessage 回查生产端
  → 生产端 checkLocalTransaction() 查本地 DB → 返回 COMMIT/ROLLBACK/UNKNOWN
  → COMMIT/ROLLBACK 走②③；UNKNOWN 下轮再查（15 次上限后丢弃+告警）
```

**一句话**：半消息先"占位不可见"→ 本地事务结果决定"转正或作废"→ 未决时 Broker **主动回查**兜底——把"发消息"纳入本地事务的一致性范围。

## 三、完整调用链（四条）

### 3.1 发送半消息（生产端 → Broker）

```
sendMessageInTransaction(:1381)
 ├─ putProperty(msg, PROPERTY_TRANSACTION_PREPARED, "true")(:1397)
 ├─ send(msg) → sendKernelImpl：sysFlag |= TRANSACTION_PREPARED_TYPE(:905)
 └─ Broker SendMessageProcessor：识别事务消息 → TransactionalMessageBridge.putHalfMessage(:211)
      └─ parseHalfMessageInner(:219)：
           queueId = 0（固定保存位）
           topic → RMQ_SYS_TRANS_HALF_TOPIC
           原 topic/queueId 存入属性 REAL_TOPIC / REAL_QID
      → 正常落盘（CommitLog）→ 对 Consumer 不可见
```

### 3.2 二阶段（生产端上报 → Broker 决策）

```
endTransaction(:1471)
 ├─ 从 sendResult.offsetMsgId 解码 commitLogOffset（半消息寻址键！）
 ├─ EndTransactionRequestHeader{commitLogOffset, commitOrRollback, ...}
 └─ Broker EndTransactionProcessor.processRequest(:55)
      ├─ slave 模式直接拒绝（:63）——只有 Master 能处理事务
      ├─ COMMIT → commitMessage(:616)：getHalfMessageByOffset → 还原 REAL_TOPIC/REAL_QID → 重新 putMessage → 消费者可见
      ├─ ROLLBACK → rollbackMessage(:621)：只写 OP 标记（半消息不还原，靠 OP 跳过）
      └─ 两者都写 OP topic：getOpMessage(:637) → OP batch 合并写入
```

### 3.3 回查（Broker 主动 → 生产端）

```
TransactionalMessageCheckService(:25) 每 30s（transactionCheckInterval:267）onWaitEnd(:53)
 └─ TransactionalMessageServiceImpl.check()
      ├─ needDiscard(:90)：CHECK_TIMES ≥ transactionCheckMax(15) → 丢弃 + 写 TRANS_CHECK_MAX_TIME_TOPIC
      ├─ needSkip(:107)：超过 fileReservedTime → 跳过
      ├─ OP 已标记 → 跳过（已决）
      ├─ checkImmunityTime(:258)：默认 transactionTimeOut(6s) 免疫窗（可被消息属性覆盖）
      └─ listener.resolveHalfMsg(:71) → sendCheckMessage(:51)
           → CHECK_TRANSACTION_STATE(39) 请求发给同 ProducerGroup 任一在线实例
           → 生产端 checkTransactionState(:360) → listener.checkLocalTransaction() → endTransaction
```

### 3.4 OP 标记与幂等（防重复回查）

```
每次 commit/rollback 后写 OP topic（buildOpTopic:37 = RMQ_SYS_TRANS_OP_HALF_TOPIC）
  → 回查前先查 OP：已标记 → 跳过（不会重复回查/重复还原）
  → OP 条目由 TransactionalOpBatchService 批量合并（高吞吐下每半秒上千决策）
```

## 四、使用（生产口径）

### 4.1 API 使用（原生 + Spring）

```java
// 原生
TransactionMQProducer producer = new TransactionMQProducer("tx-group");
producer.setTransactionListener(new TransactionListener() {
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) { /* 执行本地事务 */ }
    public LocalTransactionState checkLocalTransaction(MessageExt msg) { /* 回查：只读查 DB */ }
});
producer.sendMessageInTransaction(msg, arg);

// Spring（rocketmq-spring，xhs 口径）
@RocketMQTransactionListener
class OrderTxListener implements RocketMQLocalTransactionListener {
    public RocketMQLocalTransactionState executeLocalTransaction(Message msg, Object arg) { ... }
    public RocketMQLocalTransactionState checkLocalTransaction(Message msg) { ... }
}
// rocketMQTemplate.sendMessageInTransaction(topic, message, arg);
```

### 4.2 配置速查

| 配置 | 默认 | 说明 |
|---|---|---|
| `transactionCheckInterval` | 30s | 回查扫描周期 |
| `transactionCheckMax` | 15 | 最大回查次数（超限丢弃 + 写 CHECK_MAX_TIME_TOPIC） |
| `transactionTimeOut` | 6s | 免疫窗（checkImmunityTime 默认值） |

### 4.3 生产实践（回查实现要点）

- `executeLocalTransaction`：只做本地事务，返回三态（COMMIT/ROLLBACK/UNKNOWN）
- `checkLocalTransaction`：**只读查询**本地事务结果——**查询异常返回 UNKNOWN**（Broker 下轮再查；xhs `OrderTransactionListener` 口径）
- 回查要快：查询走索引/缓存（回查有超时，慢查询拖垮回查吞吐）
- 消费端仍要幂等（事务消息也是 at-least-once）
- 监控：HALF topic 堆积 / `TRANS_CHECK_MAX_TIME_TOPIC` 计数（丢弃告警）

## 五、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **半消息+回查 而不是 2PC prepare** | 先 prepare 等 commit | 避免 prepare 消息长期占用资源；半消息"不可见"无锁语义；回查把决策权还给生产者（本地事务状态只有它知道） |
| **半消息改写 topic 而不是单独存储** | 事务消息单独文件 | 复用 CommitLog 存储/刷盘/复制——事务消息也是普通消息，只是 topic 特殊 |
| **OP topic 标记已决** | 靠半消息本身状态位 | 半消息在 CommitLog 不可变；用独立 OP 条目表达"已决"，回查时 O(1) 跳过 |
| **回查而不是超时自动回滚** | 超时即回滚 | 超时≠本地事务失败（可能已提交）——自动回滚会丢已提交的业务；回查以本地事实为准 |
| **UNKNOWN 语义** | 只允许 commit/rollback | 生产端查不到结果时保守返回 UNKNOWN（下轮再查），避免误决 |

## 六、生产陷阱（含复现/验证）

| # | 陷阱 | 根因 | 修复 |
|---|---|---|---|
| 1 | **回查风暴** | 大量事务消息 + 回查逻辑慢/DB 抖动 | 控制事务消息比例；回查查询加缓存/索引；xhs 口径：查询异常返回 UNKNOWN（下轮再查） |
| 2 | **半消息堆积** | 生产端长期不决（回查 15 次上限内） | 监控 HALF topic 堆积；`TRANS_CHECK_MAX_TIME_TOPIC` 告警；修复生产端回查实现 |
| 3 | **Slave 处理 EndTransaction 失败** | slave 拒绝（:63） | 事务消息只在 Master 处理——主从切换窗口内 end 请求重试 |
| 4 | **回查次数耗尽消息被丢弃** | 15 次上限（~7.5min） | 告警 + 人工核查（丢弃记录写在 TRANS_CHECK_MAX_TIME_TOPIC） |
| 5 | **误以为半消息可被消费** | 不了解 HALF topic 语义 | HALF topic 无订阅者——消费者永远看不到（生产排查"消息发了没收到"时的常见误判） |

## 七、面试 Q&A（含面试官意图）

**Q1："事务消息的完整流程？"**（意图：是否读过两端）
发送半消息（改 topic/queueId + REAL_TOPIC 属性）→ 本地事务 → endTransaction（commit 还原 / rollback 标记）→ 未决回查（30s/15 次/6s 免疫窗）。**加分**：offsetMsgId 是半消息寻址键。

**Q2："半消息对消费者可见吗？为什么？"**（意图：HALF topic 理解）
不可见——HALF topic 无订阅者；commit 才还原到真实 topic。**危险信号**：说"可见但被过滤"。

**Q3："回查为什么可能查不到？怎么处理？"**（意图：UNKNOWN 语义）
本地事务未提交/DB 不可用/超时——生产端返回 UNKNOWN 让 Broker 下轮再查（xhs OrderTransactionListener 口径：查询异常返回 UNKNOWN）。**加分**：15 次上限后丢弃+写 CHECK_MAX_TIME_TOPIC。

**Q4："事务消息和 2PC 的区别？"**（意图：对比思维）
2PC：协调者主导、prepare 锁资源；事务消息：半消息不可见+回查（决策权在生产者本地事务）——**MQ 特化 vs 通用协议**。对比篇见 P02-对比 D-03。

**Q5："OP topic 是干什么的？"**（意图：回查幂等机制）
记录"已决"标记：commit/rollback 后写 OP（批量合并）；回查前查 OP 跳过已决——防重复回查/重复还原。
