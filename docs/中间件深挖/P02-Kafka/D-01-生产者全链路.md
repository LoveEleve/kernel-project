## 一、它干了什么：一个例子

```java
ProducerRecord<String, String> record = new ProducerRecord<>("orders", "o-1", "created");
producer.send(record, (metadata, exception) -> { ... });   // 异步：立即返回 Future
```

`send()` 一行背后，**两个线程在协作**：

```
主线程（调用 send 的线程）：
  拦截器 → 序列化（key/value）→ 分区器（选 partition）→ RecordAccumulator.append
      → 消息进"按分区组织的批次缓冲"（ProducerBatch）→ 返回 Future

Sender 线程（后台）：
  循环：从缓冲取"就绪批次"（linger.ms/batch.size 触发）→ 按 Broker 分组（同一节点合并请求）
      → 网络发送（NetworkClient）→ 处理响应（成功回调 / 失败重试）→ 幂等序列号推进
```

**一句话**：生产者 = **"主线程攒批 + 后台线程发批"** 的双线程模型——`send()` 只做入缓冲（快），网络 IO 与重试全在 Sender 线程（不阻塞业务）。

## 二、原理（心智模型，不贴源码）

### 2.1 为什么双线程

主线程若直接网络发送：业务被 RTT 拖慢 + 无法批量。分离后：
- **批量**：linger.ms（等待窗口，4.0 默认 **5ms**）+ batch.size（16KB 上限）→ 一次请求带一批
- **重试**：Sender 内部完成，业务无感（通过 delivery.timeout 兜底）
- **顺序**：同分区批次按序发出（max.in.flight 与重试策略共同约束）

### 2.2 acks 语义（可靠性核心）

| acks | 含义 | 风险 |
|---|---|---|
| `0` | 发出即成功（不等响应） | 网络丢失无感知 |
| `1` | Leader 写本地日志即响应 | Leader 宕机且未同步 → 丢 |
| **`all`**（4.0 默认） | ISR 全部确认才响应 | 最可靠（配合 min.insync.replicas） |

### 2.3 幂等生产者（4.0 默认开启）

```
PID（Producer ID）+ 每分区序列号：Broker 端按 (PID, partition, seq) 去重
  → 重试导致的重复被 Broker 丢弃（Exactly-Once 的发送侧基础）
  → 序列号乱序（max.in.flight > 1 时重试）由 Broker 拒绝 → 生产者重排/报错
约束：enable.idempotence=true 要求 acks=all 且 max.in.flight ≤ 5
```

### 2.4 分区器（4.0 变化）

- 指定 key → `hash(key) % partitions`（同 key 同分区）
- 无 key → **粘性分区**：填满一个分区批次再换下一个（减少小批次）；**自适应分区**（`partitioner.adaptive.partitioning.enable`，默认 true）——按 Broker 性能向更快的 Broker 倾斜
- 对比 RocketMQ：Kafka 分区器在**客户端**；RocketMQ 队列选择也在客户端（MessageQueueSelector）——但 RocketMQ 无"粘性攒批"语义

### 2.5 超时预算（面试常问）

```
delivery.timeout.ms（默认 120s）≥ linger.ms + request.timeout.ms（默认 30s）
  → 一条消息从 send 到最终成功/失败的**总预算**（含所有重试）
  → 重试次数（retries=MAX）受预算约束——不是无限重试
```

## 三、使用（生产口径）

### 3.1 关键配置速查（4.0 默认值）

| 配置 | 默认 | 说明/建议 |
|---|---|---|
| `acks` | **all** | 不要降级（除非可丢场景） |
| `enable.idempotence` | **true** | 保持开启（Exactly-Once 基础） |
| `retries` | Integer.MAX_VALUE | 由 delivery.timeout 兜底 |
| `max.in.flight.requests.per.connection` | 5 | 幂等约束 ≤5；关幂等时 >1 会乱序 |
| `linger.ms` | **5**（4.0 从 0 上调） | 攒批等待；延迟敏感可调 0 |
| `batch.size` | 16384 | 单分区批上限；过大费内存 |
| `compression.type` | none | 建议 lz4/zstd（省网络+磁盘） |
| `delivery.timeout.ms` | 120000 | 总预算；按业务 SLA 调 |

### 3.2 可靠性三件套（发送侧）

```
acks=all + enable.idempotence=true + 消费侧幂等（at-least-once 兜底）
Broker 侧配套：min.insync.replicas=2 + unclean.leader.election.enable=false
```

### 3.3 吞吐调优（对照）

| 目标 | 手段 |
|---|---|
| 高吞吐 | linger.ms↑（如 20-50）、batch.size↑（64KB-1MB）、compression=lz4/zstd、多分区 |
| 低延迟 | linger.ms=0、batch.size 小、acks 权衡 |

### 3.4 代码骨架（异步 + 回调）

```java
try (Producer<String,String> producer = new KafkaProducer<>(props)) {
    producer.send(record, (md, ex) -> {
        if (ex != null) { /* 记录失败（重试耗尽）*/ } 
        else { /* md.partition()/offset() */ }
    });
}
// 注意：send 返回 Future；close() 会 flush 缓冲（勿丢消息）
```

## 四、源码核心（调用链 + 行号）

### 4.1 主线程链

```
KafkaProducer.send(:824) → send(record, callback)(:940)
  └─ doSend(:956)
       ├─ 拦截器 onSend（ProducerInterceptors）
       ├─ key/value 序列化（Serializer）
       ├─ 分区：partition() != null ? 用之 : 分区器（粘性/自适应）
       ├─ ensureValidRecordSize(:1142)（max.request.size 校验）
       └─ RecordAccumulator.append(:283)
            ├─ 取/建该分区的 ProducerBatch（deque）
            ├─ 尝试追加（满了 → 新建 batch）
            └─ 返回 RecordAppendResult（含是否新批次/是否满）
  → sender.wakeup()（唤醒 Sender 线程）
```

### 4.2 Sender 线程链

```
Sender.run(:242) 循环：
  ├─ sendProducerData(:366)
  │    ├─ accumulator.ready()（哪些节点有就绪批次：linger 到期/批满）
  │    ├─ 幂等模式：TransactionManager.maybeSendAndPollTransactionalRequest()（PID/epoch 获取）
  │    └─ sendProduceRequests(:861) → sendProduceRequest(:869)（按节点合并批次）
  │         └─ NetworkClient.send()（异步 IO，max.in.flight 控制并发）
  └─ client.poll() → 响应回调 completeBatch(:664)
       ├─ 成功 → 批次完成（回调 Future/RecordMetadata）
       └─ 失败 → 可重试则 reenqueue（RecordAccumulator:504）→ 下轮重发
```

### 4.3 幂等/事务管理

`TransactionManager`（clients/.../internals/TransactionManager.java:92）：
- `bumpIdempotentEpochAndResetIdIfNeeded()`（:623）：PID 失效/epoch 递增时重置序列号
- 事务（D-04 展开）：`sendOffsetsToTransaction`(:727) 把消费位移提交纳入事务

## 五、设计哲学（反面假设表）

| 设计决策 | 反事实假设 | 为什么选这个 |
|---|---|---|
| **主线程/Sender 分离** | send 内同步网络发送 | 批量+重试不阻塞业务；攒批是吞吐的根基 |
| **粘性分区（无 key）** | 轮询（round-robin） | 轮询把每批打散到所有分区 → 大量小批次；粘性填满再换（省请求） |
| **幂等默认开（4.0）** | 默认关（3.0 前） | "默认安全"——多数场景不想要重复；代价是 acks=all/max.in.flight≤5 约束 |
| **delivery.timeout 总预算** | retries 无限重试 | 无限重试会无限积压；总预算让失败可界定（配合回调告警） |
| **客户端分区器** | Broker 端路由（RocketMQ 也可客户端） | 客户端知道分区数（元数据缓存）——省一次 Broker 交互 |

## 六、生产陷阱（含复现思路）

| # | 陷阱 | 根因 | 修复 |
|---|---|---|---|
| 1 | **消息乱序** | 关幂等 + max.in.flight>1 + 重试 | 保持幂等默认；或 max.in.flight=1（降吞吐） |
| 2 | **消息重复** | at-least-once（重试成功但响应丢失） | 幂等生产者（发送侧）+ 消费幂等（业务侧） |
| 3 | **缓冲撑爆 OOM** | 发送慢于生产（Broker 故障）+ 批次/缓冲无限增长 | 设置 `buffer.memory` + `max.block.ms`（阻塞/超时拒绝） |
| 4 | **超时配置打架** | delivery.timeout < linger+request.timeout | 保持 delivery ≥ linger + request；按 SLA 统一预算 |
| 5 | **无 key 倾斜** | 粘性分区使某一分区先吃满批 | 4.0 自适应分区缓解；热点 key 需业务打散 |

## 七、面试 Q&A（含面试官意图）

**Q1："Kafka 生产者如何保证不丢/不重/有序？"**（意图：端到端可靠性）
不丢：acks=all + retries + min.insync.replicas；不重：幂等生产者（PID+序列号）+ 消费幂等；有序：幂等 + max.in.flight≤5（或 =1）。

**Q2："acks=all 就万无一失吗？"**（意图：ISR 细节）
不——还需 `min.insync.replicas≥2` 且 `unclean.leader.election.enable=false`（防落后副本当选丢数据）。

**Q3："send() 之后消息存在哪？"**（意图：缓冲模型）
RecordAccumulator 的按分区 ProducerBatch（内存缓冲），Sender 线程按 linger/batch 触发发送；`buffer.memory` 是上限。

**Q4："Kafka 4.0 生产者有什么变化？"**（意图：版本演进）
linger.ms 默认 0→5；幂等默认开启（3.0 起）；自适应分区默认开；KRaft-only（与生产者间接相关——元数据来自 KRaft）。

**Q5："和 RocketMQ 生产者对比？"**（意图：双轨对比）
Kafka：客户端分区+攒批+幂等 PID；RocketMQ：客户端队列选择+重试换 Broker+事务消息（半消息回查）。详见 P02-对比。
