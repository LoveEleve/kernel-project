# 06-深水：循环依赖与三级缓存

## §0 它干了什么（例子先行）

```java
@Service class A { @Autowired B b; }
@Service class B { @Autowired A a; }   // 造 A 要 B，造 B 要 A——死锁？
```

Spring 的答案：**先给半成品**——A 实例化完成（还没填充）就把"早期引用"挂出去，B 拿着这个半成品完成自己，A 再回头补完：

```
造 A：实例化 A（裸对象）→ 挂"工厂"进三级缓存 → 填充 A：需要 B
  造 B：实例化 B → 挂工厂 → 填充 B：需要 A → 查缓存拿到 A 的早期引用（半成品）→ B 完成
→ A 继续填充完 → B 注入的是完整 A 的引用（最终一致）
```

- **它干了什么**：用"先暴露半成品 + 工厂延迟决定形态"解开**字段注入**的循环。
- **本篇回答**：三级缓存各存什么？为什么是三级不是两级？哪些循环注定解不了？

## §1 概念铺垫（What）

| 词 | 一句话 |
|---|---|
| **循环依赖** | Bean 图里成环（A 造要 B、B 造要 A） |
| **早期引用** | 实例化后、填充/初始化完成前的"半成品"对象 |
| **三级缓存** | 单例查找的三张表，按"完成度"分级（源码三 Map 已核） |
| **工厂级缓存** | 第三级存的是 `ObjectFactory`（**延迟决定**：到时再决定给你原始对象还是代理） |

**三级各是什么**（DefaultSingletonBeanRegistry，行号已核）：

```
一级 singletonObjects（:85）     成品——正常 getBean 从这拿
二级 earlySingletonObjects（:94） 早期引用（首次从三级工厂物化后放这里——**可能是代理**）
三级 singletonFactories（:88）   ObjectFactory 工厂——需要代理时它产出代理
```

## §2 工程使用：哪些循环能解、怎么解

| 场景 | 结果 | 处方 |
|---|---|---|
| 字段/setter 注入的单例循环 | ✅ 三级缓存可解 | 什么都不用做 |
| **构造器注入**循环 | ❌ 解不了 | 实例化就互相要——**拆环**（引入第三者/事件/懒加载） |
| prototype 作用域循环 | ❌ 不支持 | 设计问题——原型不进缓存，无"半成品"可借 |
| 解不干净又想救 | 权宜 | `@Lazy`（延迟到首次方法调用才真正解析） |

**工程纪律**：循环依赖是**设计异味**——能拆则拆（第三方中介/回调下沉）；`@Lazy` 是止痛药不是手术。

## §3 为什么是三级不是两级（推导，本篇最核心）

**朴素答案**：二级够了——成品表+早期表，B 来拿早期裸对象即可。

**But**：A 若会被 AOP 换壳（@Transactional/@Aspect），**B 注入的必须是代理**，而代理在初始化之后才生成——给 B 裸对象=事务失效的隐患（B 持有了"非代理 A"）。

**Therefore**：第三级存 **ObjectFactory**——B 需要早期引用时才调工厂，工厂检查"这个 Bean 是否需要换壳"：需要→**提前造代理**返回；不需要→返回裸对象。**三级的存在就是为了让"注入给别人的引用"和"最终出厂形态"保持一致**（代理感知的循环依赖解法）。

**Cost**：每个早期暴露都多一层工厂间接——这就是"三级缓存比两级慢一点"的全部代价；绝大多数应用无感。
