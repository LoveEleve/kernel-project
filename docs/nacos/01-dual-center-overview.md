# 01-双中心全景：注册+配置一体

## §0 它干了什么（例子先行）

xhs 一个服务启动要问两件事：

```
① "订单服务在哪？"     → 注册中心：我在这（:9848 gRPC 长连）；调用方从这拿地址列表
② "订单服务的配置是什么？" → 配置中心：数据源/MQ 配置从 Nacos 拉，改了自动推
```

Nacos 把这两件事装进一个系统——所以叫"双中心"（注册中心 + 配置中心）。xhs 25 处 yml 在用。

- **它干了什么**：服务寻址（谁在哪）+ 配置分发（参数是什么）——一个组件、一份部署、同一套三维模型。
- **输入/输出**：输入=注册请求/配置发布；输出=地址列表/配置推送。
- **本篇回答**：为什么双中心合一？三维模型是什么？2.x 和 1.x 差在哪？

## §1 掌握卡（3 条）

1. **双中心**：Naming（注册发现：实例上/下线、调用方拿列表）+ Config（配置：发布、监听、推送）——同进程同端口体系，运维一份。
2. **三维模型通用**：`namespace`（环境隔离）/ `group`（功能分组）/ `dataId` 或实例——注册和配置共用这套坐标。
3. **2.x 换了底座**：1.x HTTP 轮询 → **2.x gRPC 长连接**（客户端连 :9848，保活在传输层）——2.x 的心跳/推送/刷新全绕着这条长连转（03 专讲）。

## §2 三维模型（注册和配置同款）

```
Namespace（环境隔离：dev/prod 完全不可见）
  └── Group（功能分组：DATASOURCE_GROUP / MQ_GROUP）
        └── Data ID（配置名）/ Instance（实例）
```

| 维度 | 作用 | 隔离强度 |
|---|---|---|
| Namespace | 环境隔离（`sca-lab-dev`） | **物理隔离**——跨 ns 不可见 |
| Group | 同环境内按功能分组 | 逻辑隔离 |
| Data ID / 实例 | 具体配置/服务 | 同 Group 下唯一 |

为什么三层不是两层：只有 ns+dataId 时，一个环境里 DB/MQ/业务配置全挤一个组，运维改 DB 可能误触业务——Group 就是防这个的。xhs 实景（05/07 展开）：`optional:nacos:my-xhs-common.yaml?group=DEFAULT_GROUP`——命名空间隔离环境、共享配置多服务复用。

## §3 双中心分工

| | Naming 注册中心 | Config 配置中心 |
|---|---|---|
| 管什么 | 实例上/下线、地址列表 | 配置发布、变更推送 |
| 客户端 API | `NamingService`（D-01） | `ConfigService`（D-02） |
| 临时实例靠 | Distro AP + gRPC 保活（04） | —— |
| 配置变更靠 | 推送实例列表（04） | 推送配置内容 + 5s/3min 兜底（05） |

## §4 2.x 底座（gRPC 长连，骨架预告）

1.x：HTTP 注册 + 轮询拉配置（轮询=客户端反复定时问"有没有新的"）——高频轮询压服务端、变更延迟高。2.x：客户端与服务端建 **gRPC 长连接**（SDK 端口 9848 = 主端口 8848+1000；SDK=客户端库）：

- 保活在传输层（连接活着=实例活着——02 的"心跳"真相）
- 变更**服务端主动推**（配置刷新、实例列表都走推送）
- 1.x HTTP 端口保留兼容（迁移期两套协议同时开——双栈，06 讲部署）
