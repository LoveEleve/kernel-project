# 01-什么是ZooKeeper：四件套模型

## §0 它干了什么（例子先行）

三个服务实例选一个主（dist-theory 06 原例）：

```
每个实例到 /election 下创建【临时顺序节点】:
  /election/lock-0000000001  ← A（最小，是主）
  /election/lock-0000000002  ← B（只 watch 前一个节点 lock-00000001）
  /election/lock-0000000003  ← C
A 宕机 → 会话超时 → ZK 自动删 A 的临时节点 → 通知 B → B 上位
```

- **它干了什么**：ZK=**强一致的树形小文件系统 + 会话 + 一次性 watch**——选主/锁/配置同步全从这三块地基长出来；底层 ZAB 保证所有节点看到同一写入序（02 主场）。
- **本篇回答**：四件套各是什么？节点四类型怎么分？为什么说"临时节点=会话生命的外化"？

## §1 概念铺垫（What：四件套 + 节点四类型）

**四件套**：

| 件 | 一句话 |
|---|---|
| **znode 树** | 强一致的小文件系统——每个节点可存少量数据（MB 级上限）、可挂子节点 |
| **会话 Session** | 客户端连接的生命周期单位——心跳续约；会话亡则临时节点亡 |
| **Watch** | 一次性事件订阅——节点数据变/子节点变时通知（**用完即失效，要再订**——03 展开） |
| **ZAB** | 原子广播协议——写入全序一致的保证（02 主场） |

**节点四类型**（协调玩法的四种积木）：

| 类型 | 特点 | 协调用途 |
|---|---|---|
| **持久** | 会话断了还在 | 配置/服务注册（长存数据） |
| **临时** | **会话亡即自动删** | 在线状态的天然表达——选主/锁的地基 |
| **顺序** | 名字自动加递增序号 | 排队选主/公平锁（§0 的 lock-0001 就是它） |
| **容器/TTL**（3.5+） | 子节点聚类/超时自动删 | 元数据治理——知道即可 |

**一句话记忆**：**持久存数据，临时表活着，顺序排队用**——三者可组合（临时+顺序=§0 的选主积木）。

## §2 为什么协调器需要"强一致"（和 Nacos 的分界预埋）

选主场景容不得"两个节点都以为自己是主"——**写入必须全序一致**（A 建锁、B 看到 A；不能 B 先看到 A 后建的）。ZAB 提供这个全序（02）；对比 Nacos 注册中心的 AP 取舍（Nacos 04：短暂不一致可接受）——**协调器站 CP，注册中心站 AP**，05 选型篇正面展开。

## §3 掌握卡（2 条）

1. **四件套各司其职**：树存数据、会话管生死、watch 管通知、ZAB 管一致——**协调=在这四块地上写协议**（锁/队列/选主都是协议不是新特性）。
2. **临时+顺序是黄金组合**：在线状态（临时）× 公平排队（顺序）——§0 选主、04 的 Curator 锁，用的都是这对积木。

## §4 边界（一句话翻篇）

- 节点数据上限（1MB 级）/zxid（事务编号，ZAB 的全局递增序）等细节 → 用时查。
- 3.5+ 端口分离（8080/admin/2181）→ 04 工程侧一句。
- Watch 类型细分（ChildrenChanged/DataChanged）→ 03。
