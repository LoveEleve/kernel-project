# 02-原理一：ZAB协议

## §0 它干了什么（例子先行）

ZK 的写请求为什么"慢但可信"——ZAB 两幕剧：

```
第一幕 崩溃恢复（Leader 挂了）：
  选主——候选比 zxid（谁的数据新谁上）→ 多数派确认 → 新 Leader 带新 epoch
第二幕 原子广播（日常写）：
  客户端写 → Leader 打成提案（带 zxid）→ 广播 Follower
  → 多数派 ACK → Leader 提交 → Follower 按序应用（大家看到同一顺序）
```

- **它干了干什么**：**写全序一致的保证**——选主用 zxid 挑"最新的当家"，广播用多数派把每笔写钉进全序。
- **本篇回答**：两幕各解决什么？zxid/epoch 怎么防旧主？和 Raft 差在哪？CP 的代价是什么？

## §1 概念铺垫（What）

| 词 | 一句话 |
|---|---|
| **提案 Proposal** | Leader 对一笔写的封装（带 zxid） |
| **多数派 ACK** | 超半数 Follower 确认才提交——CP 的物理来源 |
| **zxid** | 全局单调事务 ID = `epoch(纪元) + counter`——**恢复时比大小=比数据新旧** |
| **epoch** | 换代纪元，**单调递增**——旧 Leader 的迟到提案带旧 epoch → 被拒（防旧主） |
| **恢复模式/广播模式** | ZAB 的两阶段工作态——崩溃恢复选主后进入原子广播 |

## §2 两幕剧详解

**恢复幕（选主）**：候选集里 **zxid 最大者优先**（数据最新，落盘少）；同 zxid 比 server id（兜底）；**多数派**选出才生效——少数派分区里**不产生 Leader**（这是"选举期间不可用"的根源，§4）。

**广播幕（日常）**：`提案 → 多数 ACK → 提交`——与 Raft 的 log replication 同构；**顺序应用**靠 zxid 排序——这就是 §1 的"全序一致"。

**epoch 的防旧主戏**：换代后 epoch+1——旧 Leader 从"暂停"恢复想继续提案？Follower 看到旧 epoch 直接丢——**纪元号是时间的逻辑版**。

## §3 ZAB vs Raft（dist-theory 03.4 原话收编）

**思想同源**：Leader + 多数派日志复制 + epoch/term 防旧主——**工程上可视为同类 CP 共识**；差异在叙述重心：ZAB 强调"原子广播+恢复模式"，Raft 强调"选举+日志匹配性质"。面试一句："**同一件事的两种讲法**"。

## §4 CP 的代价（和 01 §2 预埋呼应）

```
Leader 挂 → 恢复幕：写阻塞（没有 Leader 提案）→ 直到选主完成
           → 期间不可用——这就是"协调器站 CP"的账单
```

对照表（dist-theory 06 §3.5 原表）：

| 系统 | CAP | 协议 | 定位 |
|---|---|---|---|
| **ZK** | **CP** | ZAB | 协调（选主/锁/配置） |
| etcd | CP | Raft | K8s 元数据 |
| Nacos | AP（临时）+CP（持久） | Distro+JRaft | 注册+配置 |
| Eureka | AP | 无（对等复制） | 注册 |

**为什么注册中心不用 ZK**：注册看重"永远可达"（AP）；协调看重"决策唯一"（CP）——**场景决定 CAP 站位**，05 正面展开。

## §5 掌握卡（2 条）

1. **两幕一句话**：恢复幕选主（zxid 最大+多数派）、广播幕复制（提案+多数 ACK）——**多数派是 CP 的物理来源，epoch 是防旧主的逻辑闸**。
2. **面试对照**：ZAB≈Raft（同类共识）；ZK CP vs Nacos AP（场景站位）——这两句覆盖 80% 追问。
