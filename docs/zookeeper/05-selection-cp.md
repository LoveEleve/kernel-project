# 05-深水：选型与CP代价

## §0 它干了什么（例子先行）

同一件事"谁是主"，三种系统三种答法：

```
ZK：写 /election 临时顺序节点 → 全集群同一顺序 → 最小者是主（强一致，选主期间不可用）
Nacos：注册临时实例 → AP——分区两边各自看到部分列表（可用优先，短暂脑裂可接受）
etcd：Raft 日志 → 多数派提交 → 读可线性化（K8s 的选择）
```

- **它干了干什么**：把 02 的 CP 代价上升为**选型方法论**——不是"谁更强"，是"你的场景站哪边"。
- **本篇回答**：三问定站位的框架是什么？ZK 什么时候是错选？什么时候是唯一正解？

## §1 选型三问（方法论核心）

```
Q1 这个数据错了会怎样？——错=事故（双主/双花）→ 站 CP
                              错=短暂不准（少看见一个实例）→ 可站 AP
Q2 拿不到数据能不能活？——不能（决策必须唯一）→ ZK/etcd
                              能（客户端可重试/降级）→ Nacos/Eureka
Q3 规模与运维？——协调数据小、变更低频 → ZK 完全够
                              十万实例注册风暴 → AP 系才扛得住（Nacos 04 的 Distro 设计动机）
```

**一句话结论**：**选主/锁/领导协调=ZK/etcd（CP）；服务注册/发现=Nacos/Eureka（AP）；配置中心=看团队（Nacos 双模/ZK 也常用）**——dist-theory 06 §3.5 表的决策版。

## §2 ZK 的正解与错选清单

| 场景 | ZK 判定 | 理由 |
|---|---|---|
| Dubbo 注册中心（中小规模） | ✅ 常见正解 | 协调数据小；Dubbo 生态原生适配（Dubbo 系列） |
| 大规模服务注册（十万实例） | ❌ 错选 | 写风暴+AP 需求——Nacos/Eureka |
| 分布式锁（正确性优先） | ✅ 正解之一 | 临时节点自愈+全序——Curator 04 |
| 高频热点锁（每秒万级抢） | ⚠️ 不经济 | 每次抢锁走 CP 写——Redis/ZK 分段锁另议 |
| K8s 场景元数据 | etcd（同类 CP） | 与 ZK 同站位——生态定生死 |

## §3 CP 代价的工程账（02 §4 收口版）

```
Leader 宕机窗口 = 选举耗时（秒级）→ 写全阻塞 → 依赖 ZK 的选主/锁全体等待
缓解手段：多集群部署/客户端超时降级/关键路径避免长事务持锁
```

**面试金句**："ZK 的可用性问题是**窗口性**的——不是永远不可用，是换代窗口不可用；AP 系没有这个窗口但有**脏读**窗口——**两边都在拿'不一致的形态'换'可用的形态'**"。

## §4 掌握卡（2 条）

1. **三问定站位**（§1）——先问错误代价，再问可用依赖，最后问规模——顺序不能反（先看规模会把小场景的 ZK 误杀）。
2. **ZK 的不可用是窗口性的**（§3 金句）——答"为什么不用 ZK"的标准姿势：不黑它，说清窗口与场景。
