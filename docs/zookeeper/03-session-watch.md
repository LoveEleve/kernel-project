# 03-原理二：会话与Watch

## §0 它干了什么（例子先行）

会话和 watch 是"活着"的两个感知器官：

```
会话：connect → sessionTimeout（如 10s）→ 周期 PING 续约
      会话过期 → ZK 判定客户端死亡 → 删除其所有临时节点 → 触发 watch
watch：getData(path, watch=true) → 数据一变，客户端收到一次性通知
      ⚠️ 触发后 watch 失效——要再收通知必须重新注册
```

- **它干了干什么**：会话把"进程活着"外化成集群可判定的状态；watch 把"数据变了"变成可编程的通知。
- **本篇回答**：临时节点删除的触发链？一次性为什么是坑？羊群效应怎么解？

## §1 概念铺垫（What）

| 词 | 一句话 |
|---|---|
| **sessionTimeout** | 会话超时——PING 窗口；超时=死亡判定 |
| **临时节点自动删** | 会话亡的**副作用**（§0 选主可靠性的来源——A 宕机 B 上位的那半句） |
| **一次性 Watch** | 触发即失效——ZK 原生语义（不是 bug 是设计：省服务端状态） |
| **羊群效应 herd effect** | 多客户端 watch 同一节点 → 一次变更全员惊醒 → 服务端瞬间风暴 |
| **只 watch 前一个** | 公平锁解法：变更只唤醒下一个排队者——一次通知一个人 |

## §2 为什么"一次性"反而是特性（推导）

**朴素答案**：watch 常驻多好——注册一次终身收。

**But**：常驻=服务端为每个客户端存订阅表——连接数×节点数的状态爆炸；且"我还需要这个通知吗"只有客户端知道。

**Therefore**：**一次性 + 客户端自己续订**——ZK 管道只递一次，重订阅是业务的决策（"拿到通知后我还要不要继续盯"）。Curator 的高阶 recipe（04）把重订阅包进去了——**用原生 API 必须手写续订**，这是用 ZK 的第一大坑。

## §3 工程使用

```java
// 原生姿势（必须手动续订——伪代码）
void watch(String path) {
    zk.getData(path, event -> { handle(event); watch(path); }, null);  // 递归重注册
}

// Curator 姿势（04 主场）：PathChildrenCache/NodeCache 内部处理续订
```

**选主场景的 watch 姿势**（§0 回收）：**只 watch 前一个序号节点**——公平锁一次只叫醒一个；watch 所有节点=每次有人进出全员重算（羊群）。

**会话工程要点**：sessionTimeout 别太短（GC 停顿就过期）也别太长（真宕机要等久）——**10~30s 常见**；`close()` 主动关闭会立即删临时节点（优雅下线同款语义，对照内核 02 销毁钩子）。

## §4 掌握卡（2 条）

1. **可靠性的传递链**：进程死 → 会话超时 → 临时节点删 → watch 通知 → 竞争者上位——**四跳全靠前一跳自动**，这就是"ZK 锁不需要人工解锁"的原因（持有者死了系统自愈）。
2. **一次性是设计不是缺陷**：服务端零订阅状态 + 客户端自主续订——用 Curator 就忘掉这事，用原生就必须记住。

## §5 边界（一句话翻篇）

- 会话超时的服务端判定细节（tickTime/syncLimit）→ 部署配置用时查。
- 多种 watch 类型（exists/getData/getChildren × 数据/子节点事件）→ 官方文档。
- Curator 的 ConnectionStateListener（会话断连重连监听）→ 04。
