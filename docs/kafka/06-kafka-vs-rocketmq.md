# 06-深水：Kafka vs RocketMQ——xhs 为什么选 RocketMQ

## §0 它干了什么（例子先行）

同一公司两类业务，两个答案：

```
xhs 订单支付链路 → RocketMQ：半消息保证"DB 提交 + 消息发出"原子（RMQ 06）
xhs 若把埋点日志管道 → Kafka：每分钟百万条日志、下游 Flink 消费——只要"丢一条无所谓，顺序有分区内保证"
```

- **它干了干什么**：**不是谁更强，是哪个问题域**——事务/延迟/业务治理 → RocketMQ；日志管道/流处理 → Kafka。
- **本篇回答**：架构差异全景表？xhs 的选择推导？面试上这题怎么答才不像背书？

## §1 概念铺垫（What：六维全景——已审事实的组装）

| 维度 | Kafka | RocketMQ | 出处 |
|---|---|---|---|
| 存储 | 分区独立日志段+稀疏索引 | CommitLog 混写+ConsumeQueue | K02 / RMQ 03 |
| 复制 | 分区级 ISR 动态集合 | 整机级 Master/Slave | K02 / RMQ 03 |
| 进度 | 消费者提交 `__consumer_offsets` | Broker 存（5s 上报） | K01/K03 / RMQ 04 |
| 重平衡 | GroupCoordinator+Eager/Cooperative | Rebalance 全组重算 | K03 / RMQ 04 |
| 事务 | Kafka 内跨分区（包不了 MySQL） | **半消息+回查（跨 DB）** | K04 / RMQ 06 |
| 特色能力 | 分区内严格有序、幂等生产者、流处理生态 | **延迟消息/顺序消息/DLQ 治理** | K04 / RMQ 05/07 |

**一句话**：Kafka 的设计中心是"**一个可重放的日志**"（日志即产品）；RocketMQ 的设计中心是"**业务消息中间件**"（事务/延迟/可靠投递是产品面）。

## §1.5 推导：xhs 为什么选 RocketMQ（落点题）

**朴素答案**："RocketMQ 更适合业务场景"——太空。

**链条**（三个业务刚需，全部已在封卷系列有实锤）：

1. **跨 DB 事务刚需**：订单+库存+支付状态都是 MySQL 事务——要"本地事务成功才发消息"→ **半消息+回查**（RMQ 06）；Kafka 事务包不了 MySQL（K04 §2）——**第一分水岭**。
2. **延迟消息刚需**：定时支付关单/延后触发用 delay level（RMQ 07）——Kafka 无原生延迟（要自建时间轮/扫表），**多一层自研成本**。
3. **业务语义治理**：17 个业务 topic + DLQ + 幂等 + 顺序（RMQ 08 生产对照）——RocketMQ 的 Tag/组/重试模型按"业务消息"设计，Kafka 的消费模型更偏"数据流"。

**Cost（诚实边界）**：xhs 没有大规模流处理/数据管道需求——**没有这条，Kafka 的生态优势无处发力**。

**So what**：选择=**业务问题域匹配**，不是性能榜。若 xhs 要加"行为日志→实时数仓"管道，那条链路选 Kafka 才是对的——**同一公司可以两个都用，按链路选型**。

## §2 反向选 Kafka 的场景（面试防翻车）

| 场景 | 为什么 Kafka |
|---|---|
| 日志/埋点/埋点管道 | 分区内顺序+超高吞吐攒批（K04）+可重放（K01 书签模型） |
| 流处理（Flink/Kafka Streams） | 与流生态天然一体（offset 即游标） |
| 数据管道（CDC=变更数据捕获，如 MySQL→ES 同步） | 消费者自主重放=天然的"回溯能力" |
| 事务消息刚需 | ✗ 不要选 Kafka（包不了 DB——K04） |

## §3 掌握卡（2 条）

1. **六维全景背不背得住无所谓，两条轴要能现场推**：**事务边界**（跨 DB vs Kafka 内）与**产品中心**（可重放日志 vs 业务消息）。
2. **落点题话术**：三个业务刚需（跨 DB 事务/延迟消息/业务治理实锤）+ 一条诚实边界（无流处理需求）+ 反向场景（同公司按链路选型）——**这就不像背书**。

## §4 边界（一句话翻篇）

- 吞吐基准测试数字 → 翻篇（随版本/配置漂移，面试报数字易翻车）。
- Kafka 流处理生态细节 → 非本线。
- 混用时的运维双栈成本 → 运维侧。
