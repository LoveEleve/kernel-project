## 0. 术语速查

| 术语 | 含义 |
|---|---|
| **Sync 双向流** | `syncer.proto` 唯一有状态接口：`Sync(stream SyncRequest) returns (stream SyncResponse)`——**所有有状态交互都走这一条流** |
| **四阶段** | Handshake（立/恢复会话）→ Watch（全量订阅）→ Poll（增量拉取）→ ACK（确认） |
| **稀疏 ACK** | 不是每条 binlog 都确认——**批量确认一个版本区间**（start/end + notAck/failure 例外表）："100 条 binlog 只需 1 个 ACK 消息" |
| **三级优先级队列** | HIGH=30（控制信令）/ MEDIUM=20（普通配置）/ LOW=10（后台）——**注意：不是阻塞式优先级**，是三类独立轮询 |
| **三棵 BTree** | `binlogTree`（已对齐·最终下发）/ `unsyncedBinlogTree`（Kafka 侧未对齐）/ `fusionBinlogTree`（Fusion 侧未对齐） |
| **三向合并** | snapshot（全量历史点）+ Kafka binlog（实时）+ fusion binlog（拉取）——**对齐=证明无版本空洞** |
| **ReplicaRouter** | fusion 副本路由：per-configKey 绑定 replica，失败隔离 5 分钟 + 确定性轮转 |
| **QuickRestartMode** | 重启时从 versionstore 注入 LocalVersion → broker **从该版本之后推** → 秒级增量启动（vs 全量几十秒） |

## ① 它干了什么——一台母机 agent 的"上线之旅"

一台母机上的 vpc-host-agent 从启动到"VM 流量通了"，全程只在**一条 tRPC 双向流**上讲五种话：

1. **启动**：拿种子地址（LB VIP）问 `DiscoverService.ListBrokers`（失败直接 panic——agent 起不来）；按 localZoneId 就近优选真实 broker；
2. **连接**：从 LevelDB 恢复上次的 `SessionID + HIGH/MEDIUM LocalVersion` → 建流（HandshakeTimeout 10s）→ **Handshake**；
3. **订阅**：**Watch** 全量（大快照分页传：`is_complete / partition_index / partition_count`）；
4. **稳态**：`pollLoop` 每秒问一次 **Poll**（三级队列、长轮询、BatchSize 100）；收到后按 configType 聚合 → `watchIndex` 路由到 SetID → Dispatcher → Router → **Extension.OnConfigChange** → 落 LevelDB → 下发 DPDK；
5. **确认**：`acker` 每 3 秒发一次**稀疏 ACK**（批量版本区间）；broker 收到后**驱逐已确认的 binlog 释放内存**。

然后：**VM 流量通了**。断线的话重连 5 次（backoff 1→2→4→8→10s），带旧 sessionID 请求**增量恢复**；session 不认了（INVALID_SESSION）才降级全量。

## ② 链路走查（材料行号）

### 跳 1：协议面——protobuf 里读出的设计（trpc §一）

- **三个 Service**（§1.1）：`SyncService.Sync`（双向流，**所有有状态交互**）/ `Get`（一次性拉取，**无订阅关系**）/ `HealthCheck`；外加 `DiscoverService.ListBrokers`（启动期发现）。
- ⚠️ **口径纠正**（§1.1 注）：`syncer.proto` 只定义 SyncService 与 DiscoverService，**无 ReportService**——第 17 课按 36 文档 §1.1 写的"ReportService"在另一份 `reporter.proto` 里（第 18 课 §4.1 提过），两处说法**都对但归属不同文件**。
- **SyncRequest**（§1.2）：`oneof payload = handshake | watch | unwatch | poll | client_ack`——**五种话一条流**（握手 / 订阅 / 退订 / 轮询 / 确认）。
- **SyncResponse**（§1.3）：`watch`（全量推送）/ `poll`（增量推送）/ **`ctrl_signal`（Broker 主动下发的控制信令）** + **大快照分页三件**（`is_complete / partition_index / partition_count`）+ 请求级错误。
- **DataTopic**（§1.4）：`resource_scope`（ScopeType：**GLOBAL / VPC / OWNER / HOST** 四粒度）+ `config_name` + `version`（**0=全量；>0=从该版本开始增量**）+ `subscribed_keys`（空=全部，非空=按 key）。——**"增量+全量"方程直接写进了协议字段**。

### 跳 2：建立连接——五步启动与 connect 全流程（trpc §二）

**启动顺序**（§2.1）：

```
initFrameworkBase（Metrics + Storage + ExtManager）
  ↓ initFrameworkSyncer:
  Step 1. Broker Discovery —— 种子地址查 ListBrokers；就近优选；失败直接 panic
  Step 2. SetRuntimeBrokerPool —— 注入真实列表；种子保留为 fallback
  Step 3. DataSyncer.Start —— 建流 + 四个常驻 loop：recvLoop / pollLoop / sendLoop / acker.runLoop
  Step 4. 注册 CtrlSet Extensions（resource_ctrl_set / core_ctrl_set / vpc_broker）
  Step 5. 初始化 WatchRouter + 注册 50+ 业务 Extension
```

**connect 全流程**（§2.2）三个要点：`selector.NextBrokerExclude`（**排除已失败者**再选）；`prepareSessionStateForBroker` 里 **`sessionSnapshotStore.Load(addr)` 从 LevelDB 恢复旧 session（SessionID + 两级 LocalVersion）**；握手专门包了一层 `handshakeWithSessionRecovery`——**收到 `code=4 INVALID_SESSION` 就重建 stream、用空 sessionID 重发**（增量恢复失败 → 全量恢复的降级点）。全部 broker 失败 → `PanicOnAllBrokersFailed ? panic : ErrConnectionFailed`。

**为什么需要 Broker Discovery**（§2.3）：种子是 LB VIP（不稳定的逻辑入口），真实 broker 列表要动态拿——**"种子兜底 + 真实优选"双层地址体系**（与 §7.3 Seed Fallback 呼应）。

### 跳 3：Handshake 与 Session 恢复——两级降级（trpc §三 + §4.5）

- **HandshakeRequest**（§3.1）：Header（flow_id / request_id / session_id / agent_ip）+ `SessionId` + **`SessionKey`（形如 `"agentIP_proc0"`——唯一标识同步进程）**；发出后阻塞等 `HandshakeResponse.SessionId`；
- **Broker 处理**（§3.2）：`session_key` 必填；`session_id` 为空 → **新建会话，先清理同 session_key 的旧会话**；非空 → 校验，不合法回 `INVALID_SESSION (code=4)`，合法 → **恢复旧会话（增量）**；
- **Session 恢复两场景**（§3.3）：

| 场景 | Broker 侧状态 | 结果 |
|---|---|---|
| 网络闪断（< Session TTL） | session 还在 | **增量恢复**：跳过已同步 binlog；reWatch 携带 LocalVersion → broker 从该版本之后推 |
| 长时间断连（> Session TTL） | 已 Expired / TooSlow | 返回 INVALID_SESSION → Agent 空 sessionID 重握手 → **全量恢复** |

- **QuickRestartMode**（§4.5）：启动期从 versionstore 自动注入 `LocalVersion` 到 Watch 请求 → broker 从该版本之后推 → **秒级增量启动（vs 全量拉取的几十秒）**——**重启也先试增量：这是第三级降级**。

### 跳 4：Poll——长轮询与三级队列（trpc §五）

- `pollLoop` **每 1 秒**发一次；`PollReq` 带 `Queues[]`（每项：`QueueClass` + `LocalVersion` + `BatchSize=100` + `PollTimeoutSeconds`：HIGH 默认 10s、MEDIUM 默认 30s、**Max 5min**）；
- **长轮询语义**（§5.2）：超时窗内无新 binlog → 返回空（**减少空请求**）；有新 → 立即返回（不等满）；
- **三级优先级**（§5.3）：

| QueueClass | 用途 | Poll 频率 | 处理 |
|---|---|---|---|
| HIGH=30 | 控制信令（如 session 恢复） | 1s | 每次只发一个 QueueClass 的 Poll，**串行独立处理** |
| MEDIUM=20 | 普通配置（rtable/eni/service） | 1s | **MaxPendingVersions=1000——超过暂停 Poll**（背压） |
| LOW=10 | 后台任务 | 按需 | 按需 |

⚠️ **不是"HIGH 没处理完就阻塞 MEDIUM"**——不同 QueueClass 的 Poll 是独立请求，broker 按收到的顺序串行处理（**队列优先级 ≠ 抢占式调度**）；
- **接收**（§5.4）：`UpdateLocalVersion(Class, MaxLocalVersion)` → 按 configType 聚合 binlog → `watchIndex` 路由到 SetID → Dispatcher → Router → Extension；顺带记录 `BacklogCount`（还有多少没消费）。

### 跳 5：稀疏 ACK——100 条一个消息（trpc §六 + consumption §八）

**原理**（§6.2）：不逐条确认，**批量确认版本区间**——

```
已收到 binlog 100-150
  100-102 已处理完 → ACK 覆盖
  103 处理超时    → failureVersions
  104 还在处理    → notAckVersions
  105-149 已处理完 → ACK 覆盖
  150 还在处理    → notAckVersions
ACK 消息：start_version=100, end_version=150,
         not_ack_versions=[104,150], failure_versions=[103]
→ 100 条 binlog 只需 1 个 ACK 消息！
```

- **Broker 处理**（§6.3）：`UpdateAckedVersion(endVersion)` 推水位 → `EvictBefore(endVersion)` **驱逐已确认 binlog 释放内存**；notAck 不驱逐（等处理完再 ACK）；**failureVersions → 标记失败 → Agent 重新 Watch 拉全量**；
- **ACK 持久化**（§6.4）：Agent 把版本号存 LevelDB（`sessionSnapshotStore.Save`）→ 重启从这里恢复 LocalVersion → **增量恢复闭环**（与跳 3 的 QuickRestart 同一机制）；
- **三层不丢保证**（consumption §8.1）：Dispatcher→Session **阻塞写入**（channel 满不丢）/ Session binlogQueue **环形队列 + ackedVersion 追踪** / Agent ACK 协议。

### 跳 6：断线重连——5 次退避与降级次序（trpc §七）

`recvLoop` 收到 err → `onDisconnect`：**`reconnecting.CAS(false, true)` 防并发重连** → 重连循环（`MaxReconnectAttempts=5`，backoff **1s→2s→4s→8s→10s 封顶**）→ 建新流 + **带旧 sessionID 握手**：成功且兼容 → 继续 recvLoop（**增量恢复**）；`INVALID_SESSION` → 空 sessionID 重握手（**全量恢复**）；5 次全败 → cancel ctx，所有 loop 退出。另有 **ReWatch 调度**（§7.2：按 `(configType, setID)` 去重 + **3 worker 并发**（避免 head-of-line blocking）+ 携带 versionstore 的 LocalVersion → 增量恢复）与 **Seed Fallback**（§7.3：所有 runtime broker 不可达时用种子重新 ListBrokers——**打破"刷新 broker 需要 broker 推送"的循环依赖**，节流 + singleflight 防雪崩）。

### 跳 7：broker 消费端——三棵 BTree 与三向合并（consumption §二/三/四/五）

**ReplicaRouter**（§2.2）：`configKey（configName+scopeId）→ replicaId` 绑定；失败时**隔离该 replica 5 分钟** + `pickReplica` 确定性 round-robin；**仅当有备选时才隔离**——单 replica 场景保持原样（避免完全不可用）。**拉数据主流程**（§2.3）：`GetLatestSnapshot`（Redis 拉快照元信息 + CDB 拉分片数据）→ `ListBinlog`（Redis 拉 version 之后所有 binlog）。

**为什么需要 BTree**（§3.1）：broker 从**两个来源**拿 binlog——fusion 的 `ListBinlog`（HTTP API）+ **broker 自己也消费 Kafka**；两源必然重叠，需**按版本去重排序**。于是每个 ConfigHandler 带**三棵 BTree**（§3.2）：

| BTree | 数据来源 | 状态 |
|---|---|---|
| `binlogTree` | 已对齐的 binlog | **最终下发给 agent** |
| `unsyncedBinlogTree` | Kafka cached + 实时 | 等待与 fusion 对齐 |
| `fusionBinlogTree` | fusion ListBinlog 返回 | 等待与 Kafka 对齐 |

实现：Google `btree.BTreeG[*ManagedBinlog]`（**度=16**）+ `cachedMin`；操作 `Insert / Min / Max / Ascend / DeleteWhile`；**版本范围查询**= `Ascend` 里 `b.GetVersion() <= filterVersion` 跳过；**旧 binlog 清理**（§3.5）：`threshold = snapshot.Version - retentionWindow`，`DeleteWhile(<= threshold)`。

**三向合并**（§四）：新 Session 接入要"全量（fusion snapshot 版本 N）+ 增量（version > N）"，而 **Kafka 缓存的 binlog 是近 10 分钟的**——直接发 Kafka binlog 可能重复（snapshot 已覆盖），只发 snapshot 可能遗漏。**对齐条件三条**（§4.3，满足其一）：① snapshot 版本=0；② `unsyncedBinlogTree` 为空；③ **版本连续**——`maxFusionVersion+1 >= firstUnsyncedVersion` 或 `snapshotVersion+1 >= firstUnsyncedVersion`（**含义：确保没有版本空洞**）。对齐完成（§4.4）：状态转 `syncStateCompleted`，两棵未对齐树中 `version > snapshotVersion` 的**迁移到 `binlogTree`**。**InitFailed 自恢复**（§4.5）：3 次重试仍 `aligned=false` → `markInitFailed`——**不删 handler、不删 watch state、保留 pending tasks**，后续新版本通知时重新拉取，**可能自动对齐**（"失败不是终态，是待重试"）。

**Dispatcher 单协程 + 16 Worker**（§5.1）：`messageCh（buffer 1000）→ dispatchLoop（单协程，FIFO）`（routeWatchResult 单播 / routeBinlogs 广播按 SessionID hash / routeWatchError 单播）→ **16-Worker（各自 channel buffer 5000）** → `Session.Enqueue` → EventLoopWorker → `stream.Send`。**为什么单协程**（§5.2）：**保证 FIFO——WatchResult 一定先于 Binlog 到达 messageCh，全量一定先于增量**。`hashSessionID`（§5.3）= `maphash.String(hashSeed, sessionID) % workerCount`——**同一 Session 恒同一 Worker**（保序）。**阻塞写入**（§5.4）：`workerChs[idx] <- task` **channel 满时 Worker 阻塞等待**——"**宁可慢不可丢**"。

### 跳 8：Extension 分发与 Gen2 对比（trpc §八/九/十）

- **WatchRouter**（§8.1）：通过名字查找 Extension + `configTypeToExt` 映射表；**注册 50+ 业务 Extension**（§8.2 `RegisterBatch`：rtable/eni/subnet/vpc/rtb_route/acl_item/service/route…）；
- **完整事件链路**（§8.3）：

```
Kafka binlog → vpc-fusion → LevelDB 快照 → vpc-broker 拉快照
→ BTree 版本索引 → Dispatcher → Session → tRPC Stream.Send → Agent recvLoop
→ handlePollResponse 按 configType 聚合 → watchIndex → SetID → Dispatcher → Router.Handle
→ filterEvent（scope re-check + itemKey filter）  ← 端侧二次护栏
→ Extension.OnConfigChange → 解析 protobuf → 更新内存 → 持久化 LevelDB
→ 下发 DPDK route_table / neigh_table → VM 流量通了
```

- **7 态状态机**（§九）：`StateInit → Handshake → BindStream（EventLoopWorker 接管）→ StateActive →（Expired / TOO_SLOW…）→ Terminated`；**关键转换用 CAS**（防并发状态翻转）；
- **和 Gen2 ZK Watch 对比**（§十，材料两行原文）：配置存储 **ZK znode** vs **broker BTree + binlog 队列**；传输协议 **ZK TCP（Jute 序列化）** vs **tRPC + Protobuf 双向流**。

## ③ 设计推导（问题树）

**Q1：稀疏 ACK 的本质是什么？**
把"逐条确认"压缩成"**区间 + 例外表**"——消息数从 O(n) 降到 O(1)（"100 条只需 1 个"）；同思想：TCP 累积确认 / Kafka offset commit。代价是必须带 `notAck/failure` 例外，否则区间确认会**误吞**未完成的条目。另一层：ACK 同时是 **broker 内存的释放许可证**（`EvictBefore` 只认水位）。

**Q2：三级队列为什么不做"优先级阻塞"？**
材料明说不是"HIGH 没处理完就阻塞 MEDIUM"——**独立请求、串行处理**。收益：控制信令（session 恢复）不被大流量卡死，同时普通配置吞吐不受 HIGH 拖累；这放弃了"抢占"，换来了**简单可预测**（串行处理无锁）。背压仍在：MEDIUM 的 `MaxPendingVersions=1000` 超了就暂停 Poll——**推不动就停拉**。

**Q3：恢复为什么是"三级降级"而不是直接全量？**
闪断（<TTL）→ **增量**（最便宜）；超时/无效 session → **全量**（正确性兜底）；重启 → **QuickRestartMode 先试增量**。**从便宜到昂贵的阶梯**——全量永远是对的，但太贵；增量便宜，但只有连续性成立时才可用（同主题：第 17 课两阶段订阅、第 16 课 SyncOnStart）。

**Q4：三棵 BTree + 三向合并的本质？**
两个**异步来源**（Kafka 实时流 / fusion 拉取）+ 一个**已对齐账本**——"**三路合并**"（两个未对齐树各有来历，对齐=证明**无版本空洞**：`max+1 >= min`）。这是分布式数据的通用形状：**两源必重叠，去重靠版本、对齐靠连续性**。`InitFailed` 的处理尤其老到：**不删任何状态、保留 pending，等下一次通知自愈**——"失败是状态，不是终态"。

**Q5：单协程 dispatchLoop + 16 Worker 的分工？**
**谁需要全局序、谁只需要局部序**：单协程保**全局 FIFO**（全量先于增量——跨会话的因果）；hash 到 16 Worker 保**会话内序**（同一 Session 恒同一 Worker）同时吃满多核；阻塞写入兜底"宁慢不丢"。第 17 课只看到 hash 保序，这里补上了**全局序那一半**。

**Q6：`filterEvent` 的 scope re-check 为什么必须存在？**
分发链条极长（7 跳），任何一环的订阅状态都可能过期/穿越——端侧在**落 Extension 之前**再验一次 scope + itemKey，**纵深防御**。同族：第 17 课 Session 的 Ready 校验、第 14 课 TF 的 interest graph（per-chassis 过滤）。

## ④ 对照卡：Gen2 ZK Watch vs Gen3 tRPC Stream

| 维度 | Gen2（ZK Watch） | Gen3（tRPC Stream） |
|---|---|---|
| 配置存储 | ZK znode | **broker BTree + binlog 队列** |
| 传输协议 | ZK TCP（Jute 序列化） | **tRPC + Protobuf 双向流** |
| 断点/恢复 | 重注册（30-40 分钟，第 4 课） | **Session + LocalVersion + 稀疏 ACK → 秒级增量** |
| 全量下发 | ZK 一次性全量 | **Watch 分页传输（is_complete / partition）** |
| 增量发现 | watch 一次性触发（需重注册） | **Poll 长轮询 + 三级队列** |

## ⑤ 验收题

1. 稀疏 ACK 为什么必须带 `not_ack_versions / failure_versions` 例外表？去掉会怎样？
2. "不是 HIGH 阻塞 MEDIUM"这个设计放弃/换取了什么？MEDIUM 的 `MaxPendingVersions=1000` 暂停 Poll 属于哪种背压？
3. 重连的恢复为什么是"增量优先、全量兜底、重启先试增量"的三级阶梯？各自成立的**前提条件**是什么？
4. 三向合并的对齐条件为什么要写成 `max+1 >= min`？"版本空洞"具体指什么场景？
5. 单协程 dispatchLoop 与 16 Worker hash 各保证哪一级顺序？为什么"全量先于增量"必须由**全局**单协程保证？
