## ② 链路走查（材料行号）

### 跳 1：Commit 1——限频（core-fixes §Commit 1，abbdea8，4/10 12:13）

**问题**："Leader 一次性发布大量任务（如**全量对账 10 万 VPC**）→ 瞬间压爆 Redis 队列 + vpc-api-server + MySQL"——第 18 课"限频（Leader 不能一次发 10 万任务压爆 Redis）"的原现场。

**改了什么**（`reconcile_config.go`）——新增两个配置项：

```go
type ReconcileCommonConfig struct {
    WorkerConcurrency  int `default:"10"`
    WaitMsPer          int `default:"10000"`  // 等 10 秒
    ConcurrencyPerWait int `default:"100"`    // 每 10 秒最多 100 个任务
}
```

**限频逻辑**（`reconcile/leader_service.go`）：`waitMsPer=10*1000` / `concurrencyPerWait=100` / **`currentTaskCount atomic.Int32`**——发布前先 `Load()` 原子计数器检查阈值（**限频器自己也是并发安全的**——原子计数而非加锁）。

### 跳 2：Commit 2/3——租约与那个"被修出来的空指针"（core-fixes §Commit 2/§Commit 3）

**Commit 2（3fe2ed5，4/10 15:24）"分布式任务增加租约"**：材料标题即故事——15:24 上线租约（第 21 课的 Lease/Heartbeat/Recovery 三段式在此成型）。

**Commit 3（bcd7181，4/10 15:48）"修复空指针"**——**仅仅 24 分钟后**："commit 1 引入的 InitState 校验暴露了一个空指针 bug。**8 行修复**。"材料给了两个 bug 的现场：

```go
// 旧代码（buggy）
if containResourceObj {
    configState, err := mc.GetGenericConfigStateDao().Find(ctx, ...)
    //              ↑ 用 := 声明新变量，遮蔽了外层 err
    if err != nil { return err }
    obj := &control.ResourceObj{
        InitState: configState.InitState,  // ← 空指针！configState 可能为 nil
    }
}
```

**两个 bug 同框**：① **变量遮蔽**——`:=` 声明了新的 `configState` 和 `err`，外层 `err` 没被赋值，后续错误处理失效；② **空指针**——`configState` 可能为 nil 却直接 `.InitState`。**"修复自己引入的下一个 bug"**——这就是 15:24→15:48 这 24 分钟的含金量：**review 自己的改动要当成别人的代码看**。

### 跳 3：Commit 2 深读——三项机制的"一天成型"（core-fixes §Commit 2）

**规模最大的一笔**（**+923/-330 行**）："引入了 **Lease + Heartbeat + Ownership 三项核心机制**"。

- **问题**：Worker 崩溃后任务卡在 processing——"且旧 Recovery 只检查 `StartedAt + timeout`，**没有 lease 概念**"（病根画像：判定"死"的依据是"开始时间+固定超时"，而不是"活着的证据"）；
- **改动 1**：`DistributedTask` 新增 **`LeaseExpireAt *time.Time`**；
- **改动 2**：`WorkerConfig` 新增 `LeaseTTL`（默认 30s）+ `HeartbeatInterval`（默认 `LeaseTTL/3` = 10s，**默认值校验**：`HeartbeatInterval >= LeaseTTL` → 直接报错——**配置校验即防御**）；
- **改动 3**：**接口签名全部加 `workerID`**——`CompleteTask(ctx, taskID)` → `CompleteTask(ctx, taskID, workerID)`……**这是 Ownership 的入口**：从这一天起，每个写操作都要**自报身份**，"诈尸"的旧 Worker 会在签名层面就露馅（第 21 课 §八 的伏笔在此埋下）。

### 跳 4：Commit 4/5——EXECABORT 逼出的"非原子过渡"与三天后的 Lua 收口（core-fixes §Commit 4/5）

- **问题**（Commit 4，8b4b012，4/10 17:10）：commit 2 的 `saveTaskToProcessing` 用 **`TxPipeline`（MULTI/EXEC 事务）**——"Redis Cluster 下跨 slot 的 MULTI/EXEC 会触发 **`EXECABORT`**"；
- **临时修复**（材料保留的注释原文）：

```go
func (d *TaskDaoImpl) newTaskPipeline() redisclient.Pipeliner {
    // 分布式任务链路避免使用 TxPipeline。
    // 部分 Redis Cluster / Proxy 场景不支持 MULTI/EXEC
    return d.Client().Pipeline()  // ← 普通 Pipeline，非事务
}
```

- **三天后**（Commit 5，56fe2da，4/13 14:35）："Lua 脚本（锁续约 / 优先级取出） + Hash Tag"——**原子性最终收口**（第 21 课的 8 个 Lua 脚本在这里出生）。

**修复排序的启示**：EXECABORT 是"**可用性**问题"（跨 slot 直接报错），比"原子性"更急——所以**先上非原子 Pipeline 止血，原子性三天后再补**。**修复的顺序按急迫度排，不是按优雅度排。**

### 跳 5：附带七修——"顺路现形"的其他雷（accompanying-fixes）

主线在修队列，但 4 天里"顺路"修的是 **16 个工程问题**。五处现场：

- **① DELETE 复活**（430b5ab，第 20 课场景 4 的正主现场）：

```go
func (d *GenericSnapshotMergeDaoImpl) DeleteConfig(ctx, config) error {
    key := buildKey(shardId, identifier)
    // "删除" —— 但实际上不是删除！
    if err := d.db.Put([]byte(key), nil, nil); err != nil { ... }
}
```

LevelDB 的 API 三件套是 `Put`（写）/ `Get`（读）/ **`Delete`（删）**——`Put(key, nil)` 只是"写入一个 value 为空的 key"，**key 还在**——于是已删配置"复活"（材料原文："这不是删除，而是写入一个 value 为空的 key"）。

- **② resourceObj 死循环**（57f894e5，第 20 课场景 5 的正主——**五步闭环**）：

```
第1步 Leader 扫描 → 发现 resourceObj 需要初始化 → 发布 init task
第2步 Worker 拉全量 → 写入 OBJ 表
第3步 Worker 继续执行 → 检查"OBJ 是否存在" → FindResourceObj 返回 nil
      （刚写入还没查到 / scopeId="" 走错分支）
第4步 Worker 误以为 OBJ 被删 → 删除 GenericConfigState → 任务"完成"
第5步 Leader 下轮扫描 → 发现 state 没了 → 重新发布 init task → **回到第 2 步**
```

**Worker 误以为账本丢了，反手把自己刚建的删了**——**自指检查错误**的教科书现场（第 21 课"状态紊乱三根因"之一）。

- **③ continue 误用**（e28a6ef）：全局配置（`ScopeType=GLOBAL`，不属任何 SET）vs 业务配置（属某 SET）；旧代码遇到全局配置直接 `continue`——"**本意是'全局配置不需要 SET 校验'，但写成了'跳过整个处理'**"→ 全局配置的变更**永远不被回调**；
- **④ ResourceObj 缓存即真相**（67359ff + 11d901b）：ResourceObj 是元数据表（记录 `UNINITIALIZED / INITIALIZING / INITIALIZED / SNAPSHOT_AVAILABLE`），**读取频率极高**（5 个 Leader 每分钟扫、每秒几十次查）——旧代码直查 MySQL 三宗罪：高频查询打 DB / **写后读端要等 binlog 同步（延迟窗口）** / 并发下 DB 与缓存不一致。新代码改走 Redis 缓存（50-commit 表 G 组："ResourceObj 走 Redis 缓存，**22 文件**"）——**读走缓存**（`GetReadClient().GetResourceObj`）、**写走缓存**（先读 → 改状态 → `GetWriteClient().SaveResourceObj`）；更狠的是 **DAO 层防御性校验**（§4.4）：`validateConfigName` 里对 `resourceObj` **直接报错**——"not support config name, please use cache"——**把"缓存即真相"焊死在代码里：绕过缓存的路径不是被劝退，是被拒绝**；**当读取成为瓶颈时，换读源，不是加索引**；
- **⑤ 初始化限流**（65fb670）：**200 万 VPC 首先启动**的三爆（几十 GB Redis 内存 / API 被 200 万 Worker 打爆 / MySQL 200 万次 INSERT）——实现 `waitMsPer=5*1000 / concurrencyPerWait=100 / atomic.Int32` + **到阈值 sleep 后重置计数**：**与 Commit 1（reconcile 10s/100）同款手法复用**；
- （⑥ 运维接口分表分页：14 个排查接口——3 个典型问题："VM 配置没下发？查 ConfigState / 快照落后？查 Binlog / 任务卡死？查 ConsumerGroups"；⑦ 测试覆盖：**2900 行**测试——"修完把测试补到比修复还重"。）

## ③ 设计推导（问题树）

**Q1：为什么"修一个坏一个"是工程的常态？**
每次修复都是**对运行中的系统动刀**：改配置结构（限频）会碰到校验逻辑（空指针）；改写路径（租约）会碰到事务管线（EXECABORT）；换 Pipeline 会暴露出"非原子"。**刀口总会碰到别的血管**——对策不是"不犯错"，而是**让暴露来得快**：4 天 5 commit 的节奏本身就是"快速暴露 + 快速修"的能力展示。

**Q2：Commit 2 为什么能"一天成型"三项机制？**
Lease（怎么判死）+ Heartbeat（怎么续活）+ Ownership（怎么防止诈尸）——**这三件是同一个问题的三个面**："任务到底归谁"——判死、续活、验身份，缺一不可。**接口全部加 `workerID` 是个大动作**（所有调用点都要改）——它说明：**身份传递必须进入类型系统**，否则"诈尸防护"永远是补丁。

**Q3：为什么先上"非原子 Pipeline"、三天后才 Lua？**
EXECABORT 是**可用性事故**（跨 slot 直接报错、任务写不进 processing），原子性是**正确性隐患**（窗口极小）——止痛与根治分开做。**修复排序 = 急迫度 > 优雅度**；而且"非原子过渡"只在 3 天内存在，最终 Lua 收口——**临时方案可以有，但必须有到期日**。

**Q4："缓存即真相"与第 2 课 Typha 是什么关系？**
同一个主题的再现：**读放大治理**（Typha 治的是 k8s API 的读放大；这里治的是 MySQL 的读放大——"一台实例每秒几十次查"）。但"缓存即真相"比"加缓存"更进一步：**换读源的同时接下了新义务**——写路径必须同步维护缓存（否则缓存就是"假真相"）；标题四个字背后是一整套一致性约定。

**Q5：五处附带修里藏着几条"通用教训"？**
`Put(nil)`→**API 语义要吃透**（写≠删）；死循环→**自指检查要有守卫**（自己初始化自己时，"存在性检查"必须先豁免）；continue→**控制流的意图要写对**（"跳过校验"≠"跳过一切"）；缓存→**读放大会换榜**（从 DB 换到 Redis 后，Redis 成为新的瓶颈点）；限流→**同款手法可复用**（atomic+sleep 在两个模块各自出现）。**修复窗口 = 审计窗口**：盯着一处修的时候，其他雷也会现形——4 天里修掉的从来"不只一个队列"。
