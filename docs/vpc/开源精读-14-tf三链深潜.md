## 0. 术语速查

| 术语 | 含义 |
|---|---|
| **DependencyTracker** | 依赖跟踪器：**按策略**递归展开"我依赖的谁变了 → 我也要重算"——依赖是**声明**的，不是手写的 |
| **GraphWalker（interest graph）** | 为每个 ifmap 客户端计算"它关心的可达节点集"——子图选择的执行者 |
| **DB / DBGraph / DBTable** | Contrail 自研的"数据库框架"（仓库根 `src/db/`）：表 + 条目 + 状态机 + 依赖图 |
| **oper DB** | agent 侧的运行数据库（oper/ 目录下的路由/下一跳/接口各表） |
| **kstate** | "内核实况"族：每类内核对象一个 kstate 文件——oper（模型）→ 内核（实况）的同步层 |
| **resync** | 对齐机制（`agent_route_resync.cc`）——"增量+全量"方程第 N 次现身 |

## ① 它干了什么——"三张网"上的同一种旅行

一条配置变更在 Contrail 里会依次走过**三张结构相同的网**：

1. **control-node 的 IF-MAP 网**：图变更到达 → **DependencyTracker 按策略递归展开依赖**（"我引用的对象变了，所以我脏了"）→ 推 ConfigDeltas → BGP 计算；
2. **对每个 agent 的 interest 网**：**GraphWalker 计算这个 agent 关心的可达子图**（"interest graph"）→ 切出来发 XMPP；
3. **agent 内部的 DB 网**：更新进 **oper DB**（`src/db` 框架的 DBTable/DBEntry）→ **表间依赖触发**（route→nexthop→interface…）→ kstate 同步进 vrouter。

**一句话**：**Contrail 到处是同一种三件套——"表 + 依赖图 + 自动传播"**：IF-MAP 是图、DB 框架是图、agent oper 层还是图。

## ② 链路走查（file:line 级）

### 跳 1：`src/db/`——放在仓库 **根**下的"数据库引擎"

`find src -name "db_table.h"` 的答案揭示结构：**`src/db/db_table.h` / `db_entry.h` / `db_graph.h`**——**不在 agent 里，在仓库根**：control-node 的 IF-MAP 与 agent 的 oper **共用同一套 DB 框架**（佐证：`ifmap_dependency_tracker.h` 顶部就是 `class DB; class DBGraph;` 前向声明——IF-MAP 自己就架在这套 DB 上）。

机制四件：**表（DBTable）+ 条目（DBEntry，带 StateMachine 状态机做生命周期与变更通知）+ 依赖图（DBGraph：谁引用谁）+ 消费者注册**。**"共用"的两侧证据**：control 侧——IF-MAP 以 `class DB/DBGraph` 为底（前向声明）；agent 侧——`cmn/agent_db.h` 定义 `AgentDBEntry`/`AgentDBTable`（:11-12）且 `AgentDBState` 继承 `DBState`（:70-74 构造实证）——**基类在 src/db，agent 只做派生**。而直接吃 `src/db` 的还有两个共享框架：**`src/route/`（路由表框架）与 `src/ksync/`（落核框架）**（include 清单实证）——**"层蛋糕"比第 6 课看到的更厚**。

### 跳 2：ifmap 深水——"策略驱动的依赖"与"interest graph"

`src/ifmap/ifmap_dependency_tracker.h:20`（原文）：

> The DependencyTracker **recursively evaluates dependencies as specified via a policy** and pushes additional ConfigDeltas to the ChangeList. This takes the burden of dependency tracking away from the consumers and **automates it instead of being individually hand coded for each type of object**.

——注意这句的反面：**依赖关系本身是数据（策略），不是代码**。对比第 5 课 OVN 的 `engine_add_input`（图是**硬编码在代码里**的）：**"依赖图的数据化程度"是一条频谱**——OVN 在一端（代码里、编译期固定），Contrail 在另一端（策略文件里、运行期可配）。

`src/ifmap/ifmap_graph_walker.h:22`：

> Computes the **interest graph** for the ifmap clients (i.e. vnc agent).

——配套类型 `ReachableNodesSet` / `ReachableNodesTracker`：**为每个客户端算"你该看见哪些节点"**——这就是第 6 课 README 说"选子图"的执行体（548 行的 `ifmap_graph_walker.cc` + 228 行的 dependency_tracker.cc；图存储 `ifmap_table.cc` 83 行 + `ifmap_node.cc` 143 行——图框架本身很薄，**机制全在"跟踪与切分"上**）。

### 跳 3：BGP 入口——"图进、路由状态出"

`src/bgp/` 是完整 BGP 引擎（aspath / attr / evpn / export…**140 个条目**，计数实证）；**配置图 → BGP 的桥**是 `class BgpIfmapConfigManager`（`src/bgp/bgp_config_ifmap.h:468`，继承 `BgpConfigManager`）：消费 IF-MAP 的 ConfigDeltas，维护"路由实例（RoutingInstance）/ BGP 邻居"的**配置状态机**。第 6 课说"factory.cc:9 注册 BgpIfmapConfigManager"——这里就是它的类本体：**图的变更从这里变成 BGP 世界的状态迁移**。

### 跳 4：agent 侧——oper 世界、resync 与 kstate

- **收**：`controller/controller_peer`（第 6 课已读：`AgentXmppChannel@46`/`SendUpdate@54`/`IsBgpPeerActive@66`）；
- **落**：`oper/` 是 agent 的"路由世界"——`agent_route.cc`（路由表）、`agent_path.cc`（路径）、`agent_route_walker.cc`（走遍全世界的工具）；更新经 `cmn/agent_db.h` 的 **DBTable + 依赖图**传播（下一跳变 → 引用它的路由被触达）；
- **对齐**：**`oper/agent_route_resync.cc`（38 行）**——"resync"再次现身（"增量+全量"方程第 N 次）；长驻 agent + 不可靠 XMPP 流 = 必须能事后对齐；
- **进内核**（写读两条路，R1 勘误后）：
  - **写/同步 = `src/ksync/`（KSync 框架，仓库根）**——`ksync_entry.h` / `ksync_object.cc` / `ksync_netlink.cc`：**每个 oper 对象对应一个 ksync 对象，经 netlink 落 vrouter**；且它同样直接吃 `src/db` 框架——`ksync_entry.h` 顶层就 `#include <db/db_entry.h>`，卫哨 `ctrlplane_ksync_entry_h` 与 `ctrlplane_db_graph_h` **同族命名**（"控制面框架家族"的自我定位）——**"模型→内核"的通道本身也是共享框架**；
  - **读/展示 = `kstate/` 族**——每类内核对象一个文件（flow / interface / forwarding_class / drop_stats…），供 CLI 查"内核里的实况"：**"模型 vs 实况"对照中的"实况"一侧**（与我们 Inspector 同题）。

## ③ 设计推导（问题树）

**Q1："三张网"的共性一句话？**
都是"**声明关系 + 框架自动传播**"——数据结构很薄（83 行的 ifmap_table、143 行的 ifmap_node），机制全在"**跟踪变化、找全受影响者**"。这与第 5 课"增量引擎的真难点是'该重算什么'"完全同题——三种载体：Contrail **策略**（DependencyTracker）/ OVN **代码**（engine_add_input）/ felix **计算图**（calc）。

**Q2：DB 框架为什么放在仓库根、两边共用？**
control-node 与 agent 面对同一类问题（表+依赖+通知）：一套框架两处用 = **语义统一 + 人力复用**（对照：我们控制面 ZK 树与端侧 state 是两套异构机制——复用度低、但各自简单。又是那个熟悉的取舍）。

**Q3：为什么依赖要"数据化"（policy）？**
依赖写错的两个方向都致命：**少写** → 该重算的不重算（静默脏）；**多写** → 重算风暴。做成策略 = 可审计、可演进、可归因（改了哪条依赖导致行为变）。对照 OVN 的 `change_handler=NULL` 就是"这条依赖我们不打算跟踪"的显式投降——**两份代码对同一个问题的两种诚实**。

**Q4：oper / ksync / kstate 三层各管什么？**
oper=意图/结果模型，**ksync=落核通道**（共享框架），kstate=实况读取面——三者之比就是"desired vs actual vs 通道"（报告制味道）；与第 10 课 cilium 的"BPF map vs 内核行为"、第 1 课 kube-ovn daemon 的 FDB 同步同族：**每个 agent 都需要自己的"模型 vs 实况"对账面 + 落核通道**。

**Q5：深潜收官的战略 takeaway？**
Contrail 的设计母题 = **一个 DB 框架 + 一组策略驱动的图 + 自动传播**；kube-ovn 母题 = **CRD + OVN（分发外包）**；我们母题 = **ZK 树 + 快照 + 对账**——三者是"**控制面 = 数据模型的传播系统**"的三种实现，各在"依赖载体 / 传播机制 / 对齐姿态"上占一隅（见对照卡）。

## ④ 对照卡

| 维度 | Contrail（深潜） | OVN（第 5 课） | kube-ovn（第 1 课） | 我们 |
|---|---|---|---|---|
| 依赖载体 | **策略声明**（DependencyTracker） | 代码（engine_add_input） | CRD watch（K8s runtime） | 约定（ZK 路径 + 客户端） |
| 子图/过滤 | **interest graph**（GraphWalker） | per-chassis 过滤 | OVN 原生 | 分区 ZK |
| 内部模型 | **共用 DB 框架**（src/db：表+状态机+依赖图） | SB（集中） | NB/SB | agent state |
| 对齐 | resync（`agent_route_resync.cc`） | 全量重算 | reconcile | 对账（differ/account） |
| 一句话 | **表+依赖+传播的极致复用** | 两跳编译 | 分发外包 | 树+快照+对账 |

## ⑤ 验收题

1. "依赖图的数据化程度"频谱：Contrail（策略）/ OVN（代码）/ felix（计算图）——更新成本与灵活度各在哪端？
2. `src/db` 放仓库根、被 control-node 与 agent 共用——这种"框架共用"的收益与代价？和 tf-vrouter 的"一核多壳"是同类思想吗？
3. 依赖"数据化"为什么值得？依赖写错的两个方向（少写/多写）各会怎样——对照 OVN 的 `change_handler = NULL`。
4. 把"模型 vs 实况"三例摆齐（Contrail kstate / cilium map-内核 / kube-ovn FDB）说共性。
5. 收官题：一句话分别概括 Contrail / kube-ovn / 我们 的"控制面母题"。
