## §1 例：看它干了什么（编号走查）

**真实场景**（VPC 5154392，2021-10-21）：用户要求"**有 EIP 的子机走 EIP 直出，没有的走子机网关**"，于是加了一条默认路由。它的一生：

```
① 用户动作（操作日志 TVPC.AddRtbRoute）：
     rtbId=1386764, uniqRtbId=rtb-phaplgmm, vgwType=10(EIP优先)
     vgwIndex=5154392, uniqVgwIndex=vpc-rpc088bl, preference=10
     uniqRtbRouteId=rti-ddzq0spf, reqId=12582_eflz4zy4
② DB 落行（t_rtb_route）：rtbRouteId=815911, vpcId=5154392, bUseVgw=1 ...
③ ZK 树变化：/TVPC/RTB/rtb-phaplgmm/0.0.0.0|0
     ├─ 11.71.172.145:0.0.0.0:10.0.1.17    # 子机网关路由（已有）
     └─ EIPPRIORITY                        # 本课新增的节点
④ 母机 11.26.140.168 的转发表（/proc/net/tvpc/5154392/subnet_route）：
     0.0.0.0/0.0.0.0/0  type=6              ← 本课新增（EIP 优先）
     0.0.0.0/0  type=0 → 11.71.172.145 ...  ← 旧的子机网关路由，两跳并存
     生效规则：vhost 表非空 → 走 type=6（EIP 直出）；为空 → 走 type=0（子机网关）
⑤ 抓包证明改道（EIP 直出路径）：
     外层 IP:   11.26.140.168 → 9.27.88.133（TGW 的 TSVIP，而非子机网关母机）
     GRE Key:   0x004ea658
     GRE Seq:   167772162   = 10.0.0.2 的整数表示（0x0A000002）
     内层 IP:   106.52.208.59(EIP) → 8.8.8.8
```

**一句话**：用户加的是"一条路由"，而系统交付的是"**一张表的行 + 一个 ZK 节点 + 一条内核表项 + 一条改道的抓包**"——中间隔着十个环节。

## §2 骨架：十跳地图 + 地板

```
1 控制台/云API → 2 vpc-cgw(鉴权/协议翻译) → 3 sdn_oss(Saga+DB+Outbox)
→ 4 Ckafka(binlog) → 5 nfv-proxy(消费→写分区ZK + 更新CRS快照) → 6 分区ZK(/TVPC 树)
→ 7 agent-broker(母机侧聚合) → 8 vpc_agent(本地态→diff) → 9 netlink → 10 内核/DPDK(抓包可见)
```

**地板（分解公理，【推导】）**：十跳拆到底 = **5 个存储**（DB 行 / ZK 节点 / Kafka 流 / K-V 快照 / 内存 dict+内核表）+ **2 个算法**（版本比较、diff）。其余都是工程。

## §3 机制：四棵五段式小树【推导】

> 每棵树格式：Question → Naive → **BUT（死亡现场）** → Therefore（被迫设计）→ Cost。楼层：L0 物理 / L1 数学 / L2 运行时 / L3 领域不变量 / L4 经济取舍。

### T1 为什么不能直写内核？
- **Naive**：控制台拿母机列表，直接 netlink 写。
- **BUT**：这条路由要落到"子网内每台有 VM 的母机"——N 台；母机每天重启/抖动，直写=写过的就丢；3 台里漏 1 台=流量黑洞，而且**系统自己不知道**（无重试、无对账）。
- **Therefore**：只写一个权威处（DB），其余全部是副本（ZK/Kafka/本地态/内核）；副本坏了能重建。
- **Cost**：多一跳延迟（分钟级）+ 最终一致窗口。｜楼层：**L3**

### T2 为什么先写 DB，不直接写 ZK？
- **Naive**：直接创建 ZK 节点。
- **BUT**：ZK 树不支持多节点事务回滚（改多处、改一半失败谁收拾？）；用户超时重试=重复写；"我的 VPC 有哪些路由"这种查询 ZK 树做不了。
- **Therefore**：DB=Source of Truth；投递用 **Transactional Outbox**（DB 事务内同写变更日志表——25 张 Outbox 表；异步投递进程重试，卡在"发送中"的在途记录由 Mediator 周期重置——见 Gen2 系列 02 章）。
- **Cost**：DB↔ZK 之间出现"短暂不一致"窗口 → 需要 **DB↔ZK 对账子系统**兜底。｜楼层：**L3**

### T3 为什么中间要 nfv-proxy？
- **Naive**：母机直连 DB / 直连 Kafka。
- **BUT**：① 一台母机绑几百个 VPC，但 **85-94% 是冷数据**（没有运行中的 VM）——全推=浪费；② 十万级母机直连 DB=连接数/QPS 爆炸；③ 新母机上线/重启需要"当前全貌"，而 binlog 流**没有起点**（只有增量）。
- **Therefore**：nfv-proxy 加工——binlog → **分区 ZK**（`(vpcId%500)%15` 分片，15 个 VPC worker + 1 个 GlobalWorker）+ **CRS 快照**（全量，50000 条/片）；母机冷启拉快照、增量追 binlog。
- **Cost**：多一个专用进程组（14 类子进程）；ZK 存 binlog 的膨胀（group 机制/12h 窗口约束）。｜楼层：**L0 规模 + L1 放大**

### T4 母机收到变化，为什么先落本地再下发？
- **Naive**：watch 回调里直接写内核。
- **BUT（死亡现场）**：① 这条路由在母机上的"期望态"是**拼出来的**——`type=6` 与 `type=0` 两条并存，谁生效取决于 **vhost 表是否非空**，单条消息决定不了下什么；② agent 重启要重建全量；③ 内核写会失败、且**不能回滚**。
- **Therefore**：agent 维护本地模型（内存态/落盘）→ diff → 下发；失败重试 + Inspector 对账（周期 10s×6）；内核只当"最终输出"。
- **Cost**：双份状态（本地模型+内核）+ 对账工程。｜楼层：**L3**
