## ① 它干了什么——从一个"带事故味"的日常动作说起

**ZK 数据清理**这件小事，材料里写着这样一段（43）：定时调 `tools/zkCleanupSafe.sh` **安全包装脚本**执行 `PurgeTxnLog`——为什么要"包装"？因为直接跑会踩坑："**规避主服务 java.env 中 308G ZGC 等 JVMFLAGS 导致子进程启动失败**"。包装脚本还带**角色白名单、fail-fast 配置校验、灰度验证**。

**一句话**：**我们连"删 ZK 日志"都不敢裸跑**——因为 ZK 是我们的分发中枢，围绕它的每个动作都被"当生产代码写"：监控（怎么看）、备份（怎么存）、对账（怎么验）、同步（怎么搬）、管控（谁下令）、清理（怎么删）。

## ② 链路走查（七件，材料行号）

### 跳 1：定制双树——"核外任意，核内有边界"

- **31 同步器版**（3.4.6 + 128 定制提交）：主→从集群**binlog 式增量 + 全量同步**；生命周期由**自创四字命令**（`syld/syst/sypa/syfi/sysi/syss`）远程控制——第 4 课读过的"observer→跨集群同步器"改造，这里看到它的**运维接口**。
- **32 定制版**（3.5.6 + 约 60 提交）四大能力：① **zxid 进位安全**（`ZxidUtils.AtomicZxid` 原子 zxid + epoch 更新与选举配合——规避低 32 位计数器**进位**引发的集群异常）；② **只读 Observer**（`writeablePaths.N` 白名单 + `readonly.enabled.if.observer`，配套自创四字命令 **`ldcf/qucf`**）；③ **兼容混部**（修正选举消息格式判断 → 3.5.6 节点可加入 3.4.4 集群——灰度升级的技术基础）；④ 运维配套（Kona JDK11+ZGC+大页、按内存自动 Xmx、myid=IP 整数生成）。

> 第 4 课的 `fix/zxid_counter_extend`（"跳过特殊值"，未合入）与这里的 `AtomicZxid`（改进位逻辑）是**同一课题的两条解**——一个在补丁层躲、一个在内核层修。**"改得动什么"的边界再次显形：共识内核类逻辑要么不改、要么改透。**

### 跳 2：备份（30）——"转储"里的工程细节

`snapshot/txnlog → COS` 的定期备份，材料里全是细节：bucket 命名规则 `${region}-vpc-${zkType}-${appId}`、COS 目录**10 天归档 / 30 天删除**、**leveldb 记录已迁移项**（断点续传精神——与第 1 课 CVpcSyn 的 checkpoint 同族）、随包 KonaJDK；项目本身是**腾讯云 COS 团队的迁移工具改造而来**（原"本地→COS"能力被改成"SSH 拉 ZK 数据→COS"）——**工具复用**的又一例。

### 跳 3：对账（46）——"连数据库本体都自己对账"

`vpc_zk_differ`：官方 3.4.6 源码树 + 自研 Java 服务。两大主入口（`bin/service.sh start {snap|txn|all}`）：

- **SnapLogDiffer**（快照对比）：读两侧 snapshot+txnlog **重建内存数据树**，多线程逐 znode 比对**数据 / ACL / stat / 临时节点归属**，**必要时回查远端在线 ZK 二次确认**（防误报！），输出差异 JSON + 告警（`Main.java` 只打印 "please specific the main class"——真入口由 maven profile 指定）；
- **LogDiffer**（事务日志对比）：txn.log 解析成 `ComparableRequest` 列表（**multi 拆分、跳过临时节点创建**），按 **zxid 顺序**比对；
- 配套：ACL 风险规则分析器 / tvpc 路由值分析器 / **SnapLogTruncater**（截断到指定时间点，构造"干净"数据集——第 4 课 Step3 见过的工具）。

### 跳 4：监控（45）——"监控面覆盖自己人"

`vpc_monitor`（Python2，自研 epoll poller 框架）：采集对象 = **ZK 四字命令（mntr/srvr/conf/cons）+ jstat GC + 连接数 + 主从角色与选举 epoch + 持久化文件状态 + 写时延探测 + 机器指标**——而且**连同机配套组件（synchronizer/differ/cos_bak/account/zknode）一起监控**：**监控面覆盖自己人**。上报 barad/CMEM，阈值/收敛告警（星云）。核心工具三件：`collect/zk_stats.py`（四字命令解析、jstat GC、告警封装）→ `zk_mntr_stats.py`（znode/watch/延迟/收发包）→ `zk_srvr_stats.py`（leader/follower、连接数）。

### 跳 5：管控与执行（44/43）——"谁下令、谁动手"

- **zk_controller（进程名 `zk-mgr`）**：**集中管控面**——REST 管 component / cluster / zk_node / zk_pool / client；对外提供 **"就近 zk 节点"查询**（供 `vpc_agent`、`vpcgw_vpc_agent`、`dfw_api` 们回答"我该连哪个 ZK"）——**白名单是个代码常量**：`CLUSTER_NEARBY_CLIENT = [vpc_agent, vpcgw_vpc_agent, vpcgw_vpc_agent_bak, dfw_api]`（`zk_controller/api/v1/zk_node.py:110`）；另有演进版通道 `/zk_nodes_nearby/{client}/rsync_to_db`（`zk_pool2.py:112`）。Python2.7 + Falcon + SQLAlchemy + uWSGI。
- **zk_agent**（Go 1.19，gin+gRPC 单口 8383）：数据面执行者五职责——① **安全组**：serviceSg → iptables+ipset（`ZK_INGRESS_QUORUM / ELECTION / CLIENT` 链护 2888/3888/2181）；② **限流**（连接总数 / 新建速率 / 突发，limit.cfg）；③ **程序管理：启停整个运维族**（zknode/zk_alarm/zk_monitor/differ/syncer/cos_bak——**总开关就是它**）；④ 设备初始化（规则持久化）；⑤ **数据清理**（本课开场的 `zkCleanupSafe.sh`；且它**随二进制一起发布**——`cmd/dist_pkg.sh:72` 的平铺 tar 包 = `./zk_agent` + `./tools/zkCleanupSafe.sh`）。

## ③ 设计推导（问题树）

**Q1：为什么"养 ZK"要七件套？**
分发中枢 = 全系统风险面："**用 ZK**"和"**养 ZK**"是两门手艺。四道防线：**监控（发现）→ 备份（兜底）→ 对账（验证）→ 同步（转移）**，外加定制（进化）与管控（指挥）。

**Q2：differ 的粒度为什么是"znode / 事务级"？**
它对的是"**数据库本体**"，比业务对账低两级——**对账层级越低，越接近真相、也越贵**（重建数据树 + 回查在线确认的成本）。三层对账谱系在此成型：**znode 级（differ）→ 语义级（业务 account）→ 报告级（平台）**。

**Q3："就近 ZK 查询"为什么值得一个管控面？**
**接入点即路由**：客户端不需要知道 ZK 拓扑，只问"我连谁"——这是"**控制面的目录服务化**"（对照 cilium ipcache / kube-ovn 的 node-local DNS 同族）。

**Q4：`zkCleanupSafe.sh` 的故事说明什么？**
**运维脚本也是生产代码**：308G ZGC 的 JVMFLAGS → `PurgeTxnLog` 子进程启动失败 → 于是有"包装脚本 + 角色白名单 + fail-fast + 灰度"四件套。**越核心的系统，"删日志"越要仪式感**。

**Q5：定制（31/32）与运维（30/43-46）的分工？**
**定制在核内、运维在核外**：核内改动必须"改透"（zkid 进位就上 `AtomicZxid`，不是打补丁）；核外可以任意堆叠（七件套）。这正好回答第 4 课留的边界题——**共识内核：要么不改、要么改透；周边：尽情生长**。
