## ② 链路走查（材料行号）

### 跳 1：为什么必须 Event-Driven——三模式对比（event-driven §一）

**RPC 同步链**（§1.1）——四个死穴：**链断**（"一个环节挂全链路断"）／**无持久化缓冲**（"调用失败 = 消息丢失"）／**紧耦合**（"API Server 必须知道下游的所有组件"）／**不可扩展**（"增加消费者需要改 API Server 代码"）。

**Kafka 事件总线**（§1.2）——五个优点：**解耦**（"API Server 只写 Kafka，不关心下游"）／**持久化**（"消费者挂了重连从上次 offset 继续"）／**多消费者**（"同一个 binlog 被 Fusion/Broker/Audit 独立消费"）／**可扩展**（"增加消费者 = 新增 Consumer Group"）／**可重放**（"从 offset=0 重放全量（**冷恢复**）"）。

**为什么不能只用 tRPC Stream**（§1.3）——push 模型需要消费者在线："**Agent 离线 1h → Broker 内存积压巨大 → OOM**"；Kafka 是 pull + 持久化。（第 19/23 课从"怎么重连"角度讲过；这里是"**为什么架构必须双轨**"的角度。）

### 跳 2：不设 partition key 怎么保序——"快照矫正"（ordering-idempotency §一）

**源码真相**（§1.1，`producer.go:213-217`）：

```go
record := &kgo.Record{
    Topic: msg.Topic,
    Value: value,
    // 没有 Key 字段。—— Kafka 使用默认分区策略（round-robin）
}
```

→ "**同一个 VPC 的 binlog 可能分布在不同的 partition——跨 partition 没有顺序保证**"。

**乱序会怎样**（§1.2）：`[DELETE route X]` 与 `[CREATE route X]` 分落两个 partition，两种到达顺序 → 情况 B（CREATE 后到）**最终态错误**。

**为什么没出事**（§1.2/§1.3 三层保障）：

1. **概率**："同一个 VPC 的同一个配置类型——连续 CREATE→DELETE **极少**"；
2. **时间戳**：binlog 携带 `GenericCommonHeader.ts`——**但材料诚实注记**："**当前没有做 timestamp 比较**——只是 write-through `LevelDB.Put`"；
3. **快照矫正**（真正的底）——"binlog 路径（实时，可能有乱序）：`LevelDB.Put` 覆盖写入——**不在乎顺序**；快照路径（定期，保证顺序）：**从 DB 加载全量配置（正确顺序）→ PrefixScan 覆盖旧 LevelDB 状态 → 合并最近 binlog 增量 → 生成新快照**"。

**一句话**："**binlog 路径可能有乱序——但快照路径'矫正'了——全量 DB + 增量 binlog**"——"**增量+全量方程**"的又一次现身，**这次是从反面讲**：全量不只是"启动兜底"，还是**秩序的定期恢复者**。

### 跳 3：背压——从 Producer 到 Agent 的全链路（backpressure §一）

**Producer 侧：Channel Buffer 背压**（§1.1，`producer.go:52-53/187-189`）：

```go
mqChan = make(chan *common.MqMessage, config...ProduceQueueSize)  // 默认 5000
func SendMsg(msg) {
    mqChan <- msg   // 满了就阻塞！
}
```

**材料原话**："`SendMsg` 阻塞 = 调用方（API Server / Fusion internal）被限流——**这是自然的背压——不需要显式的'限频计数器'**"；代价："调用方线程被阻塞——可能影响其他操作"；缓冲区算术：**5000 条 @ 10/s 的 Publish 速度 → 吸收 500s 的突发**；"**但不会无限增大——5000 是上限**"。

**与第 17-19 课的背压线合看**：那几课是"消费侧"的背压（`unackedEvicted`/`MaxPendingVersions`/三级队列）；这里是"**生产侧**"的背压（channel 满则阻塞源头）——**一条链的两端各有一个"不许无限接单"的闸**（Producer 侧还有"发送失败 → 重试 + 错误累计超阈值切换实例"的 §1.2 机制，见下半篇）。

### 跳 4：一致性——五层存储的"版本语义地图"（consistency §1.1）

立论句（首行）："**控制面的本质 = 在多级缓存之间传递'什么是正确的配置'**"。五层全景（每层带版本语义）：

| 层 | 版本语义 | 特性 |
|---|---|---|
| **L1 MySQL CDB（SoT）** | 事务性 INSERT/UPDATE/DELETE——隐式"最新版本" | p50 ~5ms/p99 ~20ms；**半同步复制 SLA 99.95%** |
| **L2 Kafka** | **offset 递增**（唯一 offset） | 持久化/可重放/**partition 内 FIFO**；ISR=3 |
| **L3 Fusion LevelDB** | key-value——**每次 Put 覆盖** | 本地 SSD p99<1ms；**快照合并完成后删除——临时工作区** |
| **L4 t_generic_snapshot** | **snapshot version 递增**——"Broker 可判断是否需要拉新版本" | MySQL+Redis 双写；60s + 事件触发 |
| **L5 Broker BTree** | **无版本**——"崩溃后从 Layer 4 重建" | 纯内存；重启丢失 |
| Agent LevelDB + DPDK | Agent 本地持久化缓存 / **DPDK = 实际生效转发表（actual state）** | —— |

**读法**：一致性不是一句 CAP 口号——是**五层各自的"版本语义"拼成的一条链**：有的层靠事务、有的靠 offset、有的靠版本号、有的干脆"无版本可重建"。**"什么是正确的配置"= 这条链上每一层都能回答自己的那个版本。**

### 跳 5：状态与并发三题——状态机 / 原子性 / 脑裂（state-machine / concurrency-atomicity / partition-splitbrain）

**① 任务状态机 5 态**（state-machine §1.1，源码 `common/task.go:8-16`）：`pending / processing / completed / failed / timeout`；合法转换标注了**代码位置**（`ClaimTask task_dao_impl.go:174` / `CompleteTask :233` / `FailTask :261`）——"面试官要你**画出转换图并指出每条的源码行**"。**转换的原子性真相**（§1.2）："Pending→Processing：**无原子性——ClaimTask 用 Pipeline（非原子，但单 Worker 单任务——实际无冲突）**；Processing→Completed/Failed：同样 Pipeline"；**非法转换防止**："代码中检查当前状态——**已完成/失败的任务不会被重新 Claim**"（"Status != Pending 就跳过"）。

**② 原子性方案：Pipeline 为主、Lua 为辅**（concurrency-atomicity §二/§三）——**六行对照表**：

| | go-redis Pipeline | Lua 脚本 |
|---|---|---|
| 原子性 | ❌ 不保证（命令独立执行） | ✅ Redis 单线程原子 |
| 条件判断 | ❌ 不能 | ✅ 可做复杂逻辑 |
| 开发/调试 | ✅ 简单 | ❌ 内嵌字符串/内部执行 |
| Redis Cluster | ✅ **自动重定向不同 slot** | ❌ 必须同 slot |
| 适用 | 普通业务操作 | **"读+判断+写"原子** |

**"Lua 只有 3 个"**（§2.1）：优先级队列原子取出（`ZREVRANGE+ZREM`）／分布式锁释放（`GET+DEL` 值校验）／分布式锁续约（`GET+PEXPIRE` 值校验）。**结论**（§3.1）："PublishTask 只是写数据——不需要原子；**ClaimTask 的'优先级检查+取出'才需要 Lua——因为要'读+判断+删除'原子**"。**为什么没有 Hash Tag 也不担心跨 slot**（§3.2）：Pipeline 命令自动重定向 + 每个 key 独立哈希 + **3 个 Lua 只操作单个 key——天然同 slot**；**没有 TxPipeline 的原因**（§3.3）：源码直接用 `Pipeline()`——"TxPipeline 在 Redis Cluster 下跨 slot 会 EXECABORT"。
**L3 边界的诚实**（§4.1）：**Requeue 用 Pipeline 做三步（ZRem→RPush→Expire）——非原子**："Worker crash 在 1 之后、2 之前 → 任务从 processing 删了、没放回队列 → **任务丢失**"；选它的理由："Requeue 不常见（只在重试时）+ 幂等可恢复"。**唯一的"必须 Lua"**（§4.2）：锁续约——"值匹配"原子；**不用的后果**："GET → 判断 → PEXPIRE 三步分离——**中间被别人抢了锁 → 给别人的锁续约 → 脑裂**"。

**③ 脑裂与选举源码**（partition-splitbrain §1）：`SetLeader` = **SetNX + JSON 编码的 LeaderInfo**（`{NodeID, ElectedAt, ExpireAt}`）；参数：**TTL=10s / RenewInterval=3.3s（TTL/3）/ CheckInterval=30ms**（"**非 Leader 检查频率——高频检查能否成为 Leader**"）；**Lua 续约**（`cjson.decode` → `node_id` 校验 → set+pexpire）——"**只有我自己能续约**"。**④ Fencing Token——"为什么不加，如果加怎么加"**（§三）：**是什么**——"单调递增的 epoch……所有写操作都带 epoch——**低的被拒绝**"（"即使旧 Leader'复活'——它的写操作自动被拒绝"）；**为什么没做**（§3.2"**不是忘了——是当前的风险可管理**"四条）：① **TTL=10s 足够短**（旧 Leader 写窗口仅 10s）② **幂等兜底**（快照/对账幂等，重复无害）③ **`CompleteTask` 有 workerID 校验**（"旧 Worker 的 CompleteTask 被拒绝"——第 21 课 Ownership 的认领）④ **对账检测**兜底；**代价分析**："不加=每次写少 1 次 Redis GET（开销可忽略）；加了=防'双主同时写'的 corner case——但**触发概率极低**"——"**这是 pragmatic 选择：不是最优设计——但在给定约束下收益-成本比不高**"；**如果加**（§3.3）：Redis 新增 `fusion:epoch:{electionKey}`（INCR）+ 当选时**同一 Lua 里 SETNX leader + INCR epoch** + 写操作带 epoch 校验。（§2.2/2.3 前置场景：Redis 全分区→两侧各自选主各自干活→恢复后 Side B 降级、**其写入丢失**→"Recovery 看到 task-51~100 的 heartbeat 过期→Requeue"——**这组场景就是"不加 fencing 时对账+Recovery 兜底"的实测推演**。对照第 30 课九件事"中期方向：Leader Fencing Token"——同一条债，两处材料同时记着。）

### 跳 6：恢复与降级三题——冷启动 / 容错 / 降级（cold-start / fault-tolerance / graceful-degradation）

**① 冷启动 vs Crash Recovery——用状态，不用猜测**（cold-start §一）：`ConfigState` 四态——`UNKNOWN → INITIALIZING → INITIALIZED → SNAPSHOT_AVAILABLE`；**材料金句**："**冷启动的判断不是'检查 LevelDB 是否为空'——是通过数据库中 ConfigState 表的状态字段判断。这是一个更可靠的设计——状态持久化在 MySQL 中，不依赖本地状态**"（判断入口：`initconfig/leader_service.go:271-322`）。**三分支**：`UNKNOWN`→冷启动（发布 init task→全量→快照）；`INITIALIZED/SNAPSHOT_AVAILABLE`→crash recovery（查队列：有 processing 且 **Lease 过期→Recovery+Requeue**，队列空→正常发新任务）；`INITIALIZING`→**查 Lease**（过期=重初始化；未过期=等）。

**② 故障四分类**（fault-tolerance §1.1）：

| 类别 | 例 | 检测 | 恢复 | 时间 |
|---|---|---|---|---|
| 进程级 | Worker OOM / Agent crash | Watchdog + K8s health | 自动重启 | < 30s |
| 组件级 | Fusion Leader / Broker 宕机 | 选举 + 多副本 | 自动选举/切换 | < 10s |
| 基础设施级 | CDB / Kafka Broker 宕机 | 监控 | 自动 failover | < 30s |
| **系统性 Bug** | **DeleteConfig Put(nil)** | **对账发现差异** | **人工确认 + 代码修复** | 数小时-天 |

**第四类是哲学题**：前三类靠"守护/选举/failover"，**只有第四类靠对账**——我们唯一没有自动化解法的那类故障，恰好只有对账能发现它。P0/P1/P2 原则（§1.2）："**P0 挂了→整个 Region 停止→不能降级→只能等恢复**；P1→部分功能降级，**恢复后对账 + Recovery 补差异**；P2→自动恢复无感知"。（Lease+Heartbeat+Recovery 源码验证：`lock_service.go:239` `Expiration=30s`。）

**③ 依赖分级全量表**（graceful-degradation §一，七行原文）：

| 依赖 | 级别 | 降级行为 | RTO |
|---|---|---|---|
| MySQL CDB | P0 | **不降级**——API 返回 ERROR | < 30s |
| Kafka | P0 | **不降级**——API 返回 ERROR | < 5min |
| Redis | P1 | **快照/对账暂停，binlog 继续** | < 5min |
| Fusion Leader | P1 | 自动选举（SET NX） | < 10s |
| Fusion Worker | P2 | Recovery Requeue | < 30s |
| Broker 单例 | P2 | 自动切别的 Broker | < 10s |
| 单个 Agent | P2 | Watchdog 重启 | < 30s |

**Redis 降级——精确到每个动作**（§二"什么停、什么继续"）：继续 ✅——Kafka binlog 消费／LevelDB 读写／Broker Watch+push／Agent DPDK 写入（"不依赖 Redis"）；暂停 ⚠️——快照/对账/清理/新选举（需要 PublishTask 或 SET NX）。**精妙一笔**："**当前 Leader 续约 ← 本地状态续约——不需要 Redis**"。**用户影响链**："创建 VM：DB ✅ Kafka ✅ Fusion 消费 ✅ LevelDB ✅……"——**降级不是组件级开关，是动作级的清单**。

### 跳 7：观测与工程两题——指标 / 缓存 / 测试（performance-metrics / caching-strategy / testing-correctness）

**① 11 个子系统的指标全景**（performance-metrics §一）：命名规范 `vpc_fusion_{subsystem}_{action}`；每子系统三列（Histogram 耗时 / Counter 次数 / Gauge 实时值）——**两个 ⚠️ Gauge 标在"积压"上**：`distributed_task.queue_length` 与 `system.kafka_queue_length`。**面试实战法**——"从指标反推"两例：
- `kafka_queue_length 1000→50000`：四步推断（consumer 慢→查 binlog p99→查 lock p99→查 snapshot build）→"**最可能：DB 慢查询 → consumer 处理超时 → lag 增长**"；
- `reconcile diff 突增`：两个方向——"**DeleteConfig 类 bug？→ 大量 Redundant**"／"**Fusion 宕机？→ 大量 Missing**"。

**② 缓存的"物理约束论"**（caching-strategy §一）："**为什么是 7 层——不是设计选择，是物理约束**"（每层一句"必须"）；**"如果去掉某一层"代价表**：去掉 Redis→"多实例不能共享——不能分布式处理"／去掉 Fusion LevelDB→"**200 万次 DB 查询 = DB 压力 × 5000**"／去掉 snapshot→"Broker 需要 **SSH 到每台 Fusion 实例**——不可扩展"／去掉 Broker BTree→"**数十万次 DB 查询/秒——DB 不可用**"／去掉 Agent LevelDB→"母机重启后**数分钟**才能恢复转发"。**"每层不是'可选的'——是被物理约束强制存在的。"**（§二源码验证 `Release` 关闭+删除——与第 20 课闭环。）

**③ 测试金字塔与"三层防线全失败"**（testing-correctness §一/§二）：金字塔四层（单元 11 文件 Mock"**不覆盖对账怎么解读 nil**"／集成 18 文件 4000+ 行"**不覆盖跨模块语义对齐**"／E2E 9 文件"**不覆盖 kill-9 失效场景**"／压力 5 文件）+ 并发测试"50 goroutine + `-race` 全跑"。**DeleteConfig 复判**（§二，22 课事故的"测试视角"收官）：**单元测试 Pass（但不对）**——"验证了'Put nil 后 Get 返回 nil'——**这是 LevelDB 的正确行为；没验证'对账看到这条 nil 记录的行为'——对账不在单元测试范围内**"；**集成测试不存在**（"应该有的"三条：`delete→reconcile→diff=0` 等）；**E2E 没测跨模块语义**——**三层防线各守自己的语义，跨层语义无人认领**。**"如果重来"两招**（§三）：集成测试代码体——`delete→reconcile→diff=0` + **`LevelDB.Get(key) → ErrNotFound`**（"key 必须不存在"）+ TLA+ 验证"**Put(nil) vs Delete 的语义等价**"；**§四 kill-9 测试——实际没做**："集成测试用 `context.Cancel()` 模拟 Worker 停止——**非真实进程 kill**；CI 没有 kill-9 验证；灰度手动 kill——非自动化"（理想方案：Docker Compose 起全栈做 kill-9 自动化）。

## ③ 设计推导（问题树）

**Q1："面试官问 X，不是问 Y"这套句式的方法论价值？**
它把"名词"全部降维成"判决"：不是"你用了 Kafka"而是"**为什么必须**"；不是"有哪些指标"而是"**从指标能看出什么问题**"；不是"你写了测试"而是"**为什么没拦住**"。**这正是本课程 R1/R2 审查法的"出题人镜像"**——26 课的审查问的是"这条断言能不能对质"，这 13 篇的句式问的是"这套机制能不能自证"。

**Q2：一致性篇"5 层"与缓存篇"7 层"口径不一——怎么并记？**
两张图坐标系不同：一致性篇数的是"**配置真相链**"（CDB→Kafka→LevelDB→snapshot→BTree + Agent 附属）；缓存篇数的是"**缓存层次**"（把 Redis Cluster 与 DPDK 也算进去的七个"必须存在的层"）。**不是矛盾，是各自职能的两种切法**——引用时标明口径即可。

**Q3："物理约束论"最强的证据？**
"去掉某层"代价表——**"DB 压力 × 5000"／"Broker 需要 SSH 到每台 Fusion"／"数十万 QPS 直接打爆 DB"**。当"去掉一层"的代价是数量级的，层的存在就与品味无关：**架构是被物理逼出来的，不是被审美选出来的**（与第 1 课"约束不同，解不同"、第 30 课"约束决定架构"同一条公理）。

**Q4：测试金字塔的盲区与 22 课怎样闭环？**
每一层测试**只验证自己那层的语义**（单测验 LevelDB 行为、集成验组件交互）——**跨层语义（"对账如何解读 storage 的写法"）没人认领**，这就是 DeleteConfig 的三层逃生通道。后验对策在 30 课的表里已列出：E2E 补 `delete→reconcile→diff=0` + **TLA+ 对 3 个 Lua 脚本做 model checking**——**"跨层语义"要么用测试焊住，要么用形式化证明焊住**。

**Q5：Redis 降级清单里"当前 Leader 续约不需要 Redis"为什么精妙？**
因为续约的语义可以是"**本地状态续期**"（内存里的 lease 计时）而不是"再写一次 Redis"——Redis 不可用时，旧 Leader 还能凭本地状态撑过降级窗口，**避免"依赖一挂、王冠立刻落地、全员乱抢"的二次震荡**。**降级设计要精确到"每个动作依赖什么"**——组件级开关（"Redis 挂了就停一切"）会放大故障面。
