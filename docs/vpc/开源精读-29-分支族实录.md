## ① 它干了什么——四句话的提要

1. **db_dlock**：ZK 锁"抖动即雪崩"（第 28 课读过故障注入）→ 换成 **DB 锁**：容忍 2 次心跳、socket 5s、可 SELECT 可观测——**822 行换一个"不会全量自杀"的锁**；
2. **zxid**：ZK 的**事务 ID 只有 32 位 counter**——10 万 QPS 的集群**约 12 小时用完**（42.9 亿 ÷ 10 万）；溢出进位 → **误走 DIFF 而非 TRUNC** → 数据不一致/脑裂（**ZOOKEEPER-1277 经典 bug**）；分支把 counter 扩到 **40 位**（epoch 32→24）——**但未合入**：团队最后选了"跳过特殊值"的保守方案；
3. **skippath**：跨集群同步器（订阅源集群 txn log 回放）的 `skipSyncPaths` 配置**热重载时不清空旧集合**——旧路径残留 → "**不该同步的路径被同步**"（静默泄漏）；
4. **kafka_consumer**：`for record in kc` 是**无限迭代器**——topic 空闲时阻塞在底层 fetch，**让不出心跳**；进程活着、消费停了——用 **KafkaWatchdog**（600s 无心跳 → `daemon.suicide()`）把"假死"变成"真死给守护进程看"。

## ② 链路走查（材料行号）

### 跳 1：db_dlock——从"抖动即雪崩"到"可观测的锁"（db_dlock §一/§三）

**ZK 锁的四个核心问题**（§一原文表）：

| 问题 | 说明 |
|---|---|
| **ZK 集群故障=全量雪崩** | "listener 监到 LOST/SUSPENDED **立即 suicide**，ZK 集群抖动=所有 worker 同时死" |
| **session timeout 太长** | `timeout=400`（400 秒） |
| **ZK 集群运维成本高** | 独立 3 副本集群 |
| **锁状态难调试** | ZK 节点二进制，"需 zkcli 查" |

**DB 锁四答案**：容忍 2 次心跳失败（30s）／socket timeout=5s／**复用已有 CDB**／**可 `SELECT` 查锁状态**。

**核心实现**（§三）——**时间常量四件与一条不变量**：

```python
LOCK_TTL = 60s              # 锁过期时间
HEARTBEAT_INTERVAL = 15s    # 心跳间隔
HEARTBEAT_MAX_FAILURES = 2  # 2 次失败自杀（30s < 60s TTL）
CHECK_INTERVAL = 5s         # 排队轮询间隔
# 不变量: LOCK_TTL > HEARTBEAT_INTERVAL × MAX_FAILURES，即 60 > 30——留 30s 余量
```

**acquire 三步**（§3.2）：`_maybe_cleanup_expired()`（30s 一次清理，带 advisory lock）→ `_insert_lock_record()`（INSERT 行、heartbeat=0）→ **`_try_acquire_as_head()`：CAS 检查**（`SELECT min(lockId) ... WHERE heartbeatTime > NOW()-TTL`，是我就 `UPDATE heartbeat=1 WHERE ... AND heartbeat=0`）——**第 21/26 课"租约 + CAS"在 nfv-proxy 时代的纯 SQL 版**（异常体系：`LockAcquireTimeout / LockPreempted / LockDatabaseError`）。

### 跳 2：zxid_counter_extend——一个"未合入的正确修复"（zxid §一/§二/§三）

**zxid 结构**（§一）：64 位 = `epoch | counter`——"**修复前（32 位 counter）**"→"**修复后（40 位 counter，epoch 24 位）**"；ZAB 用它选 Leader（大者胜）与增量同步（`lastZxid`）。

**溢出故障链**（§二）：

```
counter 到 0xFFFFFFFF 后 +1 → 进位到 epoch → epoch 自动 +1，counter 归 0
1. epoch 自动 +1 但【实际没有 Leader 选举】
2. Follower syncFollower 检测到 counter=0 → 误判为"新 epoch 起始" → 走 DIFF 而非 TRUNC
3. 未提交的旧 epoch txn 被错误保留 → 数据不一致
4. 极端情况脑裂
```

**生产影响**："10 万 QPS 集群约 **12 小时**用完 32 位 counter（42.9 亿 ÷ 10 万）——每次溢出触发**全集群重选举 10-30 秒不可用**"；经典 **ZOOKEEPER-1277**。

**修复与结局**（§三 + 分支元信息）：核心改动 `COUNTER_BIT_WIDTH = 40L`（`ZxidUtils.java`）；**容量账**（§四）：counter 42.9 亿 → **1.099 万亿（256 倍）**，"**10 万 QPS 溢出周期：12 小时 → 4 个月**"；代价是 epoch 32→24 位（容量 1/256）；**方案演进里还有一版 48 位初稿被否**——"**epoch 太小，6.5 万次选举就溢出**"（位宽分配也是权衡）。——**但分支状态是"未合入 master——团队选了'跳过特殊值'方案"**（§五 两方案对比表）：`fix/zxid_counter_extend`＝扩展 counter 到 40 位、**❌新旧节点不能混合组集群** vs master 方案＝"保持 32 位，**跳过 0 和 0xFFFFFFFF**"、**✅完全兼容**、改动主要在 `ZxidUtils + Leader`。**"正确的修复"输给了"更省事的修复"**——工程现实的诚实记录（对照第 22 课：修复排序按急迫度；这里是按**兼容成本**）。

### 跳 3：syncer_skippath_fix——一个"静默泄漏"的修复（skippath §一/§三）

**背景**（§一）："sdn_oss 写 ZK，vpc_agent 读 ZK"；跨集群同步器（**vpc_zookeeper_3_4_6_synchronizer**）= "独立的 Java 进程，订阅源集群的 **txn log**，把事务回放到目标集群"。架构要素：**ObserverZooKeeperServer**（以 Observer 角色连源集群拿 txn 流）/ **CuratorConnect**（连目标写事务）/ **cachedRequestQueue** / **LeaderLatch**（多实例选 Leader，只有 Leader 同步）/ **remoteLastSeenZxid**（目标已见最大 zxid，只回放更大者）。**skipSyncPaths**：不需要同步的路径集合（如同步器自身管理路径 `/syncSlave/`），且有**前缀语义**（`path.startsWith(item)`——"父路径在 skip 中，子路径也跳过"）。

**Bug**（§三）：`parseProperties()` 热重载配置时——`skipSyncPaths.add(value)` **只加不清**（"直接往 skipSyncPaths 里 add，**没有先清空**"）——运维改完配置一热加载，**旧路径残留在集合里**：**该同步的路径可能被误跳（旧 include 残留）或不该同步的路径仍在跳**——一个"静默泄漏"（failure-mode-matrix 里写的"不影响业务但埋隐患"，第 28 课 Bug 回溯表第三行的正主）。**同分支还有第二个 feature——"追赶保护"**（§五，远端超时等待机制）：同步器接管/启动时要"从 `remoteLastSeenZxid` 起回放"，若源集群**跑得太快**（zxid 远超本地水位）会追不上——于是新增 `maxAllowedRemoteAheadDistance = 2000L`（**允许的落后距离**）+ `maxAllowedRemoteAheadWaitTime = 10000L`（**等待上限**），`checkRemoteAhead()` 在 `synchronizeStart()` 与 LeaderLatch 回调里裁决——**"追不上就等一会，等不了就失败，绝不放任无限落后"**（与第 17 课对齐条件"无版本空洞"、第 23 课水位判死同族：**水位差要有门限**）。

### 跳 4：kafka_consumer——把"假死"变"真死"（kafka §一/§二）

**旧消费循环的病**（§一）：

```python
for record in kc:          # 无限迭代器——topic 空闲时阻塞在底层 fetch
    msg = loads(record.value)
    zk_adapter(msg, zk, self.proxy_info)
    kc.commit_async()
```

"**无法让出控制权做心跳，无法区分'暂无消息'和'consumer 卡死'**"——进程存活、消费停止（failure-mode-matrix Bug 表第四行："**进程存活线掩盖了消费停止**"）。

**修法：KafkaWatchdog**（§二）——

```python
DEFAULT_HANG_THRESHOLD_SEC = 600    # 10 分钟无心跳 → 假死
_WATCHDOG_CHECK_INTERVAL  = 30      # 30 秒巡检
DEFAULT_POLL_TIMEOUT_MS    = 30000  # 单次 poll 30 秒
# 核心：心跳喂狗；idle > 600s → daemon.suicide()（SIGKILL 自杀）
# daemon=True 守护线程——主线程死它也死，不会成为孤儿
```

**哲学**：**假死最难救——因为没人知道它死了；把自杀权交给它自己（看门狗线程），让"看不懂的假死"退化成"看得懂的真死"，交给外部守护重启**（第 23 课 agent watchdog / 第 25 课 watchdog 父子的同族早年版）。**自杀的设计细节**（§四）：`suicide()` 先杀子进程再 `SIGKILL` 自己——**为什么不用 SIGTERM**："`daemon.handle_signal()` 把 SIGTERM 注册为'只设 g_stop=1 不退出'——**假死场景下信号处理器可能也失效**；SIGKILL 不可捕获"；**为什么不调 `kc.close()`**："close 会 commit offset、leave group、关 socket——**任何一步都可能卡死，二次阻塞导致自杀失败**"（善后交给 broker 端）。**三层重启防护**（§五）：应用层（poll 异常→`consumer_entry` sleep 60s 重启，**秒级**）／进程层（watchdog SIGKILL→父进程 **ForeverThread 30s 内**发现→重启，**~10.5 分钟**）／父进程层（`daemon.watchdog` `os.waitpid` 监控→**1-20s 随机重启**，分钟级）——**"一个人自杀"背后站着两层更大的守夜人**。

### 跳 5：04-others 四小篇——"小修复，大制度"（alarm_invalid_session / feature_3.9.2 / fix_trpc_unwatch / is_vif_ready）

**① ZK session 失效告警**（alarm_invalid_session，ZooKeeper_VPC_Monitor，2021-06-08，**+41 行 shell**）——背景：session 超时三后果（"① ZK 删除该 session 的所有**临时节点**——锁丢失；② **注销所有 Watch**——不再收通知；③ agent 看到的 ZK 数据与实际脱节——**可能下发过期配置到内核**"）；典型场景："ZK 集群压力大（**commitProcessor 瓶颈**导致心跳超时）→ 部分 agent session 超时 → ZK 清理 session → **agent 以为还连着** → 内核路由表不更新"；**最扎心的一句**："**之前没有任何告警**——运维只能在用户报障后逐台查 `zkcli stat`，**平均半小时以上才发现**"。修复很朴素：每小时 grep 日志 `Invalid session` → 去重源 IP（≤100）→ 调 `zkalarm._alarm()` 告警。**"半小时以上"→"每小时巡检"——一个 41 行脚本把 MTTA 从半小时砍到一个巡检周期**。

**② twins 双胞胎切主与"漏回放"**（feature_3.9.2，vpc_agent_dpdk_vpcgw，2026-05-11，分支 20 commit 取最新）——**twins 架构**："`vpc_agent`（主）+ `vpc_agent_bak`（备），同机部署"，`fcntl.lockf(LOCK_EX)` **文件锁争主**——"主进程崩溃 → **OS 自动释放锁** → 备进程 **3 秒内**拿到锁 → 切主"；切主时 `do_switch()` **回放最近 10 分钟 4 类 binlog** 到 DPDK（RouteTable / GlobalRoute / ServiceTable / RtbRoute）；**Bug 1**：回放**漏了 VPC**（后文）+31/-17 修复——"**主备切换的最后一公里是"把最近的历史补上"**"（对照第 23 课 ReWatch：同一个"补历史"母题）。

**③ agentos 的 UnWatch 误删**（fix_trpc_unwatch，agentos，2025-03-15，**已合入 master MR !79**）——材料原话："**agentos 是 vpc_agent 的 Go 重写版（VPC Gen3/vpc5.0 控制面框架）**"（第 16 课主角的又一官方注脚）。watchManager 三类资源（ComRes 全局 / HostCfgRes 母机 / VpcRes 按 vpcId）；**关键设计**："**一个 reqId 可被多个订阅复用**——一次 Watch 可以同时订阅多个 vpcId，共享一个 reqId"；**Bug**：旧 UnWatch 直接 `delete(wm.req, id)` **删整个 req 条目**——"当 reqId 被多个订阅复用时，取消其中一个会**连带删除共享该 reqId 的其他订阅**"（例：vpcA+vpcB 的 rtable 共 `reqId=100`，退订 A 把 B 也退了）。**病根一句话：把"共享句柄"当成了"独占条目"**——取消的粒度必须跟着**归属**走（同族：第 21 课"锁的粒度决定并行度"，这里是"退订的粒度决定正确性"）。

**④ 全局锁里的纯读接口**（is_vif_ready，vpc_agent，2025-12-10，实际代码 **+5/-5**）——`is_vif_ready`（检查 ENI 就绪，被 sdn_oss 的 CheckMigrate **逐个 ENI 串行调用**）慢的根因：**"整个检查逻辑被包在 `with state.mutex:` 全局锁里"**——而 `LightWeightAccount.do_account()` 对账流程"在**整个对账周期**（40+ 检查函数，数秒到数十秒）持锁" → "**对账一启动 → is_vif_ready 全部阻塞 → 60 秒超时堆积 → 跨 VPC 迁移失败**"；`state.mutex` 是 `state.py:370` 的全局 `threading.Lock()`（保护可变全局对象与 netlink 下发临界区，**~20 处使用**）；**为什么它不需要锁**："**纯读操作**——只读 `vif_container._enis` 和 `trunk_eni_associations`，**不下发 netlink、不修改 state**"。**+5/-5 行**：把纯读路径移出全局锁——**"全局锁的正确边界 = 写路径 + 内核临界区；只读路径不该替对账背锅"**（对照第 31 课"信号量扩散"：都是"隔离粒度不够细"的税）。

## ③ 设计推导（问题树）

**Q1：九篇的共同病根画像是什么？**
四类：**检测缺失**（invalid_session"没有任何告警"／kafka 假死／failure-matrix 的"为什么没发现"列）、**粒度错误**（unwatch 误删共享 reqId；vif_ready 全局锁罩纯读；Hash Tag 之前的跨 slot）、**补历史遗漏**（切主漏 VPC 回放）、**修复引入**（22 课空指针、27 课 schema 参数）。**"小修复，大制度"**——每篇的 diff 都很小（+41/+5/-5/3 秒切主…），但修的都是**制度性缺口**（告警制度/粒度和约/回放清单）。

**Q2："半小时以上才发现"与 failure-matrix"为什么之前没发现"列什么关系？**
同一个"**检测缺口清单**"的两个实例：那个列的是"为什么 bug 逃过防线"，这里列的是"**为什么故障逃过值班**"。**MTTD（发现时间）是控制面质量的第一指标**——第 32 课排障六步法解决"发现后怎么查"，本课这些补丁解决"**发现之前怎么知道**"。

**Q3：reqId 复用的设计两面？**
正面：**共享句柄省连接与订阅数**（一次 Watch 多 vpcId——与第 19 课"多消费者共享流"同哲学）；反面：**取消操作的默认语义变成了"杀伤面"**——`delete(req)` 的语义是"删句柄"还是"删订阅"？修复的本质是**把删除粒度降一级**（从 req 降到 (req, sub)）。**"共享设计必须先定义退订语义"**——这是所有引用计数/共享句柄系统的第一条戒律（第 17 课 binlog 引用计数的正例）。

**Q4：is_vif_ready 的"+5/-5 行"说明什么？**
**性能问题的解法常常不是"加"，是"移"**——把纯读路径**移出**临界区。判据重复三遍：**只读/无内核副作用 → 不进全局锁**。它和第 31 课"Worker 信号量被慢查询占满"是同一枚硬币：**锁与信号量的粒度 = 故障的传播半径**。

**Q5：切主回放窗口"最近 10 分钟"为什么合理？**
因为窗口的目的不是"全历史"，而是"**把没进 DPDK 的那段补上**"——10 分钟 > 一次发布/心跳周期 + 切主耗时（3 秒）+ 回放耗时，留足余量又不重放太古早的（幂等代价小、bar 简单）。同族三连：19 课 LocalVersion 重连增量、23 课跨 SET"先建新后拆旧"、本篇"切主补历史"——**"断点补历史"是整个系统线的通用胎记**。
