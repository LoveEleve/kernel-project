## 0. 术语速查

| 术语 | 含义 |
|---|---|
| **三场答辩** | 三篇的立文动机都是"面试官问"：① 你们和开源 SDN（Calico/OVN）的区别？② 和业界大厂（Google/AWS/Azure）比怎么样？③ 和 K8s Controller 什么区别？ |

## ① 它干了什么——三连问的答法

面试官的三连问其实是同一个问题换三层参照系：

```
"你们和开源 SDN 有什么区别？"      → 对照 Calico（BGP 纯 L3）、OVN（OVSDB+流表）
"你们和大厂比怎么样？"             → 对照 Andromeda（Spanner 无对账）、Hyperplane（Cell+TLA+）、VFP（统一流表）
"你们和 K8s 有什么区别？"          → 对照 Reconcile Loop 范式
```

三篇的答法也统一：**"约束不同，解不同"**（第 1 课的老话）——每场都先摆**约束**，再摆**解法差异**，最后给**pragmatic 结论**。

## ② 链路走查（材料行号）

### 跳 1：vs Calico——"BGP 驱动纯 L3"为什么不是我们的路（vs-calico-ovn §一）

**Overlay 方案对照**（§1.2）：

```
Calico（无 overlay）：不增加包头开销（无 GRE/VXLAN）——延迟最低、吞吐最高
  前提：底层必须支持 BGP——宿主机 IP 可达
  限制：所有 Pod 共享同一路由域——【没有 VPC 级别的隔离】
VPC（GRE overlay）：GRE key = vpcId——不同 VPC 流量走不同 tunnel 隔离
  代价：GRE 增加 24 bytes 包头——MTU 需要调整
```

**为什么不用 BGP——多租户隔离需求**（§1.2 的核心论证）："**BGP 只有'路由'概念——没有'租户'概念**"：VPC-A 与 VPC-B 都有 `10.0.1.0/24`，在 BGP 里是同一条路由——**路由冲突**；我们的解法是 GRE key 承载归属："数据面通过 GRE key 区分 VPC——**控制面不需要担心 BGP 路由冲突**"。

**路由传播总对比**（§1.2 表）：分布式 BGP 交换 vs 集中式控制面下发——传播延迟 `BGP convergence 1-10s` vs `tRPC push < 100ms`；规模 `BGP table ~100K 路由` vs `CDB 可扩展`；**"BGP 不适合 VPC 的原因"**三条：**200 万 VPC × 5 条 = 1000 万条路由**（BGP table 无法承载）／大量路由下 convergence 分钟级（**VPC 要秒级**）／**BGP 表达不了"安全组/ACL"**（"VPC 需要完整的网络策略栈"）。

### 跳 2：vs OVN——"OVSDB(Raft) vs MySQL+Kafka"的存储之辩（§二）

**控制面存储对比**（§2.3 表）：一致性 `OVSDB Raft（RAFT 变种）` vs `MySQL 单机事务 + Kafka 异步`；数据模型 `Logical port/switch/router`（图）+ JSON-RPC 查询 vs **关系型表**（t_vpc+t_subnet+t_vm…）+ **SQL 的灵活 JOIN/聚合**——一边是"网络对象模型"，一边是"数据库直接当工具箱"。

**"为什么 VPC 不用开源方案"的标准回答**（§四）：

> "因为规模和多租户隔离。Calico 的 BGP **没有租户概念**……BGP table 撑不住千万级路由。**OVN 的 OVSDB 是内存数据库——上限约 10 万实体**。VPC 要管 200 万个虚拟网络、**1.6 亿实体——完全超出 OVN 的极限**。……不是开源不好——**它们在各自的设计目标里都是最优的**。"

**适配边界（§四收尾三行）**：Calico 适合"K8s 集群容器网络、单租户、**1 万 Pod 以内**"／OVN 适合"中大型私有云、多租户、**1 万虚拟网络以内（逻辑实体 10 万以内）**"／VPC 自建适合"公有云、**百万级租户、千万级配置、10 万+ 母机**"。

**速记卡再补三句**（§五）："**OVN 的 scale 只有 VPC 的 0.06%**"／"**OVS OpenFlow vs DPDK——性能差 10 倍**"（软件解析每包 IP+VPC vs 硬件 hash table O(1)）／"**不是开源不好——是 VPC 规模不属于它们的达摩克利斯范围**"。

### 跳 3：vs 工业界三家——Spanner / Cell / VFP（vs-industry-practices §一/§二/§三）

**① Andromeda：为什么它可以"不要对账"**（§1.2）：

```
Andromeda 写入路径：API → Spanner 写入成功 → Honeybee Controller push → SDVNIC config
  - Spanner 是全球强一致（TrueTime + Paxos）→ "API 写入成功 = 配置生效"
  - 没有"多级缓存"概念——缓存只是性能优化，不是 Source of Truth 的副本
对比 VPC：API → MySQL → Kafka → Fusion → Broker → Agent → DPDK
  → 【5 层缓存副本——每层都可能不一致】→ 需要对账检测——因为我们没有 Spanner
```

**差距表**（§1.3）：Source of Truth `Spanner（全球强一致）` vs `CDB（单 Region 强一致）`／一致性 `强一致（无对账）` vs `最终一致（有对账）`／`SDVNIC` vs `DPDK`／`Jupiter 自研交换机` vs 商用／`Maglev` vs `CLB`／全球 vs 单 Region。**根本差距=基础设施投入**："Andromeda 是**从网络硬件到上层控制面全栈自研**——VPC 是**在商用基础设施上搭建控制面**……**不是最优解，但是在给定的基础设施约束下最 pragmatic**。"

**② AWS Hyperplane：Cell 与我们 SET 的正面比对**（§2.3 材料原表）：

| 维度 | VPC（4 SET） | AWS（Cellular） |
|---|---|---|
| 分片维度 | **容量分片（SET）** | **功能分片（Cell）** |
| 分片粒度 | 每个 SET 负责 **~50 万 VPC** | 每个 Cell 负责 **1 个服务类型** |
| 隔离性 | SET 故障影响该 SET 的所有 VPC | Cell 故障影响该服务类型 |
| 扩容 | 在 SET 内扩容 Worker | 新增 Cell——独立部署 |
| 跨片通信 | VPC 跨 SET 迁移（resourcectrlset） | Cell 间通过 API 调用 |

**"VPC 没有 Cellular 的原因"**（材料原话）："VPC 控制面**只有一个核心功能——配置管理**。不像 AWS Hyperplane 管理多个不同的网络服务。**功能单一 = 不需要 Cellular**。"**可学的两件**：blast radius（"可以考虑按 VPC 类型分 SET"）+ **形式化验证**——"AWS 用 **TLA+** 验证 Hyperplane 协议正确性……**可以引入 TLA+ 验证 VPC 的 Redis Lua 脚本——DeleteConfig 的 semantic bug 可能被检出**"（👈 直指第 22 课的事故）。**§2.4 TLA+ 正文展开**：做法=定义状态空间 + 转换规则，**model checker 穷举所有执行路径验证不变量**；**"TLA+ 能发现什么"三样**：Redis Lua 脚本的原子性问题／"**DeleteConfig 的 semantic bug——`Put(nil)` 和 `Delete(key)` 在对账看来不同**"（22 课那行代码的"形式化版本"）／状态机非法转换（"Completed→Processing 不应该发生"）；**VPC 可引入的三个场景**：① 3 个 Lua 脚本的组合执行不变量 ② 任务状态机安全属性（Pending→Processing→Completed）③ **对账一致性条件——"什么情况下对账应该报告 0 diff"**。

**③ Azure VFP：统一流表 vs 我们的分散策略**（§3.2 表）：

| 维度 | VPC（分散策略） | Azure VFP（统一流表） |
|---|---|---|
| 规则组合 | Agent 本地组合 | **控制面预编译** |
| 冲突解决 | Agent 运行时优先级 | 控制面编译时合并 |
| 下发体积 | 每类规则独立下发 | 编译后单表下发 |
| Agent 复杂度 | 高（需理解所有规则类型） | 低（只需执行流表） |
| 控制面复杂度 | 低 | **高（需要编译所有规则）** |
| 扩展性 | 增规则类型=增 agent 代码 | 增规则类型=**增编译器代码** |

**VFP 编译器解决的三问题**（§3.3 示例：SG 入/ACL 出/路由 → 优先级流表）：**规则冲突**（ACL 优先级 200 覆盖 SG 100）／**规则合并**（相同 action 合并减流表）／**规则排序**（编译后按优先级排好，Agent 只按序匹配）。**我们的取舍**："Agent 本地组合减少了控制面计算压力……**如果将来 Agent 算力充足——可以考虑控制面编译**"（一个反向的"计算上移"路标——与第 18 课 computation-agent 同方向）。

### 跳 4：vs K8s——两种控制面范式的"公理级"差异（vs-k8s §一/§二）

**K8s 信条**（§1.1）："**用户声明 desired state，controller 不停尝试让它成真**"——`etcd（单一真相）→ informer cache → workqueue → reconcile(key)`；五步（Get current→Get desired→Diff→Apply→requeue+退避）。**核心约束五条**：etcd 是**单一 SoT**／Controller **无状态**（重启从头 reconcile）／**幂等**／**失败只影响单 key**（不级联）／规模上限 **~100K Pod**。

**VPC Gen3 信条**（§1.2）："**配置变更是一个事件流——消费事件，构建快照，定期验证**"——`MySQL → Kafka → Fusion → Broker → Agent → DPDK`（**每层一个缓存副本**）+ Reconcile 独立定时（**24h 全量 200 万 VPC vs DPDK → 差异报告（不自动修复）**；5min 增量）。**核心约束五条**：**5 层存储、没有单一 SoT**／Fusion **有状态**（不能无状态重启）／reconcile 与正常路径**分离**（验证 vs 执行）／规模 **200 万 VPC**（超 etcd watch 上限）／**10 万+ Agent 不能假设全部在线**。

**§二总公理**："**约束决定架构**"——**反事实四连击**（§2.2"把 K8s 模式套到 VPC 上"）：① etcd watch 上限 **100K** vs 200 万 VPC 至少 200 万 watcher——"内存 + 网络带宽完全不够"；② reconcile 一遍 200 万 VPC：每 VPC 50 条 × 10ms = 500ms → **"200 万 × 500ms = 278 小时"**；③ Controller 无状态 vs VPC 需要 **LevelDB 24GB 缓存**——每次重启全量加载；④ "K8s reconcile 失败→重试"对 VPC 不成立（"**母机 Agent 离线——重试无意义**→需要不同的错误处理模型"）。**§三 7 维正文抽样**：**§3.1 事件模型**——K8s Watch 特性（实时 <10ms／断线从 **ResourceVersion** 续拉／"**ResourceVersion 全局递增——天然防止重复处理**"／每 watch 一个推送队列）+ 限制（**watch 上限 ≈100K**／compaction 清除历史后触发**全量 re-list**）；**§3.2 一致性**——K8s 是 CP（etcd Raft"写入成功=多数派"；informer cache 延迟 ~10ms 但"**差异窗口极小——可以被 reconcile loop 覆盖**"；"**没有第二层存储**"），代价=写延迟 p50 ~2ms/p99 ~10ms、**容量上限 8GB（默认）**、Leader 切换 ~3s 不可写——**对照我们的 AP + 最终一致 + 对账兜底**。

（📌 **闭环彩蛋**：§3.1 正文里出现的 `DeltaFIFO`——**正是第 17 课 R1 因"未授课"删掉的那个引用**；此课补上：K8s informer 的工作队列，Watch 事件落成 delta 后进入 reconcile。当时不该引，此时可以引。）

## ③ 设计推导（问题树）

**Q1：三篇的总公理是什么？**
"**约束决定架构**"——三种约束各自决定一切：**路由的租户维度**（BGP 无租户 → 我们必须 GRE key）；**基础设施的有无**（Spanner/Jupiter vs CDB/商用 → 对账 vs 无对账）；**SoT 的数量**（1 个 etcd vs 5 层副本 → Reconcile Loop vs Event Sourcing）。对照第 1 课"约束不同，解不同"——**这门课从头到尾就是这句话的 26 个实例**。

**Q2：对账是"落后的补偿"还是"韧性的来源"？**
材料立场：**补偿**（"因为我们没有 Spanner"）。但反过来读也成立：无对账方案把正确性押在**单一强一致数据库**上；对账方案把正确性摊到**多副本 + 周期性验证**上——**没有 Spanner，反而长出了"对账即平台"这一整套能力**（16/20/25/26 课四代对账）。约束逼出来的能力，未必是纯负债。

**Q3：SET 化 vs Cell 化——你点名的这题（§2.3）怎么答？**
**容量分片 vs 功能分片**：我们按"每片装多少 VPC"分（~50 万/SET），AWS 按"每片管哪个服务"分（1 Cell/服务）。**"功能单一 = 不需要 Cellular"**——我们控制面只有一个核心功能（配置管理），所以"容量 SET"就是最优形态；**但如果按 VPC 类型（普通/高安全/大客户）再分 SET，就是把 Cell 的 blast-radius 思想借过来**（长期方向表里的原话）。**另一件更值钱的**：TLA+——"**DeleteConfig 的 semantic bug 可能被检出**"：形式化验证能抓住我们 22 课用两条命换来的一行语义错误。

**Q4：VFP 统一流表为什么我们暂时不做？**
**复杂度守恒**：不是在控制面编译、就是在 Agent 组合——材料的选择是"控制面减负、Agent 复杂"，并明说反向条件："**如果将来 Agent 算力充足——可以考虑控制面编译**"。这又是"**计算上移 vs 下移**"的老坐标（第 18 课 CA 预计算 = 上移；VFP 编译 = 上移的另一种）——**上移的触发条件永远是"算力/带宽约束翻转"**。

**Q5：K8s 与我们的分水岭在哪？**
**SoT 数量与规模**：K8s 敢"无状态+无限重试"因为 **etcd 是唯一真相**（reconcile 读缓存即可）；我们 5 层副本、10 万+ 不可全在线 Agent——**只能走"事件流 + 定时验证"**。而其上限也钉死了："etcd watch 和 informer cache 的内存上限 ~100K"——**和我们的 200 万 VPC 差一个数量级以上**。范式没有优劣，**只有约束的匹配**。

## ④ 对照卡：一张总表

| 系统/范式 | 核心约束 | 它的答案 | 我们的答案（课号） |
|---|---|---|---|

## ⑤ 验收题

1. "BGP 只有路由概念、没有租户概念"——用两个 `10.0.1.0/24` 的场景说明它如何必死；GRE key 在这个故事里的角色是什么？
2. "为什么 VPC 不用开源方案"的标准回答里，OVN 的致命数字是哪个（1.6 亿 vs 10 万）？三家的"适配边界"各是几万量级？
3. Andromeda 无对账、我们有对账——把"对账"重构为"韧性来源"的正反两读各说一遍（提示：押注单库 vs 摊到多副本）。
4. **SET（容量分片）vs Cell（功能分片）**：为什么"功能单一 = 不需要 Cellular"？长期方向里"按 VPC 类型分 SET"借走了 Cell 的什么思想？
5. VFP 的"统一流表 vs 分散策略"用"复杂度守恒"解释；它在第 18 课哪条设计线上找到了同方向队友（计算上移）？
