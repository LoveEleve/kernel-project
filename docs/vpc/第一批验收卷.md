**A7 · tf-vrouter（第 7 课）**

## 标准答案（考官版 · 首轮考官代答，供复考对照）

**A1**：SoT = **OVN NB 里的逻辑对象**（LogicalSwitch + patch port 对 LSP/LRP + DHCP options），kube-ovn 写完 NB 就撒手。不需要"快照+binlog"是因为**分发被整段外包给 OVN**：ovn-northd（NB→SB）与每节点 ovn-controller（SB→OVS）自带增量通道（OVSDB 复制 + monitor），节点天生"watch 得动"。我们自研三件套是"没有 OVN + 覆盖非 K8s 场景"的约束解。出处：第 1 课 ③Q2。

**A2**：delta 是快路径（calc graph 增量推导，保延迟）；full resync 是慢路径（周期性全量重算覆盖，保正确）——数据面允许"暂时不完整"（`int_dataplane.go:2320` "will wait for the full resync" 即现场）。同构对象：**"增量+全量兜底"方程**——etcd 压缩边界、OVN I-P fallback、我们 CKV+对账全是它的实例（总章"一个方程六实例"）。

**A3**：ZK ephemeral **生命周期绑会话（连接态）**，连接断/超时即自销；etcd lease 是**独立对象**——可挂多个 key、显式续约、失效处置由业务定义。因此 ZK 里"抖动"直接翻译成"节点死亡"（ephemeral 丢、锁丢）；业务再叠加"丢锁即自杀"就是雪崩（nfv-proxy proxy_merge 案）。出处：第 3 课 ③Q2 + zklock 雪崩链。

**A4**：两份 map 覆盖两个方向：`watchTable`（path→watchers，注册/触发）与 `watch2Paths`（watcher→paths，断连清理）——单表做不到双向 O(1)。一次性（STANDARD 默认）意味着客户端要不断"删旧注册新"，**漏清任一侧就是泄漏**（agentos `fix_trpc_unwatch`："删 watch 时没清理 map"）。出处：第 4 课 跳2 + zk-learning-path Step2。

**A5**：分工线 = **"全局逻辑"中心算（northd：一份全局视图 1×N 聚合）、"本地事实"节点算（ovn-controller：本机事实×全局逻辑→OpenFlow，N×1 过滤）**。回退触发（代码级）：`inc-proc-eng.h:322-325`——change_handler 为 NULL 时"fall back to call the run method to recompute"；实例 northd 的 `en_sync_from_sb`（`inc-proc-northd.c:509`）。出处：第 5 课 跳1/跳2/Q1。

**A6**：图（IF-MAP）——选子图是图上原语（GraphWalker 沿关系走），**"选谁下发"最容易但软件复杂度最高**；树（ZK）——子树 watch 直接表达关心面，但实体关系靠约定（两棵树一致性/泄漏类工程的来源），**结构约束换简单**；平铺（etcd）——前缀约定关系，**灵活但纪律成本全在客户端**。出处：第 6 课 Q1 + 第 3/4/5 课对照。

**A7**：最先爆**内存/容量**（每核一张表 + 热流打歪单核的不均衡是复用另一面）；首包延迟有 HOLD 限流兜底（"秒级"是明说预期）；**`fe_gen_id` 属于失效协议**——流的重装/失效用它区分代际，防止旧表项/旧包被误认，缓解"逐出与失效"这条。出处：第 7 课 跳2/Q2 + `vr_flow_evict_flow@423`。

**A8**：**TOA→内核模块**（RS 装 toa.ko 解 option 254；最坏：模块不可用/需版本适配）；**UOA→网络设施**（option 31/协议号 248；最坏：**路径上任一跳交换机/路由器不支持即废**——doc 原文 "not all kinds of network switches or routers support…"）；**PP→应用**（连接建立后必须立刻解析；最坏：应用未适配把地址当业务数据读错；优点是 de-facto standard、零内核依赖）。出处：第 8 课 跳7 + doc 原文。

**A9**：因果链：① DSR 下**回包不经过 LB**；② 选路是**纯哈希**（同 5 元组任何实例算出同一 real——README："consistent in real server selection, even w/o explicit state sharing"）；③ 会话表因此只是"加速缓存"而非权威状态——重启即自愈。代价清单：RS 必须解封装（`decap/`，XDP/tc 两形态）、网络需 L3 拓扑且单口进出（不分片/无 IP options/包长上限）、健康检查需另配（healthchecking 一族）。出处：第 9 课 跳1/③Q3。

> 首轮结论：A 卷九题全部作答入库；判卷网格保留供**复考**（换人/换时间再答对照）。

## B 卷标准答案（考官版）——第 1-5 课

**1-1** SoT=OVN NB 的逻辑对象（LS + patch 对 LSP/LRP + DHCP options）；不需要两级分发因为分发整体外包给 OVN（northd NB→SB、ovn-controller SB→OVS 自带增量通道），节点天生 watch 得动；我们自研三件套是"无 OVN+非 K8s 场景"的约束解。
**1-2** needRouter=overlay 或 underlay 逻辑网关（装 LSP↔LRP patch 对，LRP 网段=子网网关）；randomAllocateGW=underlay 物理网关+VPC EIP（LRP 归 vpc 流程、随机分配）；bare=无路由器裸交换机（`CreateBareLogicalSwitch`）。
**1-3** 崩溃后靠 workqueue 幂等重试收敛（重做直到成功，status 只影响可观测）；对照 Saga=逆序补偿"撤销本次"——一次性事务 vs 收敛循环，代价分别是"补偿完备性"vs"幂等要求"。
**1-4** 防同 VPC 并发建子网导致 CIDR 冲突（先锁 VPC→查冲突→建）；敢用内存锁因为 controller 单 active（leaderelection，OnStartedLeading 才启动）=单写者；我们多实例共享 MySQL/ZK，必须分布式锁。
**1-5** 因为 L2/逻辑网络由 OVN 原生组件负责（northd+ovn-controller+OVS）；daemon 只做 K8s 侧接线补充（gateway/FDB 等）；承载子网的流表由每节点 ovn-controller 从 SB 编译下发。

**2-1** 防 datastore 侧的"N watcher×事件扇出"放大（K8s 场景事件量随节点数增长）；"50 节点"=放大成本从"推荐治理"变"必须治理"的阈值；"etcdv3 可免"=直连 datastore 无 API 层放大——两个边界都说明"放大源头在 datastore 侧"。
**2-2** breadcrumb=带序列号的快照（BTree KV 的一致点）；重连协议顺序：完整 snapshot→KVs 增量→SyncStatus(InSync)——从一致点严格续增量，故不丢不重。
**2-3** 三态=WaitForDatastore/ResyncInProgress/InSync；可以等因为"暂时不完整"被显式接受（full resync 会推平重算，int_dataplane 注释即现场），InSync 只是收敛标志而非正确前提。
**2-4** delta 保延迟、resync 保正确；calico 敢自动修=单租户 K8s 域+数据面可重算（收敛幂等）；我们多租户+误修代价高（对账误删现场）→报告制。
**2-5** 三形态=InactiveDataplane（非 leader）/进程内 intdataplane（默认，exec.Cmd=nil）/外部子进程 extdataplane；子进程是可选因为默认进程内不需 IPC；driverCmd==nil 时打印 "No driver process to monitor"（监控逻辑空转）。

**3-1** Main=原子批标识、Sub=批内递增序；没有它，"从版本重放"会把原子批拆开、重放出批内中间态（不可见态）。
**3-2** lease=独立对象（可挂多 key、显式续约、失效处置业务定）；ephemeral=节点属性+会话绑定；ZK 抖动=会话 LOST→节点/锁自销——"网络问题"被语义翻译成"节点死亡"（业务再自杀→雪崩）。
**3-3** 三原语：层级命名空间（资源树=路径）/子树 watch（child watch）/会话+ephemeral（活着证据）；三负担→三补丁：payload 小→引 CKV；一次性 watch→重注册+泄漏修复（agentos）→二代 TRPC 心跳；会话绑生死→zklock 迁 DB 锁。
**3-4** 客户端税至少三笔：① CKV 快照兜底（重连补课自建）；② /BINLOG 增量管道自建；③ 重注册纪律与 watch 泄漏修复（另有④对账 differ/account 兜缝）。
**3-5** fusion：选举=Redis `SET NX EX`+Lua 续约校验；增量=Kafka binlog；存储=LevelDB；不需要"树"因为三合一需求（层级+子树通知+会话原语）在 VPC5.0 的对象模型（分片 scope）里不存在。

**4-1** 记在 DataTree 的 `ephemerals`（session→paths 集合，DataTree.java:154）；会话终结时 `killSession` 把该 session 名下路径一次删光（:1147）。
**4-2** 双 map=注册方向（watchTable）与清理方向（watch2Paths）；一次性+双索引=高频"删旧注册新"，两侧任一漏清即泄漏——agentos `fix_trpc_unwatch` 正是"删 watch 时没清理 map"。
**4-3** 单写飞行在协调场景（读多写少）是"全序提交最简"的优点；被推到配置分发通道（写频繁量大）后成为吞吐瓶颈；§12.2 第 2 条"commitProcessor 单线程——读写竞争导致数据延迟"是其直接后果。
**4-4** epoch 防旧 leader 的过期事务被追认（换领导换 epoch），counter 保任期内单调；32 位 counter 会打满——我们做过 `fix/zxid_counter_extend`（7 文件 +40/-15，未合入）实测，最终选"跳过特殊值"兜底。
**4-5** 因为 observer 是"同步但不投票的读者"，角色语义允许被重定义（追加跨集群同步职责），而 ZAB 共识内核（选举/投票/写路径）没被动；边界=能改角色/旁路/工具链，改不动共识内核。

**5-1** 分工线="全局逻辑中心算（northd：一份视图 1×N）、本地事实节点算（ovn-controller：N×1 现场编译）"；反方案①所有节点从 NB 全量自算=N 倍全局算力+全量事件；反方案②northd 直接产每节点 OpenFlow=中心须掌握 N 份实时本地状态。
**5-2** 触发条件：change_handler==NULL → "fall back to call the run method to recompute"（inc-proc-eng.h:322-325），实例 en_sync_from_sb（inc-proc-northd.c:509）；与 felix/etcd 同题（增量不可用回退权威路径），不同在触发源（无处理器 vs 周期 vs 历史被压）。
**5-3** 集中 SB 代价=复制+每节点全量 watch 的读放大压 SB/网络；分区 ZK 代价=分区路由+跨区一致性（我们付了分区 ZK 运维/CKV/对账三笔）；千万级时中心式"全库推给每节点"的复制与 watch 压力率先暴露。
**5-4** 难题=引用闭包的变更传播（AS 变→引用它的 lflow 都要重考虑）；"谁引用谁"靠显式依赖图（engine_add_input 声明节点依赖，变更沿图传播）——外加快速路径 as_update_can_be_handled 判断"能否不重算"。
**5-5** 残留职责=K8s 场景接线（pod veth/CNI、gateway、FDB 维护）；瘦身形态=若通用层（OVN）在场，agent 可瘦成"只做场景接线"的 daemon（通用编译全交给 OVN）——我们的 vpc_agent 若当年有 OVN 本可如此。

## B 卷标准答案（考官版）——第 6-9 课

**6-1** 图：子图选择=图上原语（"选谁下发"最容易）但软件复杂度最高；树：子树 watch 简单但关系靠约定（结构约束换简单）；平铺：前缀约定关系（灵活但纪律成本全在客户端）。
**6-2** 不是同一种：GraphWalker 输入=IF-MAP 图+VM 锚点、算法=沿关系走图切子图、输出=配置子图（与路由共 XMPP 通道）；agent-broker 输入=分区 ZK/CRS 变更、算法=订阅过滤、输出=TRPC 心跳增量——同一个"过滤下发"问题，**关系闭包 vs 订阅键**两种术。
**6-3** 两条债：①"推丢了怎么办"的投递观测面（无 outbox 的可靠投递与可观测性）；②最终一致靠事后对账（Introspect）而非写入事务——债都记在对账+观测上。
**6-4** 因为材料记的是老一代接口；本仓全仓 grep 零命中、全形态统一 generic netlink——纪律：**跨代材料对代码必须逐条 grep**，文档是历史快照、代码是现况。
**6-5** 同一问题（隔离/overlay）不同抽象层：VRF 表+MPLS 标签 vs GRE key=VpcId；互换约束后各自优点变短板——TF 这套适合 IDC 互联/BGP 对接物理网，GRE-key 一招鲜适合纯云内多租户（不碰物理网）。

**7-1** 一核多壳优在"语义一致、一份修"（多形态跨平台）；两套实现优在"解耦、各自极致"（不被共同抽象拖累）；形态多且语义必须一致→多壳；形态少或性能边界差异大→各自实现。
**7-2** 最先爆**内存/容量**（千万流×每流状态；逐出压力第二）；`fe_gen_id` 缓解"逐出与失效管理"（代际区分，防旧表项/旧包误认）。
**7-3** 回包要对称（同 VRF/隧道/镜像策略），ECMP 下正反哈希不同源、反向推不出唯一解；推错=回包走错路径/统计错乱/策略不对称。
**7-4** uvhost 把 VM 数据面（virtio/vhost ring）搬进 vrouter 进程直连自家转发环；TF 的复杂度在"进程内集成（ring/线程/内存）"，我们的复杂度在"进程通道协议（TCP+protobuf）与生命周期管理"。
**7-5** 设计题：功能流（NAT/镜像/精细策略）→状态在流里；超大规模+功能外移→状态在流外——先答需求再选型。

**8-1** DR 须 RS 与 LB 同二层（云里 RS 任意子网，不成立）；SNAT 须 VIP 配 RS 回环+回程路由细节（云里不可控）；FNAT 全改源目的→拓扑解耦，故成默认。
**8-2** TOA→内核模块（toa.ko）；UOA→网络设施（路径设备须支持 option 31/私有协议 248）；PP→应用（建连即解析）；最坏：模块不可用/设备不支持直接废/应用未适配读错数据。
**8-3** 最先暴露**核间不均**（大流打歪单核——RSS 只保同流同核不保均衡；容量×核数次之）；`__lcore_conn_table_dump` 解决"跨核视图/管理"（无锁模型的边界条件）。
**8-4** preference list=每个 RS 一条固定位置偏好序列，装表取"最优先且未占"位；RS 变化只扰动对应少数槽位，不像取模全量重映射。
**8-5** 模板=**先吃透老系统语义（模式/调度器/会话/控制面），再用新引擎撞性能墙**——语义是资产、引擎是可换件。

**9-1** 省掉：netfilter 钩子链、sk_buff/协议栈、中断（轮询）、socket；对 PPS 影响最大=**sk_buff/协议栈**（每包分配+多站遍历是最大头），driver mode 在 DMA 后立即处理。
**9-2** 扁平 ARRAY：一次 O(1) 查找（寻址公式）、无需 per-VIP map（创建/句柄开销、BPF 程序内不可动态）、布局恒定缓存友好。
**9-3** lru_map=功能开关；F_LRU_BYPASS=VIP 级旁路；under_flood=洪泛不写表防击穿；F_RST_SET=**RST 不进表防会话污染**。
**9-4** 因果链：回包不走 LB（DSR）+选路纯哈希（同 5 元组同 real）+会话表只是缓存→重启自愈；代价：RS 解封装（decap/）、L3 拓扑+on-a-stick+不分片/无 options、探活另配（healthchecking 一族）。
