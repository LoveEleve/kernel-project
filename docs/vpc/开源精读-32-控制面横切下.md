## ② 链路走查（材料行号）

### 跳 1：对账篇——"设计缺陷还是设计选择"（reconciliation）

**立论三问**（首行）："你觉得对账是**设计缺陷还是设计选择**？为什么对账**只检测不修复**？如果对账本身挂了，用户最大……"

**验证路径 vs 执行路径**（§1.1/§1.2）：

```
主要路径（执行）: API → MySQL → Kafka → Fusion → Broker → Agent → DPDK
验证路径（对账）: MySQL ←┐
                        ├ 比对 → Diff Report（【不执行修复】）
                  DPDK  ←┘
对比 K8s：reconcile loop 第 4 步就是 Apply——reconcile 本身就是执行者
```

**三差异的处理纪律**（§二）：

- **Missing**（"应该有的没有"）：原因三分——**正态时间窗口**（binlog 还没消费）／异常（Kafka 丢失/Agent 写入失败）；行为——"**报告 Missing（不自动修复）→ 下一次对账（5min）检查是否自然恢复 → 持续 Missing（> 2 个对账周期）→ 可能是系统性问题（非时间窗口）→ 升级告警 → 人工排查**"——**"两次确认"制度的工程版**（呼应第 26 课 tracker 降噪）；
- **Redundant**（"不该有的却有"）：原因含 "**DeleteConfig bug——配置'复活'**"；行为——"**⚠️ 报告 Redundant——先告警不自动删除（安全考量）**→ 人工确认 → 手动清理或等待正常路径修复"。

**对账制度一句话**：**报告权与执行权分离**——发现差异是自动的，消除差异是受控的（人工/常态路径）。"设计选择还是缺陷"的答案藏在自动化程度表里：**越危险的动作，越不自动化**（Review 的姿势：L1 位置 → L2（K8s 对比）→ L3 反事实）。

### 跳 2：生命周期篇——同一份配置的"五张脸"（lifecycle §一）

**每层的操作语义映射**（§1.1，CREATE/UPDATE/DELETE 逐层）：

| 层 | CREATE 语义 | 关键注 |
|---|---|---|
| MySQL | **事务性 INSERT（ACID——要么成功要么失败）** | UPDATE=覆盖（不保留版本历史）；DELETE=物理删除 |
| Kafka | **append-only（不可变——写了就不能删）** | **UPDATE/DELETE 都是"新增一条 binlog"**（事件溯源的核心句） |
| Fusion LevelDB | **Overwrite（覆盖旧值——不保留历史）** | 临时工作区 |
| Broker BTree | 内存 Insert——**重启丢失，从快照重建** | 无版本语义（第 31 课） |
| Agent LevelDB | 本地持久化——重启后恢复 | —— |
| DPDK | `add_route`——**内核实际生效——不可回滚** | actual state |

**读法**：**同一份配置，六层六种"态度"**——有的记历史（Kafka）、有的忘历史（MySQL/LevelDB）、有的根本不负责记（BTree）、有的无法反悔（DPDK）。理解这张表，才理解"为什么快照矫正能治乱序"（第 31 课）：**Kafka 是唯一的"记忆体"，全量快照是它的"定期对答案"**。

### 跳 3：分片与隔离——"隔离拆到哪一层为止"（data-sharding / multitenancy-isolation）

**分片键 = BizScopeId**（data-sharding §1，源码 `storage/engine/table_name.go` 三分片常量 + `config_dao_impl.go:58-63` `LoadShardConfigs` **遍历所有 shard**）：配置表按 `ShardCount` 分成多个**物理表**；LevelDB key 设计 `config:%d:%s`（`config:{shardId}:{identifier}`）——**按 shardId 前缀分组**（第 20 课 key 格式闭环）。

**四层隔离全景**（multitenancy §一表）：

| 层 | 隔离机制 | 粒度 | 单 VPC 故障影响 |
|---|---|---|---|
| DB | **分区表 hash(vpcId)%250** | per-partition（**8000 VPC**） | 影响同分区 VPC |
| Kafka | 无显式 partition key | 无 per-VPC 隔离 | 不影响（**binlog 乱序但最终一致**） |
| Redis | key `task:queue:{queueName}` | per-queue（非 per-VPC） | 不影响（独立队列） |
| Worker | **信号量 + goroutine** | per-goroutine | 该 Worker 的一个 goroutine 超时 |

**单 VPC 故障扩散分析**（§二，材料自曝）：DB 慢查询 → goroutine 阻塞 30s（DB timeout）→ **"该 goroutine 占据信号量——Worker 的并发能力 -1"** → 10 个 VPC 同时慢查询 → Worker 全部 goroutine 阻塞；**缓解**："16 个 Worker 中只有 1 个受影响 → **15/16 正常**"+超时 30s 不无限阻塞；**缺失清单**（原文）：① "**没有 per-VPC 慢查询检测——不知道是哪个 VPC 在拖慢**"；② "**没有 per-VPC 熔断**"（`MaxRetries=3` 是 **per-task** 的）——建议："同一 VPC 的 task 连续失败 N 次 → backoff 5 分钟 → 只影响该 VPC"；③ 配额在 API Server 层做（Fusion 内无配额）。**隔离制度的诚实刻度**：**已隔离到 Worker 级，未到 VPC 级**——"制度到位与不到位的清单"胜过一句"我们支持多租户隔离"。

### 跳 4：迁移、部署与运维——制度的"时间维度"（migration / deployment-safety / operations-day2）

**① 四阶段迁移**（migration §二）——立论："VPC 控制面从 2014 年开始运行，Gen2 还在支持所有生产 VPC。Gen3 **不能停机迁移**——必须**在不中断业务的前提下替换核心系统**"：

```
Phase 1 双写：配置同时写 Gen2 ZK + Gen3 Fusion（Kafka binlog）；读仍 Gen2；Gen3 并行消费→快照→【验证正确性】
Phase 2 双读：部分 agent 切读 Gen3（经 Broker）；【比较两边结果】；Gen2 仍为主读源
Phase 3 切流：所有 agent 切 Gen3；【Gen2 保持写入（应急回滚）】；观察 1-2 周
Phase 4 清理：Gen2 停写→清理 ZK 数据与 CKV 快照→Gen3 独立运行
```

**"先建新，后拆旧"** 的大队形版（第 23 课跨 SET 迁移是同构的小队形；四阶段里每个阶段都**可回滚**——回滚能力是分阶段的目的本身）。

**② 部署安全的立论**（deployment-safety §一）："你写的 bugfix/disorder **改了 9657 行**——（在 200 万 VPC 的系统里）**任何一个 bug 都不是'某个 unit test 失败了'，而是'200 万 VPC 的配置变更可能停止'**"；L1 里附上 **nfv-proxy `merge_lock` 源码**（INSERT `t_merge_lock`——**唯一键冲突即加锁失败**；释放=按 vpcId+pid+transType+client 四条件删除）——**"DB 锁"这套制度的"第一现场"又添一证**（部署安全与第 27/29 课同写一段历史）。

**③ 运维 day2**（operations-day2 §1.1 日常项表）：对账 diff review（每天，**⚠️ 需人工确认 Redundant**）／监控巡检（✅ 自动告警）／Worker 数调整（⚠️ HPA 半自动）／LevelDB 磁盘清理（❌ 自动删但需人工确认）／脏数据清理（❌ 手动 SQL+脚本）。**§1.2"加一种新配置类型的全流程"——9 步跨 4+ 组件、至少 2 周**：`vpc-protos 定义 txtpb → make generate → api-server 加 handler → fusion 加 consumer → fusion 注册对账 → broker 注册 Watch target → host-agent 加 Extension/DPDK 写入 → 集成测试 → 灰度（1 SET → 观察 → 全量）`。**读法**：第 18 课说"新增配置类型**零改动**"指的是**代码生成**；这里说的是**流程成本**——两者都对：**生成零改动，制度零捷径**（灰度必须走 1 SET 起）。

### 跳 5：纵深四件——安全 / 观测 / 容量 / 测试（security / observability / capacity×2 / testing-quality）

**① 安全六层纵深**（security §一表+'速记卡'）：网络隔离✅／**API 认证 ⚠️（Basic/Bearer，默认 `global_auth=false`）**／API 限流✅（令牌桶 100req/s + 200 burst）／**服务间认证 ⚠️（静态 token，"永不过期"）**／存储认证✅／审计日志✅。**攻击面自评**："内网被突破 → HTTP API 无认证（默认关闭）→ **可直接操作配置**"；**缺失**："per-租户限流（当前只 per-IP）"。**速记卡三句**："**6 层安全——最薄的是第 2 层**"／"无 RBAC——职责分离"（权限在 API Server，Fusion 只认证"是不是合法内部服务"）／"**对账 = 安全最后防线**"（篡改→Redundant→从 DB 重下发）。

**② 排障方法论：六步追踪法**（observability §二）——"当所有监控都说'正常'但用户说'不行'"（L3 成熟度）的实操版：

```
Step 1 用户报"VM 不通" → nta.getEndpointDBInfo 确认 VM 元数据（vpcId/hostIp/subnet）
Step 2 (60s) DB 里有这条路由？     queryDBRawSQL → 无记录→查 API Server 日志
Step 3 (60s) Kafka 有这条 binlog？  clsSearchLog(topic=vpc-binlog) → 无→查 producer
Step 4 (60s) LevelDB 有这条配置？   dump/日志 → "value=nil → DeleteConfig bug"
Step 5 (30s) Broker 推送了？       Stream 状态/日志 → 无→Watch 失败
Step 6 (30s) Agent 下发了？        configCollector 查 DPDK route-table → 有→"控制面正常→问题在数据面"
```

**每一步都有：时限 + 工具 + 预期 + "如果…则…"**——**排障不是玄学，是把"链路图"顺序走一遍**（第 19 课全链路、第 22 课"修复窗口"的运维读法）。

**③ 容量两篇——"反推容量"与"瓶颈所在"**：`capacity-model`——"**不是生产实测数据，是从代码设计值反向推导**"的参数速查表（全带文件行号）：Kafka `MaxPollSize=50`/`ProduceQueueSize=5000`；Snapshot `WorkerConcurrency=50`/**`CompressAlgorithm=3 (ZSTD)`**/`TaskIntervalMs=60s`/`TaskLockMs=600s`；Reconcile `WorkerConcurrency=10`/`FullTaskIntervalMinutes=1440`；InitConfig 20；CleanConfig 10。`capacity-planning`——当前基线表（VPC **2,069,684**（MCP t_vpc）/ MySQL 连接 ~82 / Kafka partition ~100 / Redis ~100MB vs 288GB / Fusion Worker 16 per SET）——**"瓶颈所在"一句话**："**对账全量 3-9h → 2000 万时 33h（不可接受）**"；**拐点**："**对账全量 > 24h（~500 万 VPC）**"（200 万 3-9h → 500 万 8-22h，"接近 24h 的日周期"）——**扩容不先扩"最慢的验证路径"，用户它就变成新的日周期**。

**④ 测试质量篇（四层塔源码版）**（testing-quality §一）：与第 31 课同题的"升级验证版"——单元 11（**config validate 730 行** / **cache 并发 50 goroutine 312 行**）／集成 18（4000+，**DAO 全量 982 行**）／E2E 9／压力 5；**"所有测试 -race 运行（`cmd/testrunner/main.go:309`）"**；DeleteConfig 复判表更凝练——"**单元（Pass 但）没测'对账怎么解读这条 nil'；集成没测 `Delete→reconcile→diff=0 AND key 不存在`；E2E 没测 delete 后的 reconcile 与 LevelDB 状态**"。

### 跳 6：网络五篇——控制面工程师的"空间感"（03-network）

五篇的立文动机都写在首行："**你是网络控制面工程师——不是通用的分布式系统工程师**"。速览：

- **网关全景**（gateway §1.1 六种）：VPCGW（VM 出公网 SNAT/EIP；有状态 NAT+无状态路由）／PVGW（Peering/PrivateLink；"GRE 解封装→查路由→GRE 封装"）／NATGW／VPNGW（IPsec/SSL）／DCGW（专线+BGP）／CCNGW（多云，"全网状路由+BGP"）；
- **路由双臂**（routing §一 对照图）：控制面三表（`t_rtb` 定义／`t_rtb_route` 策略／`t_rule` 绑定）↔ 数据面路径（`/TVPC/RTABLE/{vpc}/{subnet}/{vmIp} → {hostIp}`）——**"一个子网级策略怎么波及 100 台 VM"**（第 20/25 课"展开"的对照底板）；
- **ACL vs 安全组**（policy §一表）：**绑定对象**子网 vs ENI/VM；**状态**无状态（入出各配）vs **有状态（入允许=出自动回包）**；**规则方向**入+出各一条 vs 各一套（第 20 课 SG/ACL 粒度论的细节化）；
- **虚拟化必答**（virtualization 首段）："**VM-1（母机A）到 VM-2（母机B）的包到底长什么样？**"——GRE 封装/解封装在哪层做（第 13 课 overlay 的"数据面版"）；
- **Service/负载均衡**（LB §1.2）：type 枚举表——`0 VNET`（用户自建 CLB，RS 本 VPC）／`1 RNET 白名单`（"系统 Service（169.254.x.x）"）／`3 REMOTE_VPC`（PrivateLink）；**材料自带"关键纠正"**："**type=1 (RNET) 不是 PrivateLink——type=3 (REMOTE_VPC) 才是**"。

## ③ 设计推导（问题树）

**Q1：把 32 篇的制度串起来，总原则是什么？**
"**报告权与执行权分离**（对账不修复）→ **危险动作不自动化**（Redundant 不自动删）→ **流程不走捷径**（新增类型必过 9 步/灰色必 1 SET 起）→ **容量不赌运气**（对账全量是红线）"。**自动化程度与危害程度成反比**——这是这批材料贯穿始终的制度观，也回答了对账篇的"缺陷 or 选择"：**在这种制度观下，对账是选择，而且是一整套制度里最主动的一环**。

**Q2：六层安全"最薄的是第 2 层"——为什么不立即修？**
约束陈述：Fusion 是**内网服务**（攻击面已缩到"内网被突破"之后）——"默认关认证"是**内网信任模型**的产物；材料把"应该默认开"写在建议栏而不是现状栏。**安全设计的每一步都是"信任边界画在哪"的选择**——改第 2 层等于重画信任边界（成本>收益之前不动）。

**Q3：容量篇为什么把"对账全量"标成瓶颈？**
因为它是**唯一随 VPC 数线性膨胀且不可并行摊薄的路径**（快照有 shard、分发有 SET，而对账要"全量 vs DPDK"对一遍）：200 万 3-9h → 500 万 8-22h → **24h 日周期红线**。**容量规划的本质是找"最先撞日周期的路径"**——找到了就知道下一笔投资该投哪里（也解释了为什么 26 课把 reconciliation 做成 Worker Pool + 聚合调度的通用件）。

**Q4：四阶段迁移与 23 课"跨 SET 迁移"的共性？**
**都把"切换"降解为"重叠"**：双写→双读→切流→清理，每阶段两边都活着、随时可退；SET 迁移"先建新后拆旧"同理。第 31 课说"宁可重叠不可空窗"——**大规模系统的替换从不做"原子切换"，只做"渐变+可回滚"**。

**Q5：映射表的 3 条 ❌ 说明什么？**
它们是"**硬件控制面下沉**"同一族——我们整套课的视角停在"agent 宿主机+DPDK 用户态"；DASH/P4Runtime/Tide 问的是"控制面住进 DPU 之后"。**不是不重要，是现行的约束还没有翻转**（对照 30 课 VFP：编译方向也标注"如果将来 Agent 算力充足"）——**挂账三件=给下一版系统留的望远镜**。
