## ① 入门版（3 分钟可转述）

【类比】数据中心与写字楼有相似的结构：一栋楼容纳多家公司，每家公司拥有独立的门牌体系，互不干扰。类比仅用于建立直觉，机制以 §2 为准。

**具体场景（真实数据）**：张三与李四在云上各购买两台服务器，均使用 10.0.0.0/16 网段：

```
张三：10.0.0.1 / 10.0.0.2          李四：10.0.0.1 / 10.0.0.2
```

- 两组 IP 完全相同，但不冲突；
- 两台 10.0.0.1 可能位于同一台物理服务器上，彼此不可见；
- 同一租户内：跨子网、跨物理机均可互通；跨租户：默认不可达。

这套体系即 **VPC（Virtual Private Cloud，虚拟私有云）**，提供三项能力：

| 能力 | 定义 |
|---|---|
| 隔离 | 每个租户独占其网段与网络配置；租户之间的转发面互相不可达 |
| 复用 | 所有租户共享同一张物理网络，而非各自独占设备 |
| 弹性 | 网络按需创建与销毁，变更秒级生效 |

一句话：**云网络让每个租户获得一套逻辑独立的网络，而物理上只有一张网络。**

## ② 讲解主体

### 2.1 一个 VPC 里有什么（对象与真实样例）

一个 VPC 不是单件资源，而是一组对象的集合：

| 对象 | 作用 | 示例 |
|---|---|---|
| VPC | 顶层容器：一个逻辑隔离域，拥有一个 CIDR 网段（网段表示法，如 10.0.0.0/16，斜杠后为掩码长度） | vpc-gu5knkob，10.0.0.0/16 |
| 子网（Subnet） | VPC 内的网段分区（绑定可用区） | 10.0.1.0/24、10.0.0.0/24 |
| VM（子机） | 用户创建的云服务器 | 10.0.1.9、10.0.1.71 |
| ENI（弹性网卡） | 子机的网络身份本体（IP/MAC 挂载其上） | eni-bmc37aa3 |
| 路由表（RTB） | 子网级路由策略 | rtb-dyf4q3ym（默认路由表） |
| EIP | 公网弹性 IP | 175.27.32.93 |

真实样例（MCP 实测，vpcId=3345906）【实证】：

```
VPC vpc-gu5knkob（10.0.0.0/16）
├── 子网 10.0.1.0/24
│   ├── VM-A 10.0.1.9  （母机 29.211.8.83）
│   └── VM-B 10.0.1.71 （母机 28.65.43.24）
├── 子网 10.0.0.0/24
├── 路由表 rtb-dyf4q3ym（无自定义路由）
├── EIP 175.27.32.93 → 10.0.1.9
└── 保留网段 169.254.128.0/17（系统用途）
```

关键观察：**两台 VM 不在同一台母机（承载 VM 的物理服务器）上**（29.211.8.83 / 28.65.43.24），但它们以为自己在一个普通二层网络里——这个"错觉"由 §2.2 的机制实现。

### 2.2 机制走查：同 VPC 跨母机的一次通信（真实数据）

以 VM-A（10.0.1.9）→ VM-B（10.0.1.71）为例，逐步走查【实证】：

```
第 1 步  源：VM-A 发出 IP 包，src=10.0.1.9，dst=10.0.1.71
第 2 步  母机 A 查转发表（route_table，按 VPC 隔离）：
         DstIp=10.0.1.71 → MasterIp=28.65.43.24     ← 查到目标母机的物理 IP
第 3 步  GRE 封装（母机 A 执行；GRE = Generic Routing Encapsulation，
         通用路由封装——在原始 IP 包外再套一层 IP 头的隧道协议）：
         外层 IP : src=29.211.8.83 → dst=28.65.43.24   （物理母机地址）
         GRE 头  : Key=3345906                          （承载 VPC ID）
         内层 IP : src=10.0.1.9   → dst=10.0.1.71       （租户虚拟地址）
第 4 步  物理网络（Underlay）转发：
         沿途设备只看到"29.211.8.83 → 28.65.43.24 的一个 IP 包"，
         不感知 Key 中承载的是哪个租户
第 5 步  母机 B 解封装：剥掉外层 IP 与 GRE 头，取出内层包与 VPC ID
第 6 步  母机 B 查邻居表（neigh_table，按 VPC 隔离）：
         10.0.1.71 → MAC=52:54:00:e8:f1:3c
第 7 步  组装二层帧，交付 VM-B
```

**vpcId 在每一跳的作用点**（这是全篇的核心机制）：

| 步骤 | vpcId 的作用 |
|---|---|
| 2 / 6 | **表按 VPC 隔离**：同一母机服务多个 VPC，各查各的转发表 |
| 3 | 封装时把 VPC ID 写入外层（GRE Key） |
| 5 | 解封装后用 Key 决定"去查哪个 VPC 的表" |

即：**虚拟网络的"身份"不是某一层的属性，而是被每一跳携带和校验的。**

### 2.3 机制走查：两台 10.0.0.1 为什么不冲突

把"隔离"拆解到每个环节——相同 IP 之所以能共存，是因为**没有任何一个环节只靠 IP 区分对象**：

| 环节 | 隔离的作用点 |
|---|---|
| 控制面数据 | 记录以 (vpcId, IP) 为键——两个 10.0.0.1 是两条不同记录 |
| 母机转发表 | route_table / neigh_table 按 VPC 组织——查表前先按 vpcId 选表 |
| 封装 | GRE Key = 本 VPC 的 vpcId——向对端声明"这是哪个 VPC 的包" |
| 对端交付 | 按 Key 选表 → 查 IP → 交付 |
| 同 VPC 同主机 | 经 vbr（每 VPC 一个的虚拟网桥）直接转发，无 GRE 封装【实证】 |
| 不同 VPC 同主机 | 各走各自的 vbr 与转发表，互不可达【实证】 |

结论：不冲突不是靠"约定"，而是**每一跳都携带 vpcId**——这也就是 T1 中"引入一层网络虚拟化"的展开。

### 2.4 设计推导：为什么长这样（四棵问题树）

> 格式：问题 → 直觉答案 → 失效点 → 被迫设计 → 代价。约束楼层：L0 物理 / L1 数学 / L2 运行时 / L3 领域不变量 / L4 经济取舍。

**【基线】** 物理机房模式——服务器直连交换机，配置 IP 即可互通；隔离通过 VLAN（虚拟局域网：交换机上按标签划分的二层隔离域）划分；一切依赖人工、独占与预先规划。

**T1 直接配置 IP 为什么不可行？**
- 直觉答案：要求租户错开网段。
- 失效点：① 租户不受控——无法强制新增租户更换网段，且私网段偏好高度集中（10.0.0.0/16 一类最常用）；② 租户注销后网段需回收复用，复用与存量记录存在冲突风险。
- 被迫设计：每个租户一个独立逻辑网络空间（VPC）——相同网段无限复用，转发判断纳入 VPC 标识（机制见 §2.2/§2.3）。
- 代价：每包携带租户标识，引入网络虚拟化。｜**楼层 L3**（规模口径：腾讯云 200 万 VPC【实证】）。

**T2 隔离为什么不能只依赖 VLAN？**
- 直觉答案：每租户一个 VLAN ID。
- 失效点：① **容量**：VLAN ID 12 bit → 4094 个可用，与数百万租户规模相差近 500 倍（L1 硬约束）【外部】；② **作用域**：VLAN 是二层概念，无法跨机房/跨地域；③ **变更成本**：新增租户需变更多台交换机，配置量随"租户数 × 设备数"增长。
- 被迫设计：租户标识从"设备配置"转移到"数据包头部字段"（封装协议字段）。
- 代价：封装开销 + 双层排障。本系统采用 **GRE**（4 字节头，Key 承载 VPC ID），未采用 VXLAN（8+8 字节）——取舍：开销更小、IP 封装满足需求【实证】。｜**楼层 L1**。

**T3 虚拟网络如何实际运行？（Overlay / Underlay 分工）**
- 直觉答案：让物理网络学习全部虚拟 IP 与租户路由。
- 失效点：物理设备需容纳"200 万 VPC × 各自路由"，表容量与学习规模不可承受；且租户路由变更同步牵动全网（耦合放大）。
- 被迫设计：两级分工——Underlay（物理网络）仅承载母机 IP 间聚合路由与多路径转发（ECMP：等价多路径，多条等代价链路分担流量），不感知租户；Overlay（由隧道承载的虚拟网络）智能集中在边缘（母机/网关），由边缘执行封装/解封装（即 §2.2 第 3/5 步）。
- 代价：边缘节点承担封装性能与表容量（数据面工程的动因，→F 卷）；排障需内外两层视角。｜**楼层 L0 × L1**。

**T4 弹性为什么要求程序化？**
- 直觉答案：按需人工配置。
- 失效点：① 创建行为不可预测（单日可达十万级 VM）；② 租户随时销毁，IP/路由/网段必须自动回收；③ 产品承诺"秒级生效"，人工流程无法满足。
- 被迫设计：配置程序化——控制面把用户意图翻译为全网配置并自动下发；配置按数据管理（版本/分发/对账）。
- 代价：控制面成为复杂分布式系统（一致性/分发/对账）——本课程后续主体（→D/E/G/H 卷）。｜**楼层 L4**。

**【负空间】** 本篇不覆盖：封装报文编码细节、控制面架构、数据面实现（均属实卷范围）；并明确："隔离"为**逻辑隔离**（转发面按 VPC 标识区分），不等同物理隔离——安全边界另由安全组（实例级/有状态）、ACL（子网级/无状态）、宿主机隔离等承担（→C 卷），不承诺绝对安全。

## ③ 追问链（专家预测 8 条，附应答骨架）

1. **Overlay 与 VXLAN 是否同一概念？** → 否。Overlay 是架构思想；VXLAN/GRE/Geneve 是具体封装协议。本系统采用 GRE，Key 承载 VPC ID【实证】。
2. **VLAN 容量到底多少？现场计算。** → 12 bit → 4096；扣除保留值 → 4094 可用。对照：GRE Key 32 bit、VXLAN VNI 24 bit【外部】。
3. **业界数据中心广泛采用 VXLAN，本系统为何选 GRE？** → 取舍：VXLAN 提供 UDP 封装与二层扩展（开销 8+8 字节）；GRE 头 4 字节、更轻。本系统结论为 GRE【实证】。
4. **Underlay 真的不感知租户？** → 是。承载母机 IP 间聚合路由与 ECMP，不承载租户前缀；租户网络在边缘终结。**边界**：网关类流量（公网/NAT/专线）涉及网关侧地址，超出本篇（→C 卷）。
5. **同一母机上不同租户的 VM 如何隔离？** → 按 vpcId 转发；同 VPC 同主机 VM 间经 vbr 直转、无 GRE【实证】（精确实现→F 卷）。
6. **封装导致 MTU 缩小如何处理？** → MTU（链路最大传输单元）缩小后，通过 TCP MSS clamp（MSS = TCP 最大报文段长度）调整：MSS 1460 → 1424（母机场景，扣除 GRE 开销 36 字节）；网关 TOA 场景降至 1400【实证】（细节→F 卷）。
7. **逻辑隔离是否等价于安全？** → 不等价；逻辑隔离只管"默认不可达"，安全边界另有多层机制（→C 卷）。
8. **不用 Overlay、每租户独占物理设备行不行？** → 即专有云形态：隔离最强、成本随租户数线性增长；公有云靠"共享物理网 + 逻辑隔离"（L4 取舍）。
