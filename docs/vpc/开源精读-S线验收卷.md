## 第 16 课（agent-broker + AgentOS）

**16-1 "推 + watch" 换"心跳拉 + 记账"，二代侧最贵的代价是什么？**
中心要**记账**：SQLite + 内存版本——broker 从"广播站"变"账房"，多了状态持有与版本管理的成本（对照：5.0 又换成流式推 + 中心继续记账，账更厚）。

**16-2 两级分片各解决什么？为什么拓扑登记在 ZK、心跳在 CRS？**
partition=**横向扩展**（broker 水平扩）；worker group=**进程内并行与隔离**。拓扑（配置）进 ZK、存活（活性）进 CRS——**分片体系自己也吃了一遍"配置树 + 心跳"的架构饭**。

**16-3 清表重建 + 全局版本号：为什么缓存可以整个扔？版本号什么角色？**
SQLite 是**缓存不是真相**——重建便宜且彻底；版本号是**缓存与真相之间的坐标系**（同构：etcd revision / OVN seq）。"SyncOnStart=全量、事件回调=增量"——"增量+全量"方程的又一现身。

**16-4 inspector 框架化的收益与代价？**
收益：对账从"各业务手写 check"升格为**平台**（CheckJob 注册 + 泛型 `Differ[T]` + 可插拔修复策略）；代价：泛型的边界=**"对象集"语义**，每个 ext 的差异语义与修复策略仍要各自想清楚。

**16-5 "上游不动、先换下游"的迁移哲学与预测？**
在**稳定的上游之下换掉整个下游**——工程上最稳的迁移顺序（先换网元侧，配置源留给 5.0）。预测（结合第 13 课反函数）：上游最终换成 Kafka + 流后，"控制面厚度"进一步向"分发工程"收拢（第 25 课五段流水即其形态）。

## 第 17 课（vpc-broker 内核）

**17-1 两阶段订阅为什么"先增量后全量"？**
**Kafka 先行**返回 cached binlog——订阅即刻可用；**Fusion 全量后到**——在 ConfigManager 里"snapshot 对齐 + cached binlog 注入"缝合接缝。反过来（先全量后增量）会让订阅起效慢、且增量要等快照完成才敢发。

**17-2 16 worker hash 保序与 Kafka partition 保序的同构/差异？**
同构：**同 key 恒落同一处理单元**（局部保序）。差异：Kafka 是存储层分区、这里是**分发层 worker**；且全局因果序（全量先于增量）由 dispatchLoop 单协程另保（第 19 课展开）。

**17-3 队列满"丢最老 + `unackedEvicted` 标记" vs 阻塞？为什么必须显式标记？**
丢老保新适合**可从快照重建**的配置流（agent 可重同步）；阻塞适合不可丢的权威数据。显式标记让 agent**知道自己漏了**（走 VersionSet 比对重同步）——静默丢=不可观测的洞。

**17-4 TOO_SLOW 触发后三侧各发生什么？**
Dispatcher：判定/隔离慢会话（不再拖累扇出）；Session：状态置 **TOO_SLOW**、队列驱逐已发生；agent：重连时收到 TOO_SLOW/INVALID_SESSION → 降级**全量恢复**。

**17-5 `ctrlSetReplica` 为什么 fail-closed？举一个同取向的例子。**
**错路由比拒服务危险得多**（路由去错 SET=系统性错乱）。同取向：第 16 课 agentos 的 Ready 校验（未就绪不接流量）、第 25 课 `repair_readonly_guard`（宁不修不乱写）——"失败方向的选择"。

## 第 18 课（5.0 全景）

**18-1 为什么 api-server CRUD"不处理业务配置"？四棒各传什么？**
它管的是**控制面自身元数据**（SET/Kafka/Topic/集群管理）。业务四棒：api-server（写 MySQL+发 binlog）→ fusion（聚合+快照）→ broker（三向合并+推送）→ host-agent（落盘+下发 DPDK）。

**18-2 拆 broker/fusion 的收益？LSMT 类比对应什么？**
**故障域隔离**："fusion 慢只影响快照更新延迟，broker 挂只影响推送不影响快照"。fusion=**SSTable**（重状态、慢、按配置规模扩容）；broker=**MemTable**（轻、无状态、按连接数扩容）。

**18-3 `source_versions` 解决什么接缝？与 17 课对照。**
CA 预计算结果的版本凭据——host-agent 拉完**无缝切回 broker 增量**（不落回全量）。与 17 课两阶段订阅同类：**让"增量起点"有凭据**。

**18-4 "1 亿条"三个不能逼出什么？限频与背压什么关系？**
不能全扫→**scopeId 分片**；不能全内存→**三层存储**（LevelDB/CDB+CRS/MySQL）；不能串行→**Leader-Worker 队列**。限频（Leader 发起侧"不许一次十万"）与背压（消费侧 unackedEvicted/暂停 Poll）是"**不许无限接单**"哲学的两端。

**18-5 LevelDB 为何赢 RocksDB？再举一例。**
轻（单线程写、无后台 compaction）→ 资源受限更可控 + 嵌入式零部署。同类：第 16 课 AgentOS 选 **SQLite**——"**选型不是选最强，是选最匹配**"。

## 第 19 课（南向协议）

**19-1 稀疏 ACK 为什么必须带例外表？**
`start/end` 区间是"整段确认"，但总有**还在处理（not_ack）**与**已失败（failure）**的条目——例外表把它们从区间里"排除出去"；去掉=未完成的被误吞=数据丢失；failure 还要触发重新 Watch 全量。

**19-2 "非阻塞优先级"放弃/换取什么？`MaxPendingVersions=1000` 是哪类背压？**
放弃**抢占式调度**，换**简单可预测**（控制信令不被大流量卡死、不同队列互不拖累）；1000 上限是**拉式背压**——"推不动就停拉"（消费者自限速）。

**19-3 恢复三级阶梯各自的前提条件？**
**增量**前提：session 存活 + 连续性（LocalVersion 有效）；**全量**前提：`INVALID_SESSION`/增量被驱逐（链断）；**QuickRestart** 前提：versionstore/watchstore 完好（重启也先试增量）。从便宜到昂贵，全量永远对但最贵。

**19-4 对齐条件为什么是 `max+1 >= min`？"版本空洞"指什么？**
对齐=**证明无版本空洞**：新会话要"snapshot 全量 + version>N 增量"，两个异步来源（Kafka/fusion）的版本区间必须**连续或重叠**才能拼出无缝全序；空洞=snapshot 与 Kafka 缓存首版本之间的断档——直接发就会漏掉中间变更。

**19-5 单协程与 16 worker 各保哪级序？为什么"全量先于增量"要全局序？**
单协程 dispatchLoop 保**全局 FIFO**（跨会话因果：全量先于增量）；worker hash 保**会话内序**。"全量先于增量"是同一 agent 的**跨事件因果**，而顺序判定发生在 messageCh 入口（任何会话都可能同时有全量与增量在途）→必须由全局单协程排队。

**19-6 `InitFailed`"等自愈" vs "重试 3 次即放弃"？**
配置流的特性是**新版本通知还会再来**（拉取幂等可重试）——失败是"待重试状态"而非终态；适用于幂等可重拉的数据面。反之有副作用/不可逆的任务该放弃 + 告警（重试会放大伤害）。

## 第 20 课（vpc-fusion 上）

**20-1 "节奏翻译器"：三种节奏各是什么？为什么不能并进 api-server？**
api-server 管**命令式/事务式 CRUD**；agent 要**状态式批量快照 + 稳定订阅**；对账要**周期式慢节奏**。三者节奏不可混（硬塞进 api-server：它不认识母机——"母机信息在 agent 那边"，且快照与对账会拖慢 API）。

**20-2 LevelDB 临时工作台：直接写 Redis 不行的两条硬约束？**
① **单 value 大小限制**（大 key 阻塞）；② **不支持范围查询**（LevelDB 有 BytesPrefix 前缀扫描）。合并期需要**随机写 + 范围读**——正是 LevelDB 的强项。

**20-3 fusion 快照分片 vs broker SET 分片：两种哲学？`threshold=10000` 属哪种可控性？**
broker：按**连接归属**（无状态扇出，求**稳定映射**）；fusion：按**配置计数**（有状态构建，求**负载均衡**）。threshold 属"**精确控制单 shard 大小**"——hash 做不到的那种可控性。

**20-4 对账三差异各触发什么动作？为什么说比"事后报告"更进一步？**
Missing→**snapshot 补齐**；Redundant→**cleanconfig 清理**；Mismatch→**snapshot 重建**——对账产出**动作**而非报告（闭环修复）；材料同时澄清"Gen2 没有系统化对账"。

**20-5 故障矩阵"四列全红"的原因？为什么"重复处理→版本冲突"比"任务丢失"更危险？**
message/snapshot 站在**唯一路径**上（所有变更都过它们）→挂=全链断。"错"（复活/版本冲突）比"停"难发现、且可能造成安全事故（`Put(nil)` 复活已删路由→流量发到已销毁母机）。

**20-6 `os.RemoveAll(d.dbPath)` 删整个目录背后的假设？**
**"工作台"假设**：真相在 MySQL/Redis，LevelDB 只是合并过程缓存——重建成本低于维护成本，"**工作台不留在现场**"。

## 第 21 课（vpc-fusion 下）

**21-1 三致命问题？"先看再拿"（LINDEX）为什么优于"先删再看"（BLPop）？**
①非原子→任务丢失；②非原子→重复消费；③无租约→卡死 processing。LINDEX 只**看**不改队列，claim 失败可**原样退回**；BLPop 取出即离队，一旦后续失败（data 被 TTL 清）任务**永久丢失**。

**21-2 Hash Tag 为什么按 `queueName` 而不是 `vpcId`？**
Lua 原子操作边界=**队列**（queue+data+processing 三键必须同槽防 CROSSSLOT）；同队列内原子、**跨队列并行**——**锁的粒度决定并行度**。

**21-3 任务 Lease 30s 与选举 TTL 15s 都改成 5s 会怎样？**
任务 lease 改短：快照构建中途被误判接管→**重复处理**（版本冲突）；选举 TTL 改短：续约抖动即失冠→**Leader 震荡**。两个数字都是"**误判成本 × 接管延迟**"的平衡点（§7.5 的 1/3 比例同理：一次抖动不丢租）。

**21-4 用"状态紊乱三根因"检查任意任务队列？**
清单：**原子性缺口**（claim 是否原子）/ **租约缺失**（卡死能否自愈）/ **自指错误**（初始化存在性检查是否豁免自身）；再加数据语义层（21-1 的 Put/Delete 一类 API 误用）。

**21-5 为什么"1 个 commit 修 28 个文件"比 2000 行的 A 组更惊险？**
A 组是机制重构（可渐进）；B 组修的是"**已删路由复活→流量到销毁母机**"的安全生产事故，根因只是 `Put(key,nil)` 一行 API 语义错误——**破坏只需一行，修复仿造一座**。

**21-6 "读双查、写只新、TTL 退役"为什么优于停机切换/双写双读？**
不停机、可回滚；**写只新=单写点**（无双写不一致风险）；旧格式靠 **24h TTL 自然消亡**后代码退役——迁移的"零操作"终态。

## 第 22 课（修复实录）

**22-1 复述"动刀碰血管"的传导链。**
`限频`（改配置结构）→ 暴露校验空指针 → `租约`（改写路径）→ 暴露 TxPipeline EXECABORT → `Pipeline 过渡` 暴露非原子 → `Lua` 收口。**每次修复都是对运行中的系统动刀，刀口碰到别的血管**——真实修复是连锁反应。

**22-2 8 行修复里两 bug 同框；"当别人的代码 review"检查哪两点？**
① **作用域**：`:=` 是否遮蔽外层 `err`；② **可空性**：`configState` 是否可能为 nil。逐行问三连："**这个变量从哪来、能不能为 nil、错误到哪去了**"。

**22-3 三机制为什么必须一次成型？"接口加 workerID"说明什么？**
Lease（判死）/ Heartbeat（续活）/ Ownership（验身份）是"**任务归属**"的同一问题三面，缺一面就漏一种死法。"接口全部加 workerID"= **身份进类型系统**：所有写路径被编译期强制自报，比"某个分支里校验"可靠（**编译约束 > 运行时约定**）。

**22-4 "先非原子止血、三天后收口"的两个原则？"到期日"怎么体现？**
① **急迫度 > 优雅度**（EXECABORT 是可用性事故，比原子性隐患更急）；② **临时方案必须有到期日**：Commit 4 的注释写明"避免 TxPipeline"，Commit 5（三天后）Lua 收口——**到期兑现写在 commit 序列里**。

**22-5 "缓存即真相"的新义务？与 Typha 同源在哪？**
写路径必须**同步维护缓存**（先读→改→`SaveResourceObj`）+ **DAO 拒绝绕过**（`validateConfigName` 直接报错"please use cache"）；不履行→"真相"与服务端不一致（假真相）。同源：**读放大治理**（Typha 治 k8s API 读放大；这里治 MySQL 读放大）——**换读源不是加索引**。

**22-6 五处附带修 → 审查清单初稿。**
① API 语义吃透（`Put(nil)`≠Delete）；② 自指检查要守卫（初始化查自己先豁免）；③ 控制流意图写对（"跳过校验"≠"跳过一切"）；④ 读放大会换榜（DB→Redis 后 Redis 是新瓶颈）；⑤ 同款手法可复用（atomic+sleep 两处现身）。**总纲：修复窗口=审计窗口**（盯一处修，其他雷现形）。

## 第 23 课（故障全景与多 SET 迁移）

**23-1 为什么唯一需人工的是 MySQL？再找一个"不可再生因而特殊照顾"的对照。**
**自动化边界=真相所在**：无状态/可重启的都能自动复活，**配置存储真相无裁判者**。对照：`versionstore`/`shutdown_marker`——快速重启的"续传依据"也被完整性与校验特殊保护（不可再生→特殊照顾）。

**23-2 Redis 景四层反应各对应哪课机制？自举问题为何是"依赖问题"？**
①双层健康检查（抗抖 3 次判定）；②选举 TTL（20/26 课）；③FetchTask sleep 60s；④心跳自杀 `executeCancel`（21 课）；"Recovery 也跑不了"= **兜底机制的兜底在 Redis 本体**——流程都正确，问题在"依赖是全局单点"（属架构依赖，不属流程缺陷）。

**23-3 "抛异常 > 变慢 > 完全沉默"：为什么 lag/stale 更难值班？限频/背压的角色？**
抛异常自带定位；**lag/stale 是爬坡指标**——没有"事件"只有"趋势"，要在趋势里判断"何时算故障"。限频/背压的角色：**哪一级都不许"无限接单"**，把沉默故障扼杀在积分饱和之前。

**23-4 "断得晚恢复贵"拆三句。**
①**检测晚**（假连真断，keepalive 30-60s 才发现）；②**驱逐狠**（broker 按 1000 水位判死并驱逐未 ACK）；③**恢复重**（增量已被驱逐→只能**全量重建**）。对比 broker 挂（立即断→增量恢复秒级）。

**23-5 "确定性计算替代协商"的两个前提？缺哪个要退回共识算法？**
前提：① 所有参与者收到**相同输入**（控制面统一分发 ResourceCtrlSet 数据——17 课 `SET_RECONCILING`/fail-closed 保这环）；② **相同纯函数**（priority+tiebreak 无歧义）。缺①则参与者输入不一致→必须协商（Raft/ZK 选举）。

**23-6 "宁可重叠不可空窗"出现在哪两处？吞重叠的机制是什么？**
迁移（先建新后拆旧）与恢复（先增量后全量）；吞重叠=**version 单调 + Extension 幂等**（重复事件收敛为一次生效）——**迁移第一原则不是"快"是"不断"**。

## 第 24 课（vpc-agent-framework）

**24-1 从工具包到微内核，框架新接管的四件事？**
① **启动线**（AgentMain 总装配）；② **生命周期**（lifecycle + shutdownstate 状态机）；③ **恢复协议**（marker→startup_recovery 决策链）；④ **对账默认件**（Reconciler 上启动线）。

**24-2 三巨头按"变化速率"分工？**
105 种业务配置（高速变）→ **extension**；Broker 协议与分布式语义（中速变）→ **datasyncer**；内核与驱动（低速但难懂）→ **dataplane**。微内核自己只留装配线 + 生命周期 + 存储 + 对账这些"慢"件。

**24-3 datasyncer"恢复四件+一致性两件"各防什么？首事件屏障为何必须框架做？**
恢复四件：整体恢复编排 / 快速重启决策 / 游标保护 / 重订阅退避。一致性两件：**首事件屏障**（防"事件比订阅先到"）、merge_remote（远端快照与本地合并）。屏障属**订阅语义公理**——业务各做必然不一致，必须框架统一。

**24-4 fake adapter 对 CI 与新人的红利？**
CI：**无内核环境整链可跑**（含对账/下发全流程回归）；新人：无需 DPDK/内核知识即可开发业务 Extension——**降低的是"进入成本"**（对照一代 ibverbs 式门槛）。

**24-5 分层对账与 16 课 inspector 的异同？**
同：都是"对账平台化"（注册 + 泛型 + 策略）。异：**对账对象**不同——16 课对"业务资源"（upstream/res/downstream 各 ext 注册 CheckJob）；24 课框架对"**订阅的 SET 视图**"（core/resource ctrl-set），业务配置仍归 Extension。原则：**对账跟着责任边界走**。

**24-6 "停机留遗言"的第三次出现在哪一层？**
第 **25 课**（host-agent 进程级）：`shutdown_marker`（storage）+ shutdownstate + `startup_recovery` 装配进启动链——Session 层（19）→ 进程层（25）；再往下的下一次若出现，会在**数据面/内核级**（如 DPDK 重建记录）。

## 第 25 课（vpc-host-agent）

**25-1 五段各解决什么？为什么 composer 与 dplane 不能合并？**
①extension 原始对象；②composer **多对象→完整期望态**；③dplane **业务对象→数据面 entry**；④Facade→⑤adapter→内核。不能合并：**关系学（跨对象汇聚）与翻译学（对象→驱动语义）是两种知识**，变化节奏与测试面都不同。

**25-2 中心预计算 vs 本地组合的分工线？各举一例。**
线：**能提前的搬走，必须本地的留下**。例：CA 预计算 `rtable_expanded`（第 18 课，静态可算）搬去中心；composer 保留依赖实时本地状态的组合（session/neighbor/驱动能力，第 25 课）。

**25-3 Runner"串行+keyed 去重"防哪两病？回调栈重计算为何危险？**
串行防**重入/死锁**（composer Recompute 被 datasyncer 回调触发，栈内做重计算会重入）；keyed 去重防**同对象连改的重复计算**（去抖）。回调栈属于别人的执行上下文——**重活必须搬出栈**（异步入 Runner）。

**25-4 `repair_readonly_guard` 与 SHADOW_MODE 打包开关为什么都要？**
两道闸互补：打包开关决定**部署形态**（影子包）；代码守卫是**运行时断言**（就算跑了写路径也拒绝）。防两种事故："包打对了但代码绕过"与"忘用只读包"——**一防误配、一防误码**。

**25-5 "Ready 三层递进"三处各是什么？OnStartupSettled 的关系？**
17 课七阶段引导（进程侧）/ 19 课 Handshake→Watch→Poll（连接侧）/ 25 课 OnStartupSettled（**数据侧：首批配置处理完才算**）。每层把"就绪"推进一步：**进程起 → 连接通 → 有数据**。

**25-6 "54 vs 60+" 并记为何优于擅自选一个？类似互证？**
保留材料原貌可回溯、不制造假权威（两个数可能各有其理）。类似互证：21/23 课选举 Key 前缀不一致——**材料自带裁决**（"面试统一用后者"）时的处理方式：引用裁决 + 如实备注。

## 第 26 课（vpc-base 底座课）

**26-1 用 distributed-task 的同构点说明"第一现场发明、第二现场抽象"。**
`Publish/StartWorker/RecoverTimeoutTasks` 三个 API 名、"列表/有序集合"两把 Redis 结构、worker `dedup id`——与 21 课 fusion 队列逐一对上；**连命名都保留第一消费者的习惯法**：机制在 fusion（第一现场）被发明，在第二/第三消费者出现后被提为库，在底座里"养老"。

**26-2 双实现给上层增加什么义务？**
①**选型责任上移**（库不替你选存储，你要懂 Redis/MySQL 的语义差异）；②**语义一致性义务**（同一任务在两种存储下的行为必须一致——双份测试就是履约成本）。

**26-3 "错比停危险"三重奏各防什么？少任何一层会怎样？**
fail-closed（**准入**：宁拒不错路由）→ readonly guard（**修复**：宁不修不乱写）→ 多次确认（**判定**：宁慢勿误报）。少①：错路由进系统；少②：影子/演练污染数据面；少③：状态抖动被当差异→**错误修复引发二次事故**。

**26-4 echo 的"不改协议/不造流量/首尾配对"能否复用？举例。**
能。例：19 课链路——同一个 `config_id` 的 binlog 在"Kafka 入"与"agent ACK 出"两端各记一笔，差值即端到端耗时；**凡有"同一标识贯穿首尾"的链路都可搭便车**。

**26-5 cache-client（标准件）与 22 课 DAO 拒绝（定制件）为何这么分？**
机制与策略分离：CAS 写/rebuild/重试队列是**通用机制**（任何 Cache-Aside 都要，进底座）；"resourceObj 必须走缓存"是**业务策略**（只有该资源域需要，留业务代码）。分的结果：机制复用（六服务共享）、策略留权（业务自定边界）。

**26-6 收官一问：vpc-base 之于 5.0 ≈ 什么之于什么？**
≈ **模具车间之于产品线**：机制先在这里造好（选举/队列/锁/对账/SDK/守护），六个服务各取一套"出门上班"；也≈"器官库之于身体"（六套服务系统共享同一套器官）。用回望的一句话版本：**"机制先在这里长大"**。
