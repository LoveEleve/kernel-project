## ① 它干了什么——"用户的一句话"与"系统的二十个操作"

**先从反面问**（first-principles §1.1）：如果不做控制面，用户怎么办？

```
"我要隔离开发和生产环境"   → 买两套物理服务器（成本高、不灵活）
"我要控制 VM 之间访问"     → 每台 VM 配 iptables（不可扩展、容易出错）
"我要让外部访问我的服务"   → 买公网 IP 绑 VM（没有负载均衡、没有高可用）
```

**控制面的价值**：把这些手动操作变成 API——**自动化的网络管理**。

**再从正面问**（§1.2）——用户一句话"创建一台 VM，它可以访问公网"，系统要做：

- 分配 IP（从哪个子网？CIDR 还剩多少？）
- 生成路由（去什么网段走什么网关？）
- 配置安全组（默认规则是什么？）
- 下发 DPDK（母机上有没有这个 VPC？要不要先建容器？）

**"控制面的本质：把用户的一句话翻译成 5 层系统中的 20 个操作。"**——这 26 课读的所有机制（分发/对账/恢复），都是在保证这次"翻译"的**正确、及时、不断**。

## ② 链路走查（材料行号）

### 跳 1：六组表的"第一性原理"——缺了它会怎样（first-principles §二）

| 表（组） | 用户需求 | 缺了它/合并它的灾难 | 关键设计 |
|---|---|---|---|
| **t_vpc** | "建一个虚拟网络，CIDR 10.0.0.0/16" | 无容器概念 → **两个子网可能分给不同租户、IP 冲突**；跨子网路由不知道同属一个 VPC | 为子网提供**容器**（同 VPC 内 CIDR 不重叠）+ 为租户提供**隔离边界**（VPC 间 IP 可重叠）；索引 `idx_owner`（"列出我的所有 VPC"） |
| **t_subnet** | "子网是 IP 管理的基本单元" | —— | （§2.2） |
| **t_rtb + t_rtb_route + t_rule**（三件套） | "三个子网共用一套策略" | **合并成一张表的三种灾难**：3 条重复记录 / `UPDATE ... WHERE subnetId IN (1,2,3)` **可能漏更新** / DELETE subnet 1 留下**孤儿数据** | t_rtb=容器、t_rtb_route=条目、t_rule=**绑定关系（M 子网 → 1 rtb）**；`UNIQUE KEY (subnetId)`——**一个子网一个路由表，没有"表级优先级"**（策略冲突在表**条目内**用 priority 解决——**简化设计**） |
| **t_rtable** | "策略展开为转发" | **合并展开的灾难**：改一条策略要更新 100 条转发——**期间新旧共存**；只更新一半 → "VM-1 到 50 走新策略、51 到 100 走旧"——**一致性更差** | **策略（t_rtb_route）与转发（t_rtable）分离**：策略改 1 条立即生效、Fusion **异步展开**逐条更新、**对账检测两者是否一致**；PK `(vpcId, subnet, vmIp)` 由**查询模式驱动**（前缀查询/前缀扫描/精查） |
| **t_security_group + t_security_group_rule** vs ACL | "有状态安全" | **只留 SG**：子网 100 台 VM 禁用 80 端口要**配 100 次** + 每 VM 独立规则**内存 O(VM 数)**；**只留 ACL**："只有 VM-1 能 SSH"做不到 | **两套系统粒度互补**：SG=VM 粒度（绑 ENI、创建时默认附加）、ACL=子网粒度（配 1 次） |
| **t_service + t_route** | "VIP 按权重分给 RS" | 用 t_rtb_route 模拟 → "round-robin"**不是合法 nextHop**（谁做轮询？）→ Agent **没有 RS 列表**无法选路 | **n:1 聚合（多 RS → 一 VIP）与 1:n 路由是两种映射**，不能互相模拟；t_service 带 RS 列表 + weight + **健康状态** |

**读法**：六组表的共同句式——"**若把 A 和 B 合并，会出现哪类不一致/哪类无法表达**"。**表设计的第一性原理不是范式，是"缺了它会漏掉哪种失败"**。

### 跳 2：同一份数据的两种脸——DB 友好 vs 硬件友好（first-principles §四）

```
DB 中的 t_rtable:
  (vpcId, subnet, vmIp, hostIp, remoteType, remoteVpcId)
DPDK 中的 route-table entry:
  (vpcId, dstIp, dstMask, remoteType, remoteIp, remoteVpcId, remoteGwId, hashSelect)
```

**为什么不同**：DB 是"**用户友好的**"——用 `hostIp` 表示下一跳（宿主机 IP 对运维有意义）；DPDK 是"**硬件友好的**"——用 `remoteIp + remoteType`（DPDK 直接用 GRE 封装到 remoteIp）、**`remoteGwId` 是网关索引（不是 IP）**（内部快速查表）、**`hashSelect` 在 DB 里根本不存在**（DPDK 做 ECMP 需要）。**翻译层在 Agent**：`hostIp → remoteIp`（直连）/ `vgwType → remoteType`（类型映射）/ `vgwId 查找 → remoteGwId`（网关索引）。

**为什么不在 DB 里直接存 DPDK 格式**：每次创建 VM 要先查"hostIp 对应的 remoteGwId 是什么"；**网关一变更就要批量更新所有 t_rtable 记录**——"硬件格式"把变化成本传染给了存储（同律：第 25 课 dplane 的"翻译学"单独成层）。

**表间隐式约束与"为什么不用外键"**（§3.1）——五条"不是外键但必须一致"的约束（子网 CIDR ∈ VPC CIDR / VM IP ∈ 子网 / 路由表绑定有效子网 / RS IP ∈ 有效 VM IP / SG 规则引用有效 SG），各有强制方式与违反后果；**不用外键的理由是性能**："大量路由操作的外键检查开销 > 数据的存储开销"→替代方案是**对账延迟校验**：

```sql
reconcile: SELECT * FROM t_rtb_route WHERE rtbId NOT IN (SELECT rtbId FROM t_rtb)
  → 发现孤儿记录 → 告警 → 人工清理
  → 不影响正常操作性能
```

**"对账替代外键"= 把一致性检查从写路径挪到离线**——同族：第 22 课"缓存即真相"（写路径减负）、第 25 课分层对账（谁维护谁对账）。

### 跳 3：从零设计的四步法与"每层延迟估算"（system-design）

**非功能七维量化表**（§1.2）——每条都带验收口径：规模（200 万×50=1 亿条｜DB COUNT）／**收敛延迟（变更→DPDK 生效 p99 < 5s）**／一致性窗口（不一致最多 24h｜reconcile diff 归零）／可用性（99.99%，年故障 < 52min）／隔离（单 VPC 故障不外溢）／扩容（<5min）／回滚（<10min，窗口 72h）。

**八步延迟预算**（§3.1 原文摘录）——p99<5s 是怎么算出来的：

| 步 | 内容 | 预算 |
|---|---|---|
| 1 | API 接收（HTTP+校验+鉴权） | ~10ms |
| 2 | 写 MySQL（INSERT+binlog 产生） | ~10ms + 1ms |
| 3 | 写 Kafka（acks=all + ISR） | ~5ms + 5ms |
| 4 | **Fusion 消费**（poll 窗口 + 反序列化 + LevelDB.Put + Pipeline） | **1-5s（窗口）** + 0.1 + 1 + 1ms |
| 5 | 快照生成（**TaskIntervalMs=60s** 周期 + 加载 + 合并 + 压缩 + 落表） | 周期 60s + 50ms + 10ms + 5ms + 20ms |
| 6 | Broker Watch（**1-5s 窗口** + 三向合并 + 找 Agent） | **1-5s** + 5ms + 1ms |
| 7 | tRPC 推送（序列化 + RTT） | ~5ms + ~5ms |
| 8 | Agent 下发（校验 + DPDK add_route） | ~0.1ms + ~1ms |

**总延迟：最快 ~1s（binlog 恰在 poll 窗口内）／p50 3-5s／p99 5-10s**——材料点明 p99 的构成："**Fusion poll 窗口 + Broker Watch 窗口叠加**"。

**读法**：延迟是最难拍脑袋的东西——这里把它拆成**八个可审计数字**，并区分"计算"与"窗口"：**p99 由窗口主导，优化方向是缩窗口，不是抠毫秒**。第 18 课"秒级"承诺的工程底稿就在这张表里。（⚠️ 口径并记：本材料快照压缩写 **ZSTD**，第 20 课材料写 **GZIP**——两处口径不一致，如实并列。）

### 跳 4：四场选型辩论——"如果选错会怎样"（tradeoff-analysis）

- **Event Bus：为什么不选 Redis Streams**（§1.2，两大致命缺陷）：
  - **offset 持久化不可靠**：Redis 重启 → Consumer Group offset 丢失 → **从 0 重放**——"200 万 VPC 的历史 binlog 全部重新处理……重放时间：百万条 × 10ms ≈ **2.8h**"（LevelDB.Put 幂等保证结果正确，但 CPU/网络白烧；AOF 缓解、最多丢 1s）；
  - **Redis 是 AP——分区下 Consumer Group 状态分裂**：两侧各自认为拥有 partition 消费权 → 同一条 binlog 双消费 → **"快照版本冲突"**——注意：**binlog 重复消费幂等能兜住，快照冲突兜不住**，这条才是"幂等救不了"的缺陷。
  - **"如果现在重选"**（§1.3）：① Redis Streams + AOF + 版本号去重（增复杂度但可行）→ ② Pulsar（自建 BookKeeper + ZK，**运维成本太高**）→ ③ RabbitMQ（Erlang 栈，**团队无经验**）——**排序依据全是运维现实，不是技术时髦**。
- **本地缓存：先列"使用特征"再选**（§3.1）——写：每秒几十~几百次 Put；读：快照生成时**前缀迭代全量扫描**；量：12KB × 200 万 = **24GB**；生命周期：**临时**（合并完即删）；并发：**单 Worker 写**。然后才是四选项对照（LevelDB ✅最优 / RocksDB ⚠️**过度设计** / BoltDB ⚠️B-Tree 写放大 / 纯内存 ✅最快……）——"**选型表把使用特征当尺子**"（与第 18 课"选最匹配非最强"同律）。
- **分布式锁：一场"故障注入"级的四方对比**（§2.1）——**ZK Lock（nfv-proxy 原方案）**：网络抖动 10s → session timeout **400s** → listener LOST → `lock.release() + os._exit(0)` → **所有 Worker 同时 suicide = 全量雪崩**（恢复后无人活、分钟级启动）；问题根源三条：**timeout 太长 / suicide 不可逆 / 没有优雅降级**。**DB Lock（db_dlock）**：心跳 SQL 失败计数 ≥2 → 抛 `LockPreempted` 才自杀——**检测 2×15s+5s = 35s（vs ZK 400s+）**、**只有持锁 Worker 受影响（非全量雪崩）**、且"心跳可观测——`SELECT` 查 `t_merge_lock` 就看到谁持锁"。**Redis Lock 为什么不行**："`SET NX` 在网络分区下**不保证互斥**"（A 无法续约、B `SET NX` 成功 → **双持锁**）——"**分布式锁需要强一致存储——Redis 不适合**"。**最终判断**："DB Lock 是最 pragmatic 的选择——复用已有 CDB、心跳可观测、强一致保证互斥"；代价=**822 行**（"不是 free lunch"）——第 29 课正主。
- **下发：三模型延迟表**（§4.1）——Push(tRPC) 最快 **<1ms** / 典型 10-100ms；Pull 最快=poll_interval、典型 0.5×interval、最坏 interval；Long-Poll 与 Push 同量级——**按"变更频率 × 延迟容忍"选型**。

### 跳 5：故障矩阵——"每个故障一份 procedure"（failure-mode-matrix）

**组织法升级**：每个故障六段式——"**现象 → 检测 → 影响面 → 恢复 Procedure → 验证方法 → 预防措施**"+ **RTO**（比第 23 课的五景全景表更"值班化"）。

**MySQL 三 case 抽样**（§1.1）：主库宕机（Blast Radius=全 Region 写停｜**CDB 自动 failover，无需人工**｜RTO <30s）／查询超时（Fusion latency p99 升高 → 查 slow log → 必要时 kill）／磁盘满（RTO 30min｜使用率 80% 告警）。**主库宕机 oncall 七步**：`30s 确认监控 → 1min 看 API 日志 → 2min 看 Kafka 有无新 binlog（没有=写入停）→ 5min 等 failover → 验证写入 → 确认 lag 恢复 → 复盘（半同步复制应无损）`——**连"怎么确认修好了"都写了**。

**历史 Bug 回溯表**（§二，五条——注意它的最后一列）：

| Bug | 发现方式 | 根因 | 修复行数 | **为什么之前没发现** |
|---|---|---|---|---|
| **DeleteConfig Put(nil)** | 对账 Redundant 增长 | LevelDB Delete 语义错误 | **1 行** | 单元测试只测 LevelDB，**没测对账联动** |
| skipPath 状态泄漏 | 监控发现不该同步的路径被同步 | 重新初始化没清空 skipPath set | 144 行 | 该路径同步是"**静默**"的——不影响业务但埋隐患 |
| **ZK Lock 雪崩** | ZK 网络抖动后所有 Worker 同时死 | **listener LOST → suicide** | **822 行（新 db_dlock）** | ZK session timeout 是已知设计，**雪崩风险被低估** |
| Kafka Consumer 假死 | 小时级消息不消费 | Consumer 无心跳但进程存活 | 121 行 | **进程存活线掩盖了消费停止** |
| VPCGW 切主漏 VPC | 切主后部分 VPC 不通 | `do_switch` 没回放 VpcBinlog | 4 行 | 触发概率低（只有新创建 VPC 受影响） |

**影响面分级**（§三）：P0（年 <1 次，RTO <5min）：MySQL 主库 / Kafka 全集群 / 全部 Broker；P1（年 1-3 次，RTO <30min）：Redis 全集群 / Fusion LevelDB 损坏 / DeleteConfig 类 Bug。

**"为什么之前没发现"这一列是精髓**：它把每个历史 bug 变成**检测缺口清单**（单测盲区 / 静默路径 / 风险低估 / 存活假象 / 低概率）——与第 27 课"双盲区"、第 22 课"修复窗口=审计窗口"同一条脉。

## ③ 设计推导（问题树）

**Q1：四篇的组织法有什么共同点？**
都是"**对照与前提**"驱动：表=**缺了会怎样**；延迟=**每层多少毫秒**；选型=**如果重选/选错**；故障=**怎么检测怎么恢复**——四个文档把散落在系统里的**隐性判断全部变成可对质条目**。这正是本课程 26 课的审查方法论（回源、并记、逐条对质）的"**出题人视角**"：会这么写文档的人，就是会用这套尺子量你的人。

**Q2："用户想要简单、系统需要复杂"在 26 课里的表现？**
控制面=**把一句话翻译成 20 个操作**——S 线的所有机制（分发/对账/恢复）都是在保这次翻译的**正确、及时、不断**；第 18 课"管 VM 路由只是 1/74"是同一句的另一面（用户以为一句话，系统有 74 种名词）。

**Q3：八步延迟预算的方法论？**
**拆成可审计数字 + 区分"计算"与"窗口"**——p99 由 Fusion poll 窗口 + Broker Watch 窗口叠加主导（1-5s ×2）：**要改进 p99，去缩窗口（拉高 poll 频率/长轮询），而不是在微秒级的计算项上抠**。没有这张表，"p99<5s"是一句口号；有了它，是一份**分工到每层的预算合同**。

**Q4："为什么之前没发现"列的深层价值？**
它把事故史变成**检测能力的缺口目录**：单测盲区（Put(nil)——只测存储没测联动）、静默路径（skipPath）、风险低估（ZK 雪崩）、存活假象（假死——**存活≠在干活**）、低概率（切主）。**与 23 课"双盲区"、27 课"传感器被蒙"同族**——一个成熟控制面的标志是：**它知道自己的仪表盘哪里是瞎的**。

**Q5：表中"ZK Lock 雪崩（822 行 → 新 db_dlock）"与本课程的哪条线接上？**
这是 **29 课（分支族实录）的主角之一**——第 4 课读过 ZK 的 session/ephemeral 语义，第 22-23 课读过"ZK 作为锁的雪崩风险被低估"，这里直接给出了事故名与修复规模（**822 行**）。"ZY 锁→DB 锁"的一代工程史，正好由加餐批最后一课收尾。

## ⑤ 验收题
