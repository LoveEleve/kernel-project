## 0. 术语速查

| 术语 | 含义 |
|---|---|
| **Gen3 / vpc5.0** | 控制面第三代（2024 年起）：**核心目标=完全去掉 ZK 依赖**，Go 重写，微服务 |
| **10 个子项目** | 6 个独立服务（api-server / fusion / broker / host-agent / computation-agent / vpc-ops）+ 3 个 Go 库（vpc-base / vpc-protos / vpc-agent-framework）+ **1 个 AI 工具集（skills）** |

## ① 它干了什么——"创建一台 VM"在三代之间

用户点"创建 VM"，配置要走到母机。**Gen3 的完整路径**（材料 §3.3 原文流程）：

```
用户创建 VM
  ↓ vpc-api-server 写 MySQL + 发 Kafka binlog（protobuf；per-scope version 递增）
  ↓ vpc-fusion 消费 binlog → 存 Redis 聚合 → 生成 LevelDB 快照 → 写 t_generic_snapshot 表
  ↓ vpc-broker 经 fusion-sdk 直读 CDB/CRS 快照 + 拉 Kafka 增量 → 三向合并
  ↓ tRPC 推送给 host-agent（protobuf over gRPC）
  ↓ host-agent Extension 持久化到 LevelDB → 下发 DPDK（Vpcsp 协议）
```

同样的旅程在三代的代价（材料 §1 能力对照表的四行，直接抄）：

| 业务能力 | Gen1 / Gen2 | **Gen3** |
|---|---|---|
| 配置变更生效延迟 | 分钟级（ZK Watch + diff） | **秒级（Kafka binlog + tRPC Stream）** |
| agent 重启恢复 | 30-40 分钟（Gen1）/ 秒级（Gen2 CKV） | **秒级（LevelDB 本地缓存）** |
| 配置对账 | 无系统化对账 | **独立 reconcile 模块（全量每天 + 变动 5 分钟）** |
| 配置清理 | 无独立清理模块 | **独立 cleanconfig 模块（定时 + 事件触发）** |

**一句话**：三代换的是"分发工程学"——**分钟级 → 秒级，靠换分发材质（ZK Watch → Kafka binlog + tRPC Stream）与换恢复策略（重注册 → 本地缓存）**；"30-40 分钟"这个第 4 课读过的数字，在这里有了官方对照。

## ② 链路走查（材料行号）

### 跳 1：10 个子项目——一张地图（overview §二）

**6 个独立部署服务**（§2.1）：

| # | 子项目 | 部署位置 | 一句话职责 |
|---|---|---|---|
| 1 | **vpc-api-server** | 中心集群（多副本） | 接入层 API + Saga CRUD + Kafka binlog 分发 |
| 2 | **vpc-fusion** | 中心集群（Leader-Worker） | 配置中转 + 快照构建 + 对账 + 清理 |
| 3 | **vpc-broker** | 中心集群（**按 SET 分片**） | 无状态扇出 + tRPC Stream 推送（=S2a 读过的那个） |
| 4 | **vpc-host-agent** | **每台母机** | 母机 daemon + 54 Extension 转发配置到数据面 |
| 5 | **computation-agent** | 中心集群 | **预计算服务**（路由表展开 / VM 邻居表展开） |
| 6 | **vpc-ops** | 中心集群 | 运维编排中间层（**Python** + Celery） |

**3 个 Go 库**（§2.2）：`vpc-base`（16+ 公共包）/ `vpc-protos`（**代码生成器**，105 配置类型）/ `vpc-agent-framework`（Agent 微内核：DataSyncer + Extension + Storage + DataPlane + Reconciler——**S3 的主角**）。

**1 个 AI 工具集**（§2.3）：`skills`——11 个 CodeBuddy/AI agent 开发辅助 skill（extension-generator、reconcile-task-generator、dplane-assembler…）——**明确标注"非运行时组件"**。它出现在架构文档里这件事本身，是 2024 代际的注脚：**"人怎样写代码"被写进了系统文档**。

### 跳 2：两个反直觉认知（overview §3.3 + §二）

**认知一：api-server 不处理业务配置**。容易混淆的点：`vpc-api-server` 的 CRUD handler 处理的是 **5.0 控制面自身的元数据**（SET / Kafka / Topic / Fusion / Broker 集群管理、资源绑定）——**VM/ENI/路由/ACL 这些业务配置根本不走它**，而是"写 MySQL + 发 Kafka binlog"之后，由 **fusion → broker → agent** 接力分发（见 ① 的流程图）。

**认知二：静态结构的"三三制"**。6 服务里有 3 个在"分发链"上（api-server → fusion → broker → host-agent 四棒中的三棒）、1 个在"算力"上（computation-agent）、1 个在"运维"上（vpc-ops）；3 个库分别是"地基"（base）、"契约"（protos）、"内核"（framework）。**读 5.0 的地图先记住：分发是主干，计算与运维是两只手，契约（protos）是骨架。**

### 跳 3：规模账本——数字逼出来的设计（capabilities §一/§三）

**规模表**（§3.1）：广州单地域 **200 万 VPC**；配置类型 **105 = 74 业务 + 15 控制 + 8 fusion + 8 api_server**；单 VPC 平均 ~50 条 → **总量 ~1 亿条**；变更**每秒数十次**；**数万台母机**；54 Extension；多 SET。

先泼一盆冷水（§1.1）：**"VPC 控制面 = 管 VM 路由"只覆盖业务的 1/74**——74 种业务配置分 9 域：路由 12、网络对象 15、ACL 7、高可用 3、流量镜像 6、服务/网关 12、可观测 2、跨 AZ 统计 3、其他 14+。**每种配置类型都有独立的 binlog 流、快照、Extension 处理逻辑**——"这是项目复杂度的核心"（§1.2 原文）。

**"1 亿条"的三个不能**（§3.2）：

- **不能全量扫描** → 必须按 VPC 分片（**fusion 按 scopeId 分任务**）；
- **不能全内存** → 必须 LevelDB 临时合并缓存 + CDB/CRS 持久化 + MySQL 全量表（**三层存储各司其职**）；
- **不能串行处理** → 必须 Leader-Worker 分布式任务队列——**"这是 bugfix/disorder 修的核心"**（第 21 课的伏笔，材料自己标好了）。

**"每秒数十"逼出**：高吞吐消费 + **增量合并（不能全量重建）** + **限频**——"Leader 不能一次发 10 万任务压爆 Redis"（**背压再现**：第 17 课的 `unackedEvicted` 在中心侧的同族）。**"数万台母机"逼出**：SET 分片 + 海量长连接 + **agent 重启不惊群**（LevelDB 本地缓存秒级恢复——"30-40 分钟"之痛的终局答案）。

## ③ 设计推导：材料自带的"六问"

这份材料罕见地自带"面试追问"式决策问答（overview §四），逐条转述：

**Q1 为什么 tRPC 不用 gRPC/HTTP？** 内部 RPC 标准 + **Polaris 服务发现**深度集成；**原生 server streaming** 适合 broker→agent 长连接推送场景；三个 proto 各司其职（`syncer.proto` 双向流 / `reporter.proto` 上报 / `discover.proto` 发现）。

**Q2 为什么 LevelDB 不用 RocksDB？** RocksDB 更强（列族、迭代器丰富），LevelDB 更轻（**单线程写入、无后台 compaction 线程**）——"母机资源受限场景下更可控"。三处用法各有深意：fusion 存快照（**临时缓存，合并完删除**）/ broker 存 binlog 持久化 / agent 存本地缓存（重启秒级恢复）；且**健康检查失败自动降级到内存存储**。**"选型不是选最强，是选最匹配"**——对照第 16 课 AgentOS 选 SQLite 而非分布式 DB。

**Q3 为什么拆 broker 和 fusion？**（材料自评为"Gen3 最核心的架构决策之一"）

| 维度 | vpc-fusion | vpc-broker |
|---|---|---|
| 状态 | **有状态**（Leader-Worker，Redis 协调） | **无状态**（水平扩展） |
| 计算密度 | **重逻辑**（binlog 合并、快照、对账） | **轻逻辑**（BTree 版本索引 + 16 worker） |
| 扩容维度 | 按**配置规模** | 按**母机连接数** |
| 类比 | LSMT 的 **SSTable** | LSMT 的 **MemTable** |

不拆的问题："母机连接数会拖慢快照构建——两个职责互相影响"；拆开后：**"fusion 慢一点只影响快照更新延迟，broker 挂了只影响推送不影响快照"——故障域隔离**。

**Q4 为什么有 computation-agent？** host-agent 冷启动要展开路由表（关联 ENI/Subnet/RemoteGw 多表），大规模 VPC（几万条路由）本地展开开销大、拖慢冷启动 → **计算上移**：CA 复用 vpc-agent-framework（`agent_role: "computation"`）、订阅同一批 HOST Broker、结果存 LevelDB；响应携带 **`source_versions`，host-agent 拿到后可无缝切回 broker 增量订阅**（接缝克星再现——第 17 课"snapshot 对齐 + cached binlog 注入"的姐妹设计）。两种展开：`rtable_expanded`（+NextHop/DstMask/ZoneGwIPs）与 `vmentry_expanded`（mac/host_ip）；`ZoneGwIPs` 存全量 AZ 网关 IP，**FetchSnapshot 时按请求 zone_id 过滤**。

**Q5 为什么 vpc-ops 用 Python？** 复用 ATE（内部 Celery 框架）+ Python 运维生态 + **不在数据热路径上**（延迟不敏感）+ 历史基建——**"热路径用 Go、编排用 Python"的分工**。

**Q6 为什么 vpc-protos 是元数据驱动核心？** **Gen1/Gen2 的问题**：每种配置类型（VM/ENI/Route/ACL…）都要手写四样——DB Model（Python class）/ ZK 路径处理 / merge 逻辑 / agent 下发逻辑，**加一种新配置类型要改 10+ 个文件**。**Gen3 的方案**：手写一个 **txtpb** → 自动生成五样——proto 定义 / Go GORM Model / SQL DDL / gRPC/tRPC 桩代码 / **运行时 registry 注册**——**加新类型只改 1 个 txtpb 文件、零改动其他代码**。105 = 74 业务 + 15 控制 + 8 fusion + 8 api_server；快照落地 `t_generic_snapshot` 表（"generic"一词本身就是红利）。

**综合问：'去掉 ZK'之后，ZK 的职责去哪了？** 分发材质（Kafka + tRPC Stream）、记账（MySQL + Redis + LevelDB 三层）、对账（fusion 的 reconcile 模块）、清理（cleanconfig 模块）——**ZK 不是被'删掉'的，是被整个体系分摊掉的**。三代进化的本质：**把一棵树，换成了一队流水线。**
