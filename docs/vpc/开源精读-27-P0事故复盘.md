## 0. 术语速查

| 术语 | 含义 |
|---|---|
| **uniqVpcId** | VPC 的全局唯一 ID——由 `vpc_id + count（重用次数）` 打包加密而来（扩展欧几里得**模逆**） |
| **VPC_BIT_LEN = 20** | vpcId 占 20 位 = **1,048,576 个值**——**ID 空间是循环的**：自增每 +2^20 就回绕一次 |
| **跃迁保护** | 自增 ID 接近 `1,048,576 × N`（提前 1000）时，**自动跳到 `N×2^20 + 65535`**——跳过冲突区间 |
| **冲突区间 0~65534** | 回绕后低 20 位若落在这段，可能与**旧 vpcId** 撞车——这就是"回绕"与"重用"的接缝 |
| **get_auto_increment 失效** | 2025-09-30 的 schema 参数改动，底层 ORM 实现差异 → 跃迁保护**误判"还没到阈值"** |
| **安灯工单** | 内部事故升级流程（Lighthouse 报障 → VPC 侧卷入） |
| **两种报错** | 类型 1：`uniqVpcId=null`（INSERT 主键冲突，4 条）；类型 2：`AppIdMismatch`（反解到**别人家的** vpcId，1032 条） |

## ① 它干了什么——用一行算术讲完这场 P0

**事故当天，广州的 VPC 自增 ID 长到了 4,195,297。** 把它代入编码规则——低 20 位 = `4,195,297 - 4 × 1,048,576 = **1,093**`——落进了**冲突区间（0~65,534）**：

- 新 VPC 的 `uniqVpcId` 与**旧 vpcId 的编码空间重叠**；
- 轻则 INSERT 主键冲突（创建直接失败：`uniqVpcId=null`，4 条）；
- 重则**反解出别人家的 vpcId**——"VPC 创建成功，但不属于你"（`AppIdMismatch`，1032 条）。

**本应拦住它的"跃迁保护"**（自增接近临界时自动跳过冲突带）**失灵了**——2025-09-30 一次看似无关的 schema 参数改动，让 `get_auto_increment` 返回错误值，保护误判"还没到阈值"。

**修复也是一道数学题**：DBA 第一次 `+100` 无效（低 20 位 1,093 还在冲突带）；第二次直接跳到 **4,720,720**（低 20 位 `526,416 > 65,535`）——**现场恢复**。

**一句话**：这是一场"**ID 循环空间 + 跳栏失灵**"的事故——**所有把 ID 当循环资源用的系统，都住在一个随时可能回荡的钟形空间里**；本次是"跳栏"（跃迁保护）因为一次依赖升级而崴脚。

### 跳 2：算法与跃迁保护——"ID 空间的钟形回声"（incident §3.1-§3.4）

**唯一 ID 生成三件套**（§3.1，源码 `sdn_oss/common/vpc_id_util.py:246-257`、`common/id_util.py:160-181`）：

```python
VPC_BIT_LEN = 20  # vpcId 占 20 位 = 1,048,576 个值
# 编码: count（重用次数）放高位, vpc_id 放低 20 位
def encode_uniq_vpc_id(vpc_id, count):
    return encode_uniq_id('vpc', ((count << VPC_BIT_LEN) | vpc_id))
# 解码: 低 20 位 = vpc_id, 高位 = count
def decode_uniq_vpc_id(uniq_id):
    prefix, postfix = decode_uniq_id(uniq_id)
    return prefix & ((1 << VPC_BIT_LEN) - 1), prefix >> VPC_BIT_LEN, postfix
```

- 外层再包一层**扩展欧几里得模逆**（`inverse(a, b)`——"`ax + by = gcd(a,b)`"）做**可逆混淆**：让 uniqVpcId 看上去随机、但可无损反解；
- 于是形成"**ID 钟形空间**"：自增 ID 每 +1,048,576，低 20 位**回绕一次**——回绕就可能撞上旧 vpcId。

**跃迁保护**（§3.4）——跳栏：

```
当 DB 自增 ID 接近 1,048,576 × N 时（提前 1000）:
  → 自动将 auto_increment 跳到 1,048,576 × N + 65535
  → 跳过冲突区间（0 ~ 65534）
实现: get_auto_increment() 定期检查当前自增值
      → 判断是否接近 2^20 的倍数 → 是 → ALTER TABLE t_vpc AUTO_INCREMENT = 目标值
```

**§3.2 两种模式——冲突带为什么恰好是 0~65,534**：

- **小于 65,535 的 vpcId（旧模式）**：地域内唯一、**可被不同租户复用**——decode 后低 20 位就是**真实 vpcId**（即**旧 vpcId 的真实值域 = [0, 65,534]**）；
- **大于 65,535 的 vpcId（新模式，CCN 等需求）**：**全球唯一分配**、按需投放；**DB 自增 ID 作为"对象 ID"参与 encode**——decode 后低 20 位是**自增 ID 的低 20 位（不是真实 vpcId）**。

**§3.3 材料原文的完整冲突算式**：

```
自增 ID = 4,195,397 = 1,048,576 × 4 + 1,093
  → decode 低 20 位 = 1,093
  → 与 vpcId=1093 的旧 VPC 冲突
  → 租户 A 创建新 VPC → uniqVpcId 反解 → vpcId=1093
  → vpcId=1093 属于租户 B → "资源不在指定 AppId 下"
```

**原理收口**：回绕带**恰好叠在旧 vpcId 的真实值域上**——K < 65,535 就撞进"旧模式 ID 的户籍地"；而旧 vpcId **还允许跨租户复用**，撞车的后果直接升级为"**资源落在别人的 AppId 下**"。**跳栏就是把这条"户籍地"空出来**。

### 跳 3：BUG 的引入与测试盲区——"跳栏为什么没跳"（incident §3.5/§3.6）

**BUG 引入**（§3.5）——一次"看起来无害的规范化"：

```
2025.09.30 的特性变更:
  目的: 新增 schema 入参，解决多 schema 下 get_auto_increment 表名传递不规范
  改动: 给 ORM 框架的 get_auto_increment 调用增加 schema 参数
BUG:
  底层 ORM 框架实现差异 → get_auto_increment 返回错误值
  → 跃迁保护误判"还没到阈值"（实际已经到了）
  → auto_increment 持续增长，进入冲突区间
  → 新创建的 VPC 的 uniqVpcId 与旧 vpcId 冲突
```

**读法**：改的是"**传参规范**"，坏的是"**保护的输入**"——`get_auto_increment` 的返回值就是跃迁保护的**传感器信号**；传感器被蒙了一层（错误值），跳栏在关键时刻没起跳。**任何"基础设施级函数"的语义，都隐含在依赖它的保护机制里**——改规范的人只看到调用点，看不到保护环。

**为什么测试没发现**（§3.6）——**两个盲区**：

- **环境盲区**："测试主干环境的自增 ID **已超过 1000 万** → 跃迁保护**永远不会触发**（已经跳过了所有冲突区间）→ **不具备验证条件**"——测试环境**跑得太超前**，反而永久失去了触发窗口；
- **告警盲区**："香港一直有 `get vpc curr increment not exists` 告警 → 说明获取 auto_increment 偶尔失败 → 但香港的自增 ID 还没到达临界值 → **告警存在数月但未引起重视**"——**预警信号存在 ≠ 被管理**（没有 owner/阈值定义/升级路径的告警=噪音）。

**两条合起来**：**边界条件不在常规环境里（主干跑过头），预警信号不在常规流程里（香港挂数月）**——两个盲区叠着，P0 才成立。

### 跳 4：DBA 修复的数学验证——"紧急操作也有正确性条件"（incident §四）

**第一次尝试（+100）→ 无效**：

```
4,195,397 = 1,048,576 × 4 + 1,093
             decode 低 20 位 = 1,093
             1,093 < 65,535 → 仍在冲突区间 → 无效！
```

**第二次尝试（+500,000）→ 有效**：

```
4,720,720 = 1,048,576 × 4 + 526,416
             decode 低 20 位 = 526,416
             526,416 > 65,535 → 已跳过冲突区间 → 有效！
```

**材料原话**："**不是随便加个数就行的——必须确保低 20 位落在 65,535 之上。+100 不行，+500,000 可以。**"——P0 里的 hot fix 是**带着数学条件的一次跳栏**：**紧急 ≠ 降标**（对照第 22 课"8 行修复两个 bug"：hot fix 的正确性从不因"急"而打折）。

### 跳 5：两种报错与八项改进——"脏数据分两类，防护分三层"（incident §五/§六）

**两种报错，两种伤害**（§五）：

| 类型 | 症状 | 根因 | 数量 |
|---|---|---|---|
| 1 | VPC 创建**直接失败**（`InternalError`；DB 里 `uniqVpcId` 为 null） | 生成的 uniqVpcId 与 DB 已有主键**冲突 → INSERT 失败** | **4 条** |
| 2 | 创建**成功但不可用**（`UnsupportedOperation.AppIdMismatch`） | **反解出的 vpcId 属于另一个租户**——"例: 反解出 vpcId=606，但 DB 中 vpcId=606 属于另一个租户"→ 查 t_vpc → owner 不匹配 → 报错 | **1032 条** |

**类型 2 比类型 1 阴险**：类型 1 当场炸（用户马上知道）；类型 2 是"创建成功了，但不是你的"——**静默错配**，要靠对账/告警才发现（对照 23 课"错比停危险"）。

**八项改进**（§六全表）：① 广州 +500K 止血 ✅ / ② 修复 `get_auto_increment` ORM 兼容性 BUG ✅ 发布 / ③ 配置 OSS 告警（`get vpc curr increment not exists`）✅ / ④ 配置 CGW diff vpc owner **电话告警** ✅ / ⑤ 脏数据联系用户清理（进行中）/ ⑥ 跃迁逻辑优化（待排期）/ ⑦ 补 VPCID 申请自动化用例（待排期）/ ⑧ **梳理其他配置（安全组等）的自增 ID 跃迁逻辑**（待排期）。

**分布读法**：前四项（止血 + 修复 + 两条告警）已办——**恢复与观测优先**；⑥⑦⑧ 排队——**根因预防与同类排查是慢工程**。其中 **⑧ 最有杠杆**：它不仅修本案，还要回答"**这套系统里还有多少个同样的跳栏？**"——**把个案变成风险面清查**，是复盘的最高级动作。

## ③ 设计推导（问题树）

**Q1：为什么"给调用加个 schema 参数"能打穿 P0？**
因为改的是**传参规范**，坏的是**保护的输入**——`get_auto_increment` 是跃迁保护的传感器，返回值错了，跳栏的判定就错了。**基础设施函数的语义隐含在所有依赖它的保护里**——这是"修复/重构引入新 bug"家族的又一员（22 课变量遮蔽、21 课 EXECABORT 同族）：**动规范的人看不见保护环**。

**Q2：两个测试盲区，各是环境问题还是流程问题？**
① 环境盲区（主干自增超 1000 万）：**测试环境的"超前"消掉了触发条件**——是**环境治理问题**（需要能构造"临界态"的环境/测试手段，如第 22 课 65 题里"补自动化用例"）。② 告警盲区（香港挂数月）：**告警没有归属与升级路径**——是**流程问题**（owner/阈值/升级三件事，缺一即噪音）。

**Q3：止血快、根因为何要 3 小时？**
止血是**绕过病灶**（DBA 数学，两次试探）；根因是**找到病灶**（跨系统追链：告警 → Lighthouse → VPC → 自增序列 → ORM → 2025.09.30 特性）。**P0 的正确姿势：先绕过（恢复业务）、再解剖（防复发）**——顺序反了就会在抢救室里做病理研究。

**Q4："低 20 位 > 65,535"这条条件为什么值得单独记？**
因为它证明"**紧急操作也有正确性条件**"——+100 的直觉忽略了冲突带的存在；+500,000 是算过的。**P0 中最危险的时刻，往往是为了快而跳过验证的时刻**——本案例恰好相反：DBA 用数学把 hot fix 做对了。

**Q5：八项改进的分布说明什么？**
"**恢复与观测先行（1-4 已办）、预防与清查慢行（6-8 排队）**"是事故复盘的常态——但分布本身也暴露风险：**⑧ 同类排查拖得越久，第二起 P0 的倒计时走得越久**。

**Q6：与第 22 课"分支级修复实录"拼起来看？**
| 维度 | 22 课（分支级） | 本课（生产级 P0） |
|---|---|---|
| 发现的途径 | 开发自查/审查 | 值班告警 → 安灯 → 跨团队 |
| 影响面 | 模块内 | **一个地域的 VPC 创建面**（1032 条脏数据） |
| 修复要求 | can be 三天后 Lua 收口 | **7 小时闭环，hot fix 带数学条件** |
| 共同病根 | **"看起来无关的改动"打穿"隐含假设"** | 同左（schema 参数 vs 变量遮蔽/API 语义） |
| 共同对策 | 修复窗口=审计窗口；把隐含假设**显式化**（测试/告警/注释） | 同左（⑧=把同类假设全部翻出来） |
