# 全链路走查：一次配置变更的 12 跳与每跳的失败账

> 定位：横向收官实践件——把"按下一个按钮 → 内核生效"拆成 12 跳，逐跳回答四个问题：
> **失败长什么样 / 谁兜底 / 多久自愈 / 面试怎么说**。
> 纪律：**不引入新断言**——每跳均溯源到九课（`开源精读-01..09`）、`开源精读-收口总章.md`、`vpc-lab/review-log.md`（R1-R4）与材料。
> 标本：一代链"给路由表加一条路由"（二代/三代差异随跳标注）。**失败账总表见文末。**

## 0. 读法

12 跳 = 写侧 3（校验/Saga/原子入箱）+ 出箱与通道 2（Outbox/Kafka）+ 分发 2（消费落 ZK/快照）+ 端侧 2（agent 消费/就绪与对账）+ 落地 2（下发/转发）+ 收口 1（对账闭环）。

---

### 跳 1 · 入口：校验与配额

**机制**：信封校验 / region / 分布式令牌桶（`sdn-oss/api/cgi_base_tvpc.py`；R1）。
**失败的样子**：直接拒绝，调用方拿到错误码。
**谁兜底**：不需要——**副作用为零**。
**自愈**：即时（重试合法请求即可）。
**面试口径**：失败前置化——"能拒绝的都拒绝在写之前"。

### 跳 2 · Saga 正步骤链

**机制**：`add_step(forward, backward, skip_on_codes)` 正序执行；失败**逆序回滚**（`sdn-oss/api/tvpc_handle.py`；R1 实证）。
**失败的样子**：某步失败 → 已完成步骤全部逆序补偿。
**谁兜底**：补偿链本身；**回滚失败 → Redis 24h + `Revert.TVPC.*` 重试接口 + 告警**（R1）。
**自愈**：即时回滚；补偿失败靠重试接口/对账。
**OSS 对照**：TaskFlow `RevertAll`/`REVERT_FAILURE`（同一课题的另一种答卷）。
**面试口径**：Saga 是"一次事务的语义"——代价是补偿必须完备（不可回滚步骤只能放最后）。

### 跳 3 · 原子点：业务表 + Outbox 同事务

**机制**：写路由行 + 写 `t_service_trans(sendState=0)` 在**同一个 MySQL 事务**（R1）。
**失败的样子**：事务回滚 = **整个变更从未发生**（最后一道"零副作用"护栏）。
**谁兜底**：InnoDB 原子性。
**自愈**：即时。
**面试口径**：**DB 是唯一真实源**——ZK/Kafka 都是"提交后的派生品"；这才是"先写 DB 还是先写 ZK"不再是两难的原因。

### 跳 4 · 出箱：Outbox 扫描器（20 生产者 + CRemedialThread）

**机制**：20 生产者扫 `sendState=0`（batch 100）→ CAS claim(0→1) → 发 Kafka → mark_sent(1→2)；发送失败**重置 0 + retryCount+1**；CRemedialThread **60s** 巡检"卡在 1"的崩溃残留，周期 30s（R1）。
**失败的样子**：三种——发送失败（重试）/ 进程崩溃（留 1 态）/ 重试超限（**sendState=3 死信 → 告警**）。
**谁兜底**：重试计数 + CRemedialThread + 死信告警。
**自愈**：秒-分钟级；（崩溃残留 ≤60s 判定 + ≤30s 巡检）。
**面试口径**：**at-least-once + 幂等在下游**；"发出去了吗"的服务端答案就是 `sendState` 四个值。

### 跳 5 · Kafka 通道（16 分区，vpcId 做 key）

**机制**：topic `vpc5.service.{vpcId%16}`、key=vpcId——同 VPC 同分区**保序**（R1）。
**失败的样子**：分区暂不可用 → 生产侧重试/回退 0；消费侧假死 → nfv-proxy 的 ForeverThread 自检 + 双份消费进程（R2；双份语义材料未展开）。
**谁兜底**：生产端重试链 + 消费端看门狗。
**自愈**：秒-分钟。
**OSS 对照**：felix 的 poll 驱动+看门狗哲学（第 2 课）——"活着但不出活"必须被检测。
**面试口径**：顺序性用"分区键"钉死；可靠性用"至少一次 + 幂等"摊平。

### 跳 6 · 分发第一段：nfv-proxy 消费 → 分区 ZK /BINLOG

**机制**：消费 binlog → 写 `/BINLOG/{vpcId}/{资源组}`；同 VPC 保序**承接上游**（跳 5 的分区键序 + 本跳单消费者顺序写）；`master_zk` 拓扑变更 → **自杀重建**（随机延迟防惊群）；写失败无应用级死信——由**进程级自愈**兜（看门狗重建 + Kafka 位点续）。
**失败的样子**：消费断 → Ckafka 位点续；写 ZK 失败 → 异常暴露给守护层（无应用级重试）；拓扑变更 → 重建。
**谁兜底**：Kafka 位点 + 看门狗重建（下沉到进程级；重放由下游幂等吸收）。
**自愈**：秒-分钟。
**面试口径**：ZK 只做"信号与小配置"——大 payload 早被引流到 CKV（zk-knowledge §12）。

### 跳 7 · 快照通道（CKV：fragments / 版本 / 断点 / 交集缺失）

**机制**：快照=大列表切 fragments + 版本列表（agent 按版本读一致代）；**断点续传**；**交集缺失判断**只重做缺失部分（`init_vpc_common.py`；R2）。
**失败的样子**：单片失败 → 断点续传；版本落后 → 按版本重读。
**谁兜底**：断点 + 版本语义。
**自愈**：分钟级（只重做缺失集，不盲目全刷）。
**OSS 对照**：Typha 的 breadcrumb（第 2 课）——同一个"重连/新节点从一致点起步"课题。
**面试口径**：**"快照+增量"两级分发**里，全量侧的价值是"一致点"，不是"备份"。

### 跳 8 · 端侧消费：watch + 快照回放/合并（vpc_agent）

**机制**：watch ZK 子树 + 拉 CKV 快照（一代通道）；二代形态由 `the_2g_op` 负责"快照+binlog 本地合并回放"；local_db 落地（材料 28）。
**失败的样子**：watch 丢失/泄漏（agentos `fix_trpc_unwatch`）；agent 重启 → **30-40 分钟重注册全部 watch**（zk-knowledge §12.2——"树的税"）。
**谁兜底**：重注册（慢）；二代改用 **agent-broker TRPC 心跳增量**（结构换代）。
**自愈**：**慢**——这正是二/三代把分发从 ZK 移走的第一驱动力。
**OSS 对照**：felix 三态就绪（WaitForDatastore→ResyncInProgress→InSync，第 2 课）——"补课"要显式建模，不能假装瞬时。
**面试口径**：一代的"树"把重连成本压在端侧；二代的"心跳"把状态收到 broker；三代的"流式 Watch/ReSync"把它做成一等公民。

### 跳 9 · agent 就绪与对账姿态

**机制**：ready 语义（ready ZK / 实时 ready 列表）+ Inspector 周期对账——修复姿态**按层分**：一代 agent 大量检查是"对账**与修复**"（`fix_global_route`、eip/havip/mirror/jnsgw/host 对账修复，材料 28）；VPC5.0 fusion 的 reconcile 才是明确的"只报告不修复"（出处：vpc-lab `vpc-fusion/internal/service/reconcile/reconcile.go` 头注"我们是报告制"；另见总章④）。
**失败的样子**：漏下的变更 → 能修的按项自动修；不敢修/跨域的产报告。
**谁兜底**：agent 的 fix_* / 汇聚层的报告 + 流程。
**自愈**：对账周期（分钟-小时级）——修复姿态按"误修代价"分层。
**OSS 对照**：felix 自动 resync / OVN 全量重算（单租户敢修）；我们**分层**——数据面检查敢修，汇聚/平台层更谨慎。
**面试口径**：**"什么时候敢自动修"是误修代价的函数**——把"不敢修"显式化为报告制，本身就是设计。

### 跳 10 · 下发数据面（netlink / DPDK 通道）

**机制**：state → netlink 编程 vpcko；DPDK 分支走 TCP+protobuf 到 PAL 进程（材料 28）。
**失败的样子**：netlink 失败 → agent 重试/周期覆写（**期望态可重放**）。
**谁兜底**：期望态模型本身（幂等重放）。
**自愈**：秒级（重放）。
**OSS 对照**：etcd watch replay（第 3 课）/ felix resync（第 2 课）——"权威态在，重放即自愈"。
**面试口径**：下发指令**幂等**是整条链"重启免费"的前提。

### 跳 11 · 转发本身（无状态 LPM）

**机制**：GRE + LPM，route-based、**状态在流外**。
**失败的样子**：无会话可坏——最坏是"没生效"，不会"生效坏了"（无 TTL/逐出/污染面）。
**谁兜底**：无状态本身。
**自愈**：无需。
**OSS 对照**：DPVS 会话表 / Katran per-CPU LRU / tf-vrouter flow entry 的"状态账单"（第 7-9 课）——我们用"功能外移"免掉了这张账单。
**面试口径**：**"状态放哪"是数据面设计的第一题**（总章三维表：在流里/在核里/不在）。

### 跳 12 · 对账闭环（differ / account：报告 → 修复）

**机制**：differ/account 周期比对 DB ↔ ZK/CKV，输出差异报告（材料 45/46；R1）。
**失败的样子**：对账自身失败 → 告警 + 下一周期。
**谁兜底**：告警 + 下一轮 + **人的流程**。
**自愈**：取决于处置流程（小时-天）。
**面试口径**：**自愈链的最后一格是"人的流程"**——把最后一格显式化（报告与流程），比假装全自动更诚实。

## 13. 压成面试三句话

1. **写侧**："所有变更在一个 Saga 链里完成，业务表+发件箱**同事务**原子提交——DB 是唯一真实源，ZK/Kafka 都是派生投递。"（跳 1-4）
2. **分发侧**："下发是'快照+增量'两级：ZK 只做信号与小配置、大 payload 走 CKV；同 VPC 保序用分区键与行锁钉死。"（跳 5-7）
3. **端侧与兜底**："端侧有'重注册的税'——所以三代一路把分发从 ZK 移到 TRPC/流式 Watch；对账分两层：agent 侧按项自动修（fix_*），汇聚与平台层报告制——**检测全自动，修复按误修代价分层**。"（跳 8-12）
