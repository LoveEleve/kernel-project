## §2 负面空间总清单（10 笔）

| # | 欠账 | 换回了什么 | 篇 |
|---|---|---|---|
| 1 | 至少一次：INCR 类重放可双加 | 实现简单、无分布式事务 | 01/05 |
| 2 | 队列满丢弃，**无全量补齐路径** | 事件循环永不受累 | 04 |
| 3 | 异步 send 失败仅告警 | 捕获路径零阻塞 | 04 |
| 4 | EVALSHA 缓存未命中原样复制（NOSCRIPT 风险） | LRU 有界内存 | 03 |
| 5 | 重放 3 次失败跳过——该条永久缺失 | 消费不卡死 | 05 |
| 6 | 阻塞命令复制但重放跳过（消费动作不代执行） | 重放线程永不挂死 | 05 |
| 7 | replace 在途操作可能失败 | 热替换能力 | 06 |
| 8 | 动态路由反射转发无方法缓存 | 版本无关 | 06 |
| 9 | 无 starter 时防回环靠自觉 | 有 starter 时全自动 | 07 |
| 10 | earliest 可被用户配置覆盖 | 不蛮横改用户配置 | 07 |

**总规律**（一句话成本律）：**旁路系统的每一笔"不阻塞、不伤主业务"，都是拿"自己的完整性"换的**——10 笔账全符合这条。

## §3 与 Redis 原生复制的能力对照

| 能力 | Redis 主从 | PolyCache |
|---|---|---|
| 全量同步（psync，主从首次同步整库的命令） | ✅ | ❌（04-2：新机房靠业务/人工灌数） |
| 增量+断点续传 | ✅ | 部分（Kafka earliest 兜启动窗口，长期积压靠告警） |
| 双向多主 | ❌ | ✅（source 防回环，双向各自写本地） |
| 业务零侵入 | ✅ | ✅ |
| 命令级可过滤 | ❌ | ✅（Interceptor/写目录） |

**定位**：PolyCache 不是"更好的主从"，是**多活场景的逻辑复制层**——用 Kafka 换 WAN 复制、用命令语义换字节流镜像；放弃全量同步，启动窗口靠 earliest、长期积压靠告警与人工——这是设计选择不是缺陷清单。

## §4 面试叙事三段（可直接口述）

> **问题**：多机房就近读写，Redis 原生主从是单向 WAN 复制、延迟带宽都差，应用双写要改每处代码——我们需要**业务零改造**的双向逻辑复制。
>
> **设计**：拦截点选在 Redisson 的 Netty 连接管线（所有 API 汇合处），用官方 NettyHook 挂出站 Handler；只复制写命令（Redis 官方 ACL write 目录），EVALSHA 通过 SCRIPT LOAD 登记翻译成 EVAL；消息走 Kafka **按 key 分区保序**，捕获端单线程发送不堵事件循环，**成功才发布、重放完成才提交偏移**（至少一次）；重放端用 ByteArrayCodec 字节直捅 CommandAsyncExecutor，**先克隆 Config 再装捕获**防回环。
>
> **代价**：至少一次（INCR 可双加）、队列满丢弃无补齐、重放失败 3 次跳过——旁路系统"不伤主业务"的每一笔都是拿自己的完整性换的，这 10 笔账我们都写进了文档和监控计数。
