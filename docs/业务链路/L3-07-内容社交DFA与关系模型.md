# L3-07 — 内容社交域：DFA、上传与关系模型

> **定位**：L3 业务域链路第 7 篇（P0 缺口：33-内容与社交）。四段式：**时序 → 决策 → 组件映射 → 拷打**。
> **依据**：xhs-project 内容代码（DFAFilter/上传/社交关系）+ 33-内容与社交。

---

## 一、它干了什么：发布/上传/社交三链

**发布链（笔记发布校验）**：
```
文本预处理（去空格/特殊字符/全角转半角）→ DFA Trie 匹配 O(n) → 通过即落库发布
词库：静态 classpath（sensitive-words.txt）+ 动态 Redis（sensitive-word:list）
运营改动 → Redis PUBLISH（sensitive-word:reload）→ 各实例重建 Trie（volatile 原子替换，读无锁）
```

**上传链（三重校验，顺序即安全）**：
```
① Content-Type 白名单（JPEG/PNG/GIF/WebP）
② 大小 ≤5MB（必须在 getBytes 之前 —— 防大文件 OOM）
③ 魔数校验（只读前 12 字节，WebP 头最长；防 Content-Type 伪造）
→ UUID 命名（从 Content-Type 推扩展名，不信任客户端文件名）+ 日期目录 → 落盘（可切 MinIO）
```

**社交关系链**：
```
点赞：Set（myxhs:like:note:{noteId}，SADD 天然幂等）+ 用户反向索引 + 双层幂等（@Idempotent 5s + SADD）
关注：ZSet（score=关注时间）+ 拆侧 Lua（follow_self/follow_target：两侧各自原子）
收藏：ZSet/关系表 + 24h 版本窗口（VERSION_TTL_HOURS=24，防取消事件乱序回放抹掉新状态）
```

## 二、设计决策

| 决策 | 为什么 |
|---|---|
| **DFA 而非正则/LIKE** | 10 万词库 × LIKE = 10 万次扫描；Trie 一遍 O(n) |
| **预处理防绕过** | 用户插空格/特殊符号/全角 —— 匹配前归一化，否则形同虚设 |
| **Pub/Sub 热更新** | 多实例各持 Trie，不广播会出现"A 拦 B 不拦"；volatile 引用原子替换，读无锁 |
| **上传先大小后魔数** | 顺序即安全：大文件 getBytes 直接 OOM；魔数只读 12 字节，不读全文件 |
| **点赞 Set 而非计数器** | Set 记录"谁点了"（可查状态）+ 天然幂等；计数由计数服务单独维护 |
| **拆侧 Lua** | 关注要同时改"我的列表"和"对方粉丝"（不同用户维度）；拆侧各自原子 + 事件最终一致，避免跨用户大事务 |
| **24h 版本窗口** | MQ 乱序/延迟：取消事件晚到会抹掉"重新点赞"；窗口内旧版本丢弃 |
| **无审核队列（边界）** | DFA 通过即发布 —— 主动说明不是"完整内容审核体系" |

## 四、拷打问题

1. **"DFA 和 AC 自动机区别？"** Trie 单模式多词匹配；AC 加失败指针，超大规模线性匹配；10 万级两者可用，DFA 实现简单。
2. **"词库热更新怎么做？"** 运营写 Redis + PUBLISH；各实例收消息重建 Trie（volatile 原子替换，读无锁）。
3. **"点赞为什么用 Set 不用计数器？"** Set 记录"谁点了"可查状态 + SADD 天然幂等；计数单独维护（Set 人数=计数权威）。
4. **"24h 版本窗口解决什么？"** 取消事件乱序晚到抹掉新状态；窗口内按版本拒绝旧事件。
5. **"拆侧 Lua 为什么拆？"** 两侧不同用户维度；各自原子 + 事件最终一致，避免跨用户大事务。
6. **"共同关注大 V 会 OOM 吗？"** 取交集前限制条数；大 V 列表走分页/缓存（防内存爆）。
