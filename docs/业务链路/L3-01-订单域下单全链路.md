# L3-01 — 订单域：下单全链路（9 步时序 + 设计决策）

> **定位**：L3 业务域链路第 1 篇（P0 缺口：29-订单域）。四段式：**时序 → 决策 → 组件映射 → 拷打**。
> **依据**：xhs-project 订单域代码（OrderService/OrderEventService/OrderCloseJob/OrderMappingRepairJob）+ 29-订单域 + 8 场景并发对抗报告。

---

## 一、它干了什么：下单 9 步时序（`OrderService.createOrder`）

```
① 幂等校验：SETNX userId:bizIdentifier（24h）→ 重复提交直接拒绝
② 分布式锁：SETNX user:create:{userId}（UUID+Lua释放，10s）→ 防并发下单
③ 商品校验三重门：SPU 状态（下架拒绝）→ 同 SKU 合并行拒绝（防超卖）→ 库存预检（Feign 查 available）
④ 金额计算：total - coupon = pay（优惠券先算折扣，后核销）
⑤ 事务消息：半消息 → OrderTransactionListener.executeLocalTransaction（落库+本地消息）→ COMMIT
   + markSuccessByTransactionId（防 LocalMessageRetryJob 30s 双投）
⑥ 优惠券核销：couponFeign.useCoupon（乐观锁 WHERE status=0）→ 失败则 cancelOrder（"打折的订单必有已核销的券"）
⑦ 延时关单：delay-level 16（30min）消息（失败不影响下单）
⑧ 事件+快照：appendEvent(CREATED) + takeSnapshot（失败不影响下单）
⑨ 映射表：saveOrderNoMapping（同步写，失败靠 RepairJob 补录，不阻塞）
```

## 二、设计决策（每步为什么）

| 步骤 | 决策 | 为什么 |
|---|---|---|
| 幂等键带 userId | 原实现不带 → 不同用户同 bizIdentifier 互斥 + 可被恶意抢占 | 键必须表达"谁的什么操作" |
| 锁 10s + UUID + Lua | 短临界区；抢不到拒绝（不排队） | 下单是高频入口，排队即雪崩 |
| 校验三重门（SPU/同 SKU/库存） | T-047 纵深防御 + 超卖根因（两行同 SKU 只扣一行） | "拒绝比静默合并安全" |
| 事务消息而非本地事务 | 跨服务（订单库+库存预扣）要原子 | 半消息+回查是最终一致（K01/K06） |
| markSuccess 防双投 | 事务消息 COMMIT 后 broker 必投递；本地消息表只做回查兜底 | 双投靠消费者幂等兜底（注释写明） |
| 核销失败取消订单 | 优惠券是资金属性（错发=资损） | 用"取消"保"券账一致"，不用"重试"赌 |
| 延时+扫描双保险 | 延迟消息不保证必达（丢/积压/消费失败） | 定时扫描是终线（每分钟粒度） |
| 事件 targetStatus=-1（T-110） | 创建事件目标状态 0 与初始 status 相同 → 幂等检查恒真 → 事件从不落库（链断） | **区分"记录事件"与"状态流转"**：-1 只记录不更新；重放跳过 |
| 映射不阻塞 | 映射是查询辅助非核心数据 | 同步写+失败降级+RepairJob 收敛（分层设计） |
| 地址快照 | 用户可改/删地址 | 历史单保留下单当时信息（对账/发货/纠纷取证），与用户表解耦 |

## 四、拷打问题（8 场景并发对抗 + 经典）

**对抗实测（8 场景全过）**：
```
并发重复支付回调×5 → 幂等收敛（唯一键+状态机）
取消 vs 支付 → 取消赢 + 自动退款闭环（条件 UPDATE 裁决同时写）
重复退款回调 → 幂等（退款单状态机）
确认收货 vs 退款 → 无跳变（状态机非法转移拒绝）
同 bizIdentifier 并发 → 只 1 单（幂等键+锁双保险）
部分退款 → 累计=全额才置 5（金额累加器，非单次判断）
```

**经典追问**：
1. **"SEND_OK 后本地事务失败怎么办？"** 看 orderId：已提交→保留幂等键按成功返回（回查/本地消息兜底）；未提交→删键报错——"订单已创建但接口报失败→用户重试同 bizIdentifier 生成重复订单"是最危险的分支。
2. **"优惠券核销与订单落库谁先谁后？"** 先落库（事务消息内）后核销；核销失败取消订单——顺序不能反（先核销后落库失败=券丢了）。
3. **"T-110 教什么？"** 幂等判断要区分"状态流转"与"记录事件"——创建事件 targetStatus=-1 + 重放跳过。
4. **"映射表丢了怎么办？"** 同步写+失败降级+RepairJob 扫描补录——"查询辅助"的定位决定"不阻塞主流程"。
5. **"关单消息丢了？"** 延时消息（主）+ OrderCloseJob 每分钟扫 30 分钟前待付款（终线）——延迟消息不保证必达是前提。

## 五、话术

> "下单是 9 步：幂等键防重 → 分布式锁防并发 → 商品三重校验（SPU 状态/同 SKU 合并/库存预检）→ 算金额 → 事务消息落库 → 标记防双投 → 优惠券核销（失败取消订单）→ 延时关单 → 事件快照映射。关键设计：幂等键带 userId（防互斥和抢占）；事务消息解决跨服务原子；核销失败必须取消订单（资金属性）；关单是延时加扫描双保险；事件用 -1 区分记录和流转（T-110 教训）；映射表不阻塞主流程。8 场景并发对抗全过：取消和支付同时到，取消赢且自动退款。"
