# L3-08 — 通知推送域：聚合、未读与订单事件接入

> **定位**：L3 业务域链路第 8 篇（P0 缺口：55-通知与推送域）。四段式：**时序 → 决策 → 组件映射 → 拷打**。
> **依据**：xhs-project 通知代码（聚合器/未读对账/推送表/SSE）+ 55-通知与推送域 + init-xxljob.sql。

---

## 一、它干了什么：聚合/未读/推送三链

**聚合链（防骚扰）**：
```
同一用户同类型同目标同天 → 一条通知（aggregate_count++）
唯一键 uk_aggregate(user_id,type,target_id,notify_date) → 并发合并交给 DB（冲突转 UPDATE）
订单类走 updateOrderLatest 分支：同订单当天只保留最新状态（避免"已付款/已发货"堆两条旧标题）
```

**未读链（DB 权威）**：
```
未读数存 DB（高基数小值，DB 更稳——与计数的 Redis 权威相反，按数据特征选）
Redis 加速读；UnreadReconcileJob 对账收敛（cron `0 */10 * * * ?` = 每 10 分钟）
```

**推送链（任务表 + 实时）**：
```
t_push_task（任务）+ t_push_task_fail（失败落表可重试/排查）+ t_push_template（模板）
实时通道：SSE（SseEmitterManager + SseCrossInstanceSubscriber 跨实例路由）
SSE 不可用 → 降级拉取（站内信已落库，打开 App 可见——实时失败不丢信息）
```

**订单接入（三埋点，本轮修复前缺失）**：
```
OrderNotificationPublisher：支付成功 / 发货 / 退款成功 → MQ 异步 → 通知聚合器
此前订单域未接通知（链路推演发现：下单后用户无站内信）→ 修复后 E2E 回归
```

---

## 二、设计决策

| 决策 | 为什么 |
|---|---|
| **聚合唯一键** | 并发合并交给 DB（冲突转 UPDATE count），天然幂等；应用层查改有竞态窗口 |
| **最新态刷新** | 只做 `ON DUPLICATE UPDATE count` 会保留旧标题（用户看到"已付款"实际已发货）→ 订单类必须 UPDATE 内容 |
| **未读 DB 权威** | 高基数小值 + 易丢更新 → Redis 做加速层；与计数（Redis 权威）相反——"按数据特征选权威源" |
| **对账周期 10 分钟** | init-xxljob.sql 实测口径（55 章"5 分钟"已过时，以配置为准） |
| **失败落表** | 推送失败必须可查（t_push_task_fail），否则"发了但没到"无人知 |
| **三埋点异步** | 通知走 MQ 不阻塞交易；失败可重试；聚合降噪后落库 |
| **SSE 降级拉取** | 实时通道是优化项，站内信落库是底线——降级不丢信息 |

## 四、拷打问题

1. **"聚合并发下会重复插吗？"** 唯一键兜底，冲突转 UPDATE；订单类走最新内容刷新（防旧标题）。
2. **"未读为什么不用 Redis 权威？"** 高基数小值易丢更新；DB 权威 + Redis 加速 + 10 分钟对账——与计数选型相反。
3. **"推送失败怎么发现？"** 失败落表 + 告警；站内信落库可回看（实时失败不丢信息）。
4. **"通知量大拖垮主链吗？"** MQ 异步 + 聚合降噪；订单事件只发不阻塞；失败重试有上限。
5. **"订单域未接通知怎么发现的？"** 业务全链路推演（29 步主线走一遍发现无消费方）——链路推演的价值不在单服务。

---

## 五、话术

> "通知三件事：聚合防骚扰、未读要准、推送可查。聚合用唯一键把并发合并交给数据库，订单类通知还要刷新最新内容，不然用户看到的还是旧标题。未读数放 DB 权威、Redis 只加速，每 10 分钟对账收敛——和计数的选型正好相反，看数据特征定。推送失败必须落表，否则发了没到没人知道；实时走 SSE，不可用就降级拉取，反正站内信已落库。之前还发现订单域根本没接通知，下单后用户收不到站内信，后来补了支付发货退款三个埋点。"
