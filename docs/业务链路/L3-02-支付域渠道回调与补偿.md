# L3-02 — 支付域：渠道、回调幂等与补偿体系

> **定位**：L3 业务域链路第 2 篇（P0 缺口：30-支付域）。四段式：**时序 → 决策 → 组件映射 → 拷打**。
> **依据**：xhs-project 支付域代码（PaymentService/Jobs/独立数据源）+ 30-支付域 + P1-1 自动退款闭环。

---

## 一、它干了什么：支付/退款双链路时序

**支付链（创建→渠道→回调→通知）**：
```
① 防重复发起：SETNX payment:paying:{orderId}（TTL 30min）→ 重复点支付直接拒绝
② 落支付单：status=0 待付款（独立数据源 my_xhs_payment，绕过分片）
③ 渠道路由：PayChannelStrategy 按 payType（Mock 同步成功 / 支付宝 / 微信异步等回调）
④ 回调处理：验签 → 乐观锁 UPDATE ... WHERE status=0 → 成功置 1（重复回调影响 0 行→直接返回成功）
⑤ 通知订单：MQ 通知 + 5 分钟后补偿任务兜底（最多 10 次，超限告警人工）
```

**退款链（申请→渠道→回调→回补）**：
```
① SETNX payment:refunding:{paymentId}（TTL 7d，覆盖渠道长处理窗口）
② 退款单 status=退款中 → 渠道退款 → 回调乐观锁更新（成功/失败）
③ 部分退款：累计 status=1 金额，累计=支付额才置订单 5 + 库存回补（非单次判断）
④ 取消 vs 支付竞态：取消赢 + payment 侧自动退款闭环（P1-1）
```

## 二、设计决策

| 决策 | 为什么 |
|---|---|
| **策略模式隔离渠道** | Mock 同步 vs 真实异步是两种时序；同一套状态机适配，业务代码不碰 SDK |
| **回调验签先行** | 不验签=伪造支付（资金风险）；验签失败直接拒绝，不进状态机 |
| **乐观锁而非分布式锁做幂等** | 单行状态更新，条件 UPDATE 本身原子；Redis 锁只防"重复发起"（跨请求），两层职责不同 |
| **SETNX TTL 差异化** | 支付 30min（=订单超时）；退款 7d（渠道处理长 + 低频可接受占用） |
| **补偿窗口 5 分钟** | 给实时通知重试留时间，避免和正常链路抢资源；10 次上限后转人工（不无限重试防雪崩） |
| **独立数据源** | 支付表绕过分片路由（精确路由+原子更新）；为支付域独立拆分预留（表+状态机+补偿一起带走） |
| **对账死代码教训** | 注释写"每天对账"但无调度入口=从不执行 → 补 XXL-Job 入口；"注释里的定时要有调度证据" |

## 四、拷打问题

**经典追问**：
1. **"回调验签怎么做？"** 渠道公钥/密钥验签（Mock 验签名头）；失败直接拒绝，不进状态机——验签是资金链路第一道门。
2. **"重复回调会改状态吗？"** 不会：乐观锁 `WHERE status=待支付`，第二次影响 0 行 → 直接返回成功（幂等 natural）。
3. **"补偿 10 次还失败？"** 告警转人工 + 事件记录；对账兜底；不无限重试（防雪崩）。
4. **"取消和支付同时到？"** 条件 UPDATE 裁决：取消赢；payment 侧自动退款闭环（P1-1）——退款单最终 status=1。
5. **"部分退款怎么算？"** 累计已成功退款金额，累计=支付额才置订单已退款 + 库存回补（防"退一半就关单"）。
6. **"渠道退款失败重试吗？"** **缺口**：mock 10% 失败实测置 FAIL + 通知订单，需人工/重发；建议加重试+上限+告警（已登记未落地）。
7. **"支付域怎么拆出去？"** 表已独立数据源 + 状态机内聚 + 只依赖订单号 → 拆时带走补偿/对账/事件表，本地调用变 RPC。

---

## 五、话术

> "支付是策略模式加统一状态机：Mock 同步、真实渠道异步回调，回调验签后乐观锁更新，重复回调影响 0 行直接返回成功。防重复发起是 Redis SETNX（支付 30 分钟、退款 7 天）加乐观锁双保险。通知失败有补偿任务——5 分钟窗口、最多 10 次、超限告警人工。踩过一个坑：对账任务注释写每天跑但根本没有调度入口，是死代码，后来补了 XXL-Job。支付表单独走独立数据源绕过分片，为以后拆支付域做准备。已知缺口：渠道退款失败不自动重试。"
