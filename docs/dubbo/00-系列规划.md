## 二、十一篇结构（主线 01-09 + 补全 10-11；每篇 = 一个问题 + 一个 lab 实验）

### 01 从0开始：RPC 为什么存在？手写最简 RPC 会死在哪？

- **核心问题**：本地方法调用 `demo.sayHello()` 为什么不能直接跨进程？
- **五段式**：
  - 朴素答案：把对象通过 Socket 发过去就行；
  - 死在哪：地址空间隔离（对象引用只是进程内地址）→ 必须序列化；网络不可靠（超时/半包/断连）→ 必须协议与重试；服务在哪（写死 IP）→ 必须寻址；
  - 所以：RPC 的四件事 = 代理（像本地一样调用）/ 序列化 / 网络传输 / 寻址；
  - 代价："透明调用"是假的——每次调用多了序列化、网络、超时语义。
- **演化**：手写 100 行最简 RPC（`lab-naive`）跑通 → 列出它的 **7 个死点**（硬编码地址/裸协议/零扩展/无容错/无治理/不可观测/配置混乱）→ 每个死点就是后续一篇的入口 → 给出 Dubbo 全景（四角色 + 十层架构）作为本系列地图。
- **lab**：新增 `lab-naive`（无第三方依赖，手写序列化 + Socket + 动态代理）。
- **覆盖**：无（预备篇）；**课程对照**：Dubbo 01 温故知新 / 12 分层，RPC 01 / 07。

### 02 从用到懂：Dubbo 怎么用？为什么你的超时不生效？

- **核心问题**：配置不就是赋值吗？为什么 consumer 设了 1s 超时，实际却是 3s？
- **五段式**：朴素答案"配置=赋值" → 死在哪：配置有来源与层级（`-D` JVM 参数 / 外部化配置 / API / XML / 注解；consumer / provider / method 三级覆盖），升级后两侧不一致 → 所以：配置对象是**部署入口**（D-1），加载顺序与覆盖规则是设计 → 代价：灵活性的复杂度。
- **内容**：API/注解/XML 三种用法（lab 直连示例逐行拆）；`DubboBootstrap → ServiceConfig.export() → ReferenceConfig.init()` 源码入口；配置加载顺序实验。
- **lab**：`scripts/02-direct-invoke.sh` + `scripts/03-timeout-precedence.sh`（提供方 5s / 消费方 3s / 方法级 1s 三级覆盖对照）。
- **覆盖**：D-1；**课程对照**：11 配置加载顺序 / 12 分层 / 05 点点直连。

### 03 服务怎么被"发布"和"订阅"？

- **核心问题**：consumer 怎么知道 provider 在哪？
- **五段式**：朴素答案"写死 IP"（直连）→ 死在哪：扩缩容、故障转移全要改配置 → 所以：注册中心（注册/订阅/通知）+ 动态目录 → 代价：注册中心成为新的依赖与故障点（注册成功≠可调用）。
- **内容**：export 三环节（配置→导出→注册）；refer 与 RegistryDirectory 通知；Nacos 注册中心接入；空目录/禁用地址/override 的排查。
- **lab**：`scripts/04-registry-nacos.sh`（Nacos 模式 `-Dlab.registry=nacos://...`）+ kill/重启 provider 看目录通知。
- **覆盖**：D-4（+D-1）；**课程对照**：19 发布 / 20 订阅 / 25 注册扩展。

### 04 处处可扩展：SPI / Adaptive / Wrapper

- **核心问题**：为什么 Dubbo 的协议、集群、负载均衡、过滤器都能换？
- **五段式**：朴素答案"工厂 + if-else" → 死在哪：每加一个扩展都要改框架 → 所以：Dubbo SPI（键值对加载 / 单例 / 包装器 / 自适应 / 自动激活）→ 代价：装配复杂，同名扩展与 Scope/ClassLoader 容易"配置生效但行为不符"。
- **内容**：JDK SPI 的缺陷；`ExtensionLoader` 主链；`@Adaptive` 代码生成；Wrapper 与 `@Activate`；实例注入。
- **lab**：`scripts/05-spi-extension.sh`（自定义 Filter 扩展；LoadBalance 用内置实现对照，见 05 篇）。
- **覆盖**：D-2；**课程对照**：14-18（SPI/Wrapper/Compiler/Adaptive/实例注入）。

### 05 一次调用到底经过了什么？

- **核心问题**：`demo.sayHello()` 这一行，到网络之前发生了什么？
- **五段式**：朴素答案"代理直接发请求" → 死在哪：集群、路由、负载均衡、过滤器、上下文都要插进这条链 → 所以：Proxy → Invoker → Filter 链 → Cluster（Router/LB）→ Protocol → Exchange → Netty 的分层责任链 → 代价：每层都有包装，调试要看穿多层 Invoker。
- **内容**：动态代理与 Invoker；过滤器链；集群容错策略；条件/标签路由；随机/轮询/最少活跃 LB；RpcContext 与隐式传参。
- **lab**：`scripts/06-call-chain-lb.sh`（自定义 Filter 打印调用链；多 provider + LB 对照）。
- **覆盖**：D-3 / D-5；**课程对照**：21 调用流程 / 24 Filter / 23 集群 + RPC 09-12。

### 06 请求如何变成网络字节？

- **核心问题**：一次调用在网络上长什么样？超时后 provider 真的停止了吗？
- **五段式**：朴素答案"对象直接发" → 死在哪：协议要兼容/可扩展/能定位请求（request id），timeout 只是 consumer 的等待上限 → 所以：协议头 + 序列化 + Netty pipeline + DefaultFuture 关联 → 代价：一个连接承载多服务，service key/引用计数/优雅关闭都是坑。
- **内容**：Dubbo 协议设计（魔数/头/body）；序列化与安全白名单；DubboProtocol export/refer 与共享连接；Netty pipeline；DefaultFuture 的 sent/received/timeout/cancel。
- **lab**：`scripts/07-protocol-async.sh` + `tools/wire-proxy.py`（抓包观察协议）；timeout 后 provider 继续执行实验；异步调用。
- **覆盖**：D-6 / D-7；**课程对照**：22 编解码 / 02 异步 / 26 线程池 + RPC 02-05 / 17。

### 07 服务不可用怎么办？

- **核心问题**：一个 provider 挂了或变慢，调用方应该怎么办？
- **五段式**：朴素答案"报错给用户" → 死在哪：重试会放大非幂等操作（重复扣款）、变慢会拖垮线程池 → 所以：集群容错策略 + 路由/LB + 熔断限流 + 优雅上下线 → 代价：每个策略都要求业务语义配合（幂等键/超时预算）。
- **内容**：Failover 重试次数与条件；重试×超时的叠加放大；路由规则；熔断限流；优雅关闭/优雅启动。
- **lab**：`scripts/08-failover-graceful.sh`（retries 放大 + 业务异常不重试 + 优雅下线 wait 对照 + 标签路由）。
- **覆盖**：D-5；**课程对照**：23 集群 + RPC 09-15。

### 08 生产治理与诊断

- **核心问题**：上线后怎么不出事？出了事怎么查？
- **五段式**：朴素答案"加日志" → 死在哪：隐式传参断链、泛化调用、参数验证/缓存/事件/鉴权等横切需求、线程池耗尽、上下线不可控 → 所以：Filter 扩展体系 + QoS + metrics/tracing → 代价：治理插件异常策略必须与业务失败策略区分。
- **内容**：RpcContext 隐式传参；泛化调用；参数验证/缓存/事件通知/服务认证；流量控制；QoS 单机运维命令；线程池与连接数排查；优雅下线。
- **lab**：`scripts/09-governance-qos.sh`（RpcContext/泛化/缓存 demo；QoS 命令；线程池耗尽复现与诊断）。
- **覆盖**：D-8 + 支撑域；**课程对照**：03-10 / 27 + RPC 19。

### 09 收束：一次调用的完整旅程 + 设计哲学

- **内容**：把 01-08 串成"一次调用的一生"（从 consumer 方法到 provider 方法，每一层引用对应篇目）；Dubbo 的设计哲学复盘（统一 URL 模型 / 微内核 + SPI / 分层责任链 / 模型隔离）；**与项目对照**：xhs-project 用 Feign/Spring Cloud，为什么？Dubbo vs Feign 的治理模型对照；生产检查清单（配置/注册/超时/重试/线程池/上下线）。
- **lab**：`scripts/10-full-journey.sh`（消费方/提供方 Filter + 抓包，一次调用端到端 trace）。
- **覆盖**：综合；**课程对照**：结束语 + RPC 24。

### 10 集群深化：条件路由 / 最少活跃 / 服务分组（补全篇）

- **核心问题**：路由规则为什么"写了不生效"？leastactive 为什么和 random 一样？
- **内容**：条件路由（`router=condition` 按名激活、`when => then` 规则、匹配最终 invoker URL、force/兜底）；**直连不建 RouterChain** 的边界；LeastActive 的 active 来源（`ActiveLimitFilter`/`actives`）；group/version 的注册/订阅级隔离（对比 tag 路由）；其余容错形态速览。
- **lab**：`scripts/11-routing-lb-group.sh`（直连负面对照 + Nacos 条件路由 + leastactive 三组对照 + 分组隔离）。
- **覆盖**：D-5 深化；**课程对照**：23 集群 + RPC 10/11/16。

### 11 协议扩展与 Triple：多协议共存与治理插件（补全篇）

- **核心问题**：换协议要不要重写服务？Triple 和 dubbo 协议在网络上差在哪？
- **内容**：Protocol SPI + @Adaptive（回扣 04）；多协议共存（多个 ProtocolConfig）；Triple = HTTP/2（protobuf / 非 protobuf 反射打包）；抓包对照（16 字节头 vs HTTP/2 前言）；metrics/tracing 插件插入点（源码口径，标注未实验）。
- **lab**：`scripts/12-triple-protocol.sh`（同服务双协议导出 + tri 调用 + wire-proxy 抓 HTTP/2 帧）。
- **覆盖**：D-6 支撑域 + D-8 插件；**课程对照**：27 协议扩展 + RPC 24。
