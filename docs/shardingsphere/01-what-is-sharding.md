# 01-什么是分库分表：核心概念全景

## §0 它干了什么（例子先行）

一张订单表 10 亿行，最朴素的"拆"法长这样：

```
原来（一个库一张表）：
  my_xhs_order 库 → t_order（10 亿行）

拆完（4 个库，每库 4 张表）：
  my_xhs_order_0 库 → t_order_0 / t_order_1 / t_order_2 / t_order_3
  my_xhs_order_1 库 → t_order_0 ... t_order_3
  my_xhs_order_2 库 → t_order_0 ... t_order_3
  my_xhs_order_3 库 → t_order_0 ... t_order_3
  共 16 个"格子"，每格约 6250 万行

业务代码照写：INSERT INTO t_order (...)   ← 还是这一句
ShardingSphere 在中间：这条 SQL 该进哪个格子？
```

- **它干了什么**：**逻辑上还是一张表，物理上是 16 张小表**——中间件负责算路、改写、汇总。
- **本篇回答**：这一套玩法需要认识哪些词？它们怎么互相咬合？

## §1 掌握卡（3 条）

1. **一句话定义**：分库分表=按**分片键**把逻辑表的数据切分到多个**数据源（库）**和多个**表**中；框架在 SQL 执行前算出目标格子，执行后把多格结果**归并**回来。
2. **三组必须分清的词**：**逻辑表**（代码里写的 `t_order`）vs **物理表**（真的 `t_order_0..3`）；**分片键**（路由依据，xhs=user_id）vs **分片规则**（键→格子的算法）；**分片**（一个格子=一个库内一张物理表）。
3. **中间件两种形态**：**JDBC**（进程内 jar，xhs 用）vs **Proxy**（独立代理进程）——02 讲为什么选 JDBC。

## §2 词汇表（What 大放送，按依赖顺序）

### 第一层：切分本身

| 词 | 读法 | 例子（xhs） |
|---|---|---|
| **逻辑表** | 代码/SQL 里看到的"假"表 | `t_order` |
| **物理表** | 磁盘上真的表 | `t_order_0` ~ `t_order_3` |
| **数据源（ds）** | 一个数据库连接目标 | `ds0`~`ds3`（= `my_xhs_order_0~3` 库） |
| **分片键** | 决定进哪个格子的列 | `user_id` |
| **分片规则** | 键 → 格子的映射公式 | 两级哈希（见 §3） |
| **分片策略** | 用几个键路由 | `standard`（单键，xhs）/ `complex`（多键）/ `hint`（强制指定——03 讲） |
| **两级分片** | 先定库、再定表 | ds=hash%4；表=(hash/4)%4 |

### 第二层：特殊表与配套

| 词 | 读法 | 一句话 |
|---|---|---|
| **绑定表** | 绑成一组的分片表 | 同键同格子——JOIN 不炸（`t_order` 五张表全绑，04 细讲） |
| **广播表** | 每库都放一份的小表 | 字典类；**xhs 未用** |
| **映射表** | 分片外的第二索引 | `order_no→user_id`，非分片键反查用（06） |
| **影子表** | 压测专用副本表 | `t_*_shadow`，压测数据不污染生产（06） |
| **逻辑索引/DDL** | 对逻辑表建索引 | 框架翻译成对 16 张物理表逐一下发 |

### 第三层：主键与执行

| 词 | 读法 | 一句话 |
|---|---|---|
| **分布式主键 Snowflake** | 全局唯一 ID | 时间戳+workerId+序列——**分片后自增 ID 会撞车**，必须换（05 三坑主场） |
| **workerId** | 机器身份 | 同机多实例必须不同（05 事故 2） |
| **解析** | SQL 读懂 | 五步之一（03） |
| **路由** | 算出格子 | 五步之一（03） |
| **改写** | 逻辑表名→物理表名 | 五步之一（03） |
| **归并** | 多格结果合并 | 五步之一（03） |

## §3 两级哈希长什么样（词先脸熟，04 深讲）

xhs 的规则（修复后版本）：

```
库：ds${(user_id.hashCode() & 0x7fffffff) % 4}
表：t_xxx_${((user_id.hashCode() & 0x7fffffff).intdiv(4)) % 4}
同一个 user_id：先除 4 定表内序，再定库——两级配合，16 格均匀撒
```

为什么有 `& 0x7fffffff` 和 `intdiv`——**事故 1（倾斜）的答案**，05 揭晓。

## §4 概念咬合图（一张图收口）

```
业务 SQL（写逻辑表 t_order）
  → 中间件（JDBC 形态）
      解析 → 拿到 user_id（分片键）
      路由 → 按分片规则（两级哈希）算出 ds2.t_order_1（分片）
      改写 → t_order 换成 t_order_1
      执行 → 走 ds2 数据源（Hikari 连接池）
      归并 → 16 格的结果按需合并（排序/LIMIT/聚合）
  → 返回业务
配套：Snowflake 发主键（不撞车）/ 绑定表保 JOIN（04）/ 映射表保反查（06）
```
