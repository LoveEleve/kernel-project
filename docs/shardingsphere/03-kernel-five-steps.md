# 03-内核五步：解析-路由-改写-执行-归并

## §0 它干了什么（例子先行）

业务发一句最普通的 SQL，中间层替它跑完全程：

```sql
SELECT * FROM t_order WHERE user_id = 10001 ORDER BY create_time DESC LIMIT 10
```

```
① 解析：ANTLR 把 SQL 读成结构——表=t_order（逻辑）、条件 user_id=10001、要排序分页
② 路由：拿 user_id=10001 按分片规则算 → 唯一分片（示意 ds2.t_order_1；主键查询只去一格）
③ 改写：t_order → t_order_1；LIMIT 10 保持（单分片无需改写）
④ 执行：走 ds2 数据源的真实连接
⑤ 归并：只有一格的结果直接返回；若查询扫 16 格（无键查询）→ 各格 LIMIT 10 → 内存合并排序再取 10
```

- **它干了什么**：把"逻辑 SQL"翻译成"物理 SQL 集"再把结果拼回来。
- **本篇回答**：五步各干什么？绑定表为什么能防笛卡尔积？跨分片分页为什么贵？

## §1 掌握卡（4 条）

1. **五步流水线**：解析（读懂）→ 路由（算格子）→ 改写（换表名/改分页聚合）→ 执行（多数据源）→ 归并（排序/聚合/LIMIT 合并）——K12①原表。
2. **路由看有没有分片键**：SQL 带分片键→**单格直达**（最常见路径）；不带→**全路由**（扫所有格子再归并——慢的根源，06 映射表就是给它修路）。
3. **绑定表防笛卡尔积**（追问4）：分片规则**同构**的表绑一组——同 user_id 的 `t_order` 行和 `t_order_item` 行落在**同一格**，JOIN 在单分片内完成；不绑的话最坏要试 16×16=256 组物理表组合（每库拉全表——K12 陷阱5 原话）。
4. **跨分片分页的代价**（追问6）：`LIMIT 10 OFFSET 1000` → 每格都要查前 1010 条 → 内存归并取第 1000~1010——**页越深每格捞得越多**；产品侧对策=禁跳页/改游标。

## §2 五步逐个说

| 步 | 干什么 | 坑位 |
|---|---|---|
| 解析 | ANTLR 文法→语法树（表/列/条件） | 只认标准 SQL 方言子集 |
| 路由 | 分片键→（数据源，表） | 无键=全路由（陷阱7 的入口） |
| 改写 | 逻辑表→物理表；**分页/聚合/IN 改写** | 改写错=结果错——典型事故（06 案例）出在路由不在改写 |
| 执行 | 按格子分组，各数据源真执行 | 连接池按 ds 独立（04：Hikari 10/2） |
| 归并 | 多格结果合并：排序/去重/聚合/LIMIT | 内存与 CPU 在这付账 |

## §3 策略与算法（01 §2 的展开）

- **策略**：`standard`（单分片键——xhs 订单域）/ `complex`（多键联合）/ `hint`（不解析 SQL，**强制指定**路由——运维/补偿专用通道）。
- **算法**：`INLINE`（表达式：`ds${user_id % 4}` 这类——xhs 用）/ `ClassBased`（自定义 Java 类——算法复杂时接管）。

## §4 一条 SQL 的三种命运（收口表）

| SQL 形态 | 路由 | 归并 | 快慢 |
|---|---|---|---|
| 带分片键（90%） | 单格 | 无需 | 快——设计目标 |
| 绑定表 JOIN 同键 | 同格 JOIN | 无需 | 快——绑定表的回报 |
| 无键查询/深分页 | 全路由 | 重 | 慢——06 映射表/产品约束来治 |
