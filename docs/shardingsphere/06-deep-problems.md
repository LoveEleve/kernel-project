# 06-深水问题：主键·倾斜·非分片键·扩容

## §0 它干了什么（例子先行）

分片上线后的一次实测，数据令人怀疑人生：

```
131 单订单，期望均匀撒进 16 格
实际：ds1.t_order_0 = 99 单、ds2.t_order_0 = 32 单、其余 14 格 = 0
→ 75% 数据挤在 2/16 个格子——分片形同虚设
根因：user_id 是 Snowflake 生成的，拿它的低位取模
```

- **它干了什么**：本篇收四个**原理级难题**——分片键选完之后，真正让人翻车的都在这。
- **本篇回答**：Snowflake 为什么有三个坑？低位取模为什么会倾斜？非分片键查询有几种解法？扩容到底怎么扩？

## §1 掌握卡（4 条）

1. **Snowflake 三坑**：时钟回拨（等待/异常策略）/ **低位取模倾斜**（§3 案例）/ **worker-id 冲突**（同机多实例——修复=IP+端口推导）。
2. **倾斜的原理**（不是玄学）：Snowflake 低位段是**毫秒增量+序列**——低流量下毫秒差带来的位移全被 `<<22` 的低位零吃掉、序列恒 0 → `id % 16` 恒定；**修复=高位混入**（`hashCode & 0x7fffffff` 再取模）。
3. **非分片键两解**：**映射表**（order_no→user_id 第二索引+补录 Job，工程解）/ **基因法**（订单号里嵌 user_id 后缀，设计解——生成时就把路由信息带上）。
4. **扩容的诚实答案**：固定 4×4 **无 rehash**——真扩容=双写迁移（新老规则并行）+影子比对+切读；K12 原话"这才是'会做'而不是'做过'"。

## §2 Snowflake 原理与坑位地图

```
id = (时间戳 << 22) | (workerId << 12) | 序列
     41 bit          10 bit（0~1023）    12 bit（每毫秒 4096 个）
```

| 坑 | 机理 | 对策 |
|---|---|---|
| 时钟回拨 | 时间戳倒退→ID 冲突 | 框架等待/抛错策略 |
| **低位取模倾斜** | 低位段与时间弱相关，取模后不均匀 | **不拿低位取模**——hashCode 混高位（§3） |
| worker 冲突 | 同机多实例同 workerId | 三级注入：env → `-Dworker.id` → `floorMod(ipPart*31+port, 1024)`（04 已用） |

**为什么单实例自增也必须换**（01 §2 回收）：分片后 16 个格子各自自增必然撞车——**分布式主键是分片的入场券**。

## §3 倾斜案例的完整机理（含金量最高）

```
user_id = Snowflake：低流量时同毫秒、Δseq=0
  → 相邻 id 只差"毫秒增量 << 22"——<<22 的低 22 位全是 0
  → 对 16（2^4）取模：只看最低 4 位 → 恒为 0（同批用户永远同格）
修复前实证：99/32/0×14（K12③原数字）；映射表 131=131——**证明不是数据丢了一致性没问题，纯路由倾斜**
修复：hashCode(x) & 0x7fffffff 再取模——把高位搅进低位
验证：16/16 格全有数据（41/31% 的头部是热点用户 10001 单用户聚集——业务热点非算法缺陷）
```

**两个必须一起讲的教训**：
1. **算法切换是破坏性变更**——旧数据按旧算法存，新算法读不到它们（不迁移=数据"消失"）；
2. 所以有配套迁移（`migrate-sharding-hash.py`，脚本 682 行；游标扫 5 表×16 片，停服约 2 分钟）+ 审计脚本（分布+映射+路由抽查）——**改分片算法=一次带审计的小型迁移项目**。

## §4 非分片键查询（陷阱 7 的两解）

| 解 | 做法 | 代价 |
|---|---|---|
| **映射表** | 独立非分片库放 `order_no→user_id`，先查映射再路由；写入同步落 + 补录 Job（@XxlJob 5min）兜底 | 多一跳 + 补录窗口 |
| **基因法** | 订单号尾部嵌 user_id 的分片后缀——**路由信息长在 ID 里** | 要改发号规则，存量不可用 |
| （反面）全路由 | 16 格都问一遍 | 慢的根源，只有兜底时才用 |

xhs 选映射表（工程改动最小）；基因法是"从设计根上消灭问题"的另一派——K12 发散提了两派并存。

## §5 扩容：没有银弹

```
固定分片数的现状（xhs 主动披露）：无 rehash——扩容不能"加格子就完"
真扩容三步（K12⑤8 口径）：双写迁移（新老两套路由并行写两处）→ 影子表比对（数据核对）→ 切读（读流量切到新规则）
框架侧有 Scaling 工具（K12 发散）——方案先行，别等爆炸再想
```
