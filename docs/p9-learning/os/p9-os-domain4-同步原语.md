## 一、锁的实现（自旋锁 vs 互斥锁）

### 自旋锁（Spinlock）

```
原理：获取锁失败时循环重试（忙等，不睡眠）
  → 临界区短时高效（无上下文切换开销）
  → 临界区长时浪费 CPU（忙等烧 CPU）

实现：CAS（原子指令）获取锁标志
  lock: bts [lock], 0   ← x86 原子置位
  jc retry              ← 已锁则重试

使用场景：
  内核：短临界区（中断处理/自旋等待）
  用户态：futex 的自旋阶段（短等待自旋，长等待睡眠）
```

### 互斥锁（Mutex）

```
原理：获取锁失败时睡眠（让出 CPU）
  → 临界区长时高效（不烧 CPU）
  → 临界区短时有上下文切换开销

实现：futex（Fast Userspace Mutex）
  无竞争：用户态 CAS（快）
  有竞争：系统调用 futex（内核等待队列）

使用场景：
  用户态：pthread_mutex/Java synchronized（JVM 域5 锁膨胀）
  内核：长临界区（mutex_lock）
```

### 对比

| | 自旋锁 | 互斥锁 |
|---|---|---|
| 等待方式 | 忙等（烧 CPU） | 睡眠（让出 CPU） |
| 开销 | 无切换（短等待快） | 有切换（长等待快） |
| 适用 | 临界区短（微秒级） | 临界区长（毫秒级） |
| 中断上下文 | 可用（不能睡眠） | 不可用（会睡眠） |

### P9 追问链

- **Q：自旋锁和互斥锁什么时候用？** → 短临界区自旋；长临界区互斥；中断上下文只能自旋
- **Q：futex 是什么？** → 用户态快速互斥锁（无竞争 CAS，有竞争系统调用）
- **Q：自旋锁有什么问题？** → 长临界区浪费 CPU（忙等）；多核竞争激烈时性能差

## 二、内存屏障（Memory Barrier）

### 问题：指令重排序

```
编译器/CPU 为优化性能重排序指令：
  编译器重排序：编译器优化（如循环展开）
  CPU 重排序：乱序执行（提高流水线效率）

多线程问题：
  线程 A: data=1; ready=true;
  线程 B: if(ready) print(data);
  → 重排序可能导致 B 看到 ready=true 但 data=0
```

### 内存屏障类型

```
LoadLoad：保证屏障前 Load 在屏障后 Load 之前完成
StoreStore：保证屏障前 Store 在屏障后 Store 之前完成
LoadStore：保证屏障前 Load 在屏障后 Store 之前完成
StoreLoad：保证屏障前 Store 在屏障后 Load 之前完成（最强）

x86：TSO（Total Store Order）只保证 StoreLoad 有序（其他隐含有序）
  → volatile 写 = StoreStore + StoreLoad（x86 只需 StoreLoad mfence）
  → volatile 读 = LoadLoad + LoadStore（x86 隐含，无需屏障）
```

### 衔接 JVM volatile（域2 已讲）

```
JVM volatile：
  写 = StoreStore + StoreLoad 屏障（禁止写之前操作重排到写后）
  读 = LoadLoad + LoadStore 屏障（禁止读之后操作重排到读前）

x86 实现：
  volatile 写 = lock addl $0,(%rsp) 或 mfence（StoreLoad）
  volatile 读 = 无需屏障（x86 TSO 隐含 LoadLoad/LoadStore）
```

### P9 追问链

- **Q：内存屏障解决什么？** → 指令重排序（编译器/CPU 优化导致的可见性问题）
- **Q：x86 需要几种屏障？** → 只需 StoreLoad（TSO 隐含其他三种）
- **Q：volatile 和内存屏障关系？** → volatile 写/读插入内存屏障（保证有序性）

## 三、RCU（Read-Copy-Update）

### 原理

```
RCU：读多写少的同步机制（无锁读）
  读：直接访问（无锁/无原子操作，极快）
  写：① Copy（复制数据）② Update（更新指针）③ 等待宽限期（旧读者完成）→ 释放旧数据

宽限期（Grace Period）：
  所有 CPU 都经过一次上下文切换（旧读者全部完成）
  → 之后才释放旧数据（安全）

应用：
  内核：路由表/链表（读远多于写）
  Linux：VFS 目录项/网络路由
```

### P9 追问链

- **Q：RCU 适合什么场景？** → 读多写少（读无锁，写 Copy+Update+等宽限期）
- **Q：宽限期是什么？** → 所有 CPU 经过一次上下文切换（旧读者全部完成）
- **Q：RCU 和读写锁区别？** → RCU 读完全无锁（更快）；读写锁读也有 CAS 开销

## 四、死锁

### 死锁四个条件（必要条件）

```
① 互斥：资源独占
② 占有且等待：持有资源又等其他资源
③ 不可剥夺：资源不能被强制回收
④ 循环等待：进程间形成等待环

预防：破坏任一条件即可
  统一加锁顺序（破坏循环等待）
  tryLock 超时（破坏占有且等待）
  减少锁粒度（减少互斥）
```

### 死锁排查

```
Java：jstack 自动检测（"Found deadlock"）★ JVM 域5 实测
OS：  /proc/<pid>/task/*/stack（线程栈）
      echo t > /proc/sysrq-trigger（内核线程转储）
```

### P9 追问链

- **Q：死锁四个条件？** → 互斥/占有且等待/不可剥夺/循环等待
- **Q：怎么预防死锁？** → 统一加锁顺序/tryLock 超时/减少锁粒度
- **Q：怎么排查死锁？** → jstack 自动检测（JVM）；/proc 栈（OS）

## 补充 #1：读写锁（rwlock）

```
读写锁：读共享/写独占
  读锁（共享锁）：多个读者可同时持有
  写锁（独占锁）：写者独占（读者/其他写者等待）

规则：
  读-读：可并发
  读-写：互斥
  写-写：互斥

实现：
  内核：rwlock（读计数+写标志）
  用户态：pthread_rwlock / Java ReentrantReadWriteLock

适用：读多写少（如配置读取/缓存）
  读多：读锁无竞争（并发读）
  写少：写锁独占（短暂阻塞读者）

问题：
  写者饥饿（一直有读者→写者等不到）→ 公平模式（写者优先）
  读写升级（读锁→写锁）可能死锁（需先释放读锁再获取写锁）
```

### P9 追问链

- **Q：读写锁规则？** → 读共享/写独占；读-读并发，读-写/写-写互斥
- **Q：读写锁适合什么？** → 读多写少（配置/缓存）；写多时退化为互斥锁
- **Q：写者饥饿怎么办？** → 公平模式（写者优先）或避免长期读锁

## 补充 #2：活锁/饥饿（死锁的补充概念）

```
死锁（Deadlock）：互相等待，永久阻塞
  例：A 持有锁 1 等锁 2；B 持有锁 2 等锁 1

活锁（Livelock）：都在运行但无进展（一直重试）
  例：A 让 B 先走；B 让 A 先走；互相让路（都在动但过不去）
  → 与死锁区别：活锁线程在运行（不阻塞），但无进展
  → 解决：加随机退避（重试间隔随机化）

饥饿（Starvation）：低优先级进程长期得不到 CPU
  例：高优先级进程持续运行（CFS 有 nice 权重，但极端情况）
  → 实时调度：低优先级 CFS 可能被实时进程饿死
  → 解决：调度器保证最低服务（CFS 有 min_granularity）

三者对比：
  死锁：阻塞（不动）
  活锁：运行但无进展（乱动）
  饥饿：运行但分配不均（动得少）
```

### P9 追问链

- **Q：死锁/活锁/饥饿区别？** → 死锁=阻塞；活锁=运行无进展；饥饿=分配不均
- **Q：活锁怎么解决？** → 随机退避（重试间隔随机化，打破同步）
- **Q：饥饿怎么解决？** → 调度器保证最低服务（CFS min_granularity）
