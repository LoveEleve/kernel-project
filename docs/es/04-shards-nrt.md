# 04-分片与近实时：写入后为什么1秒才搜到

## §0 它干了什么（例子先行）

bulk 写完 100 条，**立刻**查 count：

```
写入完成 → count 查出 0！     ← 此刻还没 refresh
1 秒后（或主动 refresh）→ count=103
```

- **它干了什么**：写入先进内存 buffer，**默认每 1 秒**才变成可搜索的 segment——这是"近实时（NRT）"而非实时。
- **输入/输出**：输入=写请求；输出=1 秒后才可搜（但写本身早就成功了）。
- **本篇回答**：为什么 1 秒？refresh 和 flush 差在哪？分片是什么、怎么定数？

## §1 掌握卡（4 条）

1. **写入三站**：buffer（不可搜）→ 1s refresh 成 segment（**可搜**，还在 PageCache 内核页缓存）→ 30min/512MB flush 落盘（**持久化**）。**可搜索 ≠ 已持久化**。
2. **translog 兜底**：两次 flush 间的写入日志，默认每请求 fsync（强制刷盘落盘）——宕机可恢复；丢数据的口子只在改异步 translog 后。
3. **分片=分布式底座**：索引=N 个主分片（`_id` hash 路由）+ 副本（高可用+读扩展）；**建索引时定死不可改**（单分片 10-50GB 经验值）；写要同步所有副本（副本多写慢）。
4. **搜索广播**：请求发所有分片、各查各的、协调节点合并——**这就是深分页贵的原因**（03 §5 回顾）。

## §2 写入三站（为什么不是实时）

每次写入都立即建 segment+刷盘 → 写吞吐崩。ES 的权衡：

```
写入 → ① 内存 buffer（不可搜） + ② translog（持久化保障）
  ↓ 每 1s（refresh_interval）
① → 新 segment（可搜，仍在 PageCache，未 fsync）
  ↓ 每 30min 或 translog 满（flush）
segment fsync 落盘 + 清 translog
```

| 机制 | 作用 | 默认 |
|---|---|---|
| **refresh** | buffer → segment（**可搜索**） | 1s |
| **flush** | segment fsync + 清 translog（**持久化**） | 30min / 512MB |
| **translog** | flush 间的写日志（宕机恢复） | 每请求 fsync |

调法：写多搜少调大 refresh 提吞吐；要求快见调小或写入带 `refresh=true`。

## §3 分片

```
index(notes) → [P0][P1][P2]   主分片（_id hash 路由）
                 ↓ 每个主分片带副本
               [R0][R1][R2]   副本（读扩展 + 高可用）
```

- 写：路由到主 → 同步副本 → ack（确认返回，数量由 `wait_for_active_shards` 控制）。
- 搜：广播全分片 → 本地检索 → 协调节点合并。
- 副本三面：主挂副本顶（高可用）/ 搜索打副本（提升 QPS=每秒请求数）/ 写同步所有副本（**副本多=写慢**）。

## §4 坑

"写完立刻搜"搜不到（近实时，本 lab 实测 count=0）/ refresh ≠ 持久化 / 分片过多（每片有集群状态与段合并开销，不是越多越好）/ 过少（扩不了容）/ 副本 0 是实验配置，生产至少 1。

## §5 边界（一句话翻篇）

- 段合并（segment merge）机制 → 用时查。
- 协调节点路由算法细节 → 知道"hash 路由+广播合并"即可。
- xhs 生产拓扑（D4 口径：业务 ES :19200 多节点）→ 不深考证，06 对照用到再说。
