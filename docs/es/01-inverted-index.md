# 01-倒排索引：为什么搜批量能秒找到

## §0 它干了什么（例子先行）

库里 100 万条笔记，搜 `批量`：

```
MySQL LIKE '%批量%'：全表扫描——100 万条就卡了（左模糊用不上索引）
ES：100 条秒出
     └─ 因为文档入库时就切成了词，建好了"词 → 文档列表"的表
```

- **它干了什么**：预先切词建映射——搜索是**查表**，不是扫表。
- **输入/输出**：输入=搜"批量"；输出=词"批量"挂着的文档 ID 列表。
- **一句话**：倒排索引 = **词项（term）→ 文档 ID 列表（posting list）** 的映射表。

```
正向（文档→词）: 笔记1: [批量,笔记,1]  笔记2: [批量,笔记,2]
倒排（词→文档）: 批量 → [1,2,…,100]   ← 搜索"批量"直接取它
```

## §1 掌握卡（3 条）

1. **为什么快**：建表时切词倒排，查询变成词典查找——对比 MySQL 左模糊扫全表；范围/排序/聚合靠 doc_values（列存，03 讲）。
2. **三步链路**：分词（standard 中文按字切，生产用 IK）→ 倒排表（词频算分、位置支持短语）→ 查询（分词→查倒排→合并→BM25 打分）。
3. **两个铁律**：索引和查询的 analyzer（分词器）必须一致（分词不可逆）；ES 不是数据库（无事务、近实时、要同步——"事实源"永远在 DB）。

## §2 MySQL 两个不够用

| 需求 | MySQL | ES |
|---|---|---|
| 全文检索（分词+相关性） | `LIKE '%x%'` 用不上索引；全文索引弱 | 倒排+分词+BM25 打分（BM25=按词频+逆文档频率给相关性打分） |
| 海量多条件筛选+排序+聚合 | 组合索引爆炸 | 倒排+doc_values（列存=按列组织的数据副本，排序/聚合专快） |

xhs 场景（笔记标题/内容/标签检索+召回排序——召回=先从大集合捞出候选再精排）就是典型：**DB=事实源，ES=检索副本**（同步链路 05 展开）。

## §3 三步链路

**① 分词**（实测：`小红书种草笔记`）：

```
standard：[小,红,书,种,草,笔,记]   ← 按单字切，"笔记"能中（笔+记都命中）
IK（xhs 生产）：[小红书,种草,笔记]  ← 词典驱动，粒度合理召回准
```

**② 倒排表**：每个词项挂 posting list（文档 ID + **词频**（BM25 打分用）+ **位置**（短语查询"笔记 批量"相邻用））。

**③ 查询**：`match` 把输入分词 → 每词查倒排 → 合并（OR/AND）→ BM25 打分 → 排序。

## §4 坑与边界

| 坑 | 说明 |
|---|---|
| 中文默认按字切 | 生产必须 IK（02 讲怎么配） |
| 分词不可逆 | 索引时怎么切查询时也怎么切——**两侧 analyzer 一致** |
| 倒排只管词项 | 范围/排序/聚合走 doc_values（03 展开） |
| ES 不是数据库 | 无事务/近实时（04）/要同步（05） |

## §5 边界（一句话翻篇）

- BM25 公式细节 → 面试知道"词频+逆文档频率"即可，算法不深挖。
- 中文分词器选型细节 → 02。
- 同步（Canal/MQ）→ 05。
