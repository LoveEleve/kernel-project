# 08-面试口径（vpc5.0 版）

> 前七章是"知识"，本篇是"讲法"。核心纪律：**数字带口径、坑比成果值钱、边界先认、每段留钩子**。
> 口径优先级：面试卡 > 我的推断；两版数字（如选举 TTL）统一说"秒级 TTL + TTL/3 续租，以仓库为准"。

## §0 它干了什么（例子先行：90 秒开场，背到能脱稿）

> "面试官好，我是 [姓名]，做云网络控制面方向，主要用 Go。
> 过去一年多我在腾讯云 VPC 控制面，参与 **vpc5.0（Gen3）** 的建设——200 万 VPC、约 1 亿条配置的变更都要经过它，下发到十万级物理设备的 Agent 和内核/DPDK 数据面。我在里面负责**配置中转（vpc-fusion）**这条链路，主要做了三块：
> 第一块是**分布式任务调度中心**——快照、对账、清理任务靠它触发和分发，我把它从'非原子、崩溃会丢任务'改造成 Lua 原子化 + 租约自恢复；
> 第二块是**配置一致性**——修掉了快照里已删配置'复活'的语义缺陷，并把元数据改成'缓存即真相'支撑高频扫描；
> 第三块是**运维可观测**——建了十余个运维接口 + 控制台，让'配置为什么没下发'能自查。
> 另外我独立完成过一次 P0 事故的根因定位，约 60 分钟。
> 我擅长的是：**把'看起来能用'的分布式组件做到'生产可交付'**。"

## §1 掌握卡（口径纪律 7 条）

1. **零丢失 = at-least-once + 幂等收敛**——绝不说 exactly-once；"零丢失"是相对旧实现 BLPop"取出即丢"的说法。
2. **Gen3 未全量灰度**——"内部建设完成、灰度准备中""我在建设期参与"；说"已上线"当场翻车。
3. **认领边界**：可认领 = fusion 的调度/一致性/运维接口；broker 三向合并、tRPC 协议、SET 迁移、agent Extension、数据面 DPDK——"讲机制理解，不认领"。
4. **包装词要自曝**："调度中心"是我按角色的叫法，系统里叫 Leader-Worker 任务队列。
5. **数字带口径**：系统口径（200 万/1 亿/86ms）vs 我的数字（90s 恢复/零丢失）分开说。
6. **坑比成果值钱**：讲事故链（现象→根因→修复→验证）；不把"自己改错再修"包装成战绩。
7. **留钩子**：每条线结尾"想先深挖哪条？"——把话语权接回来。

## §2 三条线讲法（各 60-90 秒）

**线 1 调度可靠性**：问题（丢/重/卡死→该 VPC 变更永久不生效）→ 改造三层（8 Lua 原子化 + Hash Tag；Lease/Heartbeat/Recovery 三段式 + ownership 三重校验在 Lua 内；LIndex 替代 BLPop + 旧 key 双写双读 + 能力探测 + 16 项治理 + 首启限频）→ 结果（三类故障消除）。

**线 2 数据一致性**：Put(nil) 复活（key 还在→快照复活→流量发到已销毁 VM→对账 Redundant；修复=Delete + 测试观测点改"遍历为空"）；缓存即真相（ResourceObj 高频扫描→写缓存异步落库→DAO validateConfigName 五方法防绕过→双丢全量重建）。

**线 3 运维与事故**：十余接口四大类（快照/消息/资源/清理）+ 分表分页 token；watchdog+systemd 两层守护；P0（22:43 卷入→60 分钟定位：症状两类→ID 编码 20 位回绕→跃迁保护依赖 get_auto_increment→git 回溯 2025-09 ORM schema 入参→临界复现；止血/修复非本人）。

## §5 王炸故事（挑 2-3 个讲）

① 任务零丢失（租约三段式 + 竞争窗口）；② 已删配置复活（Put(nil)/遍历断言）；③ 首启 200 万限频（27.8h 直面）；④ Redis Cluster 的坑（TxPipeline EXECABORT→Lua）；⑤ 缓存即真相；⑥ P0 60 分钟（现场算 1,093/526,416）。

## §6 开放题：万能四步 + 沙盘速览

**万能四步**：①先澄清约束（规模/语义/延迟/成本）→ ②分层方案（接入→传输→状态→端侧）→ ③取舍（至少两组对比）→ ④回扣自己的系统。

| # | 题 | 一句话思路 |
|---|---|---|
| Q1 | 从零设计任务调度中心 | Leader 多域 + Worker 水平扩 + 租约 + Lua + 限频 + 对账兜底；低规模可砍租约 |
| Q2 | 端到端 86ms→10ms | 先澄清端到端还是单跳；拆链路找大头；批量化/预计算/数据面直连；拿 CA 回扣 |
| Q3 | Redis 全挂 30 分钟降级 | 先澄清"不停"指什么；fail-stop 理由（错误>延迟）；"降级先设计如何验证没漏" |
| Q4 | 配置 105→500 | 元数据驱动已备好；瓶颈在快照/对账/Extension；按域分片 |
| Q5 | 跨 Region | 单元化 vs 全球强一致；现状单 Region + CCN；"不是我能拍板的，取舍在基础设施投入" |
| Q6 | 漂移自动收敛 | 检测→分类→动作；防震荡=幂等+限速+单飞+抑制窗口；"自动收敛风险>收益" |
| Q7 | 10 倍流量哪里先崩 | 依赖链排查+容量公式；先崩可能是共享资源（MySQL/Redis）；分段闸门回扣 |
| Q8 | 变更全链路可回滚 | 版本化→反向变更→双跑→切流→审计；"回滚是生成反向变更，不是撤销历史" |

## §7 Capstone：系统设计推演（白板"设计一个 VPC 控制面"）

- **需求**：功能 8 条（VPC→子网→VM→路由→安全→LB→跨 VPC→混合云）；非功能量化（200万×50=1亿条 / p99<5s / 24h 对账窗口 / 99.99% / 单 VPC 不外溢 / 回滚<10min+72h）。
- **数据模型三原则**：三表分离（t_rtb→t_rtb_route→t_rule，解决策略复用）；策略与转发分离（1 条策略↔N 条 VM 级转发）；无外键是刻意（高频变更下校验开销>收益）。
- **架构选型表**：MySQL（非 etcd）/ Kafka（非 Redis Streams）/ tRPC Stream（非 gRPC）/ LevelDB（非 RocksDB）——每条都有"够用就好"的理由。
- **AP 论证**：CP=等 10 万+ agent ACK 不可行；AP+对账——"**AP 不是理想，是 pragmatic；对账就是这个选择付的账单**"。
- **容量**：对账是全系统最短板（2000 万时 33h→改增量为主）；发布限频 3.3x 余量、Worker 85x 余量。
- **Tradeoff 四连**：① Redis Streams 两缺陷（offset 存内存重启回放 2.8h + AP 分区双 consumer）——"省 Kafka 的成本会以故障形式还回来"；② 锁三方案（ZK 雪崩/DB 可查/Redis 锁需强一致）——"锁的正确性交给 DB，可观测交给表"；③ LevelDB vs RocksDB——"不为不需要的并发优化付费"；④ Push vs Pull（0.5 次/天/VPC——Pull 浪费；Push 防重连风暴=限频+合并+增量）。

## §8 行业对比三句话（细节引用 Gen2 系列 16 章，不重复）

1. **讲共性**："控制面问题在业界是收敛的——分发/版本/分片灰度/诊断对账，题面由物理约束决定。"
2. **讲取舍**："差异在取舍：Google 用 Spanner 换掉对账，我们用对账换掉对 Spanner 依赖；UCloud 全异步事件驱动，我们 binlog+分层扇出。"
3. **讲认知**："所以对账不是落后，是**基础设施条件下的 pragmatic 选择**。"（红线：Andromeda/Hyperplane/UCloud 都是别人的系统——只讲题面与取舍，不认领。）

## §9 业务口径（业务面/终面）

- **三类用户**：云租户（即时生效不中断）/ 内部运维（可查可灰度可回滚）/ 下游系统（有版本可对齐）。
- **四大业务指标**：创建即用 / 规则即生效 / 销毁即停止 / 业务不中断——fusion 是唯一中转，卡死全命中。
- **20 场景一句话**："VPC 控制面管的不只是路由——20 个场景、74 种业务配置；fusion 是所有场景的统一中转。"
- **价值量化四问框架**：正向（秒级生效=基础体验）/ 负向（调度卡死→一批 VPC"配置了不生效"→所以做到零丢失自恢复）/ 成本（多付对账与人工兜底、省基础设施自研）/ 边界（金额口径不归我，我不越界）。

## §10 追问演练精选（第二轮 + 自省）

- **S2 僵尸任务**：心跳只证明进程活着——任务级 Timeout + 进程级 watchdog 两层兜；根本缓解=把任务粒度做小。
- **S4 孤儿头**：data TTL 到期→discardQueueHead 显式丢弃，否则队头永久阻塞；"任务可由对账重触发，不追求绝不丢一次调度"。
- **C2 Redis 内存**：队列永不在途 200 万（边发边消费）；**诚实认边界：发布侧没有水位背压**。
- **X1/X2/X3 为什么不用 Kafka/DB/Streams 做队列**：Kafka 顺序流不适配抢单+租约+优先级+延迟重入队；DB 轮询把压力打到 MySQL；Streams 的 PEL 替代不了"score=过期时间的显式租约索引"——共同前提："**任务不是唯一真相源，可从权威数据重建**"。
- **D1/D3 版本与脏数据**：自增版本判"连续性"；存量 nil key 靠快照重建+对账清，不写一次性脚本；"修复要管向前正确，还要答存量怎么办"。
- **E1/E3 应急与复盘**：前 10 分钟=定影响面→查上下游→症状分类→找最近变更→保现场；报告=时间线（含每次尝试结果）+根因链+归属+**可验证的改进项**。
- **R1 只留 3 个 Lua**：claim/finish/requeue（领取→完成→恢复闭环；claim 最不可替代）。
- **R2 最脆弱单点**：Redis（调度状态唯一载体，fail-stop）；其次 Leader（四域隔离+15s 租约）。
- **L1 claim 六连**（压轴）：验头→抢头返回 0→重试空转但不丢（先看不删）→丢弃孤儿的必要→崩溃 30s 过期→旧 Worker 复活被 ownership 拒。
