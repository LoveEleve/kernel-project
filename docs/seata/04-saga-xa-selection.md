# 04-SAGA、XA与四模式选型

## §0 它干了什么（例子先行）

四种模式一句话各一个场景：

```
XA：   银行转账（强一致是硬要求，锁拿久点无所谓）——DB 原生 2PC（两阶段提交：准备好了再统一提交/回滚）
AT：   电商下单（大多数场景）——Seata 自动补偿，默认选它
TCC：  秒杀抢库存（并发打满，全局锁扛不住）——业务写三方法，无锁
SAGA： 订单→调度→维修→结算（流程跑几小时）——每步提交，失败反着补
```

- **它干了什么**：XA/SAGA 是 AT/TCC 光谱的两端——XA 更强一致更慢，SAGA 更长事务更复杂。
- **输入/输出**：输入=业务场景；输出=选型决定。
- **本篇回答**：SAGA 怎么治长事务？XA 靠什么保强一致？四模式怎么选？

## §1 掌握卡（3 条）

1. **SAGA = 状态机 + 反向补偿**：每步本地提交立即释放资源；失败从失败节点前一节点开始逐个补偿——治"分钟/小时级长事务"（AT/TCC 的锁/冻结全程持有，扛不住）。
2. **XA = DB 原生 2PC**：Seata 只协调不补偿；PREPARE 到 COMMIT 全程**持锁**——强一致、性能最低、需 DB 支持 XA、不可混分支。
3. **选型一句话**：AT 默认；强一致金融级 XA；高并发/非 JDBC 资源 TCC；长流程 SAGA——一致要求越强越慢，流程越长越要手写补偿。

## §2 SAGA：长事务的解法

**问题**：AT 全局锁/TCC 冻结都"全程持有"——流程跨分钟/小时级会锁爆。

**解法**：状态机引擎（`saga-engine`），用 JSON 写流程定义（DSL=领域特定语言，这里特指 Seata 的 StateLang 流程描述格式）：

```
正向: [下单]→[扣库存]→[调度]→[维修]→[结算]   每步本地提交、立即放资源
         │                │
反向:   [取消订单]        [取消调度]…         失败→从失败点前一步开始反着补
```

每个 State 配 `CompensateState`；失败回退到前一节点的补偿态；**补偿链必须幂等**（可能被重复调用——和 02/03 的"重试必重复"同根）。lab 不实操（长事务场景 + 状态机引擎依赖重），架构+JSON 读懂即可。

## §3 XA：DB 原生 2PC

```
XA START → 业务 SQL → XA END → XA PREPARE（锁持续持有！）
  → TC 收集各分支 PREPARE：全 OK → XA COMMIT；有 FAIL → XA ROLLBACK（锁才放）
```

与 AT 的本质区别：**AT 一阶段就提交放本地锁，XA 的锁从 PREPARE 拿到 TC 决议**——无失败窗口（AT 的"先提交再补偿"有窗口，靠全局锁+镜像校验兜，02 §3/§4）。XA 换来的"强一致"=任何时刻对外都是全局最新结果，没有中间态可见。

两要点（面试常问）：**先注册分支再 XA start**（XA start 要 Xid，BranchId 由注册生成——与 AT 相反）；**代理两式**（优先普通 DataSource 建 XAConnection 保持透明，但驱动兼容有坑→也支持直接代理 XADataSource）。

限制：每分支都支持 XA 协议；**不可混 XA/非 XA 分支**；换 `DataSourceProxyXA` 只改类名。

## §4 四模式对比（D1 §六原表）

| | XA | AT | TCC | SAGA |
|---|---|---|---|---|
| 原理 | DB 原生 2PC | 自动补偿（undo） | 业务三方法 | 状态机+补偿 |
| 侵入 | 零（靠 DB） | **极低** | 高 | 高 |
| 一致 | **强一致** | 最终一致 | 最终一致 | 最终一致 |
| 锁 | 全周期 | 一阶段后放本地锁，仅全局锁 | 无锁 | 无锁 |
| 性能 | 低 | 中 | 高 | 高 |
| 适用 | 金融强一致 | **大多数场景** | 自定义一致性需求 | 长事务（分钟/小时） |

**记忆钩**：一致性强度和性能反着走（XA 强而慢，SAGA/TCC 快而靠业务实现保一致）；自动化程度也是梯度——XA/AT 全自动（DB/Seata 管），TCC/SAGA 全手写（三方法/状态机+补偿）。
