# LB-01 负载均衡全景：客户端 vs 服务端

> 用途：把"负载均衡"这个词的全景立起来——两种形态怎么分、分别用在哪、为什么 Spring Cloud 选了客户端 LB

> 素材：训练营 stage-1 第 11-12 章（概念）/ 网关课程 L16·L46（实测）/ xhs-project（生产）
> 前置：无（本篇是地基）；后续：02 名单从哪来 → 03 挑法全集 → 04 SCLB 接入

## 0. 例子先行：同一个请求的两种走法（具体到地址）

假设有 2 台后端实例：`10.0.2.11:8081`、`10.0.2.12:8081`。

**走法一：服务端负载均衡（以 Nginx 为例）**

```text
调用方 ──①──> Nginx（10.0.0.10:80） ──②──> 10.0.2.11:8081 或 10.0.2.12:8081
                ↑ Nginx 自己挑、自己建第二段连接
调用方从头到尾只认识 10.0.0.10 —— 它不知道后端有几台、是谁
```

**走法二：客户端负载均衡（SCLB）**

```text
调用方（进程内存里有一份名单 [10.0.2.11:8081, 10.0.2.12:8081]）
      ──①──> 直接连 10.0.2.11:8081
      ↑ 挑在调用方自己的进程里完成；没有中间人
```

一句话：**两种形态都做"从多台里挑一台"；区别是"挑"这个动作跑在谁的进程里**——跑在中间人（Nginx）里 = 服务端；跑在调用方（你的程序）里 = 客户端。

---

## 1. 掌握卡（3 条）

1. **判定标准**：名单（后端 IP 列表）在谁手里、"挑"在哪执行——**Nginx 的配置里 + Nginx 进程** = 服务端 LB；**调用方进程内存里 + 调用方代码** = 客户端 LB（怎么一眼判定：见 §5 判别口诀）。
2. **方向分工**：**南北向** = 用户/外部 → 内网的"入口方向"（像从地图南走到北），多用服务端 LB（DNS/SLB/Nginx/K8s Ingress）；**东西向** = 内网服务之间的"横向调用"，多用客户端 LB（SCLB / Dubbo / gRPC）。**生产是叠加，不是二选一**。
3. **内核模型**：负载均衡 = **名单 + 挑一个**；真正的复杂度来自"**名单会变**"（扩缩容/发布/宕机）——本系列后续（02 名单 / 03 挑法 / 07 摘除）都是围绕它展开。

---

## 2. 先把词说清："客户端"= 调用方

"客户端负载均衡"里的"客户端"**不是指浏览器/App**，而是**一次调用的发起方**：

| 场景 | 谁是"客户端"（发动调用的） |
|---|---|
| 网关调下游服务 | **网关**（所以网关里的 `lb://` 是客户端 LB） |
| 服务 A 用 Feign 调服务 B | **服务 A** |
| 浏览器访问网站 | 浏览器 |

"服务端负载均衡"里的"服务端"= **中间那台专职分发的机器**（Nginx/SLB）——它既不是调用方，也不是业务服务。

---

## 3. 服务端 LB 的三种形态（从粗到细）

| 形态 | 代表 | 认什么 | 能做什么 | 短板 |
|---|---|---|---|---|
| **DNS 轮询** | 域名配多个 A 记录 | 只认域名 | 零成本、跨机房（严格说是"解析期"分发，非请求级） | TTL/客户端缓存导致切流量慢；**无健康检查**；分布不均 |
| **L4（传输层）** | LVS / F5 / 云 SLB | IP:端口、连接 | 高性能、扛连接量 | 看不懂 HTTP（不能按路径/头分发） |
| **L7（应用层）** | Nginx / APISIX / Kong / Envoy | HTTP 路径/头 | TLS 卸载、灰度、限流、按业务路由 | 比 L4 重；要维护配置 |

共性：**名单和挑法都在它自己那里**（Nginx 的 `upstream` 配置、SLB 的控制台）；调用方只要知道它的地址，其它一无所知。

> 服务端 LB 深入不在本系列（网关选型视角见 [`L40`](../gateway/L40-gateway-selection-boundaries.md)）；本篇只需"够对照"。

---

## 4. 客户端 LB：把"名单 + 挑"搬进调用方进程

```text
名单从哪来：注册中心（Nacos 推送实例列表——02 详解）
挑  法在哪：调用方进程内的 LB 内核（SCLB——03/04/05 详解）
怎么用：URL 写服务名（`lb://demo-provider`）= 告诉 LB 内核"帮我挑一个"
```

**为什么 Spring Cloud / Dubbo / gRPC 选客户端 LB**：

1. **少一跳**：没有中间转发，延迟低；
2. **无中心瓶颈**：流量涨了是"每个调用方各自分担"，不存在所有流量压一台 Nginx；
3. **请求级策略**：调用方手里有完整请求上下文（header/灰度标签/zone/连接数）——灰度和"最少连接"这类策略在客户端做最自然。

**代价**（后面课程会反复回到这里）：

1. 每个调用方都要装一套 LB 库 + 注册中心客户端（**语言相关**：Java 用 SCLB，Go 要自己实现）；
2. **名单一致性自己扛**：每个调用方各自缓存/刷新实例列表——L46 实测的"实例死了网关 35 秒才知道"就是这条代价的现形（07 详解）。

## 5. 两种形态对照 + 判别口诀

| 问题 | 服务端 LB（Nginx） | 客户端 LB（SCLB） |
|---|---|---|
| **名单（后端 IP 列表）在哪** | 在 LB 的配置里（`upstream`） | 在**调用方进程内存**（注册中心推送） |
| **"挑"在哪执行** | LB 进程 | **调用方进程** |
| 连接几段 | 两段（你→LB→后端） | **一段直连**（你→后端） |
| 后端 IP 对调用方可见吗 | 不可见 | 可见（要自己连） |
| **一台后端挂了的表象** | **502 Bad Gateway（来自 LB）**，你不知道后端是谁 | **`Connection refused: <后端IP>`（你自己连的）** |
| 语言无关性 | 任何客户端都能用 | 每种语言要有自己的 LB 库 |
| 策略灵活性 | 全局统一，主要靠 HTTP/TCP 信息 | 每个调用方可定制（能用请求上下文） |
| 典型方向 | 南北向入口 | 东西向服务间 |

**判别口诀**：**停掉一台后端，看错误出现在谁的日志里**——

- Nginx 的日志报"连某后端失败"、你的程序只收到 `502` → **服务端 LB**；
- 你自己的日志出现 `Connection refused: <后端IP>` → **客户端 LB**。

> 实锤（L46 实测，2026-10-07，日志节选）：网关（客户端 LB）——
> `AnnotatedConnectException: finishConnect(..) failed: Connection refused: /192.168.13.128:8082`
> 网关**亲自去连**了 8082，所以它眼里有后端名单。

## 6. 生产是叠加的：xhs 的完整链路

```text
用户
 │  ① 服务端 LB：DNS/SLB/K8s Ingress 从【网关集群】里挑一台
 ↓
网关（Spring Cloud Gateway）
 │  ② 客户端 LB：网关从【demo-provider 名单】里自己挑一台，直连（SCLB）
 ↓
服务 A
 │  ③ 客户端 LB：服务 A 用 Feign 调服务 B，同样自己挑、直连（SCLB 同内核）
 ↓
服务 B
```

- ① 名单和挑法在中间层 → 网关无需任何 LB 代码；
- ②③ 名单和挑法在调用方进程 → 网关/服务 A 自己就是负载均衡器；
- xhs-project 的 `k8s/` 有 ingress/service 模板（①），内部网关与服务则是 SCA 客户端 LB（②③）。

## 7. 生态对照（谁属于哪一派）

| 系统 | 形态 | 备注 |
|---|---|---|
| DNS 轮询 | 服务端（最原始） | TTL/缓存/无健康检查 |
| LVS / F5 / 云 SLB | 服务端 L4 | 高性能四层转发 |
| Nginx / APISIX / Kong / Envoy | 服务端 L7 | 南北入口、TLS、灰度、限流 |
| **K8s Service** | **服务端**（kube-proxy/iptables/IPVS 转发） | 集群内也有"服务端 LB" |
| **Spring Cloud LoadBalancer** | **客户端** | 本系列主角（`lb://`、`@LoadBalanced`） |
| Dubbo | 客户端 | 注册中心 + 本地软负载 |
| gRPC | 客户端（内置 pick_first / round_robin） | 也可外置代理（xDS/Envoy） |
