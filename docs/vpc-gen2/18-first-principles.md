# 18-第一性原理与复刻指南：为什么这么设计

> 前 17 篇讲"怎么做"；本篇回答"为什么"——面试讲法（设计取舍）与复刻（优先级/避坑）两条线。
> 标注：【实证】= 材料有据；【推导】= 按约束推导；vpc5.0 对比项标【vpc5.0】。

## §0 它干了什么（例子先行）

面试官："如果让你从头设计一个 VPC 控制面，你先做什么？"

材料给的答案（反直觉）：**先做对账，不是先做推送**——"推送是加速，对账是保底；没有对账的系统是开环系统，一定会漂移"。这就是第一性原理的用法：先回答"它到底是什么"，再回答"先做哪个"。

## §1 掌握卡（6 条）

1. **定位**：它不是 SDN 控制器（不做路径计算）——是**大规模分布式配置同步引擎**："把集中式数据库里的期望状态，可靠复制到十万台机器的内核里，并保证最终一致"。
2. **它是闭环控制系统**：期望→控制器→受控对象→传感器（Inspector）→致动器（Repair）；对账不是可选功能，是架构核心组件。
3. **混合模型**：推送（低延迟）+ 对账（纠错）——纯推送丢事件=永久漂移；纯拉取十万台=打挂 ZK。
4. **Saga 是约束逼出来的**：ZK/Kafka 不支持 XA → 2PC 不可能；事件溯源无法原子"发 Kafka + 写 ZK" → Saga（代价=隔离性弱，声明式配置可接受）。
5. **三代共存是风险控制**：1% 问题——材料例：5000 台就是 50 台受影响（十万台量级则更多）——灰度白名单切换、随时回滚、无需重启。
6. **复刻优先级**：P0=配置存储 / 对账 / Agent+驱动；P1=推送 / Saga / Composer；P2=Outbox / 确认降噪 / 灰度 / 分片。

## §2 定位与硬约束

```
传统 SDN（OpenDaylight/ONOS）= 路径计算（SPF/CSPF/TE）→ 流表
本系统 = 不做任何路径计算（路由用户配/上层算好）——只做"期望状态 → 十万台内核"的可靠复制
定性决定一切：无拓扑发现（无 BGP-LS）/ 无路径计算（无 SPF）/ 无流表压缩；
             需要可靠分发（Kafka/ZK）/ 一致性保证（对账）/ 扩展（分片）
```

| 约束（硬性） | 数字 | 架构影响 |
|---|---|---|
| 设备数量 | 十万台 | 不能中心化 pull（同时拉=打挂服务器） |
| 冷热不均 | 85-94% 冷 | 全量分发浪费 85% |
| 网络分区 | 必然发生 | Raft 强一致在分区时不可用 |
| 内核模块不可改 | vpcko 接口固定 | netlink 向下兼容是死约束 |
| 老代码不能停 | Python 2.7 Agent 在跑 | 新架构必须与旧共存 |
| 延迟 / 一致性 | 秒级 / 最终一致 | 不需要毫秒级、不需要强一致 |

## §3 闭环控制回路（对账 = 核心组件）

```
开环（无对账）：推送→执行→无反馈 → ZK 断连丢事件 / netlink 假成功 / 内存错误 → 永久漂移
闭环（有对账）：推送→执行→读回实际→比较→修复 → 任何不一致下一轮收敛
  "对账周期 = 系统收敛时间上限"
  对账本身也要防误修复（多次确认）→ PID 类比与确认参数见 10 §3
```

- 对账救过的场（材料点名）：#6 发现 152 台不一致 / #10 发现孤岛残留 / #14 至少检测到。
- 完整失败模式枚举（主文档 5.1——推送全都感知不到、对账全都能感知）：ZK 断连错过事件 / netlink 假成功 / 内存被意外修改 / 内核 OOM 丢路由 / 冷启动不完整 / 幽灵路由残留 / 时序竞争乱序。
- 修复方向原则：以更上游为准；修复策略与确认参数 → **10 §3**。

## §4 四个关键抉择（为什么不是别的）

1. **推送 + 对账（而非纯推 / 纯拉）**：纯推送丢事件=永久不一致（#2 ZK leader 故障、#22 Kafka 缺 Partition 即证明）；纯拉取——ZK 单核 1-3M children/s 撑不住十万台同时 getChildren，且 85% 冷数据白拉。
2. **Saga（而非 2PC / 事件溯源）**：2PC 要求所有参与者支持 XA——ZK/Kafka 不支持；事件溯源无法保证"发 Kafka + 写 ZK"原子、重放数据量 TB 级不可行。Saga 代价=隔离性弱——可接受因为**配置是声明式**（不是转账），中间态由对账修复。
3. **Kafka 不直推 Agent**：十万 Agent = 十万 Consumer——Kafka 不支持；同 partition 多 consumer 只有一台能消费；Agent 重启触发 rebalance 全体暂停。→ 分层：Kafka → Broker（少量）→ Agent（海量扇出）。
4. **三代共存（而非 Big Bang）**：全量切换出问题=全部受影响、回滚=再升一次；灰度白名单切换——出问题只影响对应比例、回滚=移出白名单、无需重启。

## §5 复刻优先级（材料原文排序）

```
P0（没有它不能工作）: ① 配置存储（MySQL）② 对账（★ 最重要但最易被忽略）③ Agent + 数据面驱动
P1（有了更好）:       ④ 配置推送（Watch/MQ）⑤ Saga ⑥ Composer
P2（工业级）:         ⑦ Outbox ⑧ 多次确认降噪 ⑨ 灰度切换 ⑩ SET 分片
```

## §6 复刻者最可能犯的六个错（材料原文）

1. 先做推送后做对账 ← 应反过来（推送是加速、对账是保底）；
2. 对账发现差异直接修复 ← 需要确认降噪（≥2 次，3 次更安全）；
3. 修复"先加 missing 再删 extra" ← 要考虑中间态（#8 的 -1）；
4. 删除保护阈值对所有场景一刀切 ← 恢复期要区别对待（#10）；
5. 假设推送消息不会丢 ← 一定会丢，实现时就准备好"丢了怎么办"；
6. 假设 ZK/Kafka 永远在线 ← #2 / #22 / #7 都是证明。

## §7 边界

- 09 为**设计推演文档**（"给另一个 AI 的架构决策指南"）——约束表 / 灰度周计划等为推演口径，具体数字以机制篇为准。
- Composer（RTableComposer / pendingSvcRTable）与"Broker 无状态"属【vpc5.0】形态，本系列只作对照。
- 可复现性边界（13）：vpcko / DPDK 不可移植（无源码、绑内核/硬件）；概念验证可用标准 Linux 替代（VXLAN / veth / iptables / tc）——本系列不做搭建指南。
