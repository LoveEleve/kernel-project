# 06-推导 review：无源码，把实现推出来

> 目的：二代管道的实现细节没有源码，靠**前提推导**补齐：先审前提（标 floor），再对每个未文档化点做推导（常识答 → 反例 → 被迫设计 → 代价）。
> 证据分级：**【实证】**材料有据；**【推断】**结构推导；**【开放】**参数级待源码。

## §2 推导正文

### Q1 节点命名：为什么"版本序可确定"是硬约束？

- **常识答**：名字随便取，读的时候看内容。
- **反例**：消费侧要"给我 version > N 的 binlog"。若名字不能确定序，每次都要全量列出+解析+排序；且乱序到达后树必须能"自排序"才能被正确重放。
- **被迫设计**：**要么定宽零填充（名字典序=版本序），要么消费侧解析版本首字段再排序**。二选一，都满足。
- **裁决**：材料三态冲突（§2 示例 `1517070001_I_...` 无填充 / 树示例纯填充 / 代码 `:020d`）。结合"值通常为空 + BinlogParser 解析文本行 + binlog 自带内容"三点，最可能形态 = **节点名 = 文本 binlog 字符串（版本首字段），消费侧解析取版本**；纯填充名为旧形态/占位。**【开放】**
- **代价**：每次范围读多一次解析；换来命名简单、内容在名。

### Q2 组什么时候闭合？merge 水位在哪？（核心）

- **常识答**：组满（GroupSize）才合并。
- **反例**：低变更 VPC 永远不满（快照永远旧）；组满≠无迟到写（P2 乱序），合并早了会丢迟到。
- **被迫设计**：合并对象 = **已闭合组**；闭合信号 = **后继组出现**（版本单调 ⇒ 正常流不再回写）；水位 = **最后一个已闭合组的 trigger**（活动组不动）。迟到兜底 = 12h 拒写（把迟到限制在窗内）+ snapshot_differ 周期对账 + agent 对账。
- **代价**：极端迟到（合并后到达）短暂漏进快照，靠对账收敛；消费侧落后水位 → Slow Path 拉快照（系统接受）。
- **变体**：更保守"滞后一组再合并"（合并 N 时要求 N+1 也闭合）——**【开放】**。

### Q3 12h 窗口为什么是"拒写"而不是"保留"？

- **常识答**：12h 是 binlog 的保留期。
- **反例**：延迟/重放的老消息写进旧组 → 版本低于已合并水位 → 树里出现"幽灵旧版本"，永远无人消费 → 污染。
- **被迫设计**：**写入侧校验 ts，超 12h 拒写**——本质是"合并延迟 < 12h"的显式假设（把迟到约束在系统能兜底的范围内）；保留问题交给"合并后清理"。
- **代价**：真迟到 >12h 的变更从 binlog 通道丢失——权威在 DB，对账可补。

### Q4 为什么 master 要"扫→管道→限流分发"三段？

- **常识答**：worker 各自扫 VPCRECENTCHANGE 领活。
- **反例**：200 万 VPC 的反向索引扫描是全局动作，多 worker 重复扫=浪费+任务重复；vm_prop 压缩慢，无节制分发会打爆 worker（长任务占槽、pending 爆炸）。
- **被迫设计**：单实例 master（锁）→ 扫 VPCRECENTCHANGE → 任务 lpush 到 CRS pending 管道 → 从管道取任务 + **计数限流**分发 → worker rpop。任务幂等（Q5）⇒ 重复无害，限流只管成本。
- **代价**：master 单点（锁+重启重建）；多一跳 CRS。

### Q5 合并为什么能幂等？

- **常识答**：任务只发一次。
- **反例**：master 重启、worker 崩溃、重复扫描——任务必然重复。
- **被迫设计**：幂等靠**版本比对**：读 version_list 最新版 → 读其后 binlog → **没有新 binlog 直接跳过**；同 (vpc,type) 用 `/SNAPSHOT_LOCK` 互斥；写新版本=追加+裁旧，天然可重入。
- **代价**：空跑任务也要读一次 version_list + 扫目录。

### Q6 VPCRECENTCHANGE 为什么这样设计？（冲突吸收）

- **常识答**：一张"最近变更 VPC"的表。
- **反例**：单大节点会爆（200 万 VPC）；临时节点崩溃即丢索引；无界增长扫不动。
- **被迫设计**：**时间片桶（分钟键）+ 计数提前滚动（≥5000）+ 持久节点（靠滚动清理，不靠过期）+ 发布保护（9:30-9:39 收敛当前桶）**；master 只扫最近若干桶。
- **代价**：桶粒度 = 发现延迟 vs 目录数。**已闭合（Round 10）**：主文档 §2.3 ★ 更正——`minute_groups` 是分钟粒度；"10 分钟"实为 9:30-9:39 发布保护时段（protect_recent_change_event）。【实证】

### Q7 快照工程的一组取值推导

- **页大小 7000~50000**：条目字节 × 页条目 ≤ 单 value 安全上限（rtable 条目小→5 万；config 类大→7k~1w）。
- **保留 4 版**：为"最新版损坏回退 + 慢路径追赶 + 并发窗口"留边际；成本 = 4×快照。
- **worker 快照**（`hbgw_worker_*`）：broker 冷启动要"整个 worker 库镜像"（SQLite .db 分片）——落盘即用（MD5 校验 → 快照表 rename → 版本 ×10000 移位）。
- **编码二分**：per-type 快照"文本解析"（SnapshotParser）vs §5.2 "proto"——推断：**路由/配置类=文本行，网关/worker 类=protobuf**（vpc_ckv.proto 的存在是后者的实证）。

### Q8 消费侧为什么分两条形态？

- **母机（数万）**：broker 扇入（15+1 worker 分片）→ 心跳 **Pull**（agent 带版本问差，broker 按 6 Pack 回增量/全量）。Pull 的必然性：兼容 Python 时代 agent（无长连接）；且 Pull 天然背压、broker 不维护订阅状态。
- **网关（少数、关键）**：直连 CKV+分区 ZK（the_2g_op）——主备倒换要"回放近期 binlog"（do_switch），直连更可控；且进程粒度快照本就是为它们定制。
- **代价**：两套消费路径 = 两套对账/运维。

### Q9 lazymerge 为什么存在、选什么？

- **常识答**：正常合并就够。
- **反例**：不在 VPCRECENTCHANGE 的冷 VPC 永不触发 → 快照越来越旧 → 冷启动拉旧快照+追赶变长（甚至超窗）。
- **被迫设计**：**每小时低优先级全量扫描**，补"长期无变更但快照落后"的 VPC；聚焦 6 类高频/大快照类型（global route / rtb_route / vm_prop + 3 类）。**【开放】**：另外 3 类名字材料未列（Round 10 复核：主文档同列这 3 类，另 3 类仍缺）。
- **代价**：每小时全扫的 IO/CPU。

## §5 负空间（系统不保证什么）

- 不保证合并即时（分钟级延迟）
- 不保证 binlog 永久保留（合并后清理 + 12h 拒写）
- 不保证乱序零丢失（对账收敛）
- 不保证快照与 binlog 同一时点强一致（最终一致）
- 不保证慢消费侧增量连续（断裂即全量）
