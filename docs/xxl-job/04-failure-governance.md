# 04-失败治理：跑挂了怎么办

## §0 它干了什么（例子先行）

K13 记录的三起真实事故，一起看：

```
事故1：cron 写成 '0/60 * * * * ?' → 秒字段增量 60 越界 → Admin 自动禁用任务
       → trigger_status=0、日志零记录——"任务存在但从未运行"，业务零感知
事故2：每日任务撞上关机窗口 → misfire=DO_NOTHING 直接丢弃 → feedCleanup 零执行
       → 仅 admin 日志一条 WARN
事故3：日报显示"失败 633 条" → 拆开：绝大多数 trigger_code=500（调度失败，重启窗口）
       + handle_code=0（未上报）+ 真业务失败仅 2 条
```

- **它干了什么**：失败治理=**预防**（预览校验/幂等）+ **补救**（misfire/重试）+ **可见**（口径拆解/告警）。
- **本篇回答**：misfire 两策略怎么选？重试什么时候用？"633 失败"教了什么？

## §1 掌握卡（4 条）

1. **misfire 两策略**：`DO_NOTHING`（丢弃，默认——高频任务"下轮天然追平"）/ `FIRE_ONCE_NOW`（恢复后补跑一次——**每日任务必改**）——xhs 按任务频率分级。
2. **失败重试默认关**（`executor_fail_retry_count` 多为 0）：失败**交下一轮 + 对账自愈**——任务设计成"失败下轮再来"比"当场重试 N 次"更稳（03 的幂等底线配套）。
3. **cron 静默禁用是头号坑**：增量越界（`0/60`）→ Admin 自动停用、零业务日志——**上线前用"下次执行时间"预览校验**（K13 追问5 实测结论）。
4. **日报口径三分**：调度失败（trigger_code=500，执行器不在线）/ 未上报（handle_code=0）/ 业务失败（handle_code=500）——**"失败数"必须拆开看**（事故 3）。

## §2 预防：三道闸

| 闸 | 做什么 | 出处 |
|---|---|---|
| cron 预览 | 上线前看 Admin 算出的"下次执行时间"——算不出=非法 | 追问5 |
| 任务幂等 | 唯一键/条件更新——锁失效或人工触发时兜底（"幂等才是底线"话术原话） | 陷阱4/追问6 |
| 部署审计 | init SQL + 巡检——P-D20：19 任务仅 ~8 可调度（挂错组/地址 NULL） | 陷阱5 |

## §3 补救：misfire 与重试的分工

```
错过窗口（关机/Admin 停机）→ misfire 策略管
  高频（30s/1min）→ DO_NOTHING——下一轮马上补上，无需补跑
  每日（2:00/3:00）→ FIRE_ONCE_NOW——错过就是一天，恢复即补

执行失败（业务异常/超时）→ executor_fail_retry_count 管（xhs=0）
  → 下一轮再来 + 对账自愈——因为任务本来就幂等（§2）
```

**为什么不盲目开重试**：补偿任务单轮可能处理几百条，整任务级重试=整批重跑；幂等下"下轮再来"代价更低、语义更干净。

## §4 可见：口径与告警的缺口

- **口径**：`xxl_job_log` 双码（02 §3）——排障先拆码再下结论（633 教训）。
- **审计**：每任务 `trigger_last_time` 巡检（追问7——xhs 就是靠"零日志"发现事故 1 的）+ `xxl-job-health-check.sh` 脚本。
- **缺口主动披露**（K13④/陷阱7）：**任务失败无独立告警**（依赖 Admin 邮件/人工）——接入告警通道是待办，不是已做。

## §5 边界（一句话翻篇）

- Admin 邮件告警配置 → 运维时查。
- 长任务拆分（陷阱8：SERIAL 排队雪崩→拆任务/DISCARD_LATER）→ 06 任务分层时一句。
- 对账"差异可自愈"的业务设计 → 06。
