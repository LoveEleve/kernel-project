# 01-为什么不用Scheduled

## §0 它干了什么（例子先行）

xhs 同一个仓库里两种定时并存（实证）：

```
TccTimeoutJob      → @Scheduled(fixedRate=60000) + Redisson 锁   ← 单机定时
PaymentReconcileJob → 既有 @Scheduled 痕迹，又注册进 XXL-JOB     ← 双轨
支付/库存/优惠券补偿对账 20 个文件 → @XxlJob                      ← 框架化
```

- **它干了什么**：`@Scheduled` 是"进程内闹钟"；XXL-JOB 是"**调度中心说几点跑、哪台机器跑、失败怎么办**"的分布式系统。
- **本篇回答**：@Scheduled 死在哪？调度框架多管了哪四件事？xhs 为什么两条腿走路？

## §1 掌握卡（3 条）

1. **@Scheduled 四宗罪**（每条都有 xhs 实证）：多实例重复跑（K13 兜底第一条就是"Redis 锁互斥"——痛点真实）/ 无执行日志报表（事故"任务从未运行"只能靠 DB 现值反查）/ 失败无治理（misfire=错过触发窗口后的补跑策略，选 DO_NOTHING 就静默丢弃，业务无感）/ 不能手动触发调参（救火靠重启）。
2. **调度框架多管四件事**：**谁来跑**（调度中心选路由）/ **跑没跑**（日志+状态码）/ **跑挂了**（重试/告警/misfire 策略）/ **临时干预**（手动触发/停启用）。
3. **xhs 双轨的分界**：低风险单实例可容忍的（模拟器、健康探测、内存清理类）留在 `@Scheduled`；**补偿/对账/超时/Outbox 发送**这些"丢了就是资损（资金损失）/数据错"的上 XXL-JOB——**按"丢了赔不赔"选轨道**。

## §2 @Scheduled 四宗罪（逐条实证）

| 罪 | 具体现象 | xhs 侧证据 |
|---|---|---|
| 多实例重复 | 3 实例部署→对账 Job 跑 3 份，互踩/重复补偿 | K13④"锁只保证通常单实例"——自研 Redis 锁就是给 @Scheduled 的止血贴 |
| 无日志报表 | "任务从未运行"无处可查 | 事故 1/2 都靠查 DB `trigger_status`/`xxl_job_log` 才定位 |
| 失败无治理 | 错过窗口静默丢弃 | 事故 2：`misfire=DO_NOTHING` 每日任务零执行仅 admin WARN |
| 无临时干预 | 改 CRON/立即跑一次=发版重启 | XXL 侧：控制台改配置/点手动触发，秒级生效 |

## §3 调度框架的分工（三角色预告）

```
调度中心 Admin：几点跑？跑哪台？失败了？——决策与记录（05 讲内部）
执行器 Executor：业务代码所在进程——只负责"被点名后执行 JobHandler"（02）
注册中心：执行器启动把地址注册给 Admin——Admin 才知道能派给谁（02）
```

**为什么必须分离**：调度决策和业务执行的故障域（出问题时的影响范围——谁挂了谁还活着）要分开——业务进程重启/发布时，Admin 还知道"这个任务现在没人接、要不要 misfire"；反过来 Admin 挂了，执行器已领到的任务照跑。02 展开注册与心跳。

## §4 双轨的实证边界（诚实说）

- xhs **不是**"全面 XXL"：19 处 `@Scheduled` 仍在服役（含 TccTimeoutJob 这种关键补偿——它**自带 Redisson 锁**（06 详看），是"@Scheduled+自研锁"的极限用法）。
- 20 个文件 `@XxlJob`；K13② 口径：**24 个任务 / 10 个执行器组**（组=执行器的分组，一组进程共担一类任务；代码文件数≠admin 注册任务数——一个文件可注册多个、组按业务域拆）。
- 教训口径（K13 P-D20）：**部署后任务要审计**——19 任务曾仅 ~8 可调度（挂在 sample 组、地址 NULL）。"引了框架≠任务真的在跑"。
