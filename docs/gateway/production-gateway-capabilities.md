## 2. 为什么要自研？—— 4 个原因

| # | 原因 | 具体 |
|---|---|---|
| 1 | **规模** | 单集群数万实例、**百万 QPS**、毫秒级 P99 —— 开源网关默认架构撑不住 |
| 2 | **性能与成本** | **Go/C 网关内存几百 MB，Java 网关几 GB**；数万实例下资源成本差一个数量级 |
| 3 | **深度定制** | 全链路灰度（跨服务标签传递）、单元化/多活、内部 RPC 协议转换、风控/WAF 集成 |
| 4 | **生态绑定** | 内部的服务发现/配置中心/发布系统/监控都是自研的 → 网关必须深度集成 |

## 3. 生产级网关的能力清单（功能维度，8 类）

### ① 路由（核心）
- 多维匹配：path / header / query / method / host / cookie / **权重**
- **动态路由**（热更新、不重启）
- 路由版本化 / 灰度 / 回滚
- 优先级与冲突处理

### ② 流量治理
- **限流**：多维度（IP / 用户 / 接口 / 全局）、单机 / **集群**
- **熔断**（断路器三态）
- **降级**（fallback）
- **重试**（幂等 + backoff + jitter）
- **超时**（分层：连接 / 响应）
- **负载均衡**（轮询 / 随机 / 权重 / 一致性哈希 / 同 zone）
- 健康检查 / 实例摘除

### ③ 安全
- 认证（JWT / OAuth2 / **mTLS**）
- 授权（RBAC / ABAC）
- 防重放 / 防篡改（HMAC + nonce）
- **WAF / 防刷 / 风控**
- **TLS 终止 / 证书管理 / 双向 TLS**
- 安全头（HSTS / CSP / X-Frame-Options）

### ④ 灰度与多活 ★ 大厂重点
- 灰度：按比例（Weight）/ 按标签（Header / Cookie / 用户）
- **全链路灰度**（标签跨服务传递）★
- 蓝绿 / 金丝雀
- 多活：**zone 路由 / 就近接入 / 故障隔离 / 切流**

### ⑤ 协议
- HTTP/1.1、**HTTP/2**、**HTTP/3（QUIC）**
- WebSocket、SSE
- **gRPC**（HTTP/2 + protobuf）
- **RPC 协议转换**（Dubbo ↔ HTTP）

### ⑥ 可观测
- 指标（**RED**：Rate / Error / Duration）
- 链路追踪（traceId 全链路 + span）
- 访问日志（结构化 / 采样）
- 告警

### ⑦ 运维
- 配置动态推送
- 管理 API（路由增删查 + **权限控制**）
- 多实例一致性
- 平滑发布 / 优雅停机

### ⑧ 扩展性
- 插件 / 过滤器机制
- **热插拔**
- 自定义协议 / 自定义 LB

## 4. 性能维度

| 维度 | 生产级目标 |
|---|---|
| **吞吐** | 单机 10 万+ QPS（Go/C 可达百万） |
| **延迟** | 网关**自身开销 < 1ms**（P99） |
| **资源** | 内存占用小、**无 GC 停顿** |
| **连接** | 连接池 / 长连接复用 / 零拷贝 |

## 5. SCG 在其中的位置（能力对照）

| 能力 | SCG | 差距 |
|---|---|---|
| 路由（多维/动态） | ✅ | — |
| 限流 | ✅ 基础 | 热点参数/集群弱 |
| 熔断 / 重试 / 超时 | ✅ | — |
| 负载均衡 | ✅（SCLB） | 策略有限，要自研 |
| **认证** | ❌ **不内置** | **要自研**（L32/L39） |
| 安全头 | ✅ | — |
| 灰度（比例） | ✅ Weight | — |
| **全链路灰度** | ❌ | **要自研** ★ |
| **多活 / 单元化** | ⚠️ | **要自研**（zone 路由） |
| HTTP/1.1、HTTP/2、WS、SSE | ✅ | — |
| gRPC | ⚠️ 有限 | 要自研 / 换网关 |
| 可观测 | ✅ 好 | — |
| **性能** | 中（Java + GC） | 不如 Go/C |
| **生态 / 开发效率** | ✅ **最好** | — |

## 6. 什么时候该自研 / 不该自研

| 不该自研 | 该自研（或换 Nginx/APISIX） |
|---|---|
| QPS < 几万 | **百万级 QPS** |
| 标准 HTTP 场景 | 需要**全链路灰度 / 单元化** |
| 团队没有基础设施组 | 自研协议 |
| （自研 = 长期维护 + 招人成本） | 成本敏感（大规模） |

**常见折中架构**（很多公司这么干）：

```
CDN/SLB → Nginx（接入层：TLS终止/静态/粗限流）
        → SCG（业务网关：鉴权/路由/灰度）
        → 微服务
```

## 7. Gateway × Sentinel：功能重叠怎么选

### 7.1 功能对照

| 能力 | Gateway 自带 | Sentinel | 关系 |
|---|---|---|---|
| 路由 | ✅ 核心 | ❌ | Gateway 独有 |
| 负载均衡 | ✅（SCLB `lb://`） | ❌ | Gateway 用 SCLB |
| 限流 | ✅ `RequestRateLimiter`（Redis 令牌桶） | ✅ 更强 | **重叠** |
| 熔断 | ✅ `CircuitBreaker`（Resilience4j） | ✅ | **重叠** |
| 降级 | ⚠️ 靠熔断 fallback | ✅ fallback/blockHandler | **重叠** |
| 系统保护（LOAD/RT/线程数） | ❌ | ✅ `SystemRule` | **Sentinel 独有** |
| 热点参数限流 | ❌ | ✅ `ParamFlowRule` | **Sentinel 独有** |
| 集群流控 | ⚠️ 有限 | ✅ Token Server | Sentinel 更强 |

### 7.2 为什么重叠 —— 层次不同

| | Gateway 自带 | Sentinel |
|---|---|---|
| 定位 | **网关本地能力** | **服务治理平台** |
| 依赖 | 无额外（除 Redis） | 需要 Dashboard + 规则中心 |
| 粒度 | 路由级 | 接口级 / 参数级 / 服务级 |
| 跨服务统一 | ❌ | ✅ |

### 7.3 选型判断

| 场景 | 选什么 | 理由 |
|---|---|---|
| 只有网关要限流，规则简单 | **Gateway 自带** | 少一个依赖 + 少一套规则中心 |
| **已有 Sentinel 治理体系** | **Sentinel**（`sentinel-spring-cloud-gateway-adapter`） | 统一规则中心/控制台 |
| 需要热点参数 / 系统保护 / 集群流控 | **Sentinel** | Gateway 自带做不到 |
| 网关和服务要**统一阈值** | **Sentinel** | 一套规则管到底 |

> **关键：两者不冲突，可共存，但生产通常选一个**（避免两套规则、两套阈值打架）。

### 7.4 分层限流的正确姿势（架构面试点）

```
客户端 → [网关限流] → [服务A限流] → [服务B限流]
          入口层            精细层
       保护整个系统      保护单个服务（DB连接池等）
```

**两层都要** —— 网关限流防 DDoS/全局过载；服务限流保护自身资源。

## 8. 面试答法（30 秒）

> "生产级网关的能力分四层：**路由 / 流量治理 / 安全 / 可观测**，再往上还有**灰度与多活**。
> Spring Cloud Gateway 覆盖了大部分，差距主要三点：
> ① **极端性能**（Java + GC vs Go/C）；
> ② **深度定制** —— 全链路灰度、单元化路由，SCG 只给了 Weight 比例灰度，这些要自研；
> ③ **超大规模** —— 数万实例下 Java 网关的内存成本很显著。
> 大厂自研主要是**规模和成本**驱动。我们项目用 SCG，是因为 QPS 在它的舒适区、Java 生态开发效率高；但**灰度/多活我们做了自研**，因为 SCG 原生只支持比例灰度。"
