## 40.1 先看反例：把网关当"万能中间层"会怎样

一个典型反例（不少项目真的这么长出来的）：

```
网关里塞了：
  ① 风控规则（判断这笔下单要不要拦截——业务逻辑）
  ② XSS 过滤（扫描/转义请求体里的 <script>）
  ③ 响应聚合（调 3 个服务拼一个首页接口——BFF 逻辑）
  ④ 大文件上传的校验（读完整 body 算签名/查内容）
  ⑤ 分布式事务编排（下单在网关里按顺序调库存→支付→订单）
  ⑥ 全量请求响应日志（带 body 落库）
```

六条对应的六个后果（都有我们前几课实测的影子）：

| 塞进去的东西 | 后果 |
|---|---|
| 业务逻辑（风控） | 业务变更要**改网关发版**；网关从"通用组件"退化成"业务系统" |
| XSS 过滤 | 要**缓存完整请求体**（L28/L38：body 一碰就全量缓冲）；大 body 爆内存；合法内容含 `<script>` 被误杀 |
| 响应聚合（BFF） | 网关承担业务编排，**多团队改一个网关**；聚合超时/降级语义复杂化 |
| 大文件校验 | 流式被破坏、内存放大；上传应走对象存储/CDN |
| 事务编排 | 网关需要业务状态（**变成有状态**）→ 无法随意扩缩/重启；本质上造了个"分布式单体" |
| 全量日志 | 网关内存/IO 被日志拖垮；日志应采样/异步，审计事件在服务内 |

**判据**（本课的总原则）：网关应该是 **无状态、快进快出、通用** 的一层。
- **无状态**：实例可随意扩缩/重启，不承载业务状态；
- **快进快出**：单个请求占用的资源有界（时间、内存），不排长队；
- **通用**：换业务不用改网关。

凡是违背这三条的（需要业务上下文、长期占用资源、改变请求语义），都该往服务内放。

## 40.2 选型：五个候选，怎么选（本课 🔴①）

### 候选对比

| | **Spring Cloud Gateway** | **Nginx（+OpenResty）** | **APISIX / Kong** | **Envoy / Istio** | **云厂商 API 网关** |
|---|---|---|---|---|---|
| 定位 | Java 业务网关 | 接入层/反向代理（C） | 专业 API 网关（OpenResty/Lua） | 服务网格数据面（C++） | 托管网关 |
| 技术栈 | JVM / WebFlux | C / Lua | Nginx + Lua + etcd（APISIX）/ PG（Kong） | C++ / xDS | 云服务 |
| 性能 | 中（JVM+GC） | **高** | 高 | **高** | 看厂商 |
| 动态配置 | Actuator / 注册中心 / 配置中心 | 原生弱（reload）；OpenResty 可做 | **强**（etcd/控制面，热更新） | **强**（xDS 热更新） | 强 |
| 扩展方式 | Java 过滤器/GlobalFilter/Java DSL | C 模块 / Lua | **插件生态**（限流/认证/日志/WASM） | Filter / Lua / WASM | 厂商插件 |
| 生态 | **Spring Cloud 全家桶** | 最广（事实标准） | 中 / 国内活跃（Apache） | K8s/Service Mesh 标准 | 云内 |
| 适合 | Java 团队、业务网关、要写自定义逻辑 | 统一入口、TLS 终止、静态/粗粒度、极致性能 | 中大型 API 管理、要控制台/插件、多语言团队 | K8s/多云、东西向治理、非 Java 栈 | 不想运维 |

（"性能/生态"列是业界共识口径；具体压测数字随版本/配置变化，面试别背死数字，说"量级与取舍"。）

### 决策清单（按优先级）

1. **团队栈**：Java + Spring Cloud → SCG 的开发效率无可替代；Go/C 团队 → Envoy/APISIX 更自然；
2. **规模与性能**：单体几万 QPS 以内，SCG 舒适；**十万级以上/成本敏感**要考虑 C/Go 系（Nginx/APISIX/Envoy）；
3. **是否要控制台/动态治理**：要运营化（路由管理、插件、配额后台）→ APISIX/Kong/云网关；纯代码配置 → SCG/Nginx；
4. **是否 K8s / Service Mesh**：东西向流量治理交给 Envoy/Istio，网关只做南北向；
5. **要不要写"重逻辑"**：要在网关做业务定制（灰度标签、协议转换）→ SCG（Java 生态）或 APISIX（插件）；
6. **运维成本**：自研/开源都意味着长期维护（见素材文档"该不该自研"）。

### 常见组合（比"单选"更常见）

```
① 经典两层：
   CDN/SLB → Nginx（TLS 终止 / 静态 / 粗限流）
           → SCG（认证 / 路由 / 灰度 / 细治理）
           → 微服务

② K8s 场景：
   Ingress（Nginx/Envoy） → 服务（治理下沉 Service Mesh/服务内）

③ API 管理场景：
   APISIX/Kong（控制台 + 插件） → 微服务（SCG 可省）
```

**一句话选型口径**：**没有"最好的网关"，只有"和团队/规模/场景匹配的网关"**；大厂自研是规模/成本驱动（素材文档有 4 个原因），不是开源不行。

## 40.3 边界：什么不该放网关（本课 🔴②）

### ① 业务逻辑（风控/订单校验/业务规则）

网关应该"通用"：风控规则、订单状态校验这类**需要业务上下文**的逻辑，放服务内（或独立的风控服务）。
放网关的代价：业务迭代绑定网关发版；多团队共用一个网关，发布排队；网关测不了业务回归。

### ② XSS 过滤 —— 明确不该（v5 重点，3 个理由）

| # | 理由 | 展开 |
|---|---|---|
| 1 | **转义是渲染层的事** | 后端返回 JSON、不渲染 HTML；真正的 XSS 防线在**输出时的上下文转义**（前端框架默认转义）与 CSP；网关全局"洗"一遍既不知道上下文，也不该承担 |
| 2 | **要在网关缓存完整请求体** | 扫描/转义必须读完整 body → 破坏流式（L28：body 一旦被读就要缓存重放；L38：`ModifyRequestBody` 全量缓冲），大 body 直接爆内存 |
| 3 | **误杀** | 合法内容里出现 `<script>` 字样（代码分享、富文本、日志回显）会被拦——**在网关做内容判断，误伤面不可控** |

**面试口径**：能答"**为什么不该在网关做 XSS 过滤**"，比"怎么写 `XssFilter`"值钱得多。

### ③ 大文件传输 / 流式场景

- **纯转发是流式的**（SCG/Netty 默认不落盘、不聚合）；
- 但**只要挂 body 类过滤器**（`ModifyRequestBody/ResponseBody`、`LocalResponseCache`、带 body 缓存的 `Retry`、XSS 过滤），就退化成**全量缓冲**——大文件不能这么过；
- 正确做法：大文件走**对象存储/CDN 直传**（前端拿签名直传 OSS），网关只处理元数据接口。

### ④ 长事务 / 跨服务编排

网关做"下单 → 扣库存 → 支付"的顺序编排，等于把业务状态塞进网关：
- 网关变成**有状态**的（要记录/补偿/重试）→ 不能随意扩缩、重启要小心；
- 事务一致性、补偿逻辑、幂等——这些是**服务编排层/BFF/工作流引擎**的活；
- 结论：**网关做单跳转发，不做多跳编排**。

### ⑤ 细粒度鉴权（L39 结论）

认证（你是谁）统一放网关；**粗粒度授权**（路径/角色）可放网关；**"这笔订单是不是你的"必须放服务内**。

### ⑥ 响应聚合 / 数据脱敏？（灰色地带，谨慎）

- 聚合（BFF）：如果只是"网关顺手拼两个接口"，会慢慢长成业务编排（见④）；要做就明确它是**独立 BFF 层**，不是网关过滤器；
- 脱敏：字段级脱敏需要理解数据结构与业务（哪些字段敏感），放服务内更安全；网关层适合做**通用**的（如统一抹掉某响应头）。

### 边界速查表

| 能力 | 放网关？ | 原因 |
|---|---|---|
| 路由 / 限流 / 熔断 / 超时 / 重试 | ✅ | 无状态、通用、快进快出 |
| 认证 / 粗粒度授权 / 安全头 / TLS | ✅ | 边缘统一 |
| 灰度（比例/标签） | ✅（全链路灰度需自研/服务配合） | 入口分流 |
| 访问日志（采样） | ✅ | 通用 |
| **XSS 过滤** | ❌ | 渲染层的事 + 缓存 body + 误杀 |
| 业务规则（风控/校验） | ❌ | 需要业务上下文 |
| 大文件/流式 body 加工 | ❌ | 全量缓冲 |
| 长事务编排 | ❌ | 有状态 = 分布式单体 |
| 细粒度业务鉴权 | ❌ | 业务语义在服务内 |
| 业务级数据聚合/脱敏 | ⚠️ 谨慎 | 需要就独立成 BFF 层 |

## 40.4 职责划分：一张表汇总 L36–L39（本课 🔴③）

| 能力 | 边缘（CDN/Nginx） | 网关（SCG） | 服务内 |
|---|---|---|---|
| TLS 终止 | ✅（常见） | ✅ | ✅（零信任时） |
| 认证 | ❌ | ✅ **统一入口认证** | 服务间 mTLS |
| 粗粒度授权 | ❌ | ✅（路径/角色） | — |
| 细粒度鉴权 | ❌ | ❌ | ✅ |
| 限流 | 粗（IP/连接数） | 中（路由/用户/接口） | 细（资源/DB 连接池） |
| 熔断 | 实例级剔除（Envoy outlier） | 粗（路由级，本地状态） | 细（依赖级 + 业务降级） |
| 重试 | ❌（别在多层重试） | ✅（幂等白名单） | ✅（业务幂等兜底） |
| 响应缓存 | ✅ 静态/CDN | ⚠️ 谨慎（L38：本地、无失效） | ✅ 业务数据（Redis） |
| 灰度 | 静态/地域 | ✅ 比例/标签（入口分流） | 业务灰度（逻辑） |
| 日志/追踪 | 访问日志 | 入口 traceId 注入、访问日志 | 业务日志、审计事件 |
| 业务逻辑 | ❌ | ❌ | ✅ |

**读表口诀**：**边缘管"接入与静态"、网关管"通用治理与统一入口"、服务管"业务语义"**。
同一能力可以放多层，但要明确**主职责层**（例如限流：网关是入口配额，服务内是资源保护——两层配合，不是二选一）。

## 40.5 面试话术（两个 30 秒）

**选型**：

> "选型看四个维度：**团队栈、规模、动态治理需求、是否 K8s**。
> 我们是 Java 团队、QPS 在几万以内、要在网关写自定义逻辑 → Spring Cloud Gateway 是最优解（Spring 生态开发效率最高）；
> 如果到了十万级 QPS 或成本敏感，会考虑把接入层换成 Nginx/APISIX 做 TLS 与粗粒度治理，SCG 只留业务网关；
> 如果上 K8s + Service Mesh，东西向交给 Envoy，网关只做南北向。"

**边界**：

> "网关应该保持**无状态、快进快出、通用**。
> 所以业务逻辑、长事务编排、大文件处理都不放网关；
> 特别是 **XSS 过滤**——转义是渲染层的事，网关做要缓存完整 body（破坏流式），还会误杀含 `<script>` 字样的合法内容，我们不做。"
