# Rate Limiting（限流）专题 — 概念、算法、分布式与架构

> 定位：**限流是通用工程概念，不属于任何单一框架。** 本专题把它作为一个技术领域讲透。
> 与课程的关系：**Gateway 的实现**（Redis+Lua 令牌桶 / `KeyResolver` / fail-open / 两组实测）见 **L36**；本专题回答"为什么 / 怎么选 / 放在哪 / 阈值怎么定"。
> 证据口径：算法与业界实现（SCG / Guava / Sentinel）均来自**本地源码实证**（源码树或 sources jar）；Nginx/Envoy 等无法本地验证的标注"文档口径"。凡未验证的都不写成断言。

**本专题回答五个问题**：
① 限流在保护谁？（§1）
② 它和熔断/降级/并发限制有什么区别？（§2）
③ 算法有哪些、怎么选？（§3）
④ 多实例下计数怎么共享？（§4）
⑤ 放哪一层、阈值怎么定、被限之后怎么办？（§5~§7）

## 1 限流的保护对象 —— 一个具体场景

秒杀接口：后端容量 **200 QPS**，平时 50 QPS，开抢瞬间 **2000 QPS**。

不限流时的典型故障传播路径：

```
2000 QPS 涌入
  → 线程池/连接池打满 → 请求开始排队
  → 排队时间 > 客户端超时 → 客户端重试（流量再翻倍）
  → 排队更长 → …… → 级联故障（cascading failure：无关服务一并不可用）
```

加上限流之后：超过 200 的部分**快速失败（429）**，后端在容量内稳定服务。

**所以限流保护的是三层对象**：

1. **自己**（入口/网关）：在突发流量下保持可用
2. **下游**（服务 / DB / 第三方）：请求量不超过其容量上限
3. **公平性**：多租户 / 多客户端之间的配额公平

一句话：**限流通过拒绝==超出配额==的请求，保障系统在过载条件下持续可用** —— 它属于**过载保护（overload protection）**机制（同族还有排队、降级、熔断）。

## 2 概念辨析：限流与相邻的防护机制

以下五个机制同属**过载与故障防护**，但**控制对象、判据、执行时机**各不相同。统一场景：**网关 → 下游服务**（线程池 100、平均处理时延 0.5s、吞吐容量 200 QPS）。

| 机制       | 英文                             | 控制对象             | 判据                          | 执行时机                                    | 本场景中的行为                                  |
| -------- | ------------------------------ | ---------------- | --------------------------- | --------------------------------------- | ---------------------------------------- |
| **限流**   | Rate Limiting                  | 单位时间的**到达速率** λ  | 不依赖请求内容与下游状态                | **准入控制**（admission control）：请求进入处理流程前执行 | 超过 200 QPS 的部分返回 429 或进入等待队列             |
| **并发限制** | Concurrency Limiting（Bulkhead） | 某一时刻的**在途请求数** L | 与 λ 联动（L = λW）              | 准入控制                                    | 在途数达到线程池容量 100 后，新请求排队或拒绝                |
| **熔断**   | Circuit Breaker                | 对**单个下游依赖**的调用行为 | 下游**错误率 / 响应时间**超过阈值        | **故障隔离**（fault isolation）：由已发生的失败触发     | 进入 OPEN 状态后对该依赖直接返回失败（fallback），不再发起实际调用 |
| **降级**   | Fallback / Degradation         | 被拒请求的**响应内容**    | 不实施控制                       | 控制动作之后的响应策略                             | 返回缓存数据、默认值或预设错误，而非透传失败                   |
| **背压**   | Backpressure                   | 响应式流的**数据生产速率**  | 下游订阅者的处理能力（`request(n)` 协议） | 传输层机制，由消费端驱动                            | 框架自动执行，不作为业务配置项                          |

术语级区分：
- **限流与熔断**：限流以**到达速率 λ** 为判据、属准入控制，在流量正常时同样生效；熔断以**错误率/时延**为判据、属故障隔离，仅在下游失效后切换状态。二者互不替代。
- **限流与并发限制**：分别约束 λ 与 L，换算关系由 Little's Law 给出（下文）；Sentinel 中 `FLOW_GRADE_QPS` 对应限流、`FLOW_GRADE_THREAD` 对应并发限制（见 §8）。
- **降级不实施控制**：它是限流/熔断/错误路径的响应策略。
- **背压是流控协议**，由响应式框架执行，不是网关配置项。

### Little's Law：并发、速率与时延的恒等关系

```
并发数 L = 到达速率 λ × 平均处理时间 W
```

系统处于稳态时该式恒成立（排队论守恒律；与"路程 = 速度 × 时间"同构）。

**代入场景**（线程池容量 100）：

- 稳态：`200 QPS × 0.5s = 100 并发`，恰为线程池容量
- 处理时延由 0.5s 恶化至 5s：`200 QPS × 5s = 1000 并发`，为容量的 10 倍

即**到达速率不变时，并发随处理时延线性增长** —— 仅约束 λ 无法保证 L 不超过容量。

**三者必须联合配置**，每项约束一个变量：

| 配置 | 约束变量 | 单独缺失的后果 |
|---|---|---|
| 限流 | λ 的上限 | λ 无约束 |
| 超时 | W 的上限 | W 恶化 → L 持续增长，限流失效 |
| 并发上限 | L 的上限（硬约束） | λ 或 W 任一失控时无最终保护 |

这是"治理四件套"（超时 / 重试 / 熔断 / 限流）的推导基础；各机制的配合见 L37。

## 3 算法谱系：每个算法都在修上一个的 bug

所有限流算法其实都在回答**两个问题**：

1. 长期平均速率允许多少？（稳定值）
2. 允不允许突发？（尖峰）

——算法的差别，本质是这两个问题答案不同。

> **精确化注记**：上面两句方向正确，但粒度不足。"允不允许突发"装不下突发配额（**多大**、**多久**），且丢了一整维——**准入动作**（超限后是拒绝还是排队等待）。完整判断分两层：

**L1 合约层**（算法向调用方承诺的三件事）：

| 合约要素 | 含义 | 各算法的值（实际情况） |
|---|---|---|
| 长期平均速率 λ̄ | 每秒允许通过多少 | 固定窗口：N/T；令牌桶：rate；漏桶：流出速率；GCRA：1/单位间隔 |
| 短时突发（**多大**） | 瞬时最多放过去多少 | 令牌桶：≤ capacity；固定窗口：最多 ~2N（边界突刺）；漏桶排队版：≤ 队列长度 |
| 短时突发（**多久**） | 吸收多长时间的尖峰 | 令牌桶：回满耗时 = capacity/rate（如 100/s+300 → 平时100/s，瞬时300，3秒回满） |

（突发配额的实测例：SCG Lua rate=2/cap=2 时第3发被拒、1秒后回满，见 L36 §36.3。）

**L2 实现与行为层**：

| 实现要素 | 选项 | 例子 |
|---|---|---|
| 时间模型/状态 | 窗口计数 / 全时间戳 / 双变量(tokens,ts) / 单 TAT | 内存 O(1)（桶/GCRA）→ O(n)（滑动日志） |
| 准入动作 | **拒绝** vs **排队等待** | Guava `acquire()` **等待** enforced（返回休眠秒数；`tryAcquire` 才拒绝）vs SCG 返回 429；Sentinel `ThrottlingController` **匀速排队**（前身 `RateLimitController`，参数为 `queueingTimeoutMs + maxCountPerStat`） |
| 公平与分布式协调 | KV 划分 / 原子脚本 / 批量预领 / 本地汇总 | 属跨算法工程维度，见 §4 |

说明：同一族算法可以换准入动作——Guava 的令牌桶用**等待**，SCG 的令牌桶用**拒绝**。所以"拒绝还是排队"是独立于算法家族的维度；"公平与分布式协调"则不区分算法，归入 §4。

### 3.1 固定窗口计数（Fixed Window）

每 1 秒一个窗口计数，超 N 拒绝，窗口结束清零。

- ✅ 实现最简（Redis `INCR` + `EXPIRE`）
- ❌ **边界突刺**：限 100/s，第 1 秒最后 10ms 打 100 发、第 2 秒头 10ms 再打 100 发 → **10ms 内实际过了 200 发**

### 3.2 滑动窗口日志（Sliding Window Log）—— 精确，内存开销 O(n)

记录每个请求的时间戳，统计"过去 1s"的请求数。

- ✅ 精确
- ❌ 内存 **O(请求数)**，高 QPS 下昂贵

### 3.3 滑动窗口计数（Sliding Window Counter）—— 工程常用

把 1s 切成 N 个格子（如 10 × 100ms），用"当前格子 + 前一个格子按权重"估算窗口值。

- ✅ 平滑、内存 O(格子数)
- ⚠️ 近似（误差 ≤ 1 格，工程可接受）；Sentinel 的指标统计就是滑动窗口

### 推导：从固定窗口到分桶计数（含均匀假设的误差分析）

**第一步：为什么不能只记一个数。** 固定窗口每 1 秒一个计数器（`[1s,2s): count=a`、`[2s,3s): count=b`）。在 T=2.5s 要回答"[1.5s, 2.5s] 内多少请求"时给不出答案——固定窗口只认识整秒窗口，不认识滑动窗口。

**第二步：切格子。** 把 1s 切成小格（如 100ms），每格一个计数器。T=2.5s 时 `[1.5s, 2.5s]` 恰好是 10 个整格 → 直接求和，结果精确。

**第三步：边界不对齐怎么办。** T=2.53s 时窗口为 `[1.53s, 2.53s]`，覆盖三部分：

- 完整格 `[1.6, 2.5)`（9 个）：直接求和，精确；
- 正在填充的格 `[2.5, 2.53)`：取"已过部分"，精确（它已发生的就是窗口要的全部）；
- **只有头部部分格 `[1.53, 1.6)` 需要估计**：假设格内请求均匀分布，按重叠比例折算——
  `[1.5,1.6)` 格计数为 A，则 `[1.53,1.6)` ≈ (1.6−1.53)/(1.6−1.5) × A。

完整公式：`estimate = Σ完整格 + 头部格 × (格尾 − 窗口起点) / 格长`。

**第四步：代价分析。** 内存从 O(请求数) 降到 O(格子数)；偏差上界为一格的量。更细的格子永远到不了精确（头部永远有一格不对齐），代价是查询求和开销线性增长——Sentinel 默认 1 秒只切 2 格即此取舍。

> 注：Kafka 的多层时间轮是"多层时间粒度"思想在**调度领域**的对应物（解决"X 毫秒后触发"）；限流领域一般用固定格数而非多层轮。

### 3.4 令牌桶（Token Bucket）—— 允许突发（burst-tolerant）

桶容量 `capacity`；按 `rate` 加令牌；请求取 `requestedTokens` 颗，取到才放行。

```
每次请求到达：
  tokens = min(capacity, tokens + (now - last) * rate)   // 按时间补足令牌
  if tokens >= requested: tokens -= requested; 放行
  else: 拒绝
```

- ✅ **长期平均 = rate，瞬时突发 ≤ capacity**
- 参数分工：**`rate` 管长期、`capacity` 管突发**（capacity=1 → 严格匀速；capacity 增大 → 允许更大的突发流量）
- SCG 的 `RedisRateLimiter` 就是其 Redis 实现（Lua 脚本原子执行）（L36 §36.3 有逐行 + 实测）

**突发设计的三层优势**（为什么是"允许突发"而非"匀速"）：

1. **对内平滑、对外宽容**：稳态吞吐 = `rate`（下游看到的长期压力可控）；瞬时上界 = `capacity`（客户端/上游的突发被吸收，不因"非匀速到达"被误限）
2. **突发窗口可量化**：一次可透支 `capacity` 个令牌，回满耗时 `capacity / rate` 秒（rate=100/s、capacity=300 → 平时 100/s，瞬时可发 300，3 秒回满）——"允许突发多久"直接换算成参数
3. **对比固定窗口无边界突刺**：突发受 `capacity` 截断；固定窗口在清零瞬间可双倍放行（§3.1 的问题）
4. **对比漏桶保留了客户端体验**：漏桶强制匀速（整形），令牌桶允许"攒着突发"——面向客户端突发的场景（搜索、页面加载）优于匀速方案

### 3.5 漏桶（Leaky Bucket）—— 恒定输出速率

请求先入队，以**固定速率**流出；队满则拒。

- ✅ 输出绝对平稳（**shaping**）——适合"保护下游"；Nginx `limit_req` 是这个口径（文档口径）
- ⚠️ 概念澄清：漏桶有"整形"（排队，延迟换平稳）与"整速"（超速即拒）两种用法；Nginx 的 `burst + nodelay` 就在这两者之间调（`burst` 概念上与令牌桶的 capacity 异曲同工）

### 3.6 GCRA（Generic Cell Rate Algorithm）

令牌桶的**等价数学形式**：不存"令牌数"，只存一个"理论到达时间（TAT）"，每次请求推进它。

- ✅ 省内存（一个数）、天然好原子化；Redis Cell 模块 `CL.THROTTLE` 用它（README 自述 "fairly sophisticated GCRA"）
- 面试点：**令牌桶 / GCRA / 漏桶 是同一族的三种表达**

### 3.7 怎么选

| 算法 | 允许突发 | 平滑度 | 精度 | 内存 | 典型实现 |
|---|---|---|---|---|---|
| 固定窗口 | 边界突刺 | 差 | 有边界误差 | O(1) | Redis INCR |
| 滑动窗口日志 | 看窗口 | 好 | 精确 | O(n) | 自研 |
| 滑动窗口计数 | 平滑 | 好 | 近似 | O(格子) | Sentinel 指标 |
| **令牌桶** | ✅ 可控 | 一般 | 精确 | O(1) | Guava / SCG |
| **漏桶** | ❌（排队） | 最好 | 精确 | O(队列) | Nginx limit_req |
| **GCRA** | ✅ 可控 | 一般 | 精确 | O(1) | Redis Cell |

**一句话选型**：需要允许突发流量（burst）→ 令牌桶/GCRA；需要恒定输出速率 → 漏桶；结构最简 → 固定窗口；精度与复杂度折中 → 滑动窗口计数。

（突发容忍与速率平滑的取舍，分别对应"面向客户端突发"与"面向下游稳定"两种目标。）

### 3.8 两个容易忽略的工程细节

- **requestedTokens / 权重**：一次请求可以"扣多颗"（大响应、按响应大小计费、批量接口）
- **桶的 TTL**：空闲后要能自动清理（SCG 的 Lua：`ttl = capacity/rate × 2`）

## 4 分布式限流：多实例下的计数一致性

### 4.1 为什么本地计数不可行（数量级分析）

10 个实例，每个用本地计数器限 100 QPS → 后端实际能收到 **1000 QPS**。
**阈值被"乘以实例数"**——各实例独立计数，无法感知其他实例已消耗的额度。

### 4.2 四种工程方案

**a) 集中计数（Redis 等）+ 原子操作** —— 主流
- 所有实例对同一个 key 原子增减；SCG/大多数网关：Redis + **Lua**（读-算-写一个脚本，单线程原子）
- 代价：每次判断 +1 次 RT；Redis 成为依赖/单点

**b) 配额分片（本地预领）** —— 性能优化
- 每实例先领一批令牌（如 1000 颗），本地消耗，用完再领
- 牺牲精度（余量不均时可能提前拒绝）换性能（大幅减少远程往返）

**c) 独立 token server / 集群模式**
- Sentinel 集群流控就是"token client ÷ token server"结构，用批量领 token 摊薄 RT（sentinel-core `cluster/client` 目录为证）

**d) 两层防线**
- 网关做分布式限流（全局口径）+ 每个服务做单机限流（资源自保）
- 单机限流器（Guava/Sentinel 单机）**不能替代**分布式限流，但可以做最后一道

### 4.3 原子性从哪来

- "读-改-写"不是原子操作 → 并发下会**超发**
- 解法：**Lua 脚本**（Redis 单线程原子执行）或 **CAS/乐观锁**（失败重试）
- Redis Cluster：同一限流的多个 key 要用 `{hash tag}` 落同一槽位（SCG 的 `{routeId.key}` 即此）

**"进程/线程安全的令牌获取"——四种写法与各自的原子性**（面试高频）：

| 模式 | 适用算法 | 写法 | 原子性保证 | 已知隐患 |
|---|---|---|---|---|
| **INCR** | 固定窗口计数 | `INCR key` → 返回值 > limit 即拒；**只在返回 1 时** `EXPIRE key ttl` | 单命令原子 | INCR 与 EXPIRE 是两条命令：中间进程崩溃 → key 永不过期（用首键设 TTL 或 `SET key 0 EX ttl NX` 预建规避） |
| **SET NX EX** | 名额池 | `SET limit_key 1 NX EX ttl` | 单命令原子 | 只适合"固定名额"，非计数 |
| **ZADD/ZCARD** | 滑动窗口日志 | `ZADD` 时间戳 + `ZREMRANGEBYSCORE` 清理 + `ZCARD` 计数 | 各命令原子；多命令间存在极小竞态窗口 | 高 QPS 下内存与命令数开销大 |
| **Lua 脚本** | **令牌桶 / 滑动窗口计数 / 任意状态机** | 读状态 → 补充 → 扣除 → 写回，**一个脚本** | Redis 单线程执行整脚本 = 原子 | 脚本要短（阻塞单线程）；集群需 hash tag |

结论：**计数器类限流用 INCR（+首键设 TTL）即可；带状态的令牌桶必须 Lua**——INCR 表达不了"按时间补充 + 容量截断 + 令牌扣除"的多字段状态机。多实例并发调用同一 Lua → Redis 单线程排队执行 → **不存在"两个请求同时消耗同一令牌"**。

两个现实问题：
- **主从异步复制**下，故障切换可能丢最近的写 → 极小概率超发（可容忍，或用 `WAIT` 强制同步）
- **集群**：同一限流的多个 key 必须用 `{hash tag}` 落同一槽位（SCG 的 `{routeId.key}` 即此）

**完整调用序列（生产级细节）**：

```bash
# 1) 固定窗口（INCR）——TTL 只由"第一个键"设置
redis> INCR rate:api:172.16.0.1
(integer) 1
redis> EXPIRE rate:api:172.16.0.1 1        # 仅返回 1 时执行：中途崩溃也不会留下永不过期的 key

# 2) 令牌桶（Lua，SCG 的方式）——生产用 EVALSHA 复用脚本缓存
EVALSHA <sha1> 2 request_rate_limiter.{demo.user1}.tokens request_rate_limiter.{demo.user1}.timestamp 2 2 "" 1
# 首次 EVAL 加载 → 之后 EVALSHA；Redis 重启/驱逐 script cache 后返回 NOSCRIPT → 必须能优雅回退为重新 EVAL
```

两条进阶风险（必须知道）：

- **Lua 阻塞**：Redis 单线程执行脚本，慢脚本/大 key 会阻塞所有请求 —— 限流脚本必须短小（读两个 key、做四则运算），禁止 `KEYS`/循环大集合
- **主从与多机房**：异步复制下故障切换可能丢失最近一次令牌扣除 → 极小概率超发（容忍；严格场景 `WAIT 1 0` 等待同步）
- （第五种方案：`WATCH/MULTI` 乐观锁 —— 冲突即重试，高并发下重试风暴，工程上少用）

### 4.4 故障策略：fail-open vs fail-close（必须显式选）

| 策略 | 行为 | 适用 | 风险 |
|---|---|---|---|
| **fail-open** | 存储/限流器故障 → **放行** | 可用性优先（SCG 的选择，源码注释引 Stripe 0.01% 失败率） | 静默失效 —— **必须告警** |
| **fail-close** | 故障 → **拒绝** | 安全/计费优先（金融常见） | 存储短暂不可用即导致全量拒绝 |

（fail-open 静默失效比拒绝更危险——SCG 的源码注释明确要求"set an alert"。）

### 4.5 性能与内存

- 一次判断一次 RT（本地 Redis 通常 <1ms；跨机房链路则显著增大）→ 高 QPS 下集中计数的存储压力大
- 优化：Lua 减往返、批量、GCRA 省内存、本地短 TTL 缓存热点 key 的余量

## 5 放在哪一层：分层防御

```
客户端(库) → CDN/WAF → 网关 → 服务 → DB
              ↑每层限的"东西"和"粒度"都不同
```

- **CDN/WAF**：四/七层攻击（SYN flood、CC）
- **网关**：入口配额（IP / 用户 / 接口 / 全局）—— 统一口径、一处保护全体下游；但**不懂业务语义**、对**内部调用无效**
- **服务**：业务级（用户等级/热点参数）、**内部扇出**、资源自保（DB 连接池）
- **DB**：连接数 / 慢查询

**南北 vs 东西**：网关站在**南北向**（客户端 ↔ 系统）边界；**东西向**（服务 ↔ 服务）是服务网格 sidecar（Envoy 等）的地盘——两者常配合（网关常作为网格的 ingress）。

**"网关 vs 服务"不是二选一**：

- 网关管"入口级、跨服务统一"的量（粗粒度、统一）
- 服务管"业务语义上"的量（细粒度、内部调用）
- 只在网关实施 → 服务间调用不受保护；只在服务实施 → 策略不统一、入口缺少统一防护

### 5.1 三层纵深限流架构（Nginx / 网关 / 业务层）——面试标准答法

**职责分工**：

| 层 | 典型工具 | 限流维度 | 判据 | 计数位置 | 目标 |
|---|---|---|---|---|---|
| **接入层**（Nginx/CDN） | `limit_req` / `limit_conn` | 单 IP / 连接数 | 粗（按来源） | 每机本地（无 Redis） | 挡洪水与攻击，保护网关本身 |
| **网关层**（SCG / Sentinel） | `RequestRateLimiter`（Redis+Lua）/ Sentinel | 接口 / 租户 / 用户 / ApiKey | 细（按业务键） | **集中共享**（Redis）或集群 token | 统一入口配额 + 熔断/灰度联动 |
| **业务接口层**（服务内） | Sentinel 单机 / `@SentinelResource` | 热点参数 / 方法 / 用户等级 | 最细（业务语义） | 单机内存 | 资源自保 + 兜底 |

**协同机制四条**：

1. **判据递进**：IP → 用户 → 接口 → 参数，层层收口（上层拦"谁来"，下层拦"进来之后干什么"）
2. **余量分层**：上层给宽（挡明显洪水）、下层给严（保业务 SLA）——避免同一流量被多层重复拒绝
3. **独立计数、互为冗余**：各层独立判断；任一层失效，下层仍兜底（纵深防御的意义所在）
4. **状态一致性**：网关层的集中计数要选可靠方案（Redis+Lua 或 Sentinel 集群）；规则经配置中心（如 Nacos）统一下发

**面试收尾句**：三层不是"重复做三遍"，而是"**不同判据、不同成本、不同兜底**的纵深"。

**三层各在请求生命周期的哪个阶段拦截**：

```
客户端 ──TCP──► [Nginx: 连接/速率计数（HTTP 头尚未解析，被拒代价最低）]
                  ──HTTP──► [SCG: 解析完成、进入业务前 → 429]
                              ──RPC──► [业务服务: 方法执行前 → 触发降级]
```

**三段真实配置（骨架）**：

```nginx
# 接入层 Nginx —— 每机本地计数，零 Redis
http {
    limit_req_zone  $binary_remote_addr zone=per_ip:10m rate=1000r/s;
    limit_conn_zone $binary_remote_addr zone=conn:10m;
}
server {
    location /api/ {
        limit_req  zone=per_ip burst=500 nodelay;   # 突发 500 直接放行（不排队）
        limit_conn conn 50;
    }
}
```

```yaml
# 网关层 SCG —— 跨实例共享（Redis + Lua 令牌桶）
filters:
  - name: RequestRateLimiter
    args:
      redis-rate-limiter.replenishRate: 2000
      redis-rate-limiter.burstCapacity: 4000
      key-resolver: "#{@tenantKeyResolver}"          # 按租户（自定义 KeyResolver）
```

```json
// 业务层 Sentinel —— 规则托管 Nacos，resource = 按接口
[{ "resource": "order/create", "grade": 1, "count": 500, "strategy": 0, "controlBehavior": 0 }]
// grade: 1=QPS(0=线程数)  strategy: 0=直接拒绝  controlBehavior: 0=快速失败
```

**阈值拆分示例**（总闸 10W 如何分到三层）：

| 层 | 阈值 | 依据 |
|---|---|---|
| Nginx per-IP | 300 r/s + burst 500 | 单客户端异常上界（正常用户 <10 r/s） |
| SCG per-租户 | 2W QPS（总和 ≤ 9.5W） | 租户合同 + 留 5% 透传余量 |
| 业务 per-接口 | 创建订单 500 QPS | 下游容量（DB 写入上限）反推 |

**协同的三个工程难点**（面试可主动讲）：

1. **身份对齐**：接入层只见 IP、网关层才见 uid —— 用户级限流**只能在网关/业务层做**，Nginx 只能做 IP 粗层（这不是分工偏好，是信息位置决定的）
2. **跨层重复计数**：入口放行的请求到服务层又被限一次（两层阈值不同步）→ 需要**内部流量豁免**（网关注入内部调用标识，服务层识别后跳过）或按"外部/内部"分开建资源
3. **重试的跨层放大**：客户端重试 1 次 = 各层都计 2 次 —— 各层**重试预算必须对齐**（网关关闭盲重试，或统一退避策略）

### 5.2 10W QPS 高并发怎么限：先算成本，再选架构

**第一步：算"限流判定本身"的成本**
10W QPS × 每请求 1 次 Redis Lua = **10W ops/s 的限流调用**——本地 Redis 单机虽可达此量级，但与业务共用时延迟抖动、主从复制压力大，且等于把"入口可用性"绑在 Redis 上（必须配合 fail-open 策略）。

**第二步：四层方案（粗维度本地化、细维度集中化）**

1. **接入层**：per-IP `limit_req` / `limit_conn`（每机本地计数、零 Redis 成本）→ 先挡掉攻击与异常流量的大头
2. **网关层·粗维度**：按 IP/接口的限流用**每实例本地计数**（10 实例 × 1W = 10W，无共享状态）→ 覆盖绝大部分流量判定，**0 次 Redis**
3. **网关层·细维度**：按用户/租户才走 Redis，配合**配额分片**——每实例每秒预领 1000 个令牌、本地扣除，Redis 调用从 10W/s 降到**实例数级别**；热点 key 再加本地短 TTL 缓存
4. **业务层**：Sentinel 单机 QPS/并发 + 热点参数兜底；数据层连接池限流

**备选**：Sentinel 集群模式（token client/server 批量领 token，按资源粒度）——治理规则需与熔断统一管理时选用。

**一句话**：**粗维度本地化、细维度集中化、按 key 预领额度、多层纵深**。

## 6 阈值怎么定：从容量测试到自适应

- **压测定容量**：先测单实例极限 QPS（看水位拐点：CPU / RT 突增）→ 取 **70%~80%** 作安全值 → 反推入口配额
- **用 Little's Law 校验并发**：λ × W 不能超过线程池/连接池
- **多租户/大促**：按比例分配（付费等级、业务优先级）
- **自适应限流（思想）**：
  - 观察**拥塞信号**（排队时间 / RT 变化），接近容量时自动收紧——TCP Vegas、Netflix `concurrency-limits`、Sentinel 系统规则都是这个思路
  - 优点：不用拍阈值；缺点：滞后与震荡，需要阻尼设计
  - （实现级细节属独立领域，本专题只建立概念）

**网关自身的容量核算**（限流架构的前提是网关撑得住 10W）：

- 单网关安全 QPS 由压测定（Netty 非阻塞，瓶颈常在 CPU/序列化/下游等待）：如单机 1.5W → 10W 需 ≥7 实例再加冗余
- 到下游的连接数 = 并发在途数（10W × 50ms = **5000**）→ HTTP client 连接池、下游 accept 队列按此配置（与超时联动）

**判定路径的优化顺序**（不是每请求都打 Redis）：

1. 本地粗判（每实例 IP/接口计数）→ 命中即可出结果，**0 次 Redis**
2. 热点 key 本地短 TTL 缓存（如 100ms 内本地扣除）
3. 其余才走 Redis Lua（或配额分片预领）
4. 观测兜底：Redis 调用耗时/失败率打进指标，联动 fail-open 告警

**容灾**：Redis 半数不可用时的策略显式化（fail-open 必须有告警）；多机房就近读写（每机房独立 Redis + 阈值按机房分摊）。

### 6.1 阈值怎么算：以 10W QPS 为例的双向推导

"10W QPS 的限流阈值"不是拍出来的，来自**两个方向的推导取交集**：

**自顶向下（业务推）**：

```
历史峰值 × 增长系数（或大促目标 ÷ 单请求业务价值）
  → 业务峰值 QPS（如 8W）
  → 入口阈值 = 业务峰值 × 1.2（安全系数）
```

**自底向上（容量推）**：

```
单机压测极限 QPS（定位瓶颈：CPU / 连接池 / 下游）
  → 单机安全值 = 极限 × 水位 70%~80%（如 8k × 0.8 = 6.4k）
  → 系统容量 C = 单机安全值 × 实例数（N = 16 → 10.2W）
  → 入口阈值 = C − 内部预留（异步任务/运维流量，如 5%）≈ 9.7W
```

**取交集与修正项**：

- 阈值 = min（业务需要, 系统可承接）—— 缺口靠扩容/降级补齐，不能靠限流硬扛
- **重试放大**：阈值要含重试预算（如 ≤10% → 真实到达 ≈ 设定 × 1.1）
- **预热（warm-up）**：冷启动前 N 秒不按满额（Sentinel `WarmUpController`、Guava `SmoothWarmingUp` 都为此而生）
- **Little's Law 反推容量**：10W QPS × 平均 50ms = **5000 并发** → 线程池/连接池/实例数按此配
- **分层给阈值**：入口总闸 10W → 每接口 2W → 每用户 10/s（防单点），层与层之间留透传余量
- **反馈校准**：以 429 率、P99 时延、错误率闭环调参（→ 自适应限流）

**压测怎么给出"极限与水位"**：

- 阶梯压测（每级持续 ≥60s）：吞吐曲线出现**平台**、P99 时延**拐点突增**处 = 容量拐点
- 水位不是固定 70%~80%：**依赖资源类型**（CPU 密集可取高水位、依赖下游/连接池应取低水位）、是否可预热、下游是否还有余量
- SLA 换算：可用性 99.9% → 每月允许 43 分钟不可用 → 429 拒绝率目标可换算成"每小时允许多少次"
- 分时段/分租户：大促与日常阈值分表下发（Sentinel 按时间线切规则 / 网关侧动态改配置）

**10W 的现实校验**（别只算 QPS，还要反算资源）：

- 下游连接：10W QPS × 平均 50ms 在途 = **5000 并发连接** —— 网关连接池、下游 accept 队列按此配
- 网关实例数 = 10W ÷ 单网关安全 QPS（再加冗余）；GC 与序列化是常见瓶颈

## 7 被限之后：响应策略与客户端配合

- **返回什么**：`429 Too Many Requests` + `Retry-After`（不应返回无 `Retry-After` 的 503，也不应直接断开连接）；带 `X-RateLimit-*` 让客户端自省
- **排队还是失败**：
  - 快速失败：防刷、重试无益（默认建议）
  - 排队/削峰：延迟可容忍且"必须成功"（消息、异步任务）
- **客户端要配合**：指数退避 + **抖动（jitter）**——否则 429 后全体同时重试 → 二次尖峰
- **重试预算（retry budget）**：给重试设上限（如 ≤10% 流量）；否则"重试"本身就是放大器（L37 详）
- **观测三件套**：被限速率、**被限 key TOP**（被限最频繁的键）、**fail-open 次数**（存储故障频率）

## 8 业界实现对照（实证版）

| 实现 | 算法 / 机制 | 形态 | 证据 |
|---|---|---|---|
| **SCG `RedisRateLimiter`** | 令牌桶 + Redis/Lua | 分布式 | 本仓源码 + L36 两组实测 |
| **Guava `RateLimiter`** | `SmoothBursty` = 令牌桶（`maxBurstSeconds=1`，只允许多存 1 秒的量）；`SmoothWarmingUp` = 预热/冷启动 | 单机 | **sources jar 实证**（`RateLimiter.create(...)` 的分支 + `maxPermits = maxBurstSeconds × permitsPerSecond`）|
| **Sentinel** | 四控制器：`DefaultController`（直接拒绝）/ `ThrottlingController`（匀速排队）/ `WarmUpController`（预热）/ `WarmUpRateLimiterController`；维度：`FLOW_GRADE_QPS=1` 或 `FLOW_GRADE_THREAD=0`（**限线程数 = 并发限制**）；另有集群模式 | 单机 + 集群 | **sources jar 实证（1.8.8）** |
| **Nginx** | `limit_req`（漏桶口径，burst+nodelay）/ `limit_conn`（并发） | 单机 | 文档口径（未本地验证）|
| **Redis Cell** | GCRA（`CL.THROTTLE`） | 分布式 | README 自述（"fairly sophisticated GCRA"）|
| **Envoy / Kong / APISIX** | 各自组件（本地/分布式限流） | 边车/网关 | 未验证（需要时再查）|

三个值得记住的对照结论：

1. **Sentinel 的"线程数"模式就是并发限制** —— 同一套规则把 λ 和 L 两个维度都做了（对照 §2 的 Little's Law）
2. **Guava 的 `maxBurstSeconds=1`** —— 默认只存 1 秒余量，防止"长时间空闲攒出一波巨峰"
3. **大家都收敛到同一族算法**（令牌桶 / GCRA / 漏桶），差别在"**单机 vs 分布式、有无控制台/动态规则**"

### 8.1 选型深问：用户/租户级（按 key）限流，为什么用 Redis+Lua 而不是 Sentinel？

这道题的考点是"**维度决定架构**"：

| 维度 | Sentinel | Redis + Lua |
|---|---|---|
| 统计位置 | **进程内**（单机内存）；集群模式经 token server | Redis（集中共享） |
| 控制粒度 | 按**资源（resource）** 的 QPS/线程数；热点参数按预设参数、单机统计 | 任意 **key**（userId/tenant/apiKey…），key 空间大且动态 |
| 跨实例共享 | 单机无共享；集群按资源批量领 token；按"动态用户 key"扩展需自定义 | 天然共享（KV 计数） |
| 规则管理 | 动态规则（Nacos/控制台）、与熔断/热点联动 | 规则在应用内（yml/代码） |
| 典型成本 | SDK/agent + （集群模式）独立部署 | 一次 Lua 调用（本地 <1ms） |

**结论**：

- **接口/资源级**（维度少、要求动态规则、要与熔断/热点联动）→ **Sentinel**
- **用户/租户级配额**（key 空间巨大、跨实例必须共享）→ **Redis + Lua**（或等价的集中计数）
- 二者**常并存分层**：Sentinel 管"接口 QPS + 熔断"，Redis+Lua 管"租户/用户配额"
- 补充：SCG 原生 `RequestRateLimiter` + 自定义 `KeyResolver` 就是"按 key 的 Redis+Lua"实现（L36 实测），无需引入 Sentinel

（对照 xhs：已用 Sentinel 做接口级限流、规则托管 Nacos；若要加"用户级配额"，新增一个 `RequestRateLimiter` 过滤器即可，不必引入第二套治理框架。）

**把 Sentinel 的机制看清（才能说清"为什么它不适合用户级"）**：

- **三种流控模式**（`FlowRule.strategy`）：直接（资源自身）/ 关联（限被拖累的资源，如下单时限制查询）/ 链路（按调用链入口）—— 全部**围绕 resource**
- **四种流控效果**（`controlBehavior`）：快速失败 / WarmUp 预热 / 排队（匀速，漏桶语义）/ WarmUp + 排队
- **热点参数限流**：最接近"按 key"，但**参数值需预设/可枚举**（写进规则）、统计在**单机**（跨实例不共享计数）→ **不能**直接当"用户级分布式配额"用
- **集群模式**：token client 向 token server **批量申请**额度（摊薄 RT）；token server 的高可用（半数可用、client 降级策略）需要独立部署与显式配置

→ 用户级限流的三条硬要求：**任意 key、跨实例共享、按 key 独立状态** —— Sentinel 默认都不满足；Redis+Lua 三个 KV 天然满足。

## 9 常见误区（每条都值得背）

1. **限流 ≠ 熔断**（量 vs 错/慢）
2. **阈值凭经验设定**（缺少压测与容量水位依据）
3. **只限入口、不限内部调用**（一次入口请求扇出 10 个 RPC）
4. **不算重试的账**（重试 = 放量；限流阈值要含重试）
5. **单机限流当分布式**（阈值 × 实例数超卖）
6. **不定义失败策略**（存储故障时静默 fail-open 而无告警，危害最大）
7. **忽略 key 的公平性**（NAT、换 IP、爬虫）
8. **无限流观测**（不知道谁在被限、是否误伤）
9. 将限流视为唯一防护手段（慢依赖需超时/熔断配合；容量不足需扩容）

## 10 面试怎么答："你怎么做限流？"

```
① 目标与位置：保护谁（入口/下游/公平）→ 放哪层（网关入口配额 + 服务业务级）
② 维度：全局/租户/用户/接口（key 设计 + 公平性取舍）
③ 算法：令牌桶为主（允许突发），rate/burst 怎么定
④ 分布式：Redis+Lua 原子计数（或配额分片）——讲清"为什么本地不行"
⑤ 失败策略：fail-open/close + 告警
⑥ 配套：429 + Retry-After、退避抖动、观测三件套
```

（④⑤ 是回答深度的区分点。）

### 10.1 "做过限流吗？"——STAR 应答框架与可出示的证据

**结构**（45 秒版）：

1. **场景**：什么业务、峰值多少、为什么需要限流（一句）
2. **目标与阈值**：阈值怎么算出来的（引用 §6.1 的双向推导）
3. **实现**：维度（key）→ 算法与分布式方案（令牌桶 + Redis+Lua / Sentinel）→ 分层（§5.1）
4. **故障与观测**：失败策略（fail-open + 告警）、429 + Retry-After、被限 key TOP 观测
5. **取舍收尾**：为什么选它而不是另一个（§8.1 的 Sentinel vs Redis Lua）

**本课程可直接出示的证据**（"做过"= 能跑给面试官看）：

- Lua 令牌桶实测：rate=2/cap=2 → `2 放行 → 第 3 发拒绝 → 1s 后补充`，桶状态 `tokens/timestamp/ttl=2`（§36.1 实验 A）
- 空 key 坑：`denyEmptyKey` 默认 403 / 关闭后不限流（§36.1 实验 B）
- fail-open 源码（Stripe 注释）+ fail-close 的场景选择
- 项目侧：xhs 网关 Sentinel 接口级限流（规则托管 Nacos）→ 可讲"动态规则 + 演进路径"

**没做过怎么答**：用"原理 → 实验 → 取舍"代替"项目叙事"：先讲清 §6.1（阈值）与 §4（分布式），再给出本仓可复现的实验（命令级），最后讲清选型取舍（§8.1）。
