# 05 故障检测与选主：怎么判断一个节点"挂了"？

> 定位：分布式理论快读第 5 篇（补全篇，面试中频）。**例子先行**：3 节点集群里 B 不响应了。
> 对照：权威大纲 `01-分布式理论/02-system-failure-models + 11-leader-election-broadcast`。
> 已学对照：Nacos 集群成员管理（D-13/A-07）、Redis Sentinel（docs/redis 06）——本篇是它们的"为什么"。

---

## 一、它干了什么：一个例子

**场景**：3 节点集群（A/B/C），B 突然"不响应"。A/C 怎么知道 B 是**真的挂了**，还是**只是网络慢/GC 卡顿**？

```
T0:    A 给 B 发心跳探测 → 无响应
T0+2s: 又失败 → A 把 B 标记为 SUSPICIOUS（怀疑，但不确定）
T0+8s: 连续失败次数 > 阈值 → A 把 B 标记为 DOWN → 发布成员变更事件
       → 若 B 是 Leader → 剩余节点发起选主（多数派投票）→ 新 Leader 接管
T0+15s: B 恢复了 → 探活任务发现 B 存活 → 状态回到 UP
```

**它干的事一句话**：用**心跳 + 超时**把"没有响应"翻译成"故障怀疑"，再用**多次确认 + 多数派选举**把怀疑升级为行动——**故障检测器本质上不可靠**（无法区分慢/死/分区），只能做"怀疑"。

---

## 二、为什么需要它：选主/共识的第一步

- 共识协议（Raft/ZAB）都假设"能感知节点状态"——**故障检测是前置基础设施**；
- 检测太敏感 → 误杀健康节点（网络抖动就选主，抖动停不下来）；
- 检测太迟钝 → 故障期间服务不可用时间长；
- 更危险的是**误判引发双主**（分区两侧各自认为对方死了，各选一个主）。

---

## 三、怎么做：心跳、确认、防双主

### 3.1 心跳 + 超时（最常用）

| 设计 | 取舍 |
|---|---|
| 固定超时（如 2s 无响应） | 简单；超时值难定（网络 P99 vs 故障发现速度） |
| 自适应（φ accrual 故障检测器） | 按历史延迟动态算"怀疑度"，Cassandra 采用 |
| 多次确认 | 连续 N 次失败才判死（抗抖动） |

**核心认知**：不存在"准确的故障检测"——异步网络里，"慢"与"死"**不可区分**（这是 FLP 不可能性的直觉来源）。

### 3.2 对接 Nacos：成员状态机（源码级）

```
MemberInfoReportTask（每 2s）：轮询一个其他节点，报告自己的元数据
  成功 → UP（failAccessCnt 重置 0）
  失败 → SUSPICIOUS（failAccessCnt + 1）

MemberUtil.onFail（Nacos 2.3.0）：
  失败次数 > nacos.core.member.fail-access-cnt（默认 3）
  或错误含 "Connection refused" → 直接 DOWN
  → MembersChangeEvent → DistroMapper 重建 healthyList（重新分配负责节点）

UnhealthyMemberInfoReportTask（每 5s）：遍历非 UP 节点主动探活 → 恢复则回 UP
```

（证据：nacos-lab A-07/D-13；`ServerMemberManager` REPORT 2s/探活 5s，`MemberUtil:54` 默认阈值 3）

### 3.3 对接 Redis Sentinel：两级判定

| 级别 | 含义 | 触发 |
|---|---|---|
| **sdown**（主观下线） | 单个 Sentinel 认为主挂了 | 单哨兵 PING 超时 |
| **odown**（客观下线） | 多数 Sentinel 达成一致 | sdown 数量 ≥ quorum |

odown 后：Sentinel 之间**选举领导者**（类似 Raft 投票）→ 执行故障转移（提升从库）。（证据：docs/redis 06）

### 3.4 选主安全：防双主三件套

| 机制 | 作用 |
|---|---|
| **quorum 提交** | 新主必须拿到多数派选票；旧主无法提交（拿不到多数派） |
| **任期（term/epoch）单调** | 每次选举任期 +1；旧主看到更高任期立即退位 |
| **租约/fencing token** | 给"主"发放带期限的授权；过期自动失效；下游用 token 拒绝旧主写入 |

### 3.5 脑裂（split-brain）：分区时谁说了算

```
分区 [A] | [B C]（A 是旧主）
→ B/C 选新主（多数派），继续服务
→ A 无法提交（无多数派）→ 客户端超时（CP：牺牲可用性）
→ 恢复后 A 见到更高任期 → 退位，用新主日志覆盖自己
```

**若不用 quorum**（如 MySQL 双主/某些中间件主从）：两侧都以为自己是主 → **双写冲突**——这就是"脑裂"。

## 四、值不值得深挖 & 面试问答

**值不值得**：故障检测思路 + 防双主三件套必问（🔴）；φ accrual/FLP 证明翻篇（🟢）。

**Q1：怎么判断一个节点挂了？**
心跳 + 超时 + 多次确认（故障怀疑）。注意：异步网络里无法精确区分"慢"与"死"，检测器只能给出怀疑。

**Q2：误判（抖动）怎么防？**
① 连续 N 次失败才升级（Nacos failAccessCnt>3）；② SUSPICIOUS 中间态 + 定期探活恢复（Nacos 5s）；③ 选主需多数派，避免单点误判引发切换。

**Q3：如何防止脑裂/双主？**
quorum 提交（旧主写不进）+ 任期单调（旧主自动退位）+ 租约/fencing（下游拒旧主）。

**Q4：Nacos 的失败检测参数？**
成员报告 2s 一轮、连续失败 >3 次（或连接被拒）→ DOWN、5s 探活恢复；DOWN 触发 `MembersChangeEvent` → Distro 重新分配。

**Q5：Redis Sentinel 的 sdown/odown 区别？**
sdown = 单哨兵主观判定；odown = 达到 quorum 的哨兵一致判定（才允许故障转移）。
