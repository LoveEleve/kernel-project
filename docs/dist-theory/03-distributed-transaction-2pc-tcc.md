# 03 分布式事务：2PC、3PC 与 TCC 如何保证跨服务原子性？

> 定位：分布式理论快读第 3 篇（面试核心）。**例子先行**：下单跨"订单库 + 库存库"的原子扣减。
> 对照：权威大纲 `01-分布式理论/08-2pc-3pc-tcc`。本篇是 **Seata 的前置**（AT/TCC 模式的理论基础）。

---

## 一、它干了什么：一个例子

**场景**：下单 = 订单库 `INSERT order` + 库存库 `UPDATE stock-1`，要求**要么都成功，要么都不做**。

**2PC（两阶段提交）**：

```
阶段1 准备(Prepare): 协调者问各参与者"能提交吗？"
  订单库: 写 redo/undo，锁住订单行 → Yes
  库存库: 写 redo/undo，锁住库存行 → Yes
阶段2 提交(Commit): 全 Yes → 协调者下令 Commit → 各自提交并释放锁
       回滚(Rollback): 任一 No/超时 → 协调者下令 Rollback → 各自回滚
```

**TCC（Try-Confirm-Cancel）**——把"锁"换成"业务预留"：

```
Try:     订单库插入"待确认订单"；库存库 stock-1、frozen+1（预留）
Confirm: 订单确认；冻结库存真扣（都成功）
Cancel:  订单取消；frozen-1 归还（任一失败）
```

**它干的事一句话**：在**没有全局事务管理器**的分布式环境里，用"准备/预留 + 提交/补偿"两阶段，把多个本地事务拼成一个"要么都成、要么都撤"的整体。

---

## 二、为什么需要它：本地事务的边界

- `@Transactional` 只覆盖**一个数据源**；跨服务调用不在同一个事务里；
- 网络超时让状态**未知**（不是成功也不是失败）——必须靠协议来收敛；
- 直接"先扣库存再下单"会因失败留下**悬挂数据**（扣了但没单）。

---

## 三、怎么做：三代方案的取舍

### 3.1 2PC / XA：最直接，但问题最多

| 问题 | 说明 |
|---|---|
| **同步阻塞** | 准备后到提交前，资源一直锁定（库存行被锁）→ 吞吐差 |
| **协调者单点** | 协调者挂了，参与者卡在"准备"状态（阻塞） |
| **数据不一致窗口** | 阶段2 部分参与者收到提交、部分没收到（协调者宕机）→ 需要人工/超时补偿 |
| **实现** | XA 是 2PC 的数据库标准（MySQL XA、JTA） |

**3PC**：在 2PC 前加 `CanCommit`、并把"准备"拆成 PreCommit → 减少阻塞窗口、缓解协调者单点；但**仍不能完全解决分区问题**（面试一句话即可）。

### 3.2 TCC：用业务补偿换性能（面试重点）

| 阶段 | 做什么 | 关键要求 |
|---|---|---|
| **Try** | 业务预留（冻结库存/预扣余额） | 预留量要能取消 |
| **Confirm** | 真正生效（幂等！） | 只做确认，不再做校验 |
| **Cancel** | 释放预留（幂等！） | 必须能处理"Try 没成功也来 Cancel" |

**TCC 三大坑（必问）**：
1. **空回滚**：Try 没执行（超时/未到达），Cancel 先到了 → Cancel 必须能识别"没 Try 过"并安全返回；
2. **悬挂**：Cancel 比 Try 先到（网络乱序）→ Try 到达时发现已 Cancel → 必须拒绝执行；
3. **幂等**：Confirm/Cancel 会被重试 → 用事务控制表（唯一键）防重复。

### 3.3 Seata AT：TCC 的"无侵入版"（预告）

- **AT 模式**：业务只写 `@GlobalTransactional`；Seata 自动生成 **undo log**，一阶段提交本地事务 + 全局锁，二阶段异步回滚（用 undo log 反向补偿）；
- **与 TCC 的关系**：AT 是"自动补偿"，TCC 是"手动补偿"——AT 简单但有全局锁开销，TCC 性能好但要写三套接口；
- **对照 xhs-project**：券/库存走"预扣 + 确认"（本质是 TCC 思路）。

## 四、值不值得深挖 & 面试问答

**值不值得**：2PC 的问题、TCC 三坑必问（🔴）；3PC 一句话；XA 会用（🟡）；Seata AT 留到 Seata 单元深挖。

**Q1：2PC 最大的问题？**
同步阻塞（锁持有到二阶段）+ 协调者单点 + 阶段2 的不一致窗口。

**Q2：TCC 和 2PC 的本质区别？**
2PC 是**资源层锁**（数据库锁），TCC 是**业务层预留**（不锁资源、可取消）——TCC 换来了性能，代价是业务侵入与补偿复杂度。

**Q3：为什么 TCC 的 Confirm/Cancel 必须幂等？**
协调者会重试（超时未知），同一阶段可能执行多次；用事务控制表（xid+分支+状态，唯一键）保证只生效一次。

**Q4：空回滚和悬挂怎么解决？**
空回滚：Cancel 时查事务控制表——无 Try 记录则插入"已回滚"标记并返回；悬挂：Try 执行前查表——已存在回滚标记则拒绝执行。

**Q5：AT 和 TCC 怎么选？**
AT 无侵入、开发快，适合常规 CRUD（接受全局锁）；TCC 适合高并发/需精细控制（如库存预扣），但要写 Try/Confirm/Cancel 三套。
