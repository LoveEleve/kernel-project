# 04 Saga、可靠消息与最大努力通知：不锁资源，如何最终把账对平？

> 定位：分布式理论快读第 4 篇（面试核心）。**例子先行**：下单后"库存→积分→优惠券"三段式流程。
> 对照：权威大纲 `01-分布式理论/09-saga-reliable-message`。本篇是 **Seata Saga / RocketMQ 事务消息**的前置。

---

## 一、它干了什么：一个例子

**场景**：下单成功后要依次：扣库存 → 加积分 → 发券。三步跨三个服务，**不要求瞬时原子**，要求"最终都对"。

**Saga（长事务拆短事务 + 补偿）**：

```
正向: T1 扣库存 → T2 加积分 → T3 发券
失败: T3 失败 → 补偿 C2 扣回积分 → C1 归还库存（反向补偿）
```

**可靠消息（把"调用"换成"消息"）**：

```
订单库: 本地事务【插入订单 + 插入"扣库存"消息】  ← 同一个本地事务（原子）
        → 投递消息到 MQ → 库存服务消费 → 扣减（幂等）
```

**它干的事一句话**：放弃"跨服务瞬时原子"，改写成**可补偿的步骤 + 可靠投递的消息 + 可重试的状态机**——把一致性成本从"阻塞/锁"挪到"补偿/幂等/对账"。

---

## 二、为什么需要它：2PC/TCC 的成本

| 方案 | 痛点 |
|---|---|
| 2PC/XA | 同步阻塞、锁资源、协调者单点 |
| TCC | 业务侵入大（三套接口）、补偿逻辑复杂 |
| **Saga/可靠消息** | 无锁、最终一致；适合长流程/跨公司/高并发 |

**关键取舍**：一致性从"强"降到"最终"——换来性能与解耦，代价是**必须处理幂等与对账**。

---

## 三、怎么做：四种主流落地方式

### 3.1 Saga 的两种模式

| 模式 | 做法 | 优缺点 |
|---|---|---|
| **编排（Orchestration）** | 中心协调器（状态机）驱动各步骤 | 流程清晰、易观测；协调器是核心 |
| **协同（Choreography）** | 各服务监听事件自发推进 | 无中心；流程散落难追踪 |

**补偿语义**：补偿操作必须**幂等**且**可执行**（C1 归还库存时库存可能已被别的单扣掉 → 补偿要能"加回"而不是"恢复原值"）。

### 3.2 可靠消息三方案（面试重点）

| 方案 | 做法 | 一致性 | 适用 |
|---|---|---|---|
| **本地消息表** | 业务库同一事务写"消息表" → 定时任务投递 → 消费方幂等消费 | 最终一致 | 通用、不依赖 MQ 特性 |
| **事务消息**（RocketMQ） | 半消息 → 执行本地事务 → 提交/回查 → 消息可见 | 最终一致 | 已有 RocketMQ |
| **最大努力通知** | 主动重试通知 + 查询接口兜底 | 弱（对账兜底） | 跨公司/第三方（支付回调） |

**对照 xhs-project**：订单用**事务消息**（`OrderTransactionListener` + 回查）、失败重试用 `LocalMessageRetryJob`、券用 **Outbox**（本地消息表思路）。

### 3.3 幂等：最终一致的"安全阀"

| 手段 | 说明 |
|---|---|
| **唯一键** | 业务表加唯一约束（订单号+操作），重复插入直接失败 |
| **去重表** | 消息 ID 记录表，消费前查重 |
| **状态机** | 只允许合法状态迁移（已支付 → 支付成功是幂等空操作） |

### 3.4 对账：最后一道防线

```
T+1 对账 Job: 业务库 vs 支付/库存流水
  发现差异 → 自动补偿（补单/退单）→ 人工兜底
```

**对照 xhs-project**：6 个 Reconcile Job（cart/counter/coupon/inventory/payment/unread）+ 手册口径"8 个对账/修复任务"（库存/券/购物车/未读/关注/消息补发/超时关单/订单映射补录）——**"最终一致"承诺的兑付方式**。

## 四、值不值得深挖 & 面试问答

**值不值得**：Saga vs TCC、可靠消息三方案、幂等必问（🔴）；最大努力通知一句话（🟡）；对账知道定位（🟡，xhs-project 有现成案例）。

**Q1：Saga 和 TCC 怎么选？**
Saga 无预留、靠补偿，适合长流程/低冲突；TCC 有预留、防超卖更强，适合资源竞争激烈（库存/余额）。**都需要幂等补偿**。

**Q2：事务消息的"回查"解决什么？**
本地事务与发消息不能同一事务（MQ 不是数据库）→ 半消息先发，本地事务执行后提交/回滚；若生产者宕机，MQ 回查本地事务状态决定消息可见性——**避免"消息发了但业务没做"或反之**。

**Q3：消费方怎么保证不重复扣库存？**
幂等三件套：唯一键（订单号）/去重表（消息 ID）/状态机；再加对账兜底。

**Q4：为什么说"最终一致 = 对账"？**
因为"最终"没有时间上界；只有对账能发现并修复"永远没收敛"的差异（丢失的消息、补偿失败）。
