# 06 ZooKeeper 与 ZAB：ZK 为什么能当分布式协调器？

> 定位：分布式理论快读第 6 篇（补全篇，面试常客）。**例子先行**：用 ZK 实现"选主/分布式锁"。
> 对照：权威大纲 `01-分布式理论/06-zab-epaxos + 12-case-studies-gfs-zk-spanner`。
> 已学对照：Nacos（AP 注册中心，nacos-lab D-14 有对比）、etcd（Raft）。

---

## 一、它干了什么：一个例子

**场景**：3 个服务实例要选一个"主"（或抢一把分布式锁）。

```
每个实例到 ZK 的 /election 下创建【临时顺序节点】:
   /election/lock-0000000001  ← A
   /election/lock-0000000002  ← B
   /election/lock-0000000003  ← C

规则: 序号最小者获得锁（A 是主）
B 只 watch【前一个节点】(lock-0001)，不 watch 所有节点
A 宕机 → 会话超时 → ZK 自动删除 A 的临时节点 → 通知 B → B 成为最小 → B 上位
```

**它干的事一句话**：ZK 提供一个**强一致的树形小文件系统（znode）+ 会话 + 一次性 watch**——用"临时节点自动清理 + watch 通知"实现选主/锁/配置同步，底层靠 **ZAB 协议**保证所有节点看到同样的写入顺序。

---

## 二、为什么需要它：协调服务的三个刚需

| 刚需 | ZK 的答案 |
|---|---|
| 选主/互斥（谁能当主） | 临时顺序节点 + watch |
| 配置/元数据同步（大家看到同一份） | znode 存储 + watch 变更通知 |
| 成员存活感知 | 会话（Session）——心跳维持，断开即清理临时节点 |

**对比**：Nacos 注册中心选 **AP**（可用性优先）；ZK 选 **CP**（一致性优先，选举期间不可用）——注册中心和协调器对 CAP 的取舍不同。

## 三、怎么做：znode、watch、ZAB

### 3.1 数据模型：znode 四种类型

| 类型 | 特点 | 用途 |
|---|---|---|
| 持久（Persistent） | 会话结束仍存在 | 配置/元数据 |
| 临时（Ephemeral） | **会话结束自动删除** | 存活感知、锁 |
| 顺序（Sequential） | 自动追加单调序号 | 排队、选主 |
| 临时顺序 | 两者结合 | **分布式锁/选主（标准做法）** |

每个 znode 带**版本号**（CAS 语义）：`setData(path, data, version)` 版本不匹配则失败——可实现乐观锁。

### 3.2 会话（Session）与临时节点

```
客户端 connect → 建立会话（sessionTimeout，如 10s）
  会话内: 客户端周期性 PING 续约
  会话过期: ZK 判定客户端"死了" → 删除其所有临时节点 → 触发 watch
```

**这是选主/锁的基石**：进程 crash 后无法续约 → 临时节点被清 → 其他实例自动接管。

### 3.3 watch：一次性通知与羊群效应

- **watch 是一次性的**：触发后需重新注册；
- **羊群效应（herd effect）**：若所有等待者都 watch 同一个节点（或父节点子列表），一次变更会唤醒全部实例 → ZK 瞬间压力大；
- **标准解法**：**只 watch 前一个序号节点**（公平锁），一次变更只唤醒一个。

### 3.4 ZAB：ZK 的原子广播协议

| 阶段 | 做什么 |
|---|---|
| **崩溃恢复（选主）** | Leader 选举：zxid 最大者优先（数据最新）；多数派选主 |
| **原子广播（复制）** | Leader 把写请求作为提案广播 → 多数派 ACK → 提交；Follower 按序应用 |
| **zxid** | 全局单调事务 ID = `epoch(纪元) + counter`；**epoch 单调递增**（防旧主） |

**ZAB vs Raft（面试一句话）**：思想同源（Leader + 多数派日志复制 + epoch/term 防旧主）；差异在细节——ZAB 强调"原子广播 + 恢复模式"，Raft 强调"选举 + 日志匹配性质"；工程上可视为同类（都是 CP 共识协议）。

### 3.5 CP 语义与对比

| 系统 | CAP 选择 | 一致性协议 | 定位 |
|---|---|---|---|
| **ZooKeeper** | CP | ZAB | 分布式协调（选主/锁/配置） |
| **etcd** | CP | Raft | K8s 元数据 KV |
| **Nacos** | AP（临时实例）+ CP（持久实例） | Distro + JRaft | 注册中心 + 配置中心 |
| **Eureka** | AP | 无（对等复制） | 注册中心 |

**ZK 的代价**：选举期间（Leader 挂）**不可用**（写请求阻塞，读可能读到旧数据——除非 sync）；所以注册中心选 Nacos/Eureka 而不是 ZK。

## 四、值不值得深挖 & 面试问答

**值不值得**：ZK 锁/选主实现、ZAB 一句话、CP 代价必问（🔴）；ZAB 协议细节（恢复阶段状态机）翻篇（🟢）。

**Q1：ZK 怎么做分布式锁？**
临时顺序节点 + 序号最小者持锁 + 只 watch 前一个节点（避免羊群）；会话断开自动释放（临时节点删除）。

**Q2：ZK 怎么选主？**
各实例创建临时顺序节点，最小者为主；主挂 → 会话超时 → 节点删除 → 下一个自动上位。（或临时节点 + watch）

**Q3：ZAB 和 Raft 的区别？**
都是 Leader + 多数派日志复制 + 单调纪元防旧主；ZAB 术语是"原子广播/恢复模式"（zxid=epoch+counter），Raft 是"选举/日志匹配"（term+index）——工程等价，面试答"思想同源、术语不同"即可。

**Q4：ZK 是 AP 还是 CP？**
CP：多数派确认才提交；Leader 选举期间写不可用。这也是注册中心普遍不用 ZK 的原因（可用性优先）。

**Q5：watch 为什么要"只 watch 前一个"？**
避免羊群效应：watch 父节点会让一次变更唤醒所有等待者；watch 前一个节点则每次只唤醒一个，形成公平有序的锁队列。

**Q6：ZK vs Nacos vs etcd 怎么选？**
选主/锁/强一致协调 → ZK/etcd；服务注册发现（要 AP）→ Nacos/Eureka；配置中心 → Nacos（配置+注册一体，本项目用）；K8s 生态 → etcd。
