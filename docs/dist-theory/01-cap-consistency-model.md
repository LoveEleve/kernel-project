# 01 CAP 与一致性模型：订单为什么可能扣两次库存？

> 定位：分布式理论快读第 1 篇（面试核心）。**例子先行**：先看一个具体故障，再展开 CAP 与一致性谱系。
> 对照：权威大纲 `01-分布式理论/01-cap-consistency-model`（书线在写正文，本篇为面试速读版）。
> 已学对照：Nacos（AP/CP 双模式）、Redis（主从/哨兵）、Dubbo（注册中心依赖）——本篇是它们的"为什么"。

---

## 一、它干了什么：一个例子

**场景**：下单要扣库存。订单服务和库存服务各连自己的 MySQL。

```
用户点"下单" → 订单服务: INSERT order (本地事务)
             → 库存服务: UPDATE stock = stock - 1 (本地事务)
```

**故障**：库存服务扣减成功，但订单服务提交前宕机 → 用户看到"下单失败"，库存却少了 1。
**或者反过来**：网络分区时两个请求同时读到 `stock=1`，各自扣 1 → **超卖**（扣两次）。

**它干的事一句话**：分布式理论解决的就是这类问题——**一个本地事务无法覆盖多个服务/节点**时，如何在"网络可能分区、节点可能宕机、状态可能不一致"的前提下，重新定义"正确"并给出可实现的方案。

---

## 二、为什么需要它：单机 ACID 为什么不够

单机靠 MySQL 事务（ACID）+ 锁/ MVCC 就能保证正确。跨服务后：

| 单机前提 | 分布式现实 |
|---|---|
| 一个事务管理器 | 每个服务各自的事务，没有全局"提交/回滚"按钮 |
| 网络可靠、调用即达 | 请求可能超时（成功/失败**未知**）、分区 |
| 时钟可信、顺序一致 | 节点时钟漂移、消息乱序 |
| 失败 = 抛异常 | 失败 = 超时/脑裂/半提交（**状态不确定**） |

**所以需要**：一致性模型（说清"允许看到什么"）+ 共识/复制（让多副本达成一致）+ 事务协议（跨服务原子性/最终一致）。

## 三、怎么做：CAP 与一致性谱系

### 3.1 CAP：分区时只能二选一（P 是必选项）

```
C（一致性）：所有节点看到同一份数据
A（可用性）：每个请求都能得到（非错的）响应
P（分区容忍）：网络分区时系统继续运行
```

**关键认知（面试高频）**：
- **P 不是可选项**——分布式系统网络一定会分区，所以真正的选择是"**分区发生时**，要 C 还是要 A"；
- **CA 系统不存在**（单机才是 CA）；
- CAP 的"二选一"只发生在**分区期间**，正常时 C/A 都能满足。

**对照我们学过的系统**：

| 系统/组件 | 分区时的选择 | 证据 |
|---|---|---|
| Nacos 临时实例（Distro） | **AP**：允许短暂不一致，注册中心不可用是灾难 | nacos-lab D-09/D-10 |
| Nacos 持久实例（JRaft） | **CP**：数据不能丢 | nacos-lab D-10 |
| Redis 主从（异步复制） | **AP**：主挂可能丢最后写入 | docs/redis 05 |
| ZooKeeper | **CP**：选举期间不可用 | 对照 |
| MySQL 主从半同步 | 可调（半同步偏 C，异步偏 A） | —— |

### 3.2 BASE：AP 路线的工程化表述

- **Basically Available**（基本可用）：允许降级（限流/排队/返回旧值）；
- **Soft state**（软状态）：中间态允许存在；
- **Eventually consistent**（最终一致）：不保证"立刻"，保证"最终"收敛。

> 对照：Nacos 临时实例"断开即删 + verify 反熵（5s）"就是 BASE 的落地。

### 3.3 一致性谱系（从强到弱）

| 级别 | 含义 | 例子 |
|---|---|---|
| **线性一致**（强） | 所有操作看起来像在单机上按真实时间顺序执行 | etcd/ZK 读写、JRaft 提交 |
| 顺序一致 | 所有节点看到相同顺序，但不要求与真实时间一致 | ZAB 广播 |
| 因果一致 | 有因果关系的操作保序 | 会话一致性 |
| **最终一致**（弱） | 停止写入后，副本最终相同 | Nacos Distro、MySQL 异步从库 |

**"最终"是多久？** 没有上界——这是最终一致最大的工程风险，所以要配合**对账**（L2-3/xhs-project 的 8 个对账 Job）。

## 四、值不值得深挖 & 面试问答

**值不值得**：CAP/BASE 必须张口就来（🔴）；一致性谱系理解到"能对照系统举例"即可（🟡）；FLP/时钟理论翻篇（D-02/D-03，面试低频）。

**Q1：CAP 是不是三选二？**
不是。P 在分布式里是必然前提；CAP 说的是**分区期间** C 和 A 二选一，正常运行时不冲突。

**Q2：Nacos 是 AP 还是 CP？**
两个都是：`ephemeral=true`（临时实例）走 Distro（AP）；`ephemeral=false`（持久实例）走 JRaft（CP）。一行 `instance.isEphemeral()` 决定路由（nacos-lab D-10）。

**Q3：最终一致会导致业务错误吗？**
会（读到旧值/重复），所以工程上要配：幂等（唯一键/状态机）、对账补偿、读己之写（必要时读主）。

**Q4：为什么不能既 C 又 A？**
分区时，要 C 就必须拒绝/阻塞部分请求（失去 A）；要 A 就必须接受副本可能不一致（失去 C）——这是物理约束，不是实现水平问题。
