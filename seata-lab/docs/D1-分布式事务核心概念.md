## 一、为什么需要分布式事务

单体应用的事务靠数据库 ACID。拆分到微服务后，一个业务操作横跨多个数据库：

| 场景 | 不一致风险 |
|---|---|
| 库存扣减（DB-A）+ 订单入库（DB-B） | 库存已扣，订单写入失败 → 数据漂移 |
| 用户注册 → 发优惠券 → 加积分 | 中间环节 RPC 超时 → 状态参差不齐 |
| 跨行转账 A→B | A 扣款成功、B 入账失败 → 资金凭空消失 |

分布式事务保证这组操作要么全部提交、要么全部回滚——在跨服务、跨数据库层面实现原子性。

**CAP 视角**：XA 选择强一致（CP），依赖数据库锁，性能最低；AT/TCC/SAGA 选择最终一致（AP），引入补偿机制，性能更高。Seata 四种模式覆盖了从 CP 到 AP 的全光谱。

## 二、TC/TM/RM 三角色与通信模型

```
                   ┌──────────────┐
   begin/commit     │  TC (Seata)  │  全局事务协调器
  ────────────────▶  │  Netty RPC   │  FILE 存储(本lab)
                    └──────┬───────┘
                           │ TM 注册全局事务 / RM 注册分支 / RM 上报一阶段完成 / TC 下发二阶段决议
         ┌─────────────────┼──────────────────┐
         ▼                 ▼                  ▼
    ┌─────────┐      ┌──────────┐       ┌──────────┐
    │   TM    │      │  RM-A    │       │  RM-B    │
    │ 发起者   │      │ 库存服务   │       │ 订单服务   │
    └─────────┘      └──────────┘       └──────────┘
```

| 角色 | 全称 | 职责 | 关键类 |
|---|---|---|---|
| **TC** | Transaction Coordinator | 维护全局事务 xid + 所有分支状态；接收 TM 的 begin/commit/rollback；下发二阶段决议给各 RM | 独立进程（Seata Server，本 lab 在 docker 中运行） |
| **TM** | Transaction Manager | 声明 `@GlobalTransactional` 的方法即为 TM——定义事务边界，发起 xid，决定提交或回滚 | `GlobalTransactionScanner`（Spring AOP 切面） |
| **RM** | Resource Manager | 被全局事务覆盖的每个数据库操作——AT 模式的 RM 通过 `DataSourceProxy` 拦截 SQL 生成反向 SQL；TCC 的 RM 是业务自己实现 | `DataSourceProxy` / `AbstractDataSourceProxy` |

**一次全局事务的完整生命周期**：
```
① TM 进入 @GlobalTransactional 方法 → GlobalTransactionScanner 切面拦截
   → 向 TC 申请全局 xid → RootContext.bind(xid) 绑定到当前线程
② 业务调用库存服务（RPC）→ Seata 拦截器在 HTTP Header 中透传 TX_XID 头
   → 下游 DataSourceProxy 拦截 SQL → 向 TC 注册分支事务（branchId）
   → 执行 SQL + 记录 undo（AT）/ 执行 Try（TCC）
③ 业务调用订单服务（RPC）→ 同上流程
④ TM 方法返回（无异常→COMMIT；抛异常→ROLLBACK）
   → GlobalTransactionScanner 切面通知 TC 最终决议
⑤ TC 通知所有 RM 二阶段：COMMIT（异步删 undo）/ ROLLBACK（执行 undo 反向补偿）
⑥ RootContext.unbind() 清理线程 xid
```

**xid 跨服务传播**：Seata 通过 `TransactionPropagationInterceptor`（Feign/RestTemplate）在 HTTP Header 中透传 `TX_XID`；下游通过 `RootContext.bind(xid)` 恢复上下文。不需要业务手动传 xid。

## 三、@GlobalTransactional 注解（唯一业务感知点）

TM 只需要在入口方法加一个注解（`integration-tx-api/.../GlobalTransactional.java`）：

```java
@GlobalTransactional(timeoutMills = 300000, rollbackFor = Exception.class)
public void createOrder(OrderDTO dto) {
    inventoryService.deduct(dto);  // RM-1: 库存扣减
    orderService.create(dto);      // RM-2: 订单入库
}
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `timeoutMills` | **60,000**（60s） | 全局事务超时——超时未完成二阶段决议则 TC 强制回滚 |
| `name` | `""` | 事务名（空=方法全限定名，用于日志/监控） |
| `rollbackFor` | `{}`（空=只回滚 RuntimeException） | 触发回滚的异常类型 |
| `noRollbackFor` | `{}` | 不触发回滚的异常 |
| `propagation` | `REQUIRED` | 事务传播——REQUIRED/REQUIRES_NEW/NOT_SUPPORTED 等 |

**AOP 实现入口**：`GlobalTransactionScanner` 作为 Spring BeanPostProcessor 扫描 `@GlobalTransactional` 方法 → 创建代理 → 切入全局事务控制（`TransactionalTemplate`）。

## 四、DataSourceProxy：RM 如何透明拦截数据库操作

AT 模式的 RM 通过代理 JDBC DataSource 实现零侵入拦截：

```java
// Spring Boot 自动装配（DataSourceProxy 包装原始 DataSource）
@Bean
public DataSourceProxy dataSourceProxy(DataSource dataSource) {
    return new DataSourceProxy(dataSource);
}
```

所有通过 `DataSourceProxy` 执行的 SQL 都会被 Seata 接管：`prepare` 阶段生成前镜像（`SELECT FOR UPDATE`）和后镜像（`SELECT`），计算反向补偿 SQL；`commit` 阶段删除 undo_log；`rollback` 阶段执行反向 SQL。

## 五、Seata 客户端配置模型

`application.yml` 中 `seata.*` 配置三大部分（本 lab 真实配置）：

```yaml
seata:
  enabled: true                          # 开关 Seata 客户端
  application-id: seata-lab              # 在 TC 中的服务标识
  tx-service-group: default_tx_group     # 事务分组名——用于 vgroup 映射
  service:
    vgroup-mapping:
      default_tx_group: default          # 事务分组→TC 集群名的映射
    grouplist:
      default: 21.130.247.89:27091       # TC 集群名→TC 实际地址列表
  config:
    type: file                           # 本地配置文件（不需注册中心）
  registry:
    type: file                           # 本地注册表（不需 Nacos/ZK）
```

**配置链**：`tx-service-group` → `vgroup-mapping` → TC 集群名 → `grouplist` → TC 实际 IP:Port。生产环境用 `registry.type=nacos` 替代 `grouplist` 硬编码。

**TC 存储模式**：本 lab 用 `file` 模式——全局事务数据存磁盘文件，重启丢失。生产推荐 `db`（MySQL）持久化。

## 六、四种模式对比

| | XA | AT（本 lab 重点） | TCC | SAGA |
|---|---|---|---|---|
| **原理** | 数据库原生 2PC | **自动补偿**：一阶段提交+undo_log；二阶段删除/回滚 | 业务自实现 Try/Confirm/Cancel | 状态机编排正向+补偿操作 |
| **侵入性** | 零（依赖 DB XA 支持） | **极低**（加 undo_log 表 + DataSourceProxy） | **高**（每个接口三方法） | **高**（手动定义全状态机） |
| **一致性强度** | 强一致 | 最终一致（全局锁期间读隔离） | 最终一致（业务实现决定） | 最终一致 |
| **锁范围** | 全事务周期 | **一阶段提交后释放本地锁**，仅持全局锁 | 无锁（靠业务幂等） | 无锁 |
| **回滚** | DB 自动 | **自动**（undo_log 反向 SQL） | 业务 Cancel 实现 | 补偿操作（人工编排） |
| **性能** | 低 | 中 | 高 | 高 |
| **适用场景** | 金融强一致 | 大多数微服务场景 | 对一致性有自定义需求 | 长事务（分钟/小时级） |

**undo_log 表结构**（AT 必须建在业务库）：

| 字段 | 类型 | 用途 |
|---|---|---|
| branch_id | BIGINT | 分支事务 ID |
| xid | VARCHAR(100) | 全局事务 ID |
| rollback_info | LONGBLOB | 反向 SQL 的序列化数据（JSON） |
| log_status | INT | 0=正常 1=全局已完成 |
| log_created / log_modified | DATETIME | 时间戳 |

唯一约束：`ux_undo_log (xid, branch_id)`——每分支一条记录。

## 七、与 RocketMQ 事务消息的关系

rocketmq-lab D6 学了 RocketMQ 事务消息（半消息+回查）——它是「本地事务 + 发 MQ」的一致方案。Seata 解决的是**跨服务/跨 DB**的一致性。两者**互补**：

```
场景1: 订单扣库存 → 发 MQ 通知发货
  → RocketMQ 事务消息即可

场景2: 订单扣库存 + 支付扣款（两个独立 DB）
  → Seata AT: @GlobalTransactional + 两个 DataSourceProxy + TC 协调

场景3（组合）: 订单扣库存 + 支付扣款 + 发 MQ
  → Seata 包裹 DB 操作 + RocketMQ 事务消息包裹发 MQ（两者独立域，xid 不冲突）
```
