# D1 — 幂等：重复消息为什么不能扣两次？

> **定位**：一致性模式第 1 篇。所有"至少一次"语义（MQ 重投、重试、补发）的地基——**消费端幂等**。
> **对照**：xhs-project `MessageIdempotentHelper`（本 lab A01 的最小复刻）。

---

## 一、它干了什么：一个例子

下单消息被 MQ 投递了**两次**（Broker 重投/Rebalance 换 owner/补发），消费者代码：

```java
public void onMessage(Message msg) {
    accountService.deduct(msg.getOrderId(), msg.getAmount());  // ← 执行了两次！
}
```

结果：用户被扣了两次钱。**修复**——处理前先"认领"消息：

```java
if (!idempotentHelper.isFirstProcess("account-topic", msg.getMsgId(), 86400)) {
    return;  // 重复消息，跳过
}
accountService.deduct(...);  // 只执行一次
```

**一句话**：幂等 = "同一个业务操作执行 N 次的效果 = 执行 1 次"——靠**唯一标识 + 去重记录**在入口处拦截。

---

## 二、为什么需要它：谁在制造重复

| 来源 | 机制 | 回链 |
|---|---|---|
| MQ 重投 | at-least-once：offset 窗口/Rebalance/超时重投 | RocketMQ D5 |
| 发送方重试 | 发送超时状态不确定 → 业务重发 | RocketMQ D3 §五 |
| 本地消息表补发 | 补发是"至少一次"（可能已发成功过） | 本 lab D2 |
| 用户/前端重试 | 重复提交 | —— |

**关键认知**：分布式下"恰好一次投递"不存在——**幂等不是优化，是义务**（消费端必须做）。

---

## 三、怎么做：三件套 + 本 lab 实现

### 3.1 三种手段（按成本递增）

| 手段 | 做法 | 适用 |
|---|---|---|
| **唯一键** | 业务表加唯一约束（订单号+操作）——重复插入直接失败 | 天然有业务键的操作（创建类） |
| **去重表** | 独立表记录已处理 ID，处理前查/插入 | 通用（无天然唯一键） |
| **状态机** | 只允许合法状态迁移（已支付→支付成功 = 幂等空操作） | 有状态流转的业务 |

### 3.2 本 lab 实现：Redis SETNX + removeMark + DB 兜底（对齐 xhs-project）

```java
// core/IdempotentHelper.java（节选）
public boolean isFirstProcess(String bizType, String bizId, long ttlSeconds) {
    String key = "msg:idempotent:" + bizType + ":" + bizId;
    try {
        Boolean success = redis.opsForValue().setIfAbsent(key, "1", ttlSeconds, TimeUnit.SECONDS);
        return Boolean.TRUE.equals(success);      // true=首次，false=重复
    } catch (Exception e) {
        log.error("Redis 不可用，降级放行", e);
        return true;                              // ← 降级放行（可用性优先）
    }
}

public void removeMark(String bizType, String bizId) {
    redis.delete("msg:idempotent:" + bizType + ":" + bizId);  // 业务失败时删除 → 允许重试
}
```

消费端模式（A01 实测）：

```java
if (!helper.isFirstProcess("account-topic", msgId, 86400)) return "重复忽略";
try {
    jdbc.update("INSERT INTO consume_record(...)");   // 第二道防线：DB 唯一键
    jdbc.update("UPDATE account SET balance = balance + ? WHERE id = 1");
} catch (Exception e) {
    helper.removeMark(...);                            // 业务失败 → 删标记允许重试
    throw e;
}
```

### 3.3 两个设计决策（面试重点）

**① 为什么 Redis 不可用时"降级放行"而不是拒绝？**
可用性优先——幂等组件挂了不能把业务全部堵死。代价：降级窗口内可能重复——**靠 DB 唯一键兜底**（第二道防线）。这就是"Redis + DB 双层幂等"的由来。

**② `removeMark` 的语义（什么时候删/不删）**：
- **删**：业务确定失败（异常回滚）→ 允许 MQ 重试
- **不删**：超时/网络异常（结果未知）→ 保守视为"已处理"（宁可漏一次重试，不可重复执行）

## 四、坑与边界

| 坑 | 说明 |
|---|---|
| TTL 语义 | 幂等标记要覆盖"最大可能重投窗口"（xhs 用 24h）；TTL 太短 → 过期后重复通过 |
| 降级放行窗口 | Redis 挂掉期间是"无幂等"状态——必须有 DB 兜底 + 告警 |
| 先扣减后标记 | 顺序必须是"先认领再执行"；先执行再标记 = 并发下双执行 |
| 分布式锁 ≠ 幂等 | 锁防并发，幂等防重复（锁释放后重放依然重复） |

## 六、值不值得深挖 & 面试问答

**值不值得**：🔴 必问——"重复消费怎么防"是分布式/消息面试的第一道题；本 lab 的 SETNX+removeMark+降级 三件套必须能背。

**Q1：Redis SETNX 做幂等，Redis 挂了怎么办？**
降级放行（保可用性）+ DB 唯一键兜底 + 告警。不能因为幂等组件挂掉拒绝业务。

**Q2：为什么失败要删标记？**
业务异常回滚后消息需要重试；不删标记 → MQ 重试全被拦 → 消息永远处理不了。

**Q3：超时为什么不能删标记？**
超时 = 结果未知（可能已执行成功）——删了会导致重复执行；保守视为已处理。

**Q4：幂等键怎么选？**
业务语义唯一：MQ 消息用 msgId（生产者 UNIQ_KEY）；业务操作 用"业务类型+业务ID"（如 `order:pay:o123`）。
