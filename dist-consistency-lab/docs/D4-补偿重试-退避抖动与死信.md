# D4 — 补偿重试：下游挂了 5 分钟，重试怎么排？

> **定位**：一致性模式第 4 篇。**收敛手段**——把"暂时失败"熬成"最终成功"或"明确死信"。
> **对照**：xhs-project `RetryBackoffUtils` + `LocalMessageRetryJob`（本 lab A04 的最小复刻）。

---

## 一、它干了什么：一个例子

下游支付服务挂了 5 分钟，你的补偿/补发任务怎么重试？

```java
// ❌ 固定间隔：每 30s 重试一次
//    → 下游恢复瞬间被所有实例的重试"对齐共振"二次打垮
// ❌ 无限重试：永远重试
//    → 死消息永远占着资源，永远无法人工介入
```

**正确姿势**——指数退避 + 封顶 + 抖动：

```
attempt 1 → ~30s
attempt 2 → ~60s
attempt 3 → ~120s
attempt 4 → ~240s
attempt 5 → ~480s（封顶）
attempt 6+ → 保持 ~480s（±20% 抖动）
超过 maxRetries → 死信（终态）
```

**一句话**：补偿重试 = **指数退避（给下游恢复时间）+ 抖动（防共振）+ 死信终态（防无限占用）**。

---

## 二、为什么需要它：三个设计动机

| 设计 | 解决什么 |
|---|---|
| **指数退避** | 下游故障通常需要时间恢复——高频重试只会浪费资源 + 加重下游负担 |
| **封顶（max）** | 退避不能无限增长（否则消息"等 10 小时"才重试）——封顶保证收敛速度 |
| **抖动（jitter）** | 多实例/多服务的重试时间对齐 → 下游恢复瞬间同时涌入（thundering herd）——±20% 打散 |
| **死信（终态）** | 重试耗尽后必须"停下来"——可告警、可人工、可分析，而不是永远重试 |

## 三、怎么做：本 lab 实现（对齐 xhs-project）

### 3.1 退避算法（`RetryBackoffUtils`）

```java
// core/RetryBackoffUtils.java（节选）
public static long exponentialSeconds(int attempt, long baseSeconds, long maxSeconds, double jitterRatio) {
    long delay = Math.max(0, baseSeconds);
    for (int i = 1; i < attempt && delay < maxSeconds; i++) {
        delay = Math.min(delay * 2, maxSeconds);      // 指数 ×2，封顶
    }
    return jitter(delay, jitterRatio);                // ±jitterRatio 抖动
}

public static long jitter(long base, double jitterRatio) {
    long delta = (long) (base * jitterRatio);
    return Math.max(0, base + ThreadLocalRandom.current().nextLong(-delta, delta + 1));
}
```

**A04 实测序列**（base=30s / max=480s / jitter=±20%）：
`[31, 51, 104, 230, 467, 503, 455, 576]` —— 指数增长、480s 附近封顶、每次带抖动。

### 3.2 重试链与死信（A04 实测）

```
attempt 1: 失败 → 2s 后重试
attempt 2: 失败 → 4s 后重试
attempt 3: 失败 → 超过上限 → 死信（终态，需告警/人工）
```

死信不是"失败"——是**明确的终态**：可监控（Gauge 指标）、可告警、可人工重放。

## 四、与"框架重试"的边界（面试易混点）

| 层 | 谁做 | 例子 | 上限 |
|---|---|---|---|
| **RPC/发送层重试** | 框架（毫秒-秒级） | Feign Retryer / RocketMQ 发送重试 / `retryTimesWhenSendFailed` | 2-3 次，共享超时预算 |
| **消费重试** | MQ 框架（秒-分钟级） | RocketMQ `%RETRY%`（3+reconsumeTimes 退避）/ DLQ | 16 次 |
| **业务补偿重试** | **业务自己**（分钟-小时级） | Outbox 补发 / 对账修复重试 / 支付回调补偿 | 自定义 + 死信 |

**关键**：框架重试管"调用"，业务补偿重试管"业务收敛"——两层都要有，不能互相替代（回链 RocketMQ D5/Feign D3）。

## 六、值不值得深挖 & 面试问答

**值不值得**：🟡 重要——"重试策略"高频；指数退避+抖动+死信的"三件套"和"两层重试边界"要能说清。

**Q1：为什么重试要加抖动？**
多实例固定间隔重试会"对齐共振"——下游恢复瞬间被同时涌入打垮（thundering herd）；±20% 打散时间。

**Q2：退避为什么要封顶？**
不封顶的话重试间隔无限增长（base×2^n），消息可能"等几小时"才重试——封顶保证收敛速度与下游保护平衡。

**Q3：重试耗尽后怎么办？**
死信终态：告警 + 人工介入（分析/重放）——不能无限重试（占资源、掩盖问题）。

**Q4：Feign 有重试了，业务还要补偿重试吗？**
要——Feign 重试是"调用级"（毫秒级、2-3 次）；业务补偿是"收敛级"（分钟-小时、跨重启）——两者不同层。
