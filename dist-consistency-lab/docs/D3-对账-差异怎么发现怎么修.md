# D3 — 对账：Redis 扣了 7，DB 还是 1000，怎么发现怎么修？

> **定位**：一致性模式第 3 篇。**最后防线**——所有"最终一致"承诺的兑付方式。
> **对照**：xhs-project 6 个 `*ReconcileJob`（本 lab A03 的最小复刻）。

---

## 一、它干了什么：一个例子

库存扣减走"Redis 实时扣 + DB 异步落库"（回链 Redis lab/库存设计）：

```
用户下单 → Redis: stock-1（实时权威）→ 发 MQ → 异步落库 DB
                                        ↑ 消息丢了/消费失败 → DB 永远慢一拍
```

结果：Redis=993、DB=1000——**用户看到的库存和实际不符**。怎么发现？

```java
// 对账任务（每天凌晨 3 点）
redisVal = redis.get("account:1:balance");   // 993
dbVal    = jdbc.query("SELECT balance ..."); // 1000
if (redisVal != dbVal) {
    jdbc.update("UPDATE account SET balance = ? WHERE id = 1", redisVal);  // 以 Redis 为准修复
}
```

**一句话**：对账 = **周期性对比两个存储 + 按权威源修复差异**——它是"最终一致"里"最终"二字的工程保障。

---

## 二、为什么需要它：最终一致的"最终"没有时间上界

- 消息可能**永远丢**（重试耗尽进死信）→ 差异永远不收敛
- 补偿可能**失败**（Cancel 接口挂了）→ 需要人工介入
- 并发窗口**必然存在**（异步落库天然滞后）

**所以**：所有走最终一致的链路，最后都必须有一道"对账"兜底——它回答"如果前面全挂了，谁来发现和修复"。

---

## 三、怎么做：权威源选择 + 差异修复（本 lab 实现）

### 3.1 第一步：选权威源（**对账最重要的决策**）

| 场景 | 权威源 | xhs 案例 |
|---|---|---|
| Redis 实时扣减、DB 异步落库 | **Redis 为准** | 库存/购物车/计数（Redis=权威） |
| DB 为准、Redis 只做缓存 | **DB 为准** | 通知未读数（DB=权威） |
| 业务库 vs 外部系统（支付/银行） | **外部为准**（或双向核对） | 支付对账/结算 |

**xhs 的口径差异**（回链 xhs 第 18 题）：同一个"对账"在不同域权威源不同——库存 Redis 为准；但 `CounterReconcileJob` 有个特例：**Redis=0 且 DB 有值时以 DB 为准**（防 Redis 丢数据被"修复"成 0）。

### 3.2 第二步：对比 + 修复（A03 实测）

```java
// A03 /a03/reconcile（节选）
long redisVal = redisBalance();          // 权威源
long dbVal = dbBalance();
if (redisVal != dbVal) {
    jdbc.update("UPDATE account SET balance = ?, version = version + 1 WHERE id = 1", redisVal);
    // 修复也要幂等 + 带版本号（防并发覆盖）
}
```

**实测**：扣 7 只写 Redis（`skipDb=true`）→ `diff=7` → reconcile → `diff=0` ✓

### 3.3 第三步：边界与告警

| 边界 | 处理 |
|---|---|
| 对账时 MQ 还有积压 | 修复后积压消息消费可能"多扣一次"——概率低且下次对账会再修（xhs 注释明确接受） |
| 差异方向异常（DB 多/少） | 不同方向不同告警级别——"Redis 有 DB 无"可能是初始化未完成（跳过） |
| 修复动作失败 | 记录 + 告警 + 下次重试（修复本身也要重试/幂等） |

## 四、两种形态（面试常混）

| 形态 | 对什么 | 差异来源 | xhs 落点 |
|---|---|---|---|
| **内部对账**（缓存一致性） | Redis ↔ DB | 异步落库丢失/延迟 | Inventory/Cart/Counter ReconcileJob |
| **外部对账**（资金） | 业务库 ↔ 支付/渠道流水 | 回调丢失/状态不同步 | PaymentReconcileJob / SettlementJob |

**外部对账**的核心是"**状态收敛**"：本地单边成功/支付单边成功/双边成功三态 → 各自补偿动作（补单/退单/关闭）。xhs 的 `PaymentNotifyCompensateJob`/`RefundTimeoutCheckJob` 是同一族的补偿任务。

## 六、值不值得深挖 & 面试问答

**值不值得**：🔴 必问——"你们怎么保证最终一致"的最后一环；**权威源选择**是区分候选人深度的点。

**Q1：对账为什么必须存在？**
最终一致的"最终"没有上界——丢失的消息/失败的补偿不会自己收敛；只有对账能发现并修复。

**Q2：对账以谁为准？**
看业务：实时扣减场景 Redis 为准（库存）；缓存场景 DB 为准（通知）；资金场景外部为准。**没有全局答案，按域定**。

**Q3：对账修复会不会引发新问题？**
会——修复时的并发窗口（MQ 积压）可能造成多扣；xhs 的口径是"概率极低且下次对账再修"——**对账不是实时一致性，是最终兜底**。

**Q4：对账任务重复执行怎么办？**
修复动作幂等（按值 UPDATE 天然幂等）+ 单实例调度（XXL-Job）+ 修复带版本号。
