## 一、速记卡（一页纸）

1. **幂等是地基**：所有"至少一次"语义（MQ 重投/补发/重试）都靠它兜底——**先认领再执行**（SETNX），失败 `removeMark` 允许重试，超时**不删**（结果未知）。
2. **Redis 幂等降级策略**：Redis 不可用 → **降级放行**（可用性优先）+ DB 唯一键兜底（第二道防线）+ 告警。
3. **三件套**：唯一键（创建类）/ 去重表（通用）/ 状态机（流转类）。
4. **Outbox = 本地消息表**：业务表与消息表**同库同事务**（原子）→ 后台补发（可靠）→ 不依赖 MQ 特性。
5. **Outbox 状态机**：0 待发送 → 1 已发送（清理）/ 2 失败（等退避窗口）/ 3 死信（终态）。
6. **Outbox 工程细节**：3s cutoff（防与即时投递并发双发）、批量 LIMIT、单实例调度/锁、定期清理、死信 Gauge。
7. **对账 = 最后防线**：周期性对比两个存储 + **按权威源修复**；"最终"没有时间上界，只有对账能发现不收敛的差异。
8. **权威源按域定**：Redis 实时扣减 → Redis 为准（库存）；DB 为准缓存 → DB 为准（通知）；资金 → 外部为准（支付）。
9. **补偿重试三件套**：指数退避（给恢复时间）+ 抖动 ±20%（防对齐共振）+ 死信终态（防无限占用）。
10. **两层重试边界**：框架重试（调用级、毫秒、2-3 次）≠ 业务补偿重试（收敛级、分钟-小时、自定义上限）。
11. **四模式组合**：Outbox/事务消息（投递）+ 幂等（消费）+ 补偿重试（收敛）+ 对账（兜底）——缺一不可。
12. **xhs 全景**：订单=事务消息；券/库存=Outbox；6 个 ReconcileJob + 手册 8 任务；DLQ 三级治理。

## 二、分组高频题

### A. 幂等

**A1. 重复消费怎么防？**
入口"认领"：`SETNX(bizType:bizId)` 成功才执行；重复直接跳过。Redis 挂了降级放行 + DB 唯一键兜底。回链：D1 §三。

**A2. 为什么失败要删幂等标记，超时不删？**
失败（异常回滚）= 确定未执行 → 删标记允许重试；超时 = 结果未知 → 保守视为已处理（宁可漏重试不可重复）。回链：D1 §3.3。

**A3. 幂等键怎么选？**
业务语义唯一：MQ 用 msgId；业务操作 `bizType:bizId`（如 `order:pay:o123`）；TTL 覆盖最大重投窗口（xhs 24h）。回链：D1 §四。

**A4. 分布式锁能代替幂等吗？**
不能——锁防并发，幂等防重复；锁释放后重放依然会重复执行。回链：D1 §四。

### B. Outbox

**B1. MQ 挂了消息怎么不丢？**
Outbox：业务表+消息表同事务（DB 不挂消息就在）→ 后台补发（Broker 恢复后投递）。实测：故障注入→恢复→补发成功。回链：D2 §三。

**B2. Outbox vs 事务消息？**
Outbox 不依赖 MQ 特性（支持任意 MQ、可审计、DB 即可）；事务消息依赖 RocketMQ（半消息+回查）。回链：D2 §二 + RocketMQ D6。

**B3. 补发会不会重复发？**
会（at-least-once）——已发成功但标记丢失会重发；**消费端幂等**兜底。回链：D2 §五。

**B4. 3s cutoff 是干什么的？**
避开"刚插入、即时投递进行中"的记录——防止补发任务与即时投递并发双发。回链：D2 §四。

### C. 对账

**C1. 你们怎么保证最终一致？**
分层：本地事务 → Outbox/事务消息（at-least-once）→ 幂等 → 补偿重试 → **对账兜底**。回链：D5 §一。

**C2. 对账以谁为准？**
按域定：库存 Redis 为准（实时权威）；通知 DB 为准；资金外部为准。xhs 特例：Counter 对账"Redis=0 且 DB 有值 → 以 DB 为准"（防 0）。回链：D3 §3.1。

**C3. 对账修复有什么风险？**
修复时 MQ 积压可能造成多扣（并发窗口）；xhs 接受"概率低+下次对账再修"——对账是兜底不是实时。回链：D3 §3.3。

**C4. 对账任务重复触发怎么办？**
修复幂等（按值 UPDATE）+ 单实例调度（XXL-Job）+ 版本号。回链：D3 Q4。

### D. 补偿重试

**D1. 重试间隔怎么设计？**
指数退避（30s→480s 封顶）+ ±20% 抖动（防共振）+ 死信终态（超限停）。回链：D4 §三。

**D2. 为什么要抖动？**
多实例固定间隔 → 下游恢复瞬间对齐涌入（thundering herd）——抖动打散。回链：D4 Q1。

**D3. 重试耗尽后怎么办？**
死信终态 + 告警 + 人工（分析/重放）——不能无限重试。回链：D4 §3.2。

**D4. Feign 有重试还要业务补偿吗？**
要——Feign 是调用级（毫秒、2-3 次）；业务补偿是收敛级（分钟-小时、跨重启）。回链：D4 §四。

### E. 选型与对照

**E1. 为什么不用 Seata 一把梭？**
Seata 适合多库原子提交；大多数业务只需"可靠投递+幂等+对账"（更轻、无全局锁）。选型看原子性需求。回链：D5 §三/§四。

**E2. xhs 各域怎么选的？**
订单=事务消息（回查 UNKNOWN）；券=Outbox；库存=分桶预扣+Outbox+对账；支付=回调三态+补偿+外部对账。回链：D5 §五。

**E3. 四模式里哪个最重要？**
幂等——其余三个模式的重复风险全靠它兜底。回链：D5 Q4。

**E4. "最终一致"怎么向业务承诺？**
承诺"可发现、可修复"（对账周期 + 修复 SLA + 告警），不是"零差异"。回链：D5 Q3。

## 三、陷阱速查（12 连）

| # | 反直觉点 | 正解 |
|---|---|---|
| 1 | 幂等先执行再记录 | **先认领再执行**（顺序反了并发下双执行） |
| 2 | Redis 幂等挂了就拒绝 | 降级**放行** + DB 兜底（可用性优先） |
| 3 | 超时也删标记 | 超时**不删**（结果未知，删了会重复） |
| 4 | Outbox 保证不重复 | at-least-once——重复靠消费幂等 |
| 5 | 补发和即时投递不冲突 | 需要 **cutoff** 防并发双发 |
| 6 | Outbox 表不用清理 | 必须清理（已发送保留审计窗口） |
| 7 | 对账统一以 DB 为准 | **权威源按域定**（库存 Redis/通知 DB/资金外部） |
| 8 | 对账修复零风险 | 有并发窗口（MQ 积压）——兜底非实时 |
| 9 | 重试固定间隔 | 指数退避 + **抖动**（防共振） |
| 10 | 重试无限进行 | 死信**终态**（告警+人工） |
| 11 | 有 Feign 重试就够 | 两层不同：调用级 vs 收敛级 |
| 12 | 有 Seata 就不用幂等 | 重试/换 owner 仍会重复——幂等是义务 |

## 五、一页纸收束

> **幂等**：SETNX 先认领 → 执行 → 失败 removeMark；降级放行 + DB 唯一键兜底。
> **Outbox**：业务表+消息表同事务 → 补发（3s cutoff/批量/退避/死信）→ at-least-once。
> **对账**：按域选权威源（Redis/DB/外部）→ 周期对比修复 → 最终一致的兑付方式。
> **重试**：指数退避（30s→480s）+ ±20% 抖动 + 死信终态；与框架重试分层。
> **选型**：原子性需求决定 Seata/事务消息/Outbox；无论哪条都配"幂等+重试+对账"。
> **xhs 全景**：事务消息（订单）+ Outbox（券/库存）+ 6 ReconcileJob + DLQ 三级治理。
