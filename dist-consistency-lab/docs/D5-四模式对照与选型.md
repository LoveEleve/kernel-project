# D5 — 四模式对照与选型：什么时候用哪个？

> **定位**：一致性模式收束篇——把 D1-D4 的四个模式放进一张决策表，划清与 Seata/RocketMQ 的边界。
> **回链**：分布式理论快读 03/04、Seata 系列、RocketMQ 系列。

---

## 一、先看一个例子：一笔订单的一致性全景

```
下单请求
  │
  ├─ ① 本地事务：扣余额 + 写订单 + 写 outbox      ← Outbox（D2）
  │
  ├─ ② 投递"订单创建"消息（失败由补发兜底）        ← Outbox 补发 + 补偿重试（D4）
  │
  ├─ ③ 下游消费（库存/积分/通知）：先查重再执行      ← 幂等（D1）
  │
  └─ ④ 每天凌晨：对比各域数据，修差异              ← 对账（D3）
```

**四个模式各管一段**——没有哪个单独能保证一致性，**组合起来才是生产方案**。

---

## 二、四模式定位矩阵

| 模式 | 解决什么 | 核心机制 | 语义 | 本 lab | xhs 落点 |
|---|---|---|---|---|---|
| **幂等** | 重复执行 | 唯一键/去重表/状态机 | exactly-once **效果** | A01 | MessageIdempotentHelper |
| **Outbox** | 可靠投递 | 同事务消息表 + 补发 | at-least-once | A02 | 券/库存 Outbox |
| **对账** | 差异收敛 | 权威源 + 修复 | 最终一致兜底 | A03 | 6 个 ReconcileJob |
| **补偿重试** | 暂时失败 | 退避+抖动+死信 | 收敛手段 | A04 | RetryBackoffUtils |

**依赖关系**：Outbox 依赖幂等（补发重复）；对账依赖幂等（修复并发）；补偿重试服务于前两者——**幂等是一切的地基**。

## 三、选型决策树

```
需要跨服务/跨库的原子性？
  ├─ 是 → 要"强一致"？
  │        ├─ 是（少用）→ Seata AT / XA（锁资源，性能低）
  │        └─ 否 → 最终一致：
  │              ├─ 单 DB + 发消息 → 事务消息（RocketMQ）或 Outbox
  │              ├─ 多 DB 跨表 → Seata TCC/SAGA（回链 Seata D3/D4）
  │              └─ 跨公司/长流程 → Saga + 可靠消息（理论 04）
  └─ 否（只是可靠投递）→ Outbox / 事务消息

无论走哪条 → 消费端必须幂等（D1）+ 链路必须配补偿重试（D4）+ 最后必须有对账（D3）
```

## 四、与 Seata / RocketMQ 的边界（面试高频）

| 问题 | 答案 |
|---|---|
| 事务消息 vs Outbox？ | 事务消息依赖 RocketMQ（半消息+回查）；Outbox 只需 DB（支持任意 MQ、可审计）。xhs 两者都用（订单=事务消息；券/库存=Outbox） |
| Seata AT 和 Outbox 冲突吗？ | 不冲突——AT 管"多库原子提交"，Outbox 管"本地事务+消息投递"；单库场景不需要 AT |
| 有 Seata 还要幂等/对账吗？ | 要——AT 的全局锁防并发，但重试/换 owner 仍会重复消费；对账是最终兜底 |
| TCC 的空回滚/悬挂谁管？ | Seata fence 表（回链 Seata D3）；业务补偿重试管"重试次数/死信" |

## 五、xhs-project 全景对照

| 域 | 一致性方案 | 权威源/要点 |
|---|---|---|
| 订单 | **事务消息**（OrderTransactionListener）+ 本地消息表补发 | 回查 UNKNOWN 语义 |
| 券 | **Outbox**（t_coupon_outbox）+ 单 Lua 领券 | 防"回滚不作废"超发 |
| 库存 | 分桶预扣（Redis 权威）+ Outbox + **对账** | 对账以 Redis 为准（含防 0 特例） |
| 购物车/计数 | Redis 为准 + 异步落库 + 对账 | CartReconcile（4 点）/ Counter（3 点） |
| 通知未读 | **DB 为准** + Redis 缓存 + 对账 | 权威源与库存相反 |
| 支付 | 回调三态 + 补偿 Job + **外部对账** | 迟到成功/退款累计语义 |
| 全链路 | 幂等（SETNX+DB 唯一键）+ 退避重试 + DLQ 三级治理 | 8 个对账/修复任务兜底 |

## 六、值不值得深挖 & 面试问答

**值不值得**：🔴 必问——"你们的一致性方案"是系统设计题的必考项；**四模式组合 + 权威源按域定** 是架构师级答案。

**Q1：你们怎么保证分布式一致性？**
分层回答：单库原子（本地事务）→ 跨库/跨服务（事务消息或 Outbox，at-least-once）→ 消费幂等（SETNX+唯一键）→ 补偿重试（退避+死信）→ 对账兜底（按域选权威源）。

**Q2：为什么不用 Seata 一把梭？**
Seata 适合多库原子提交场景；大多数业务只需"可靠投递+幂等+对账"（更轻、无全局锁、无额外组件）。选型看**原子性需求**而非"技术先进"。

**Q3：最终一致怎么向业务承诺？**
"最终"= 对账周期 + 修复 SLA；对账未收敛的差异 → 告警 + 人工——**承诺的是可发现、可修复，不是零差异**。

**Q4：四个模式里哪个最重要？**
幂等——所有"至少一次"语义（MQ 重投/补发/重试）都要靠它兜底；没有幂等，其余三个模式的重复风险全部暴露。
