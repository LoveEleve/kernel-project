## 一、自动配置的全景——3 个 @AutoConfiguration 的分工

Spring Boot 3.2.5 有 8 个 tracing 相关的 Auto Configuration，核心的 3 个：

| 配置类 | 条件 | 作用 |
|------|------|------|
| `BraveAutoConfiguration` | classpath 有 `brave.Tracer` + `BraveTracer` | 创建 `brave.Tracing` + `BraveTracer` + `BravePropagator` |
| `MicrometerTracingAutoConfiguration` | 存在 `Tracer` bean | 注册 3 个 ObservationHandler + `@SpanAspect` |
| `NoopTracerAutoConfiguration` | **不存在** `Tracer` bean | 返回 `Tracer.NOOP` 兜底 |

**为什么 BraveAutoConfiguration 声明 `@AutoConfiguration(before = MicrometerTracingAutoConfiguration.class)`？** BraveAutoConfiguration 创建 `brave.Tracing` 和 `BraveTracer` bean——这些是 `MicrometerTracingAutoConfiguration` 的依赖（`@ConditionalOnBean(Tracer.class)`）。如果顺序反了，MicrometerTracingAutoConfiguration 会因为没有 Tracer bean 而回退到 NOOP，所有 Observation Handler 都不会创建。

## 二、BraveAutoConfiguration——核心 Bean 装配链

`BraveAutoConfiguration.java:152` 起（174 行）创建 Brave 原生基础设施 + Bridge Bean：

```java
@AutoConfiguration(before = { MicrometerTracingAutoConfiguration.class, NoopTracerAutoConfiguration.class })
@ConditionalOnClass({ brave.Tracer.class, BraveTracer.class })
@EnableConfigurationProperties(TracingProperties.class)
public class BraveAutoConfiguration {

    @Bean @ConditionalOnMissingBean
    brave.Tracing braveTracing(Environment env, Sampler sampler, Factory propagationFactory,
                               List<SpanHandler> spanHandlers, CurrentTraceContext currentTraceContext,
                               List<TracingCustomizer> tracingCustomizers) {
        // W3C + span-joining 不兼容——三层检查（type/produce/consume 各含 W3C 时抛异常）
        // ...
        String appName = env.getProperty("spring.application.name", "application");
        Builder builder = Tracing.newBuilder().currentTraceContext(currentTraceContext)
                .traceId128Bit(true).supportsJoin(spanJoiningSupported)
                .propagationFactory(propagationFactory).sampler(sampler)
                .localServiceName(appName);
        spanHandlers.forEach(builder::addSpanHandler);
        tracingCustomizers.forEach(c -> c.customize(builder));
        return builder.build();
    }

    @Bean @ConditionalOnMissingBean
    brave.Tracer braveTracer(Tracing tracing) {            // ← Brave 原生 Tracer
        return tracing.tracer();
    }

    @Bean @ConditionalOnMissingBean(io.micrometer.tracing.Tracer.class)
    BraveTracer braveTracerBridge(brave.Tracer tracer,     // ← SPI 桥接，方法名 bridge
            CurrentTraceContext currentTraceContext) {
        return new BraveTracer(tracer,
                new BraveCurrentTraceContext(currentTraceContext),
                BRAVE_BAGGAGE_MANAGER);                    // ← 静态常量（L73）
    }
}

## 三、MicrometerTracingAutoConfiguration——Observation 集成

`MicrometerTracingAutoConfiguration.java:147` 装配 3 个 ObservationHandler（+ SpanAspectConfiguration，L103/L123）：

```java
@AutoConfiguration(after = BraveAutoConfiguration.class)
@ConditionalOnClass(Tracer.class)
@ConditionalOnBean(Tracer.class)
public class MicrometerTracingAutoConfiguration {

    @Bean @ConditionalOnMissingBean
    DefaultTracingObservationHandler defaultTracingObservationHandler(Tracer tracer) {
        return new DefaultTracingObservationHandler(tracer);
    }

    @Bean @ConditionalOnBean(Propagator.class) @ConditionalOnMissingBean
    PropagatingSenderTracingObservationHandler senderHandler(Tracer tracer, Propagator propagator) {
        return new PropagatingSenderTracingObservationHandler(tracer, propagator);
    }

    @Bean @ConditionalOnBean(Propagator.class) @ConditionalOnMissingBean
    PropagatingReceiverTracingObservationHandler receiverHandler(Tracer tracer, Propagator propagator) {
        return new PropagatingReceiverTracingObservationHandler(tracer, propagator);
    }
}
```

> **Boot 3.2.5 细节**：`BRAVE_BAGGAGE_MANAGER = new BraveBaggageManager()`（L73，无参构造 → tagFields 为空）——3.2.5 未装配 tag-fields/local-fields 概念（与 D6 版本注记一致）。

**为什么 Sender 和 Receiver Handler 在 `@ConditionalOnBean(Propagator.class)` 下？** 没有传播协议就无法 inject/extract trace 上下文——Sender 和 Receiver Handler 在这种情况下是废柴。如果 classpath 中存在 Propagator bean（由 BraveAutoConfiguration 提供），就注册这两个 Handler；否则只保留 Default Handler。

## 四、NoopTracerAutoConfiguration——"安全回退"模式

`NoopTracerAutoConfiguration.java:44`（44 行）在没有任何 tracing 库时创建 NOOP：

```java
@AutoConfiguration(before = MicrometerTracingAutoConfiguration.class)
@ConditionalOnClass(Tracer.class)
@ConditionalOnMissingBean(Tracer.class)  // ← 注意：有 bridge 时不存在这个条件
public class NoopTracerAutoConfiguration {

    @Bean
    Tracer noopTracer() {
        return Tracer.NOOP;
    }
}
```

**这个设计保证了**：即使只引入 `micrometer-tracing-api` 而不引入任何 bridge，`Tracer` 注入也不会抛 NoSuchBeanDefinitionException——Spring injects `Tracer.NOOP`。

**验证方法**：在 tracing-lab 中移除 `micrometer-tracing-bridge-brave` 依赖 → 编译 → 启动 → 注入 Tracer，它仍然是有效的 bean（不会 NPE），但所有 `nextSpan()` 返回 Noop Span。

## 五、日志集成——traceId 如何出现在 Logback 输出中

Spring Boot 使用 `BraveScopeDecorator` 将 traceId/spanId 写入 MDC。配置通过 `LogCorrelationEnvironmentPostProcessor`：

```java
public class LogCorrelationEnvironmentPostProcessor implements EnvironmentPostProcessor {
    @Override
    public void postProcessEnvironment(ConfigurableEnvironment environment, 
                                         SpringApplication application) {
        // 默认追加 %X{traceId:-}%X{spanId:-} 到 logging.pattern.level
        environment.getPropertySources().addLast(new TracingLogCorrelationPropertySource());
    }
}
```

**默认的日志格式**在 `logging.pattern.level` 的值最后追加 `%clr(%5p) %clr([${spring.application.name:},%X{traceId:-},%X{spanId:-}]){faint}`。

**为什么使用 `%X{}` 而不是 `$`？** `%X{key}` 是 Logback 的 MDC 占位符——从 `MDC.get("key")` 读取。`:-` 后缀是默认值语法：MDC 中不存在时输出 `-`。

**验证**：
```bash
# 发起请求后查看日志
grep "traceId" /tmp/tracing-lab.log | head -1
# 应当看到: INFO [tracing-lab,abc123,def456]
```

## 六、BravePropagationConfigurations——传播工厂的选择逻辑

`BravePropagationConfigurations.java` 根据 `management.tracing.propagation.type` 选择传播工厂：

```
propagation.type = W3C
    → W3CPropagation (traceparent + tracestate + baggage)

propagation.type = B3
    → B3Propagation.FACTORY (SINGLE: 1 个 header `b3: {traceId}-{spanId}-{sampled}`)

propagation.type = B3_MULTI
    → B3Propagation.FACTORY (MULTI: 3-4 个 header X-B3-TraceId/SpanId/ParentSpanId/Sampled)

propagation.type = W3C,B3
    → CompositePropagationFactory(W3C + B3)
    → inject 同时输出两种格式的 header
    → extract 优先解析 W3C，回退到 B3

propagation.type = null（未设置）
    → produce = W3C，consume = 全部（W3C + B3 + B3_MULTI）
```

**"inject 两种格式"的实际效果**：
```
traceparent: 00-{traceId}-{spanId}-01
tracestate: dd=s:2;o:rum
baggage: tenant-id=acme
X-B3-TraceId: {traceId}
X-B3-SpanId: {spanId}
X-B3-Sampled: 1
```

这样新旧服务都可以正确 extract trace 上下文。

## 七、生产场景量化分析

### 7.1 BraveAutoConfiguration 的启动时间

BraveAutoConfiguration 自身 + @Import 配置类提供的 Bean 的创建（Brave Initialization）：

```
TracingProperties binding     ≈ 0.1 ms
Sampler.create()              ≈ 0.05 ms
Propagation.Factory.create()  ≈ 0.2 ms
brave.Tracing.newBuilder()    ≈ 2 ms (初始化 128-bit traceId 生成器)
BraveTracer constructor       ≈ 0.5 ms
其他 11 个 Bean                ≈ 0.3 ms
────────────────────────────────────
总计                          ≈ 3.15 ms
```

在 Spring Boot 应用启动中（总时间 1-2 秒）占比 < 0.3%。

### 7.2 配置变更的风险

修改 `management.tracing.sampling.probability` 从 0.10 改为 1.0：

```
变更前: 10% 采样 → 100K requests/min × 10% × 5 spans = 50K spans/min → Zipkin
变更后: 100% 采样 → 100K × 100% × 5 = 500K spans/min → Zipkin（10 倍）

ES 索引写入: from 50K/min → 500K/min（可能超过 ES 的写入容量）
```

**防护**：Gradual rollout——不要一步从 0.10 跳到 1.0。先在 staging 环境验证 ES 的写入吞吐量。

## 八、面试核心考点

**Q1（陷阱）**：tracing-lab 的 pom.xml 中只有 `micrometer-tracing-bridge-brave` 依赖，为什么启动时能拿到 `BraveTracer` bean 而不用在任何 Bean 配置类中 new 它？

<details>
<summary>答案</summary>

完全由 Spring Boot 的 auto-configuration 驱动：

1. `micrometer-tracing-bridge-brave` 依赖引入 `brave.Tracer` class
2. `BraveAutoConfiguration` 的 `@ConditionalOnClass({brave.Tracer.class, BraveTracer.class})` 条件满足
3. `BraveAutoConfiguration.braveTracerBridge()` 方法创建 `BraveTracer` bean
4. `MicrometerTracingAutoConfiguration` 的 `@ConditionalOnBean(Tracer.class)` 条件满足（BraveTracer 已创建）

**零代码开启追踪**是 Spring Boot Observability 的核心设计理念——只需要在 pom.xml 中加一个依赖就全自动。
</details>

**Q2**：如果同时引入了 `micrometer-tracing-bridge-brave` 和 `micrometer-tracing-bridge-otel`，哪个会生效？

<details>
<summary>答案</summary>

**两个都会生效**——但会导致冲突：

1. `BraveAutoConfiguration` 创建 `BraveTracer` bean
2. `OpenTelemetryTracingAutoConfiguration` 创建 `OtelTracer` bean
3. `MicrometerTracingAutoConfiguration` 的 `@ConditionalOnBean(Tracer.class)` 同时找到两个 Tracer → 如果有 `@Primary` 或 `@Qualifier`，选择一个；否则 Spring 选择第一个注册的

**不推荐**同时引入两个 bridge——类路径冲突 + Bean 重复注册。选择一个。
</details>

**Q3（陷阱）**：`NoopTracerAutoConfiguration` 的 `@ConditionalOnMissingBean(Tracer.class)` 条件——如果已有 `BraveTracer` bean，NOOP 会被跳过。但如果 `BraveAutoConfiguration` 创建失败（如依赖缺失），NOOP 会兜底。**NOOP Tracer 创建的 Span 有 traceId 吗？**

<details>
<summary>答案</summary>

**没有**。NOOP Tracer 的所有方法返回 `Span.NOOP`，其 `context()` 返回的是 `TraceContext.NOOP`：

```java
TraceContext NOOP = new TraceContext() {
    public String traceId() { return ""; }    // 空字符串
    public String spanId() { return ""; }     // 空字符串
    public String parentId() { return null; } // null
    public Boolean sampled() { return null; } // null
};
```

所以在日志 MDC 中不会看到 traceId 和 spanId（都为空或 null）——`%X{traceId:-}` 会输出 `-`。

这就是为什么 tracing-lab 必须确保 bridge-brave 依赖在 classpath 中——否则即使应用启动正常，追踪功能也是空的。
</details>

**Q4**：`management.tracing.sampling.probability` 在运行时能动态修改吗？

<details>
<summary>答案</summary>

**不能**。`management.tracing.*` 配置是在 Spring 启动时一次性读入的（`@ConfigurationProperties`），Brave 的 `Sampler` 在启动时就锁定了采样率。

要动态修改，需要：
1. 使用 Brave 的 `DeclarativeSampler`（通过自定义 `SamplerFunction` 实现，如基于数据库查询的策略）
2. 或者在 Micrometer Tracing 2.x 中（尚未发布）可能支持 `DynamicSampler`

注意：`@RefreshScope` 也不适用于 `Sampler`——Brave 的 `Sampler` 是 final class，不支持动态重新创建。
</details>

**Q5**：为什么 `BravePropagationConfigurations` 中 W3C 和 `span-joining-supported` 不兼容？

<details>
<summary>答案</summary>

Span joining 是 Brave 在 Zipkin v2 JSON 格式中使用的概念（`shared` flag）——客户端和服务端共享同一个 span ID。W3C 标准中，SPAN 之间是严格的 parent-child 关系——不允许两个不同的进程"共享"同一个 span ID。

W3C 规范中 `traceparent` 的 `parent-id` 字段明确是父 span 的 ID（不是共享 span），基于 W3C 的传播和基于 Zipkin JSON v2 的 span joining 在语义上冲突。Brave 的选择是在检测到 W3C + spanJoining 时直接抛异常而非静默行为。
</details>

**Q6**：tracing-lab 运行时不依赖 Zipkin。修改 `management.tracing.sampling.probability=1.0` 后，每个请求的 5 个 Span 数据在何处？内存泄漏风险？

<details>
<summary>答案</summary>

Span 数据存储在 `MutableSpan`（Brave 内部的）中。`span.end()` 时 `MutableSpan` 被提交给 `CompositeSpanHandler`——但因为没有任何 `SpanReporter` bean（没有 Zipkin sender），数据没有被序列化和上报。

`MutableSpan` 在 `end()` 后被清空（`MutableSpan.reset()`）——回到 Brave 内部的对象池中复用。**不存在内存泄漏**——每个 Span 在 end 后立即释放。

如果没有 Zipkin 或其他 Reporter，span 数据仅存在于 `span.end()` 之前的时间窗口（通常 < 1ms），内存占用最小。
</details>
