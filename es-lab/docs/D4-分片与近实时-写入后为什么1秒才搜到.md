# D4 — 分片与近实时：写入后为什么 1 秒才搜得到？

> **定位**：es-lab 第 4 篇。分片（分布式底座）+ 近实时（refresh/translog）——"刚写的数据搜不到"的答案。
> **实测**：本 lab A02 的 count=0 → refresh → 103 现象。

---

## 一、它干了什么：一个例子

bulk 写完 100 条，**立刻**查 count：

```bash
curl -X POST ".../a02/bulk?count=100"   # {"count":100,"errors":false,"costMs":131}
curl ".../a02/count"                     # ← 第一版返回 {"count":0}！（此刻还没 refresh）
# 1 秒后再查（或主动 refresh）→ {"count":103,...}
```

**为什么？** ES 写入**不是立即对搜索可见**——文档先进内存 buffer，默认每 **1s** refresh 成新 segment 才能被搜索到。这就是"**近实时（NRT）**"。

**一句话**：ES 是**近实时**而非实时——写入 →（默认 1s refresh）→ 可搜索。

---

## 二、为什么需要它：写性能与搜索可见性的权衡

如果每次写入都立即让搜索可见（每次建 segment + 刷盘），写吞吐会崩塌。ES 的选择：

```
写入 → ① 内存 buffer（不可搜索） + ② translog（持久化保障）
  ↓ 每 1s（refresh_interval）
① → 新 segment（可搜索，仍在 PageCache，未 fsync）
  ↓ 每 30min 或 translog 满（flush）
segment fsync 到磁盘 + 清空 translog
```

| 机制 | 作用 | 默认 |
|---|---|---|
| **refresh** | buffer → segment（**可搜索**） | 1s |
| **flush** | segment fsync + 清 translog（**持久化**） | 30min / translog 512MB |
| **translog** | 两次 flush 之间的写入日志（宕机恢复） | 每请求 fsync |

**近实时的"近"= refresh_interval**（可调：写多搜少场景调大提升吞吐；实时要求高调小/写入时 `refresh=true`）。

---

## 三、怎么做：分片——分布式的底座

### 3.1 一个索引 = N 个主分片（primary shard）

```
index(notes) → [P0][P1][P2]  ← 主分片（文档按 _id hash 路由到某个分片）
                 ↓ 每个主分片有副本
              [R0][R1][R2]  ← 副本分片（读扩展 + 高可用）
```

- **写入**：路由到主分片 → 同步到副本 → ack（`wait_for_active_shards`）
- **搜索**：请求发给所有分片 → 各分片本地检索 → 协调节点合并（所以深分页贵——D3）
- **分片数建索引时定死**：不可改（重建索引才行）——按数据量预估（单分片 10-50GB 经验值）

### 3.2 副本的作用

| 作用 | 说明 |
|---|---|
| 高可用 | 主分片挂了，副本提升 |
| 读扩展 | 搜索可以打到副本（提升 QPS） |
| 写代价 | 每次写入都要同步到所有副本（副本多=写慢） |

## 四、坑与边界

| 坑 | 说明 |
|---|---|
| "写完立刻搜"搜不到 | 近实时——refresh 前不可见（本 lab 实测 count=0） |
| refresh_interval=1s 不是持久化 | refresh 只到 PageCache；**持久化靠 translog/flush** |
| 分片过多 | 每分片有开销（cluster state/段合并）——不是越多越好 |
| 分片过少 | 无法水平扩展（建索引时定死） |
| 副本=0 | 单节点实验常见（本 lab）；生产至少 1 副本 |

## 六、值不值得深挖 & 面试问答

**值不值得**：🔴 必问——"ES 为什么是近实时"“refresh 和 flush 的区别”“分片怎么设计”高频。

**Q1：为什么写入后 1 秒才搜得到？**
写入先进内存 buffer，默认每 1s refresh 成 segment 才可搜索——近实时（NRT）。

**Q2：refresh 和 flush 的区别？**
refresh：buffer→segment（可搜索，未落盘）；flush：segment fsync 落盘 + 清 translog（持久化）。可搜索 ≠ 已持久化。

**Q3：ES 会丢数据吗？**
默认每请求 fsync translog——宕机可从 translog 恢复未 flush 的写入；改异步 translog 才有丢失窗口。

**Q4：分片数怎么定？**
建索引时定死不可改；按数据量（单分片 10-50GB）+ 并发预估；宁少勿多（可后期重建调整）。
